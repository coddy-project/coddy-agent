# External web authentication and logout

Status: proposed plan for issue #287 and external web sign-in. The provider compatibility and remaining operational decisions listed below are not confirmed. The logout URL change can ship independently of external login.

## Existing boundaries

`internal/config/http.go` accepts password login mode; `internal/config/config.schema.json` and `internal/config/jsondto.go` define the schema and settings representation. Config writes preserve hidden values, comments, line endings and concurrent edits under `.cursor/rules/config-roundtrip.mdc`. `external/httpserver/auth.go` gates requests using bearer credentials or browser cookies. `auth_login.go` handles the local password account, TOTP challenges and logout; `auth_telegram.go` and `auth_browser.go` issue separate browser sessions. `features/webui_login.feature`, `features/webui_login_totp.feature` and `external/httpserver/bdd_webui_login_test.go` exercise the current flow. The UI uses `external/ui/src/ui/auth/AuthGate.tsx` and `authState.ts`; existing logout posts to `/coddy/auth/logout` and reloads only after success. `external/httpserver/openapi.go`, `docs/reference/http-api.md` and `docs/operate/security.md` describe the public contract.

Desktop can attach to the service rather than owning an isolated runtime. `cmd/coddy/desktop_bridge.go:65` strips the incoming desktop no-auth header and sets it only for the bridge's trusted mode. `cmd/coddy/runtime_ipc_http.go:34` configures that header on the private IPC handler, reached through authenticated local IPC. `external/httpserver/auth.go` only recognizes it when that handler has explicitly enabled it. Keep this boundary; do not infer desktop trust from loopback, User-Agent or an incoming public header. Also inspect the standalone desktop launch and origin guard before changing it.

## External sign-in: proposed protocol

Assumption: one configured OIDC issuer and confidential client per server, using authorization code plus PKCE. This is a proposal, not a statement about the target provider. A trusted reverse proxy or SAML are alternatives only after a separate protocol and trust-boundary decision; generic OAuth alone is not identity proof. Before implementation confirm issuer, client, public callback, the provider emitting the specified role claim, exact allowed role and network deployment. Require HTTPS for the public login and verified provider endpoints.

The following order is mandatory for a browser, including after expiry or mode changes:

1. Start OIDC with high-entropy one-use state, nonce and PKCE verifier, held in a bounded, expiring server-side transaction bound to the initiating browser by a short-lived HttpOnly, Secure, SameSite=Lax cookie. Use a fixed same-origin post-login destination. Callback consumes the transaction once, exchanges the code with bounded time and response size, and validates signature, algorithm allowlist, issuer, audience, `azp` when applicable, expiry, nonce and nonempty `sub` with a maintained OIDC library. Reject bad state, cross-browser callback, replay and provider errors. Never trust unsigned proxy headers as identity.
2. Read the top-level `roles` claim from the validated ID token. It must be an array of strings containing the configured exact role, compared case-sensitively. Reject a missing claim, a scalar, nested or mixed-type array, or a nonmatching role. Do not coerce or split values. The operator must configure the issuer to emit this claim in the ID token and confirm its meaning and client audience before deployment; OIDC itself does not standardize this claim.
3. On a match, atomically create a fresh opaque authenticated browser session bound to the exact `(issuer, sub)` pair. Do not promote a pre-authentication cookie. The session immediately grants full operator control, including host and shell access, configuration, tools, all chats and their direct IDs, downloads, streams and background operations, subject only to the same operational permission mechanisms as a legacy authenticated operator. This is not chat-only access. The IdP is responsible for its own authentication and any MFA policy.

External mode **replaces** the web password and Coddy QR/TOTP factor. It has no Coddy enrollment, challenge, recovery or backup-code step. Existing local password, TOTP secret and backup codes remain stored but dormant; they must neither authenticate an external browser nor need removal to enable the mode. Disabling external mode restores the unchanged local behavior and existing credentials. This is a single operator-trust domain, not tenant or per-chat isolation. A role mapping is a grant of host-level power and must be restricted accordingly.

### Peer evidence and role choice

These are local source snapshots, not evidence that the peers use OIDC `roles` or that a particular issuer emits it:

- OpenHands at `428b3dc2a0e8d3d0f689a909e2607e33d973da76`, `src/hooks/use-automation-permissions.ts`, reads the active organization's `/me` response and uses `data.role` (`owner`, `admin`, `member`) as a fallback when server-defined permissions are absent. This is an organization membership role used for automation UI permissions, not a verified ID-token claim and not proof of host-wide privileges.
- The same revision's `src/hooks/query/use-cloud-organizations.ts` filters visible organizations according to an API key's organization binding. That is a workspace restriction, not a role-membership predicate. `src/components/conversation-events/chat/event-content-helpers/should-render-event.ts` checks `llm_message.role` for `user`, a message author role, not user authorization.
- OpenCode at `f898eaeaa13fd4bde7be19a8122d49813e6a968e`, `packages/ai/src/schema/messages.ts`, constructs messages with `role: "user"`; this role likewise identifies a message speaker, not an identity-provider entitlement.

The analogy is only that an authenticated principal's membership role selects access. Coddy deliberately chooses an exact string in the top-level ID-token `roles` array, with the allowed value configured by the operator; it does not copy OpenHands' API response, its scoped permissions or its fallback. Confirm the actual domain issuer can issue this exact claim and that administrators control its assignment. If it cannot, block deployment until a separately reviewed claim mapping is specified; do not guess from email, workspace membership, message roles or unverified headers.

## Lifecycle, fencing and operating limits

- The initial implementation supports **one server process only**. Pending transactions, continuation tickets, session state and fencing generations share one process and one synchronization domain. Restart invalidates them. Multiple workers, independently replicated servers, or a load balancer spanning instances are unsupported until a shared atomic store, distributed revocation and stream coordination have their own design and tests. Sticky routing alone is not a guarantee.
- Tie each browser flow to a server-side browser generation and current authentication-policy generation. Logout and mode/config changes atomically advance the relevant generation, revoke sessions and cancel pending OIDC transactions. A callback may perform slow work outside the lock, but its final session issuance must atomically check and commit against both generations. If logout or a mode change wins, delayed work cannot issue a session; if issuance wins, logout revokes that new session. Apply the same fence to configuration changes, and test both orderings using synchronization barriers rather than sleeps. No state-changing request is retried or replayed automatically after reauthentication; the user must explicitly resubmit it.
- Proposed maximum session lifetime is 15 minutes, capped by the validated ID-token expiry, with no silent refresh. Confirm the lifetime and role-removal delay before implementation. On logout, expiry or policy revocation close active SSE, WebSocket and other privileged response streams promptly. Recheck authorization before accepting a new action. Define and test what happens to already accepted turns: close their browser stream and prevent further browser access, but do not claim that closing the connection cancels a server-side turn. The implementation must explicitly choose and document whether it cancels that turn or allows it to finish under its original authorization, including side effects, queued work, other subscribers and cancellation races. Approval of that behavior is a release gate.
- No local password, TOTP verification, backup code, Telegram Mini App or extension-ticket flow may create a full browser session in OIDC mode; cookies issued by those paths must not bypass it. Hide or disable local enrollment and recovery controls without deleting stored credentials. Review canvas/workspace capabilities and every existing bypass explicitly. The SPA gate is presentation only. Login transaction cookies are distinct from authenticated cookies; the latter retain HttpOnly, Secure and SameSite protections. Bound attempts, session stores and payload sizes; throttle verification and avoid credentials, codes, claims or callback parameters in logs, URLs, errors or Referer.
- A validated OIDC identity with the allowed role authorizes a browser for full operator control. Existing `httpserver.auth_token`, `--auth-token` and `CODDY_HTTP_TOKEN` remain separate, fully privileged machine credentials, as do their current console, ACP, swarm, script and remote UI clients. They do not require OIDC and must never count as proof of OIDC identity. Bearer credentials remain fully privileged independently of browser sessions.
- Preserve the trusted desktop no-login experience through its existing explicitly trusted bridge/private IPC or standalone boundary. A negative integration test must send `DesktopNoAuthHeader` to the public HTTP listener and prove it still returns 401, including from loopback; test bridge header stripping and `--auth`, and show a separate remote server still requires authentication. Do not extend this exception to ordinary browser requests. Preserve explicit `--no-auth` only in its supported trusted context, and document its consequences.

## Logout URL and navigation

Add optional `httpserver.login.logout_url`, independent of login mode. When absent, preserve existing behavior and legacy `POST /coddy/auth/logout` response `{ "ok": true }`. Accept only an absolute HTTP(S) URL with a host; reject userinfo, control characters and fragments, and validate on configuration load/save and again before navigation. HTTPS is recommended for production. The URL is static configuration: **it must not contain secrets, tokens, identity data or user-specific return parameters**. It is not an OIDC single-logout guarantee; a provider may require a different protocol or reject a static URL. Local logout succeeds independently of the provider's outcome.

Redact the complete URL from config JSON, errors, diagnostic output, CLI config checks, logs and telemetry. Settings may receive a presence boolean, preserve an untouched hidden value and provide a deliberate clear action. Preserve `${ENV}` references, revisions, concurrent edits and YAML formatting. Do not disclose the URL in `/coddy/auth/me` or depend on that endpoint for navigation. The destination necessarily appears to the browser in a redirect Location, browser history and the destination server; redaction does not hide it from the navigating user. Configure reverse proxies not to log Location or callback query strings.

Keep `POST /coddy/auth/logout` same-origin/CSRF-protected, with its legacy status and `{ "ok": true }` response body. On a successful eligible browser logout with a configured destination, atomically revoke its sessions, pending attempts, fence delayed issuance, and issue a short-lived, unpredictable, one-use continuation bound to that browser. Signal **only eligibility** via a response header such as `X-Coddy-Logout-Continue: 1`; set the opaque continuation in a dedicated HttpOnly, Secure when applicable, SameSite=Strict cookie scoped to the continuation path. No URL, token or ticket enters the header or JSON. An eligible request must be tied to the initiating browser's valid session or outstanding browser-bound login flow and pass the same-origin checks; bearer-only, anonymous and forged requests must not obtain a continuation. Define logout during in-flight authentication so the bound transaction itself can be invalidated without granting a session. When no destination is configured, omit the signal and preserve existing reload behavior.

After the successful POST, the SPA reads the signal from that response and performs a top-level navigation to same-origin `GET /coddy/auth/logout/continue` only if present. The GET atomically consumes the matching live browser cookie/ticket and checks the policy generation, then returns `303 Location` to the validated static destination with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Clear the continuation cookie on every outcome. Missing, expired, mismatched, replayed, invalidated and direct visits all get the same safe same-origin fallback, with no reflected input or external redirect. Cross-browser use fails. A reload, refused POST or network error must not trigger external navigation; on logout failure retain the existing state refresh behavior. Never fetch, preflight, follow redirects or call the external logout URL from the server. The external provider's redirect chain is controlled by that provider, and may fail or reauthenticate the user.

## Compatibility, config and security

- Empty external mode and empty logout URL keep current password, TOTP, recovery, open-server, desktop, bearer, response and UI behavior. Existing local credentials and enrollment remain dormant and preserved while external mode is enabled, and work again when it is disabled. An explicitly enabled but invalid OIDC configuration fails startup/save or stays closed; it never falls back to open or password mode. Apply live config updates atomically with fencing. Review startup warnings and `allow_insecure`.
- Implement types, defaults, validation and DTO handling in `internal/config/http.go`, `internal/config/jsondto.go`, `internal/config/config.schema.json` and the config API merge path. Sync `config.example.yaml`, `internal/config/ui_schema.go` and `internal/skills/bundled/configure-coddy/SKILL.md`. Preserve hidden client secrets and logout URL on unrelated saves, and provide unambiguous explicit clearing. Validate all output paths, including malformed-value errors, for redaction.
- Register any routes with the gate and update `external/httpserver/openapi.go` alongside handlers and tests. Use a fixed configured callback origin, never Host or untrusted forwarded headers. Specify trusted proxy addresses and reject spoofed forwarded values. Keep CSRF/origin protections; callback has only a narrow state-validated exception. Discovery, JWKS and token requests use configured endpoints, TLS verification, bounded responses and timeouts, carefully controlled redirects and DNS/private-network policy; cache keys safely and handle rotation. Never derive an outbound destination from an incoming request or claim. The logout URL is navigation only, not an outbound server request.
- Do not persist provider tokens in the browser or URLs. Keep only the identity and role metadata needed for the bounded local session; retain existing local factor secrets unchanged and inaccessible to external authentication. Provider role removal is not instantaneous under a local session: document the maximum effective delay and incident revocation procedure.
