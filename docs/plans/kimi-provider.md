# Kimi Provider Implementation Plan

> **For agentic workers:** Use the executing-plans or subagent-driven-development skill. This document is a plan only. Complete the first cross-review and settle its findings before writing tests or implementation.

**Goal:** Add a first-class Kimi provider with global subscription device login by default, a mainland China option, separate Platform API-key endpoints, usage limits, safe refresh, proxy support and console/web integration.

**Architecture:** Keep subscription credentials bound to a region and provider identity; never infer their destination from an arbitrary URL. Route each discovered model by its declared wire protocol, and reuse Coddy's existing transport and usage infrastructure. Platform keys are a separate credential mode and must never be treated as subscription OAuth tokens.

**Tech Stack:** Go, Coddy provider/config/session packages, OAuth device authorization, OpenAI and Anthropic transports, React/TypeScript, godog, Go and Vitest tests.

## Invariants and compatibility

1. A `kimi` row selects subscription or Platform mode and region; omitted mode means subscription and omitted region means global. Explicit Platform mode requires its own key; subscription mode rejects an explicitly configured key or key command rather than silently routing it elsewhere. Preserve inactive stored credentials on a mode or region switch without using them for the new identity. Give old configurations exactly their current meaning. Do not silently convert an existing `openai` or other compatible row. No arbitrary configured URL may receive subscription tokens. Reject invalid region/mode combinations rather than falling back across regions.
2. Endpoint allowlists compare parsed HTTPS scheme, exact host, port and normalized path; reject userinfo, fragments, encoded path tricks and untrusted redirects. Reject query strings except the exact `beta=true` query on the verified Anthropic beta inference endpoint. OAuth, models, usage and inference each have an explicit purpose-specific destination. No credential-bearing cross-origin redirect. Test-only injected clients/endpoints are private to tests, not an operator-configurable bypass. Follow existing API auth, origin/CSRF and remote-access policies for every new web sign-in route; do not expose access or refresh tokens in responses, logs, errors, URLs, SSE, metrics or UI. Identify any additional restriction needed for credential mutation and enforce it server-side, not just in the UI.
3. Keys use only Platform inference and discovery endpoints in key mode; never send a key to OAuth or subscription usage. Define explicit key versus `api_key_command` precedence consistently with existing config and prevent an OAuth credential from silently overriding a key. With no supported Platform usage endpoint, return unsupported rather than fabricate quota or report zero.
4. All outbound requests, including authorization, poll, refresh, model listing, inference and usage, go through `llm.HTTPClientForProviderProxy`, including proxy `none` and system inheritance. No nil-client fallback or accidental SDK default. Preserve cancellation, bounded response sizes, timeouts and redaction.
5. Refresh rotation must be correct across goroutines and processes sharing a credential store. Lock by stable credential identity with a cross-process OS lock, re-read inside the lock, check expiry/generation, refresh at most once, and atomically persist both new tokens with restrictive permissions before releasing the lock. Other callers consume the new generation. Never persist a stale response over sign-out or a newer login; coordinate these operations through the same lock. On invalid grant re-read once to distinguish another process's rotation; otherwise require sign-in. If remote refresh succeeded but durable persistence failed, report credential state as uncertain and do not retry the old refresh token blindly. A crash between remote rotation and durable local write cannot be made atomic without server support: document recovery by re-login and test the local failure path. Verify the lock implementation works on all supported platforms or add platform-specific implementations and cross-build checks.
6. Discovery preserves protocol, context, modalities and reasoning with each model through configuration and runtime resolution, including after restart. Never guess an unknown protocol: return a specific actionable error. Preserve user-selected logical models and unrelated provider rows on sign-in and refresh; no existing configuration is destructively replaced. A catalog change must not silently reroute a previously selected model to a different protocol without validation.

## Plan review: required refinements

### Kimi CLI login fallback

When no Coddy-managed credential exists for the selected provider row and region, a subscription row may use the installed Kimi CLI login, like Codex. A successful Coddy sign-in writes its own per-provider credential and takes precedence; sign-out removes only Coddy's credential, never the CLI's. The machine-wide CLI login serves only the sole Kimi row or the row named `kimi` among several, using the same isolation rule as Codex. This rule may assign the shared CLI account to a different row after a rename, deletion or creation; it does not provide the isolation of managed identities. A malformed, revoked or uncertain managed credential must not silently fall back to another account. Mode and region must match the CLI credential; Platform never consumes OAuth. Discovery, inference, usage, readiness and dry-run all carry the same fallback decision and configured proxy. Coddy reads a valid CLI access token but never refreshes or writes the CLI credential. Add offline fixture tests for precedence, region mismatch, multiple rows, sign-out, CLI file replacement and deletion, and absence of secrets in output. Review these additions independently before implementation.

Upstream `packages/oauth/src/storage.ts`, `managed-kimi-code.ts` and `oauth-manager.ts` define the compatibility boundary: KIMI_CODE_HOME or `~/.kimi-code`, `credentials/kimi-code.json` for China, and `credentials/kimi-code-env-<digest>.json` for global, where digest is the first 16 hex digits of SHA-256 over compact JSON with `oauthHost` then `baseUrl`. The refresh lock is the `oauth/<storage-name>.lock` directory managed by `proper-lockfile` with heartbeat and a five-second stale threshold, not the Coddy store's flock. Upstream login/logout do not acquire this lock, so a lock alone does not prevent a concurrent login/logout. Before choosing a refresh implementation, review this race and stale-lock interoperability explicitly; failure to protect a rotating credential requires a clear re-login error, not an unsafe overwrite. Verify CLI fixture compatibility with the upstream library in separate processes and report Windows limitations. Do not read private credential values for tests.

The fallback review answered 3 of 4 reviewers; the fourth failed twice with HTTP 429. Adopt read-only CLI credentials on every platform: Coddy reads only the current valid access token, never refreshes, writes or removes the CLI file. An expired or rejected token asks the operator to refresh/login in Kimi CLI or sign in with Coddy. A Coddy-only refresh intent cannot protect the CLI after a crash, and a pre-rename re-read is not atomic against CLI login/logout. A CLI fallback test suite uses a synthetic KIMI_CODE_HOME and covers both region slots and golden digest, expiry/401, no write/refresh, concurrent CLI replacement/deletion, managed precedence and corrupt managed files, multiple rows, Platform mode and sign-out. Show the active source in Settings and diagnostics, including when sign-out exposes the CLI fallback. Document this limit and do not claim full CLI refresh. Provider-name reuse must not silently transfer Coddy-managed credentials: explicitly bind credentials to stable row identity or choose and test a safe lifecycle before implementation.

### Managed provider identity

Add an optional random, non-secret `kimi_identity` to a Kimi provider row. Managed credentials bind to this identity and the canonical subscription mode and region, rather than the mutable provider name alone. Generate a fresh identity when Coddy creates a new provider row or starts a managed login for a draft lacking one; retain it when the same row is renamed. Validate its format and uniqueness within the configuration, carry it through the UI and JSON/YAML round trips, and never inherit an old row's identity solely by name after deletion. The device flow captures identity, mode and region and stores only under that tuple; a late result can at most leave an orphan for its original identity, never attach to a newly generated one. An unsaved UI draft carries its identity through the subsequent Save and drops stale results after changing its identity, mode or region. CLI login arranges for the identity to be saved before reporting a managed login connected. An existing Kimi row without identity and a sole `type: kimi` row still use eligible Kimi CLI fallback; no managed token is inferred from its name. Do not silently migrate old name-based managed files; a fresh explicit login assigns ownership. A mutable external editor can deliberately copy or restore an ID and can race an in-flight request; this mechanism guarantees isolation by the configuration snapshot and ID, not atomicity against an uncooperative editor or immediate revocation of an already started request.

Discovery requests, `providerModelsRequest`, the HTTP resolver and OpenAPI carry draft identity, mode and region together; an absent identity must not inherit a managed credential by name. Begin, complete, cancel, sign-out and a replacement login compare and update the attempt generation under the same interprocess credential lock. A completion that loses to logout is refused. For a saved row without identity, web sign-in assigns one to the draft and does not claim the saved configuration is connected until Save has persisted it; failed or conflicting Save keeps the draft and reports the reason. An orphan from a discarded draft is not silently adopted or automatically deleted. Readiness and onboarding must not execute `api_key_command` or perform a network request.

Provide an explicit operator-controlled way to inspect and delete orphaned managed credential slots by identity, with no token values in output; never delete them merely because they are absent from one configuration snapshot. When the active source is only the read-only Kimi CLI login, disable the Coddy sign-out action and explain that sign-out happens in Kimi CLI. Test both behaviors, including a managed sign-out that reveals the CLI fallback.

For manually configured logical models with no `kimi_metadata`, infer their protocol from the authenticated catalog at runtime; reject an absent model or unknown protocol. Where metadata is present, bind it to the model, mode and region and reject a catalog mismatch instead of silently rerouting it. Test a simple provider plus CLI login without metadata, managed sign-in of saved and unsaved rows, separate same-name identities, rename, delete/recreate, region and mode changes, stale login completions and other-process config edits. Cross-review this identity design before implementing it.

## Questions to resolve from evidence, not guesses

- Whether subscription `/models` always declares protocol, and how the reference handles missing or unknown protocol; exact supported model protocol values and Anthropic thinking behavior. A missing verified mapping blocks advertising that model as runnable.
- Platform `/models` metadata and per-model protocol semantics, key restrictions and whether Platform exposes a trustworthy quota endpoint. Do not reuse subscription quota or metadata without evidence.
- Upstream refresh-token rotation guarantees, retry/idempotency, expiry skew and server behavior after a response is lost. The crash window above remains even if normal locking passes.
- The precise existing Coddy credential-route access policies, reverse proxy/relay behavior and cross-platform locking facilities must be inspected and tested at implementation time; a web dialog is not a security boundary.
- Whether upstream permits the reference client's public OAuth client ID and required device headers in this integration. Confirm product/terms compatibility before release; offline tests cannot prove entitlement or regional availability.
