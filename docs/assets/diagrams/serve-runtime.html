coddy serve: one process, many subsystems

Every subsystem config.yaml enables runs as a goroutine of one process over one session manager. A dispatcher or systemd keeps that process alive and starts a fresh one when a change cannot be applied in place.

1. What keeps the process up

Background daemon
coddy serve --daemon returns once the first worker is up or has failed; both processes log to <home>/logs/serve.log
dispatcher CODDY_SERVE_ROLE=dispatcher; records itself in <home>/serve.json: pid, version, config, log, args, worker pid, last error
worker CODDY_SERVE_ROLE=worker, in a process group of its own
when the worker exits
exit 0: told to stop, the dispatcher stops too
exit 75 (ExitRestart): a new worker at once
crash, panic, OOM kill: wait 1 s, 2, 4 ... 30 s; back to 1 s after a minute up
systemd user service (coddy serve install)
coddy.service CODDY_SERVE_ROLE=service, Restart=on-failure, SuccessExitStatus=75 and RestartForceExitStatus=75, 40 s to stop, works in ~/Coddy
Foreground
coddy serve no role: nothing would start it again, so a moved address is only logged

Pre-flight (serve.Resolve) before anything binds: a subsystem enabled but built without stops the start by name, swarm.enable is true but this binary has no swarm support (rebuild with -tags swarm). A file that enables nothing, or only the exporter, is refused too.

A subsystem that fails or panics ends the whole process, and whatever keeps it up starts a clean one. The exporter is auxiliary (dashed): it fails alone, never keeps the process up by itself and may always stop.

GET /coddy/status and Settings → System read this table live: each subsystem running, starting, stopped or retained, and a saved address that waits for a restart.

3. A configuration change reaches the supervisor

edited outside the process coddy providers login, an editor, a deployment
config.FileWatcher a stat every 2 s, then load, flags applied again, compared with the live config
live config replaced Manager.ReplaceConfig (a relay alone: the runtime's holder); most settings are live at once, and GET /coddy/events says config_reloaded
reloads channel one slot: a newer config replaces one still waiting, nothing blocks the writer
Supervisor.applyConfig compares each subsystem with the config it was started from
saved by the process itself Settings screen, config_commit, a relay's settings
A listen address moved, or a surface that runs turns was turned on where only a relay runs. Weighed first, before anything else is applied:
pre-flight refuses the new file: nothing changes at all
worker or service: surfaces stop, exit 75, a fresh process binds it
foreground: logged; see Settings → System
An enable key flipped: started on the address the new file gives, or stopped. The only running surface is never stopped.
A Fingerprint moved: that subsystem stops (up to 30 s) and starts again on the new settings; the others keep running.
Nothing it reads moved: left as it is.

Stopping walks the declaration order backwards, so the bots, the relay and the scheduler stop taking work before the HTTP server goes, and running turns drain against a session store still in place. coddy serve stop signals the dispatcher, which gives the worker 30 s.

coddy serve -t and --dry-run run the same pre-flight on the file without starting anything.
