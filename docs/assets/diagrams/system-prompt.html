What Coddy sends the model on every request

A provider caches a request by its prefix: the first byte that differs from the previous request throws away the cached rest. So the system prompt is built to stay the same bytes from request to request, and what moves goes to the end.

1. The request, top to bottom

mode, model, toolset, MCP Tool definitions (the request's tools field) the built-in tools of the mode, plus MCP tools in agent and plan mode
SYSTEM MESSAGE (buildSystemPromptParts)
fixed Identity and working directory "You are Coddy, an AI coding agent...", Working directory: {{.CWD}}, a subagent's role in a child session
rendered once per turn and sent byte for byte by every step of it; with nothing on the right happening, the same bytes for the whole session
mode switch Mode and how to work ## Mode: Agent / Plan / Ask, the capabilities, the guidance on files, shell, background tasks, worktrees, web
definition files Subagent catalog the definitions spawn_agent can start, when the session may spawn
mode, model, toolset, MCP ## Available tools the same tools as text, MCP tools among them; MCP has no section of its own
config reload, workspace switch ## Slash commands the catalog of skills, a name and a description each, and the hint to call load_skill
implementing a plan Plan context agent mode, on the turn that implements an approved plan
rules generation Documents and always-on rules AGENTS.md and DESIGN.md of the agent home, then of the workspace, then the rules that always apply
rules generation ## Project instructions the files of instructions.files
fixed ## Session memory the session's notes, when it has any; the memory subagent's report never goes here
fixed <environment_context> os, arch and shell, appended whatever the template prints
hook output Hook context what SessionStart left on the session, plus this turn's UserPromptSubmit context
surface Surface block how the web UI, Telegram or Pachca shows an answer: diagrams, formatting
HISTORY, REPLAYED AS STORED
compaction Compaction summary rows the chain of summaries, oldest first, in place of the turns they cover
only grows at its end; a compaction is the one place it is rewritten
appended Messages, tool calls and results a rule a tool call activated rides in that call's result; a mention brings its file or rule in that message
APPENDED AT THE SEND BOUNDARY, NEVER STORED
every step <turn_context> UTC time (stamped once per turn), Git workspace, todo checklist, the memory report, background tasks still running
the only part out of the cache

2. What re-renders it

fixed the same for the whole session (the working directory moves only with a workspace switch) rules generation read once per generation: a compaction, a config reload or a workspace switch starts the next one, so an AGENTS.md edited mid-session waits for it named event renders the system message again on the next turn, only when that event happens; a turn that changes nothing sends the previous bytes every step new on every request, which is why it sits after the history

3. Re-rendered inside a turn

  • after a compaction, which also starts the next rules generation;
  • after worktree_open or another workspace switch;
  • after switch_model or a toolset switch that changed the tool set, and a config reload that did;
  • when a permission answer resumes the turn.

4. Kept out of it on purpose

  • the clock, the todo checklist, the memory report and running tasks: in <turn_context>;
  • a rule or nested AGENTS.md a tool call reaches: in that call's result, once;
  • a rule or file a mention brings, a /skill body: in that user message; a skill the model loads: in the load_skill result;
  • MCP server instructions: not sent at all.

A template under prompts.dir that prints {{.UTCNow}} or {{.TodoList}} is rendered again on every step and loses the cache.

Plan and ask mode use their own templates (internal/prompts/plan.md, ask.md) with the same slots, except that plan mode lists the discarded plans instead of a plan context, and ask mode, which is read-only, has no subagent catalog and no MCP tools.
