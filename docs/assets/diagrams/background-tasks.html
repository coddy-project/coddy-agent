Background tasks: one pool, three ways in, a wake on the way out

Work that outlives a tool call runs in the session-scoped task pool of the process (internal/bgtask). The model follows it with the background tools, and a task that ends can start the next turn on its own.

1. Three ways in, one scheduling path

run_command with background: true Pool.Start: the command runner starts the shell command
a foreground run_command still running at its timeout (30 s by default) Pool.Adopt: the same process, never killed and run again; its output so far goes in first, its limit is max_timeout_seconds
spawn_agent, a scheduled run, the memory run; preview_server Pool.Launch: the callback is handed the task id and its output sink first
Pool.start
  • admission first: ErrDraining while the process stops, ErrPoolFull at max_concurrent (5) running per session; a system task is never counted
  • an id bg_N, and background/bg_N/meta.json and output.log in the session bundle
  • a hard limit: timeout_seconds, else 3 × expected_seconds but at least 60 s, else 900 s; at most 3600 s
  • output into a 256 KiB window in memory and the whole log on disk; escape sequences are stripped when it is read
  • supervised to the end: exit, timeout or Stop, the record written, then the watchers told
command a shell process group with a pid and an exit code; card tag shell
agent a child session, agent {name, session_id} on the row; no pid, Stop cancels the child
server goroutines of Coddy with a url; no hard limit unless the call names one
status running → ends as succeeded failed timed_out stopped orphaned read back for a task an earlier process left running

2. How the model follows a task

Every request ends with the turn context block, which lists what still runs:

## Background tasks
- bg_3 [running] make test (elapsed 2m5s, estimated 5m) wakes you when it ends
- bg_4 [running] preview site at http://127.0.0.1:41231/ (elapsed 9m)

One line per running task, worded as background_list words it; system tasks are left out.

background_listevery task of the session, and processes still alive from an earlier run
background_outputthe last 100 lines by default, also while the task runs
background_waitblocks 60 s by default, 300 s at most
background_stopends the process group, or cancels the child
background_reapkills what outlived the coddy run that started it

Reading a finished task's output, a wait that returns it and a stop collect its result (AcknowledgeResult): that task wakes nobody.

3. The wake: a finished task starts the next turn

a task ends with notify_on_finish: on by default, recorded only when Pool.CanWake (a waker is subscribed) and the session can take a turn

Never recorded for the tasks of a subagent or a scheduled run, under coddy -p, or for a preview server; run_command and spawn_agent then tell the model nothing will wake it.

BackgroundWaker subscribed as agent.background_waker, one per process
  • waits 750 ms, so tasks ending together cost one turn
  • skips results the model collected
  • a session mid-turn: retry after 1 s, doubling to 15 s, for up to 30 min
  • at most 50 woken turns per session in a process; none while it drains
who runs the turn under coddy serve (serve.Runtime)
1the chat bound to the session Telegram or Pachca: runs like a message the person sent there; Telegram first posts a line about the wake
2the HTTP server through the session's composer relay; a permission prompt waits, persisted, for the web UI or a --remote console
3nobody up: the session manager the outcome stays in the transcript; a gated tool is denied unless the mode is bypass

The console runs it on its own UI goroutine, coddy acp through the manager.

the woken turn
  • opens with a plain outcome: id, status, exit code, runtime, error, background_output, and resume for a subagent that did not finish
  • a background_wake update first, then the message, persisted with the background_wake marker: no surface shows it as typed
  • each task's record gets woke_agent

4. Where a person sees it

Tasks panel of the web UI polls the task rows every 2.5 s while a task runs, 15 s otherwise; a bell marks a task that wakes, or woke, the agent
/tasks in the console the same rows, newest first: wakes the agent, woke the agent
GET /coddy/events background_wake with the tasks, so a console attached over --remote follows the turn
REST under /coddy/sessions/{id}/ GET background-tasks, one task with ?tail=N, POST .../stop; DELETE clears the finished ones

tools.background.enable: false drops the background option, the five tools and the turn context section. Subagent runs count against the same limits, and subagents.max_concurrent caps the child runs of the whole process.
