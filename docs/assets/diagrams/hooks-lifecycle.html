Where hooks fire

A hook is a command of yours: it reads one JSON document on stdin and answers with an exit code and optional JSON on stdout.

1. Events on the timeline of one session and one turn

session created, reopened or moved to a workspace
SessionStart startup, resume, workspace
context only: stored as hookContext in session.json, shown in every system prompt
the person sends a prompt built-ins like /compact run first
UserPromptSubmit
reject: never saved, no model call; or context for this turn's ## Hook context block
ReAct loop, every step
model call
no event
tool call passed the mode and subagent checks
PreToolUse tool name
deny: blocked by hook: … is the result; allow: no prompt; ask: a prompt even in bypass; updatedInput rewrites the arguments
the permission prompt is about to go out
Notification permission_prompt
observational: give it async: true so the prompt is not delayed
the tool runs
PostToolUse or PostToolUseFailure
Hook feedback and Hook context appended to the result; nothing is undone
the tool is spawn_agent
SubagentStart then SubagentStop
refuse the spawn, or put context in front of the child's task; SubagentStop sees status and report
/compact or an automatic compaction
PreCompact then PostCompact
veto: /compact fails, an automatic one is skipped; PostCompact gets the summary
the model ends the turn (end_turn)
Stop
block: the reason goes back as a [Stop hook] user message and the loop goes on, at most hooks.stop_loop_limit (5) times

Inside a child session every event fires for the child's own turn, with a subagent block in the payload; SubagentStart and SubagentStop fire in the parent. Stop does not fire on cancel, an error or the turn cap.

2. Which hooks run

hooks.files, lowest priority first, re-read every turn. Every matching hook of every file runs.

${CODDY_HOME}/hooks.json user
${CWD}/.claude/settings.json its hooks key only project
${CWD}/.claude/settings.local.json project
${CWD}/.coddy/hooks.json project
Project files: hooks.project_trust
deny: never read; ask (default): held until a receipt in <home>/hooks-trust.json matches project, file and digest, with one notice row per session; allow: they run like your own file. Approve with coddy hooks trust <file>.
{"hooks": {"PreToolUse": [{ "matcher": "Bash", "hooks": [{"type": "command", "command": ".coddy/hooks/guard.sh", "timeout": 30, "failClosed": true}] }]}}
  • matcher: empty or * is every call, edit|write exact names, anything else a regular expression;
  • Claude Code names are aliases: Bash is run_command, Edit and Write also apply_patch, Task is spawn_agent, an MCP tool also mcp__server__tool;
  • only command handlers run; http, prompt, agent are skipped.

3. One hook process

stdin: one JSON document {"session_id": "sess_5f1c…", "hook_event_name": "PreToolUse", "cwd": "/home/op/project", "permission_mode": "ask", "mode": "agent", "turn": 3, "tool_name": "run_command", "tool_input": { "command": "rm -rf build"}, "tool_use_id": "call_01"}
your command through the shell, or exec form with args, in the session's cwd, with CODDY_SESSION_ID and CODDY_HOOK_EVENT in a process group of its own: past timeout (default hooks.default_timeout_seconds, 60) the whole group is stopped
0, empty
no decision; silence approves nothing
0, JSON
the fields apply permissionDecision, updatedInput, additionalContext, decision, continue: false, systemMessage
0, text
context for SessionStart and UserPromptSubmit only
2
block: the JSON reason, else stderr
other
non-blocking error and a notice row also a crash, a timeout, a cancelled turn or invalid JSON; with failClosed it blocks

4. Several hooks on one event

deny > ask > allow the most restrictive decision wins
  • they run one after another in catalog order, your file first; each sees the input the previous one rewrote;
  • all of them run even after a deny, so an audit hook sees every call;
  • every additionalContext is kept in order, each text capped at hooks.max_output_chars (10,000);
  • async: true is started and not awaited: it never decides, at most 8 run at once.
