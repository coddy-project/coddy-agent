coddy-desktop: one process, one window, a frame per chat

coddy-desktop is one binary: it serves the web interface on a loopback port it remembers and opens a browser window on it in application mode. The page in that window is not the web interface - it is a tab strip over one frame per chat, and the strip drives the window itself.

1. The launcher (external/desktop)

the process on the desktop
<home>/desktop/port the same loopback port every launch; a browser scopes stored state to the origin, so the tabs come back and the tour stays seen
The HTTP subsystem, and only it one serve.Supervisor over the shared session manager; the scheduler, the bots, the relay are named in the log and left to coddy serve. No credential is asked: loopback, opened by the person who started it
The browser, in application mode --app= plus a profile of its own under <home>/desktop/profiles/, so the window is a process this run can wait on and the agent's cookie stays out of the everyday profile
The window, over X11 the system frame taken off, move and resize by EWMH, rounded corners by Shape, and a passive grab on Ctrl+T / Ctrl+W / Ctrl+Tab, which an application window would otherwise answer itself
Tray icon and autostart StatusNotifierItem on the session bus with a com.canonical.dbusmenu menu; coddy-desktop.desktop in this user's autostart folder. Nothing system-wide, nothing as root

2. The page in the window (/desktop/)

served under the SPA's catch-all, never a route of its own
GET /desktop/ one HTML file, one stylesheet, one script. A route of its own would sit behind the sign-in gate, which has no form to answer in an application window
what the strip asks of the window around it
POST /desktop/window minimise, maximise, close, move-begin, move-by, decorate, undecorate
GET /desktop/keys one long poll at a time for the chords the launcher took at the X server
GET /desktop/menu the rows are decided in Go (shell.MenuRows), so the strip's menu and the tray's are one list
GET, POST /desktop/settings open at login, the tray icon, start minimised, the system frame; kept in <home>/desktop/settings.json
The strip menu, tabs, +, the empty space that drags the window, the arrows for a row too long, and the window buttons. It wears the theme of the chat in front

3. The chats

One <iframe> per tab the web interface of this same server, same origin, #/s/<session>
A hidden tab is hidden, not unmounted that is the point of a tab: the transcript, the scroll position and the stream behind it stay
One GET /coddy/events for all of them every instance of one origin shares the stream, so tabs cost memory and not connections
System notifications the web interface raises them; the profile is told the answer before its first window, so no permission bubble opens over the strip

A key pressed in a chat reaches that frame's document and never the parent, so the strip attaches its handler to every frame's contentDocument - which it may, the frames being same-origin, and which asks nothing of the web interface.

The agent, the models, the tools unchanged: the window is a surface over the same session manager

4. One launch, end to end

Read the remembered port a desktop already serving there is handed the window, and nothing is served twice
Bind it and serve free port written back; a port that is taken yields another one, and that launch has no tabs
Open the browser on /desktop/ a fresh profile is seeded first: no translate bubble, notifications granted to this origin
Find the window, take its frame off by the process tree, because the window names a child of the browser we started
The strip asks what it may do no window to drive, no window buttons; the tabs come back from the page's stored state

Closing the window ends the process, and the server with it. The window is a Linux port: elsewhere the binary builds and serves, and CODDY_DESKTOP_BROWSER still opens a window, but nothing drives it, so the system frame stays and the strip draws no buttons of its own.
