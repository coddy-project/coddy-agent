Compaction as a chain of summary blocks

Each compaction appends one summary block after the blocks before it. Earlier blocks are never rewritten, so every request keeps its cached prefix.

1. Transcript on disk (insert-only)

covered by B2

Gray rows stay in messages.json for the transcript, rewind and export. The model no longer reads them.

2. What the model reads

system prompt
B1 The earlier conversation was compacted...
oldest first: later blocks continue earlier ones
B2 The conversation after the summary above...
user: question 5
assistant: answer 5
user: question 6
assistant: answer 6
B3 is appended here by the next compaction

Between two compactions every request opens with the same bytes up to the end of the last block, and a compaction only appends after it, so the provider's prompt cache survives.

Before the chain, the next summary retold B1 together with the tail and replaced it: early details wore away, and the cache broke from the first message on.

</transcript>
B3 inserted at the boundary, before q6

q6 and a6 stay verbatim (keep_recent_turns).

Inside one long turn the first block starts with the turn's prompt verbatim; later blocks of that turn do not repeat it.

prompt (verbatim) + summary of the earlier steps

4. Merge when the chain outgrows a third of the session model's window

The earliest blocks are retold as one row M. M has no compaction_block flag, so the chain starts anew at M, and it is inserted right after the last block it replaces. As many blocks go as bring the chain down to half of that share, M counted as long as the longest row it retells. The gap between the two marks keeps merges rare, because a merge does move the cached prefix.

what the model reads after the merge: M, B5, B6, then the tail
B1
B2
B3
B4
M = B1..B4
B5
B6
verbatim tail
retold into M; the rows stay on disk, the model stops reading them

The newest block is never merged. Blocks of the turn in progress go last, only when the earlier ones are not enough; M then keeps the turn's prompt in front, so the prompt appears once. A failed merge leaves the chain as it was.

A session compacted before the chain existed has one plain summary row: it is read as the root of a chain, and the next compaction appends a block after it.
