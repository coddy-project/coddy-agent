# Цепочка релеев

**Цель.** Второй релей за первым, со своими узлами, чтобы один клиент, подключённый к внешнему релею, доставал до всего и видел всё в списках - рой в виде дерева или кольца релеев. Так парк, разбросанный по разным сетям, объединяется в один, и каждый релей знает только своих прямых потомков.

**Окружение.** Запущенный стенд из руководства [Релей и его узлы в Docker](swarm-relay-and-nodes.md). К нему добавляются два сервиса. Механика описана в разделе [Кольца и маршруты](../operate/swarm.md#кольца-и-маршруты).

## 1. Идея

С точки зрения родителя релей - это узел. Процесс, который запускает релей (`swarm.enable`) и при этом указывает родителя в `swarm.join`, регистрируется у этого родителя точно так же, как агент, с `kind: relay`. Больше для цепочки ничего не нужно - ни второго механизма, ни перехода, который знал бы, насколько глубока цепочка.

## 2. Файлы

`inner.yaml` - релей, который присоединяется к внешнему. `token` в его записи join - его собственный клиентский токен, потому что именно это значение предъявляет внешний релей, когда проксирует в него запрос.

```yaml
httpserver:
  enable: false

swarm:
  enable: true
  host: "0.0.0.0"
  port: 12346
  name: "inner"
  auth_token: "${INNER_CLIENT_TOKEN}"
  pairing_tokens: ["${SWARM_PAIRING_TOKEN}"]
  join:
    - url: "http://relay:12346"
      name: "inner"
      pairing_token: "${SWARM_PAIRING_TOKEN}"
      token: "${INNER_CLIENT_TOKEN}"
```

Две строки в `.env`.

```bash
INNER_CLIENT_TOKEN=change-me-inner
NODE_C_TOKEN=change-me-node-c
```

Два сервиса в `docker-compose.yml`, рядом с существующими. `node-c` - обычный узел, чей релей - `inner`.

```yaml
  inner:
    image: ghcr.io/coddy-project/coddy-agent:latest
    command: serve
    environment:
      CODDY_HOME: /home/user/.coddy
      CODDY_CONFIG: /home/user/.coddy/config.yaml
      INNER_CLIENT_TOKEN: ${INNER_CLIENT_TOKEN}
      SWARM_PAIRING_TOKEN: ${SWARM_PAIRING_TOKEN}
    volumes:
      - ./inner.yaml:/home/user/.coddy/config.yaml:ro
      - inner_home:/home/user/.coddy
    depends_on: [relay]

  node-c:
    <<: *node
    environment:
      CODDY_HOME: /home/user/.coddy
      CODDY_CONFIG: /home/user/.coddy/config.yaml
      CODDY_CWD: /workspace
      RELAY_URL: http://inner:12346
      NODE_NAME: node-c
      NODE_TOKEN: ${NODE_C_TOKEN}
      SWARM_PAIRING_TOKEN: ${SWARM_PAIRING_TOKEN}
      OPENAI_API_KEY: ${OPENAI_API_KEY-}
    volumes:
      - ./node.yaml:/home/user/.coddy/config.yaml:ro
      - ./workspace/node-c:/workspace
      - node_c_home:/home/user/.coddy
    depends_on: [inner]
```

И ещё два именованных тома, `inner_home` и `node_c_home`. Внутренний релей не публикует порт - к нему обращаются через внешний.

## 3. Запуск и проверка

```bash
mkdir -p workspace/node-c
docker compose up -d
docker compose logs inner
```

В логе внутреннего релея видно, что он начал слушать порт, затем `swarm: joining relay` в сторону `relay`, затем регистрацию `node-c` у него. Проверьте с внешнего релея, с внешним клиентским токеном.

```bash
curl -s -H "Authorization: Bearer $T" http://127.0.0.1:12346/swarm/nodes
curl -s -H "Authorization: Bearer $T" http://127.0.0.1:12346/swarm/topology
```

Список узлов внешнего релея называет `inner` с `"kind": "relay"`; топология показывает за ним ещё и `node-c` с маршрутом в два перехода, потому что обход топологии спрашивает у каждого дочернего релея его собственных потомков.

Точки монтирования складываются, если выписать путь целиком, и каждый переход отрезает свой префикс.

```bash
curl -s -H "Authorization: Bearer $T" \
  http://127.0.0.1:12346/swarm/nodes/inner/swarm/nodes/node-c/v1/models
coddy -p "Say hello in one line." \
  --remote http://127.0.0.1:12346/swarm/nodes/inner/swarm/nodes/node-c --remote-token "$T"
```

Ответ на промпт приходит от `node-c` через два релея, и для этого нужен только токен внешнего релея - внешний релей аутентифицируется на `inner` токеном из `inner.yaml`, а `inner` на `node-c` собственным токеном этого узла.

Агрегированный список собирается рекурсивно так же. У дочернего релея запрашивается его собственный агрегат, а не список его узлов, поэтому сессия на `node-c` появляется на внешнем релее с `"node_path": ["inner", "node-c"]`.

```bash
curl -s -H "Authorization: Bearer $T" 'http://127.0.0.1:12346/swarm/sessions'
```

В веб-интерфейсе внешнего релея карта рисует внутренний релей блоком с `node-c` под ним; если войти в `node-c`, управление им идёт через оба перехода.

## 4. Кольцо

Узел или релей может присоединиться к двум родителям. Добавьте вторую запись в `swarm.join`, и он зарегистрируется у обоих; внешний релей тогда знает к нему два пути. Это кольцо, и оно допустимо. Маршруты строятся обходом в ширину, поэтому сообщается кратчайший, а остальные появляются как `alternates` в записи топологии узла, и на них клиент переключается, когда короткий переход отказывает. Запрос несёт id релеев, через которые прошёл, поэтому обход по кольцу завершается и не крутится бесконечно.

## Что обычно идёт не так

- **Внутренний релей регистрируется, но запрос через `/swarm/nodes/inner/...` получает ответ 401.** `token` в собственной записи join внутреннего релея не совпадает с `auth_token` внутреннего релея. Внешний релей предъявляет это значение, когда пересылает запрос во внутренний, поэтому они должны совпадать;
- **`node-c` зарегистрировался в `inner`, но `/swarm/nodes` внешнего релея его не показывает.** Так задумано - список узлов релея содержит только его прямых потомков. `node-c` есть в `/swarm/topology` и в `/swarm/sessions`, и до него можно добраться через точку монтирования в два перехода;
- **Топология внешнего релея показывает предупреждение для внутреннего.** Внутренний релей известен, но сейчас недоступен - его туннель оборвался или его аренда устарела после перезапуска `inner`. Он перерегистрируется в течение трети срока аренды; если предупреждение не уходит, проблема в сети между ними;
- **Путь монтирования перестаёт работать после нескольких переходов.** Путь, написанный вручную, ограничен тем же бюджетом переходов, что и веерная рассылка запросов, поэтому клиент не может бесконечно ходить по кольцу. Сократите маршрут и обращайтесь к узлу с ближайшего к нему релея;
- **Кольцо показывает узел один раз, а не дважды.** Так и должно быть - рой убирает дубликаты узла по его идентичности (`agent_uuid`), оставляет более короткий маршрут и указывает другой как альтернативный.
