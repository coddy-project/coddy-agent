# Coddy в CI

Шаг пайплайна, который задаёт агенту один вопрос и читает ответ, например ревью пул-реквеста, краткое описание диффа или проверку того, что документ всё ещё соответствует коду. Режим печати консоли `coddy -p` ([Консоль](../surfaces/console.md), раздел "Разовый режим печати") выполняет один ход без терминала, выводит текст ассистента потоком в stdout, а диагностику в stderr и завершается с ненулевым кодом, если что-то пошло не так. Бинарник релиза содержит консоль, а облегчённая сборка отвечает на `-p` подсказкой пересобрать её.

1. **Установите бинарник на раннер.** Однострочный установщик ([Установка](../getting-started/install.md)) кладёт `coddy` в `~/.local/bin` и создаёт `~/.coddy/config.yaml` из файла-примера, если такого файла нет. Добавьте этот каталог в `PATH` для следующих шагов.

   ```bash
   curl -fsSL https://coddy.dev/install.sh | bash
   export PATH="$HOME/.local/bin:$PATH"
   coddy -v
   ```

2. **Дайте заданию собственный домашний каталог.** В `CODDY_HOME` лежат конфигурация, сессии и журналы (по умолчанию `~/.coddy`). Направьте его во временный каталог, чтобы транскрипт одного задания никогда не попал в следующее и после удаления раннера ничего не осталось. Загрузчик читает `$CODDY_HOME/config.yaml`, а перед этим `$CODDY_HOME/.env` с переменными, которые не задала оболочка. `CODDY_CONFIG` указывает на файл конфигурации в другом месте, а `--cwd` (или `CODDY_CWD`) задаёт рабочую папку сессии, которой в задании служит чекаут. Все сессии задания попадают в `$CODDY_HOME/sessions`.

   ```bash
   export CODDY_HOME="$(mktemp -d)"
   ```

3. **Напишите конфигурацию, которая берёт ключ из окружения.** `api_key` провайдера может быть ссылкой `${VAR}`, которая раскрывается при загрузке файла, или оставаться пустым, и тогда ключ читается в момент вызова из `NAME_API_KEY`, то есть из переменной с именем провайдера в верхнем регистре, где дефисы заменены подчёркиваниями. Так `openai` читает `OPENAI_API_KEY`, а `team-gateway` читает `TEAM_GATEWAY_API_KEY`. В обоих случаях секрет остаётся в хранилище секретов CI и никогда не попадает в файл. Зафиксируйте модель и лимит ходов, потому что именно `agent.max_turns` ограничивает стоимость одного шага. Если `config.yaml` нет вовсе, одного `OPENAI_API_KEY` или `ANTHROPIC_API_KEY` достаточно для провайдера и модели по умолчанию, но заданию лучше зафиксировать свои. Все ключи описаны на странице [Конфигурация](../getting-started/configuration.md).

   ```yaml
   providers:
     - name: openai
       type: openai
       api_key: "${OPENAI_API_KEY}"   # or leave it empty: OPENAI_API_KEY is read when the model is called

   models:
     - model: "openai/gpt-5.4-mini"
       max_tokens: 16384

   agent:
     model: "openai/gpt-5.4-mini"
     max_turns: 20
   ```

4. **Проверьте конфигурацию, прежде чем тратить токены.** `coddy -t` проверяет файл, который загрузил бы запуск, по встроенной схеме и правилам загрузчика, выводит каждую проблему с номером строки и строкой `fix:` и при ошибках завершается с кодом 1, ничего не запуская ([Проверка файла из командной строки](../getting-started/configuration.md#проверка-файла-из-командной-строки)). `coddy --dry-run` выполняет ту же проверку, а затем запрашивает у каждого провайдера список моделей, и этот один запрос проверяет и адрес, и ключ. Поэтому неверный секрет даст ошибку здесь, с указанием строки, а не 401 посреди ревью ([Пробный запуск](../getting-started/configuration.md#пробный-запуск---проверка-того-на-что-указывает-файл)). Оба флага работают в любой сборке.

   ```bash
   coddy -t          # the file: schema and loader rules
   coddy --dry-run   # the file, then the providers it names
   ```

5. **Запустите промпт.** `-p` принимает промпт. `--mode ask` ограничивает ход инструментами только для чтения (`read`, `glob`, `grep`, `print_tree`, `websearch`, `webfetch`, `question`, `load_skill`, `coddy_docs_search`, `coddy_docs_read`, без оболочки, записи файлов и инструментов MCP). Для ревью это как раз то, что нужно, и запросов разрешений при этом не возникает. `--model` выбирает одну из настроенных моделей, `--cwd` - рабочую папку. Ответ идёт в stdout, всё остальное в stderr, поэтому перенаправленный stdout даёт файл, который можно опубликовать как комментарий.

   ```bash
   git diff origin/main...HEAD | coddy -p "Review this change. Read the files it touches for context, report defects with path:line, and end with one line: VERDICT: ok or VERDICT: needs work." --mode ask > review.md
   ```

   Дифф приходит на stdin и прикладывается к промпту как вложение, так же как `codex exec` принимает stdin из конвейера, поэтому модель получает его без вызова инструмента. Строка в stderr сообщает, сколько данных приложено. Промпт, слишком длинный для командной строки (в Linux операционная система ограничивает один аргумент 128 КиБ), передаётся в файле, `coddy -i review-brief.md`, или через stdin, `coddy -p - < review-brief.md`, и промпт из файла принимает дифф так же, `git diff | coddy -i review-brief.md`. Шаг, чей stdin принадлежит чему-то другому (циклу `while read` по списку файлов, `ssh` или любому заданию на раннере GitLab, который передаёт скрипт задания оболочке через stdin), передаёт `--no-stdin`, чтобы ничего не прикладывалось ([Разовый режим печати](../surfaces/console.md#одноразовый-режим-печати--p--prompt)).

   Шаг, который должен править файлы, запускается вместо этого в режиме `agent`, и на его запросы разрешений тогда отвечает не человек. `--permission-mode bypass` разрешает всё, `accept_edits` одобряет запись файлов и отклоняет команды оболочки, а `ask` (в нём начинает новая сессия, пока режим не выбран) отклоняет каждый запрос с пометкой в stderr. Инструмент вопросов получает пустые ответы. Следующий шаг продолжает ту же сессию через `coddy -c -p "..."`, поэтому второй вопрос видит файлы и результаты инструментов первого. Он сохраняет и модель, режим и режим разрешений первого шага. `--permission-mode` задаёт режим только сессии своего запуска. Шаг, который её продолжает, сохраняет этот режим вместе с сессией, а новая сессия начинает в режиме, выбранном последним внутри сессии (пока ничего не выбрано, в `ask`), что бы ни передавал предыдущий шаг. Продолжающий шаг, который не должен работать в `bypass`, снова передаёт `--permission-mode`. Шаг, сессию которого никто больше не прочитает, передаёт `--ephemeral`, и запуск удаляет её, когда заканчивается.

6. **Проверьте код выхода.**

   | Команда | Код 0 | Код 1 |
   |---|---|---|
   | `coddy -p "..."` | ход завершился, и ответ выведен | конфигурация не загрузилась, провайдер вернул ошибку, флаг назвал неизвестную модель или режим, входной промпт отклонён (два промпта, отсутствующий файл, текст не в UTF-8, больше 8 МиБ) или ход отменён |
   | `coddy -t` | файл корректен (предупреждения не считаются ошибкой) | в файле есть ошибки, или его нет |
   | `coddy --dry-run` | все проверки прошли | в файле есть ошибки, или какая-то проверка не прошла |

   Код выхода `-p` говорит о процессе, а не о вердикте. Ход, остановившийся на `agent.max_turns`, всё равно завершается с кодом 0. Попросите в промпте закончить ответ явной строкой, как выше, и пусть пайплайн ищет её через grep.

7. **Решите, что может выполнять чекаут.** `.coddy/mcp.json`, `.coddy/hooks.json` и `.coddy/agents/` приходят вместе с репозиторием и при политике `ask` по умолчанию ждут, пока оператор их одобрит, а на раннере этого никто не делает. Для собственного репозитория передайте `--mcp-project-trust allow` (его принимают и консоль, и `acp`, и `serve`) или задайте `allow` для `mcp.project_trust`, `hooks.project_trust` и `subagents.project_trust` в конфигурации задания. Для заданий, которые запускаются на пул-реквестах от посторонних, оставьте `ask` или задайте `deny`, чтобы форк не мог выбирать, что выполняет раннер. Эти три проверки описаны на страницах [MCP-серверы](../features/mcp.md), [Хуки](../features/hooks.md) и [Субагенты](../features/subagents.md).

Всё вместе в виде задания GitHub Actions.

```yaml
name: Review
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    env:
      CODDY_HOME: ${{ runner.temp }}/coddy
      OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Coddy
        run: |
          curl -fsSL https://coddy.dev/install.sh | bash
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"

      - name: Write the config
        run: |
          mkdir -p "$CODDY_HOME"
          cat > "$CODDY_HOME/config.yaml" <<'EOF'
          providers:
            - name: openai
              type: openai
              api_key: "${OPENAI_API_KEY}"
          models:
            - model: "openai/gpt-5.4-mini"
              max_tokens: 16384
          agent:
            model: "openai/gpt-5.4-mini"
            max_turns: 20
          EOF

      - name: Check the config and the provider
        run: coddy --dry-run

      - name: Review the change
        run: |
          git diff origin/main...HEAD | coddy -p "Review this change. Read the files it touches for context, report defects with path:line, and end with one line: VERDICT: ok or VERDICT: needs work." --mode ask | tee review.md
          grep -q 'VERDICT: ok' review.md
```
