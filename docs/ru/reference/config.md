# Справочник по `config.yaml`

Справочник по каждому полю `~/.coddy/config.yaml`. Описание в форме руководства (поиск файла, `.env`, настройка провайдеров) находится на странице [Конфигурация](../getting-started/configuration.md).

К справочнику прилагается машиночитаемая [JSON Schema](../../../internal/config/config.schema.json). Она опубликована по адресу **https://coddy.dev/config.schema.json** и встроена в бинарник, где `coddy -t` / `--test-config` проверяет по ней файл из командной строки (см. [Конфигурация](../getting-started/configuration.md#проверка-файла-из-командной-строки)). Подключите её к YAML language server вашего редактора, и он будет дополнять ключи и находить опечатки.

```yaml
# yaml-language-server: $schema=https://coddy.dev/config.schema.json
```

VS Code (с расширением YAML), Zed, Neovim и Helix подхватывают этот комментарий автоматически, а Coddy записывает его в каждый сохраняемый `config.yaml` (см. [Конфигурация](../getting-started/configuration.md)); IDE от JetBrains его не читают, и в них адрес схемы нужно зарегистрировать в **JSON Schema Mappings**. Соответствие схемы структурам конфигурации на Go проверяет `TestDocsConfigSchemaMatchesStructs` в `internal/config/docs_schema_test.go`. Необязательные поля с тремя состояниями (например, `compaction.enable`, `models[].stream`, `tools.output_limits.*`) принимают как значение, так и `null`; `null` означает, что поле не задано, ровно как пропущенный ключ. Сохраняя файл, Coddy просто не пишет незаданные поля - сам он никогда не записывает `null` и добавляет ключ, только если его значение отличается от встроенного значения по умолчанию, поэтому файл, который ведут вручную, остаётся компактным.

Все поля необязательны, если не помечены как **обязательные**; пустой `config.yaml` (или его отсутствие) допустим, и тогда действуют встроенные значения по умолчанию. Любое строковое значение может ссылаться на переменные окружения через `${VAR_NAME}` (они подставляются при загрузке файла). Чтобы оставить в значении **буквальный `$`** (например, в секрете вида `$2y$10$…`), удвойте его до `$$`; для полей `proxy` интерфейс делает это сам. `${CODDY_HOME}` подставляет загрузчик; `${CWD}` остаётся в загруженном значении, и его подставляет для каждой сессии тот, кто читает путь, кроме полей уровня процесса `sessions.dir`, `memory.dir` и `logger.file` (см. [Конфигурация](../getting-started/configuration.md#ссылки-на-переменные-окружения)).

## Самонастройка агента

Агентным сессиям доступно семейство типизированных инструментов настройки с отложенным применением в духе uci:

- `config_get` читает путь через точку из активного YAML-файла. Поля, похожие на секреты (в том числе `api_key_command` и любой ключ, оканчивающийся на `_api_key`, например `tools.websearch.brave_api_key`), а также значения переменных окружения и заголовков (запись `env` или `headers`, значение `default_headers`) возвращаются как `<redacted>`; список MCP-серверов в HTTP API так же показывает значения обоих файлов mcp.json;
- `config_set` **откладывает** команды в стиле UCI (`set`, `add_list`, `del_list`, `delete`), не трогая файл. Неизвестные схеме пути и команды, которые сделали бы конфигурацию некорректной, отклоняются уже на этом шаге. В возвращаемых списках команд значения, похожие на секреты, скрыты как `<redacted>`; хранилище отложенных команд держит исходные значения;
- `config_changes` перечисляет отложенные команды, которые применит коммит (секреты скрыты);
- `config_commit` применяет отложенный пакет - проверяет его, сохраняет снимок прежнего файла в `config.yaml.prev` (пустой документ, если файла конфигурации ещё не было, чтобы и первый коммит можно было отменить), атомарно записывает файл и на лету перезагружает скилы, правила, встроенные инструменты и политику доверия MCP. Коммит может запустить процессы MCP (при изменённом `mcp.project_trust`) и поменять саму политику разрешений, поэтому он запрашивает разрешение на инструмент и в режиме `ask`, и в режиме `accept_edits` (диалог пропускает только `tools.permission_mode: bypass`), а в запросе перечислены отложенные команды со скрытыми секретами. Кроме того, агенту предписано сначала попросить пользователя подтвердить сохранение. Если перезагрузка во время работы не удалась, файл восстанавливается, а отложенные команды сохраняются; если не удалось даже восстановление, отложенный список считается израсходованным, чтобы слепой повтор не применил его снова;
- `config_revert` отбрасывает отложенные команды (все или только относящиеся к одному пути);
- `config_rollback` восстанавливает снимок до коммита поверх активного файла (меняя их местами, так что второй откат отменяет первый) и перезагружает конфигурацию на лету. Для него действует та же политика разрешений, что и для `config_commit`, и агент предупреждает пользователя, прежде чем его вызвать.

Команды и пути записываются через точку, как в CLI `uci` из OpenWrt, с селектором для именованных элементов последовательностей.

| Команда | Значение |
|---|---|
| `set agent.max_turns=40` | Задать поле объекта |
| `set providers[name=openrouter]={"type":"openai"}` | Выбрать объект последовательности по скалярному полю; при записи добавить его, если его нет |
| `add_list skills.dirs=/opt/skills` | Добавить элемент в последовательность |
| `del_list skills.dirs=/opt/skills` | Удалить совпадающий элемент последовательности |
| `delete providers[name=openrouter]` | Удалить поле или элемент |
| `skills.dirs.0` (форма пути) | Индекс в последовательности |

Корневой путь (`.` или `/`) доступен только для чтения. Значения объектов и массивов записываются в JSON; строковые поля принимают текст как есть. Отложенные команды хранятся в бандле сессии, поэтому переживают перезапуски и возобновление хода после разрешения через HTTP.

Встроенный скил `/configure-coddy` учит агента этому синтаксису, порядку "сначала подтверждение, потом коммит" и безопасному поиску и установке MCP-серверов и скилов; в нём же лежит каталог разделов конфигурации для агента, и его нужно обновлять вместе с этим справочником при любом изменении схемы. Изменения слушателей уровня процесса по-прежнему могут потребовать перезапуска соответствующей команды; перезагрузка на лету гарантирована именно для конфигурации агента текущей сессии, скилов, правил, встроенных инструментов и политики доверия MCP. MCP-серверы в этот файл не входят (см. [`mcp`](#mcp)).

## Справочник полей

Раздел генерирует `make docs` из `internal/config/config.schema.json` (схемы, встроенной в бинарник и опубликованной по адресу <https://coddy.dev/config.schema.json>) и из значений по умолчанию, которые применяет загрузчик; `make docs-check` падает, если этот блок устарел. Типы указаны так, как их объявляет схема (`string or null` означает поле с тремя состояниями), значение по умолчанию показывает, во что разрешается ключ при пустом `config.yaml`, а описание повторяет строку `doc:`, которую `coddy -t` печатает для ключа. Заметки, не уместившиеся в строку таблицы, собраны ниже в разделе [Заметки](#заметки).

### `providers`

Учётные данные API и выбор транспорта для внешних LLM-провайдеров. Если api_key пуст, Coddy читает переменную окружения NAME_API_KEY (NAME - имя провайдера в верхнем регистре, дефисы заменены подчёркиваниями); строка типа "codex" входит через ChatGPT и ключ не читает.

| Ключ | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `providers` | список объектов |  | Учётные данные API и выбор транспорта для внешних LLM-провайдеров. Если api_key пуст, Coddy читает переменную окружения NAME_API_KEY (NAME - имя провайдера в верхнем регистре, дефисы заменены подчёркиваниями); строка типа "codex" входит через ChatGPT и ключ не читает. |
| `providers[].name` | строка |  | Логический идентификатор, который служит первым сегментом models[].model. Латинские буквы ASCII, цифры, дефис и подчёркивание; первой должна идти буква. |
| `providers[].type` | строка, одно из `openai`, `anthropic`, `neuraldeep`, `codex`, `devin` |  | Протокол обмена с этим провайдером. "openai" - для настраиваемых OpenAI-совместимых эндпоинтов (OpenAI, DeepSeek, Groq, Ollama, llama.cpp, LM Studio), "anthropic" - для Anthropic, "neuraldeep" - для OpenAI-совместимого API NeuralDeep на одном из двух официальных развёртываний (выбирается через api_base), "codex" - для OAuth ChatGPT с официальным бэкендом Codex (Responses API), "devin" - для аккаунта Devin (Cognition) со входом через браузер или Devin CLI, который обслуживает сервер Devin API; см. https://coddy.dev/docs/features/devin. |
| `providers[].api_base` | строка |  | Необязательное переопределение базового URL. Для типа "openai" включите /v1 (например, http://localhost:11434/v1); для типа "anthropic" укажите Anthropic-совместимый шлюз (по умолчанию https://api.anthropic.com). Для типа "neuraldeep" значение выбирает развёртывание - https://api.neuraldeep.ru/v1 (Россия, по умолчанию) или https://api.neuraldeep.tech/v1 (международное зеркало); любое другое значение сводится к значению по умолчанию. Для типов "codex" и "devin" игнорируется, они всегда используют свои официальные эндпоинты. |
| `providers[].api_key` | строка |  | Секрет провайдера. Ключ напрямую, ссылка "${ENV}", которая разворачивается при загрузке, или пусто, чтобы читать NAME_API_KEY в момент вызова LLM. Порядок разрешения - api_key -> stdout api_key_command -> NAME_API_KEY. Для типа "devin" это токен сессии Devin, и если он задан, он важнее входа через браузер и входа Devin CLI. Для типа "codex" игнорируется, он входит через ChatGPT. |
| `providers[].api_key_command` | строка |  | Необязательная команда-помощник для учётных данных. Если api_key пуст, она запускается через обнаруженную оболочку хоста (pwsh, powershell или cmd в Windows; bash или sh в остальных системах), и её stdout без краевых пробелов становится ключом. При ошибке ключ берётся из NAME_API_KEY. Для типа "codex", который ключ не принимает, не запускается никогда. |
| `providers[].proxy` | строка | inherit | inherit (по умолчанию, то же, что отсутствие ключа), none или URL прокси со схемой http://, https://, socks5:// или socks5h://. inherit следует прокси, который задаёт окружение процесса Coddy, - HTTPS_PROXY, HTTP_PROXY и NO_PROXY, но никогда для loopback-адреса; ALL_PROXY не читается. none подключается напрямую и игнорирует эти переменные. URL прокси направляет через этот прокси каждый запрос строки, включая адреса из NO_PROXY и loopback; с SOCKS имена хостов разрешает прокси. Настройка покрывает все запросы провайдера - генерацию ответов, список моделей, расход лимитов аккаунта и вход. |
| `providers[].timeout_ms` | целое число | 0 | Необязательный предел для каждого HTTP-запроса к LLM этого провайдера, включая чтение потокового тела ответа. 0 (по умолчанию) не задаёт клиентского тайм-аута, поэтому медленная обработка промпта на больших контекстах никогда не обрывается. |
| `providers[].usage_limits_panel` | логическое значение или null | true | Показывать панель расхода лимитов аккаунта этого провайдера (строку в футере консоли и /usage, раздел лимитов и баннер в веб-интерфейсе) и читать для неё эндпоинт расхода провайдера (GET /v1/limits для типа neuraldeep, эндпоинт расхода бэкенда Codex для типа codex, RPC статуса управления местами для типа devin). Без значения или true панель включена; false скрывает её и прекращает эти чтения для этой строки. Влияет только на провайдеров, у типа которых есть источник данных о расходе. |

### `models`

Именованные записи моделей, которые могут выбирать агент и интерфейс.

| Ключ | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `models` | список объектов |  | Именованные записи моделей, которые могут выбирать агент и интерфейс. |
| `models[].model` | строка |  | "provider_name/api_model_id" - первый сегмент пути должен совпадать с одним из providers[].name, остаток отправляется в API LLM (и сам может содержать слэши). |
| `models[].max_tokens` | целое число |  | Верхний предел токенов завершения на одно сообщение ассистента. Модель codex его никогда не отправляет (бэкенд Codex отвергает max_output_tokens), поэтому там он ничего не ограничивает, а coddy -t и --dry-run предупреждают о таком значении. |
| `models[].temperature` | число |  | Температура сэмплирования (0 = детерминированно; выше = случайнее). |
| `models[].max_context_tokens` | целое число | 0 | Окно контекста модели в токенах, относительно которого считают кольцо контекста в веб-интерфейсе, процент контекста в консоли и порог автоматического сжатия контекста. 0 берёт его из списка моделей провайдера, если провайдер его сообщает (хаб NeuralDeep, vLLM, OpenRouter, LM Studio), иначе 128000. |
| `models[].multimodal` | логическое значение | false | Модель принимает на вход изображения и файлы в дополнение к тексту; интерфейс показывает для этой модели кнопку прикрепления файла, и read показывает ей картинку из файла PNG, JPEG, GIF или WebP вместо отказа читать его как двоичный. |
| `models[].reasoning_levels` | список строк или null |  | Переопределяет уровни рассуждения, которые предлагаются для этой модели. Если не задано, уровни определяются по id модели (gpt-5* -> minimal,low,medium,high; серия o от OpenAI, gpt-oss*, qwen3* и модели Claude с расширенным мышлением -> low,medium,high). Явный пустой список скрывает выбор уровня. Экран настроек заполняет это поле из GET /coddy/config/reasoning-levels по кнопке "Получить уровни ризонинга". |
| `models[].reasoning_default` | строка |  | Уровень рассуждения, выбранный заранее для новых чатов; должен быть одним из итоговых уровней, иначе игнорируется. |
| `models[].allow_reasoning_off` | логическое значение | false | Показывать Off в выборе уровня рассуждения этой модели. Включайте, только если это развёртывание провайдера и модели выполняет специфичный для провайдера запрос Coddy на отключение рассуждения; автоматически Coddy проверить это не может. |
| `models[].stream` | логическое значение или null | true | Транспорт для обмена с этой моделью. Без значения (или true) ответ передаётся потоком по SSE. false отправляет один блокирующий запрос и выдаёт ответ целиком - для серверов и прокси, которые плохо работают с потоками событий. Для провайдеров типа codex не принимается, их бэкенд работает только в потоковом режиме. |

### `agent`

Значения по умолчанию для основного цикла агента (id модели и защитные пределы).

| Ключ | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `agent.queue_mode` | строка, одно из `steer`, `after_turn` |  | Предпочтительный режим очереди для Enter во время хода - steer встраивает сообщение в следующий шаг ReAct, after_turn начинает новый ход после текущего ответа. Если значения нет, интерактивные интерфейсы спрашивают при первом использовании. |
| `agent.model` | строка |  | Необязательный id из models[].model по умолчанию. Интерактивные интерфейсы (веб-интерфейс, консоль) выбирают модель для каждой сессии; вызовам без участия человека, которые не называют модель (coddy -p, coddy acp, API-запросы без выбора модели), он нужен, и при пустом значении они сообщают 'no model configured'. |
| `agent.max_turns` | целое число | 165 | Предел шагов ReAct (вызовов LLM) за один ход. По умолчанию 165; 0 снимает предел. Ход, который дошёл до предела, завершается уведомлением, где этот предел назван. |
| `agent.llm_retry_max` | целое число или null | 3 | Дополнительные попытки, общие для повторов транспорта, восстановления после пустого ответа и повторной отправки без первого токена; они расходуются, пока инструменты не продвинут работу или не придёт новое сообщение. 0 отключает эти повторы. У защиты от зацикливания, Stop-хуков, резервных моделей и ожидания сброса квоты свои пределы. |
| `agent.llm_retry_base_ms` | целое число | 1000 | Начальная пауза между повторами LLM в миллисекундах. Пауза, которую назначил сервер (заголовки Retry-After-Ms / Retry-After, фразы "Limit resets at" / "retry in Ns" в теле ответа), заменяет экспоненциальную паузу, но не дольше 60 с. |
| `agent.llm_min_interval_ms` | целое число | 0 | Минимальный промежуток между последовательными вызовами LLM в миллисекундах, повторы включены (0 отключает выравнивание темпа; например, 12000 на строгих бесплатных тарифах). |
| `agent.llm_first_token_timeout_ms` | целое число или null | 90000 | Сколько потоковый вызов LLM может молчать, прежде чем ход его отменит (защита от зависания API). Явный 0 отключает защиту; блокирующие транспорты (stream: false) под защиту не попадают. |
| `agent.llm_stream_idle_timeout_ms` | целое число или null | 300000 | Сколько потоковый ответ LLM может ничего не присылать после первых байтов, прежде чем поток будет оборван как зависший (защита от зависания посреди ответа). Уже полученный текст сохраняется, а ход завершается с указанием на зависание. Явный 0 отключает защиту; ожидание первого байта ограничивает llm_first_token_timeout_ms, а блокирующие транспорты (stream: false) под защиту не попадают. |

### `compaction`

Сворачивает старую историю диалога в сводку, чтобы длинные сессии продолжали помещаться в окно контекста модели. Ручная команда сжатия и автоматический запуск при заданном проценте окна контекста модели.

| Ключ | Тип | По умолчанию | Описание |
|-----|-----|--------------|----------|
| `compaction.enable` | логическое значение или null | true | Главный переключатель сжатия контекста (ручная команда и автоматический запуск). По умолчанию true. |
| `compaction.auto_enable` | логическое значение или null | true | Включает автоматическое сжатие при threshold_percent. false оставляет доступными ручную команду /compact и действие во всплывающей панели "Контекст", но без автоматического сжатия. По умолчанию true. |
| `compaction.threshold_percent` | целое число | 80 | Автоматическое сжатие срабатывает, когда оценка занятого контекста достигает этого процента окна контекста действующей модели (1..100). Окном служит её max_context_tokens, иначе окно из списка моделей провайдера, иначе 128000; это же окно показывает кольцо контекста в веб-интерфейсе. |
| `compaction.keep_recent_turns` | целое число или null | 2 | Сколько последних ходов пользователя (каждый с ответами агента и работой инструментов после него) остаются дословно; в сводку попадает только история до этой границы. 0 сворачивает в сводку всё окно. Если в окне не больше ходов пользователя, чем это число, сжатие оставляет меньше - автоматический запуск вплоть до промпта, на который идёт ответ, ручная команда вплоть до нуля. |
| `compaction.model` | строка | "" | Необязательная модель из models[].model для вызова, который составляет сводку. Пусто - действующая модель сессии. |
| `compaction.fallback_models` | список строк |  | Модели для составления сводки, которые пробуются по порядку, если предыдущая не сработала (id из models[].model). Собственная модель сессии - последний вариант, указана она в списке или нет, поэтому одна недоступная модель не блокирует сжатие. |
| `compaction.result_eviction` | объект |  | При сборке запроса к LLM сворачивает устаревшие результаты read/grep в короткие заглушки (сохранённый транскрипт никогда не переписывается), чтобы постраничное чтение большого файла или широкий поиск не тащили мёртвые строки в каждый следующий ход. Сохраняются только результаты, которые модель пометила (keep_result или keep:true), и последнее рабочее окно; запись в файл делает недействительными прежние read/grep, которые его охватывали. |
| `compaction.result_eviction.enable` | логическое значение или null | true | Главный переключатель вытеснения результатов read/grep. По умолчанию true. |
| `compaction.result_eviction.keep_recent` | целое число или null | 2 | Сколько последних вытесняемых результатов (страниц read, выдач grep) остаются нетронутыми как рабочее окно. 0 не оставляет ни одного. Значение по умолчанию 2 держит живыми одновременно read и grep; при 1 модель, которая сравнивает два результата, раз за разом запрашивает заново тот, который вытеснил другой. |
| `compaction.result_eviction.min_result_bytes` | целое число или null | 2000 | Результаты такого размера и меньше никогда не вытесняются (слишком малы, чтобы заменять их заглушкой). 0 делает кандидатом любой результат. |
| `compaction.result_eviction.start_percent` | целое число или null | 50 | Вытеснять, только когда оценка контекста достигла этого процента max_context_tokens действующей модели. Ниже порога история отправляется без изменений, и кэш промптов провайдера её сохраняет; заглушка, появившаяся посреди истории, делает недействительным каждый закэшированный токен после неё. 0 вытесняет с первого результата; модель без max_context_tokens вытесняет всегда. |

| `decisions.enable` | логическое значение | false | Проверять каждый вызов run_command, который не покрывает запрос разрешения (режим bypass, список разрешённых команд, грант сессии или allow-хук), и каждый вызов run_command или ssh_run_command, на чей запрос интерфейс отвечает сам (режим bypass, бот мессенджера для агента своего чата, запуск плана) или который пропустил хук, через decisions-эндпоинт и отклонять команды, классифицированные как небезопасные; отказ возвращается как результат инструмента, поэтому сессия его фиксирует. Когда эндпоинт отклоняет запрос, недоступен или ограничен по частоте дольше окна повторов или не может прочитать команду целиком, команда тоже не выполняется. |

| `decisions.threshold` | число | 0.5 | Вероятность опции unsafe, начиная с которой команда отклоняется. 0 - значение по умолчанию (0,5); ниже - строже, выше - допускает пограничные команды. Голый ответ без вероятностей считается уверенным. |

### `supervisor`

Проверяет цель сессии (/goal) после каждого хода второй моделью, продолжает незавершённую работу в заданных пределах и следит за зависшими и зациклившимися ходами; см. https://coddy.dev/docs/features/session-supervisor.

|-----|-----|--------------|----------|
| `supervisor.enable` | логическое значение | false | Сверять обычные ходы с последним запросом и без /goal. Цель сессии проверяется независимо от этого переключателя. |
| `supervisor.model` | строка | "" | Настроенная модель из models[].model, которая проверяет работу. Пусто - собственная модель сессии, которая тогда оценивает свою же работу; модель другого семейства судит лучше. |
| `supervisor.verify` | логическое значение или null | true | Подтверждать вердикт о выполнении цели перед её закрытием - субагент goal-verifier читает рабочую папку инструментами только для чтения и проверяет каждое требование. Без значения - true. |
| `supervisor.stall_seconds` | целое число или null | 300 | Сколько секунд ход цели может обходиться без обновлений, прежде чем сторож прервёт его и начнёт ход восстановления. Запросы разрешений, работающие инструменты и работающие фоновые задачи приостанавливают таймер. 0 отключает его. |

### `providers`

Список бэкендов LLM (`[]config.ProviderConfig`, `internal/config/providers.go`).

Порядок поиска ключа - `api_key` → stdout `api_key_command` → переменная окружения `NAME_API_KEY`. Строка `codex` входит через ChatGPT и не читает ни одного из них.

```yaml
providers:
  - name: openai
    type: openai
    api_key: "${OPENAI_API_KEY}"
  - name: local
    type: openai
    api_base: "http://localhost:11434/v1"
    api_key: "~"
  - name: neuraldeep
    type: neuraldeep
    api_key: "${NEURALDEEP_API_KEY}"
    # usage_limits_panel: false  # hide the account usage panel for this row
  - name: codex
    type: codex # use Sign In with ChatGPT in the bundled web UI; no api_key needed
```

#### llama.cpp как OpenAI-совместимый провайдер

`llama-server` работает как провайдер `type: openai` (`api_base: "http://host:8080/v1"`). Рекомендуемые флаги запуска:

- `--jinja` - включает на сервере шаблон чата модели, без которого не работает **вызов инструментов**. Без этого флага llama.cpp молча игнорирует параметр `tools`, и агентный цикл скатывается к ответам простым текстом;
- `-c <n>` - задайте окно контекста, достаточное для промпта агента (системный промпт, схемы инструментов и история; 16k - практический минимум, больше лучше). Когда запрос превышает контекст сервера, llama.cpp сообщает `the request exceeds the available context size` - увеличьте `-c` или уменьшите `max_context_tokens`.

Сборки llama.cpp до конца 2025 года сообщают о сбоях посреди потока нестандартным полем SSE `error:`; Coddy понимает и этот диалект, и текущую форму `data: {"error": ...}` и выводит сообщение сервера в тексте ошибки.

Для `type: codex` откройте **Настройки → Провайдеры LLM** во встроенном веб-интерфейсе и выберите **Войти через ChatGPT** или, для ACP и установок без интерфейса, выполните то же самое в терминале.

```bash
coddy providers login codex    # device flow: prints a URL and a one-time code, then waits
coddy providers list           # every provider with the credential its requests actually use,
                               # plus a warning for an openai row that has neither api_base
                               # nor a credential (its requests leave for api.openai.com)
coddy providers logout codex   # removes the Coddy-managed credential (leaves the Codex CLI login alone)
```

(До версии 1.0.11 у того же процесса входа была ещё отдельная команда только для codex, `coddy codex login | status | logout`. Её убрали в пользу команд выше, которые работают с любым бэкендом; то, что раньше сообщал `codex status`, теперь показывает `coddy providers list`.)

Успешный вход также записывает каталог подписки в `config.yaml`, так же как `coddy providers login neuraldeep` записывает модели своего тарифа (кнопка в настройках сохраняет только учётные данные). Он добавляет строку провайдера `codex`, если её нет, по одной записи `models[]` на каждую модель из каталога Codex (id, которые Codex скрывает в собственном списке выбора, например `gpt-reserve` и `codex-auto-review`, пропускаются) и `agent.model`, если она ещё не задана, - модель, которую сам Codex ставит первой. Ничего из того, что уже есть в файле, не переписывается. Существующая строка провайдера, уже перечисленная модель и выбранная `agent.model` остаются нетронутыми, поэтому повторный вход ничего не меняет. `--no-config` сохраняет только учётные данные. В записях нет `max_tokens`, потому что бэкенд Codex отклоняет `max_output_tokens`. Запущенный `coddy serve` продолжает работать с загруженной конфигурацией, поэтому перезапустите его, чтобы он увидел новые модели.

Оба пути используют одно хранилище. Имя провайдера передаётся аргументом, поэтому `coddy providers login <name>` выбирает конкретную строку codex, если в `config.yaml` их несколько (строка с именем, отличным от `codex`, либо уже есть в `config.yaml`, либо её создаёт вход с `--type codex`). У каждой строки codex свой вход; вход Codex CLI заменяет его только для единственной строки codex или, если их несколько, для строки с именем `codex` ([Несколько профилей одного типа провайдера](../getting-started/configuration.md#несколько-профилей-одного-типа-провайдера)). Coddy использует официальный поток авторизации устройства и хранит обновляемые учётные данные в `$CODDY_HOME/providers/<provider-name>/codex-auth.json` со строгими правами доступа к файлу; токены никогда не попадают в `config.yaml`. `api_key`, `api_key_command` и `api_base` для Codex игнорируются (`api_key_command`, оставленный в строке codex, никогда не запускается), а `proxy` применяется и к OAuth, и к запросам провайдера. Ограничить длину ответа модели Codex Coddy не может - на `max_output_tokens` бэкенд отвечает `Unsupported parameter`, поэтому `models[].max_tokens` у модели codex ничего не ограничивает. Поле всё равно принимается (форма настроек заполняет его в каждой строке модели), но `coddy -t`, `--dry-run` и стартовый лог `coddy serve` о нём предупреждают, а `max_tokens`, отправленный в `POST /v1/chat/completions` для модели codex, отклоняется с `400`. `max_context_tokens` задаёт другое - окно, относительно которого считают кольцо контекста и автоматическое сжатие контекста; провайдер этот лимит не применяет. Если поле не задано у модели codex, берётся окно, которое каталог Codex сообщает для модели, `context_window` (сегодня 272000 для каждой модели каталога) ([Окно контекста](../features/compaction.md#окно-контекста)). Список выбора моделей читает каталог с официального бэкенда Codex с сохранённым токеном. Бэкенд предлагает каждую модель только релизам Codex начиная с `minimal_client_version` этой модели, потому что старый бинарник Codex её не запустит. Coddy гоняет любую модель через собственный цикл и инструменты, поэтому представляется релизом Codex 0.999.0, намного выше релизов, указанных в этих ограничениях, и показывает все модели, которые предлагаются аккаунту, включая самые новые, независимо от того, какой Codex CLI установлен и установлен ли он вообще. Модели, которые Codex скрывает в собственном списке выбора, в список не попадают. Если управляемых Coddy учётных данных нет, Coddy остаётся совместимым со входом Codex CLI в `~/.codex/auth.json` (или `$CODEX_HOME/auth.json`). Запросы Codex всегда идут на официальный бэкенд; переопределить его можно только переменной уровня процесса `CODDY_CODEX_BASE_URL` (для тестов и собственных шлюзов), поэтому документ настроек сам по себе никогда не перенаправит токен OAuth.

Codex служит только бэкендом модели. Агент сохраняет собственный системный промпт Coddy, каталог инструментов, разрешения и цикл ReAct, а учётные данные ChatGPT нужны лишь для аутентификации вызовов Responses (`features/codex_auth.feature` закрепляет это и для HTTP, и для ACP).

**Срок жизни токена.** Токен доступа незаметно обновляется незадолго до истечения, и обновлённые токены записываются обратно в тот файл, откуда пришли. Если учётные данные взяты из входа Codex CLI (для той единственной строки, которую он обслуживает), этим файлом служит сам `~/.codex/auth.json`, тот же файл, что читает CLI `codex`, поэтому оба инструмента работают от одного входа, и обновление, сделанное Coddy, видно CLI (и наоборот). Управляемые Coddy учётные данные обновляются на месте в `$CODDY_HOME/providers/<name>/` и вход CLI не трогают. Выход (`coddy providers logout codex` или **Выйти** в настройках) удаляет только файл, которым управляет Coddy.

**Отчёт при запуске.** Если настроен хотя бы один провайдер `type: codex`, `coddy acp` и `coddy serve` при запуске пишут в лог по одной строке `codex credential` на провайдера - откуда взяты учётные данные и сколько ещё действует токен доступа. Отсутствие учётных данных, непригодный `auth_mode` или истёкший токен без токена обновления записываются как **предупреждение** с указанием `coddy providers login <name>`; истёкший, но обновляемый токен даёт лишь информационную строку, потому что следующий запрос его обновит. Установки без провайдера codex ничего не пишут.

**Рассуждение.** Бэкенд Codex обслуживает id моделей `gpt-5*` и `gpt-6*`, но принимает только `none`, `low`, `medium`, `high` и `xhigh`, поэтому модели на codex предлагают **`none`** там, где другие провайдеры предлагают `minimal` (явное `reasoning_levels: [minimal]` тоже переназначается). Ходы с рассуждением запрашивают сводки (`summary: auto`), чтобы рассуждение шло потоком в интерфейс, и зашифрованное рассуждение (`include: reasoning.encrypted_content`), чтобы собственная цепочка рассуждений модели дословно повторялась в следующем запросе того же хода, - так же работает Codex CLI. Повторяемое рассуждение помечается моделью, которая его создала, и пропускается, когда сессия переключает модель. Эти элементы хранятся непрозрачно в `messages.json` (`reasoning_signature`, ~1 КБ на ход ассистента), и `GET /coddy/sessions/{id}/messages` их не отдаёт.

### `models`

Список логических моделей (`[]config.ModelEntry`, `internal/config/models.go`).

```yaml
models:
  - model: "openai/gpt-5.6-terra"
    max_tokens: 8192
    reasoning_default: medium
    multimodal: true
  - model: "openai/gpt-5"
    max_tokens: 8192
    reasoning_default: medium
  - model: "local/qwen3-30b"
    max_tokens: 8192
    stream: false
```

**Модели без потоковой передачи.** `stream: false` меняет одно - coddy отправляет один блокирующий `POST /chat/completions` вместо запроса SSE и передаёт готовый ответ остальной части среды выполнения целиком. Всё дальше по цепочке не меняется, поэтому транскрипт, вызовы инструментов и бандл сессии выглядят так же; разница в том, что ничего не появляется, пока модель не закончит, а строка рассуждения не показывает живую длительность. Перед включением учтите два следствия. Нажатие **Стоп** во время блокирующего вызова теряет весь ответ, потому что сервер ещё ничего не прислал, тогда как потоковый ход сохраняет уже пришедшие токены. И клиент, который просит поток SSE, всё равно его получает, потому что переключатель управляет соединением с LLM, а соединение с клиентом не трогает. Поэтому потоковый HTTP-ответ теперь каждые 15 с несёт комментарий keepalive, чтобы прокси не обрывали ход, который молчит минутами.

Для провайдеров `type: codex` этот переключатель отклоняется. У бэкенда Codex Responses нет блокирующего режима, и соблюдать там этот ключ значило бы всё равно получать поток, лишь делая вид, что его нет.

### `mcp`

Настройки MCP, не привязанные к записи отдельного сервера (`config.MCP`, `internal/config/mcp.go`).

Сами серверы в `config.yaml` не объявляются. Они описаны в двух файлах, совместимых с Cursor,
где каждый содержит один объект `mcpServers` с ключами по имени сервера (`env` и `headers` - объекты
JSON, переключатели отдельных инструментов задаются через `disabledTools`). Это общий для пользователя
`${CODDY_HOME}/mcp.json` (по умолчанию `~/.coddy/mcp.json`, как `~/.cursor/mcp.json` у Cursor, область
"global") и локальный для проекта `<workspace>/.coddy/mcp.json` (область "local"), который при
совпадении имён побеждает глобальный файл и записи которого перед запуском требуют одобрения рабочей
папки. Старый список `mcp_servers` в `config.yaml` при следующей загрузке переносится в
`${CODDY_HOME}/mcp.json`, копия файла сохраняется как `config.yaml.bak-<time>`, а `coddy -t` сообщает
об этом предупреждением. См. [mcp.md](../features/mcp.md).

Добавлено в [issue #80](https://github.com/coddy-project/coddy-agent/issues/80).
Одобрения записываются в `~/.coddy/mcp-trust.json` с ключом из канонического пути рабочей папки
и дайджеста объявления, которое задаёт команду (транспорт, команда, аргументы, env, url,
заголовки), поэтому после изменения одобренной записи вопрос задаётся снова. Одобрить можно через
`coddy mcp trust <name>`, `POST /coddy/mcp/{name}/trust` или кнопку со щитом в **Настройки → MCP-серверы**.
На той же вкладке редактируется и сама эта политика (`POST /coddy/mcp/project-trust`), поэтому
отдельным разделом настроек она не показывается. См. `docs/features/mcp.md`.

### `tools`

Политика разрешений (`config.Tools`, `internal/config/tools.go`).

#### `tools.output_limits`

Максимальное число строк, которое результат или ошибка инструмента может вернуть в контекст LLM (`config.ToolOutputLimits`). Каждый включённый лимит строк дополнительно задаёт жёсткий **потолок в 64 КиБ на вызов**, чтобы минифицированный файл, полезная нагрузка в base64 или однострочный ответ MCP не обходили защиту. `0` отключает оба лимита для этого инструмента; незаданное поле получает встроенное значение по умолчанию. Обрезанный вывод заканчивается маркером, который подсказывает модели, как получить остальное (`offset`/`limit` для `read`, более узкий шаблон для `grep`, `page` для `websearch`).

#### `tools.background`

Ограничения фонового выполнения (`config.ToolBackground`). `run_command`, отправленный в фон, возвращает id задачи вместо вывода; результат потом собирают `background_list`, `background_output`, `background_wait` и `background_stop`. Пул живёт внутри запущенного процесса `coddy`. Каждая задача дублирует свои метаданные и перехваченный вывод в бандл сессии в `background/<task_id>/`, а задача, прерванная перезапуском, получает статус `orphaned` и не числится выполняющейся. `0` в любом целочисленном поле означает "использовать значение по умолчанию". См. `docs/features/background-tasks.md`.

### `subagents`

Субагенты (`config.Subagents`, `internal/config/subagents.go`) - дочерние агенты, которым модель передаёт работу инструментом `spawn_agent`. Определение субагента - markdown-файл с YAML-фронтматтером (`name`, `description`, `model`, `reasoning`, `mode`, `tools`, `disallowed_tools`, `permission_mode`, `max_turns`, `timeout_seconds`, `background`, `hidden`), тело которого описывает роль дочернего агента. Каждый запуск становится фоновой задачей родительской сессии с собственной дочерней сессией и транскриптом, поэтому его видят `background_list` / `background_output` / `background_wait` / `background_stop`, панель "Задачи" и `GET /coddy/sessions/{id}/background-tasks`. `0` в `max_concurrent`, `default_timeout_seconds` и `max_turns` означает "использовать значение по умолчанию"; `max_depth` - исключение, для значения по умолчанию `1` его нужно просто не указывать, потому что явный `0` запрещает запускать субагентов где бы то ни было. См. `docs/features/subagents.md`.

Одобрения определений из области проекта записываются в `~/.coddy/subagents-trust.json` с ключом из канонического пути рабочей папки, имени определения и дайджеста файла, поэтому после правки одобренного файла вопрос задаётся снова. `permission_mode`, `tools` и `disallowed_tools` в определении в любой области могут только сузить то, что мог делать родитель.

### `hooks`

Хуки (`config.Hooks`, `internal/config/hooks.go`) - команды оператора, которые запускаются в определённых точках жизненного цикла сессии. Хук читает один JSON-документ из stdin и отвечает кодом выхода и, по желанию, JSON в stdout. Хук `PreToolUse` может запретить вызов инструмента при любом режиме разрешений, одобрить его без запроса, принудительно вызвать запрос, переписать аргументы или добавить контекст, а хук `PostToolUse` / `PostToolUseFailure` может добавить обратную связь. Определения хранятся в JSON-файлах в формате Claude Code. `0` в любом целочисленном ключе означает "использовать значение по умолчанию". См. `docs/features/hooks.md`.

Одобрения файлов из области проекта записываются в `~/.coddy/hooks-trust.json` с ключом из канонического пути рабочей папки, пути файла относительно рабочей папки и дайджеста файла, поэтому после правки одобренного файла вопрос задаётся снова.

### `logger`

Логирование (`config.Logger`, `internal/config/logger.go`). Флаги ACP `--log-level`, `--log-output`, `--log-file`, `--log-format`, если заданы, переопределяют эти настройки.

`levels` повышает или понижает подробность логов для отдельных подсистем, поэтому, чтобы разобраться с неработающей командой Telegram, больше не нужно переводить весь процесс в `debug` и выискивать нужное среди всего остального.

```yaml
logger:
  level: "info"
  levels:
    - component: "gateway.telegram"
      level: "debug"
```

Компонент - имя через точку, которым подсистема помечает свой логгер; оно остаётся в каждой записи этой подсистемы, поэтому файл можно отфильтровать по подсистеме и задним числом. Родительское имя покрывает всё, что в него вложено, и побеждает самый длинный настроенный префикс - `gateway` действует на `gateway.telegram`, если у того нет собственной записи. У записи из непомеченной части процесса компонента нет, и она подчиняется `level`. Если настроить один компонент дважды, это считается ошибкой, и победитель молча не выбирается.

`--log-level` принимает ту же спецификацию в виде списка через запятую; так оператор, который запускает Coddy под systemd, повышает подробность одной подсистемы на один перезапуск, не редактируя файл.

```bash
coddy serve --log-level "info,gateway.telegram=debug"
```

Простой `--log-level debug` задаёт только корневой уровень и не трогает настроенные записи; спецификация с именами компонентов заменяет их, поэтому флаг полностью определяет, что писать в лог.

### `compaction`

Сжатие контекста (`config.Compaction`, `internal/config/compaction.go`) - пересказ старой истории диалога, чтобы длинные сессии продолжали помещаться в окно контекста модели. Действует и для ручной команды сжатия, и для автоматического срабатывания по порогу.

#### `compaction.result_eviction`

При сборке запроса к LLM сворачивает непомеченные результаты инструментов `read`/`grep` в короткие заглушки (`config.ResultEviction`), чтобы постраничное чтение большого файла или широкий поиск не закрепляли ненужные строки во всех последующих ходах. Результат сохраняется, если модель его пометила (инструментом `keep_result` или `keep: true` в вызове) или если он попадает в последнее рабочее окно; запись в файл делает недействительными более ранние чтения и поиски по нему. В сохранённом бандле сессии все результаты остаются целиком.
