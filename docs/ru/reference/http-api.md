# OpenAI-совместимый HTTP API

HTTP-интерфейс входит в бинарник, только если тот собран с **`go build -tags=http`** (`make build TAGS=http`). Он открывает маршруты в форме OpenAI и вспомогательные маршруты **`/coddy/*`**, за которыми стоят тот же менеджер сессий и тот же ReAct-агент, что и у **`coddy acp`**.

Отдельной команды у него нет. **`coddy serve`** запускает его, когда **`httpserver.enable`** равен true (так и есть, если файл не говорит иного), вместе со всеми остальными подсистемами, которые включает конфигурация, - Telegram-шлюзом, релеем роя, cron-планировщиком. У них один менеджер сессий, поэтому диалог, который начал бот, становится сессией, которую этот API показывает в списке, отдаёт потоком и может продолжить.

Встроенное SPA входит в сборку, только если задан ещё и тег **`ui`** (например, **`make build TAGS="http ui"`** или **`go build -tags=http,ui`**). Если задан только **http**, **`GET /`** возвращает **404** с подсказкой простым текстом.

## OpenAPI и Swagger UI

Спецификации генерируются заново на каждый запрос, поэтому всегда соответствуют обработчикам.

- **`GET /openapi.yaml`** - OpenAPI 3.0 (YAML); **`GET /openapi.json`** отдаёт то же самое в JSON (оба с **`Content-Disposition: inline`**);
- **`GET /docs/`** - Swagger UI (статические файлы встроены в бинарник, без CDN). **`GET /docs`** перенаправляет на **`/docs/`**.

## Аутентификация (необязательно)

Аутентификация по умолчанию **выключена** (так сложилось исторически). Учётные данные бывают двух видов, и любой из них включает одну и ту же защиту:

- **bearer-токен** для API-клиентов (`coddy --remote`, `coddy acp --remote`, релей роя, скрипты);
- **форма входа по паролю** для браузеров, она описана ниже в разделе [Вход в веб-интерфейс](#вход-в-веб-интерфейс-необязательно).

Чтобы защитить API, когда он доступен не только через loopback, задайте bearer-токен одним из способов:

- `httpserver.auth_token` в `config.yaml` (поддерживает `${ENV}`);
- `--auth-token <token>` у `coddy serve`;
- переменная окружения `CODDY_HTTP_TOKEN`.

Когда токен настроен, каждый маршрут `/v1/*` и `/coddy/*` требует
`Authorization: Bearer <token>`, а без него возвращает `401` с вызовом `WWW-Authenticate: Bearer`.
Оболочка SPA и статические файлы остаются публичными, чтобы клиент мог загрузиться и запросить
токен; `/docs` и `/openapi.*` защищены, если не задано `httpserver.public_docs: true`. Токен
никогда не возвращается в `GET /coddy/config` (он скрыт, DTO сообщает только `auth_configured`). Токены,
переданные через `--auth-token` / `CODDY_HTTP_TOKEN`, никогда не записываются в `config.yaml` и переживают
горячую перезагрузку через `PUT /coddy/config`. Если аутентификация работает по сети, используйте TLS
(или прокси, который завершает TLS). Если сервер без токена слушает адрес вне loopback, при запуске в журнал
пишется предупреждение, кроме случая, когда задано `httpserver.allow_insecure: true`.

Без токена интерфейс не требует аутентификации, поэтому держите его за подходящими сетевыми ограничениями.

### Вход в веб-интерфейс (необязательно)

Bearer-токен защищает API, но браузеру через него не войти. SPA показывает `Unauthorized (401)`,
а поля для ввода токена в нём нет. Форма входа даёт браузеру учётные данные для той же защиты.
По умолчанию она **выключена**, и конфигурация, которая о ней не упоминает, работает в точности как
раньше.

```yaml
httpserver:
  host: 0.0.0.0
  auth_token: "${CODDY_HTTP_TOKEN}"   # unchanged: for API clients
  login:
    enable: true
    user: "pasha"
    password_hash: "$$argon2id$$v=19$$..."   # written by `coddy serve set-password`
    session_ttl_hours: 720                   # 0 = until the browser closes
```

Запишите учётную запись командой, а не вручную.

```bash
coddy serve set-password --user pasha
```

Команда дважды спрашивает пароль (один раз и без приглашения, если стандартный ввод подключён к каналу),
сохраняет хеш argon2id и включает форму, правя `config.yaml` на месте, так что комментарии и порядок ключей
сохраняются. В хеше, введённом вручную, каждый `$` нужно удвоить (`$$argon2id$$v=19$$...`), потому что этот
файл при загрузке раскрывает `$NAME` как ссылку на переменную окружения; `coddy -t` сообщает об этом, когда
находит хеш, который больше не разбирается.

Учётная запись может целиком жить и в окружении, это путь для контейнера или юнита
systemd. `CODDY_HTTP_USER` и `CODDY_HTTP_PASSWORD` (открытым текстом, хешируется при запуске сервера,
в файл никогда не пишется) сами включают форму, так же как `CODDY_HTTP_TOKEN` включает
защиту по bearer-токену без `auth_token`. Естественное место для них - `$CODDY_HOME/.env`. Когда учётная
запись есть и в файле, и в окружении, побеждает окружение, а явное `login.enable: false` в
файле выключает форму, даже если переменные заданы. Флага `--login-password` нет, потому что
пароль в командной строке виден в `ps`.

Форму обслуживают три маршрута, и все три доступны без учётных данных, потому что именно через них
проходят защиту.

| Маршрут | Что делает |
|---|---|
| **`GET /coddy/auth/me`** | `login_required`, `auth_required`, `authenticated`, а для браузера, который вошёл, ещё `user` / `expires_at`. SPA вызывает его при загрузке, чтобы выбрать между экраном входа и приложением. |
| **`POST /coddy/auth/login`** | `{user, password}`. При успехе ставит cookie `coddy_session_<host digest>` с `HttpOnly` и `SameSite=Strict` (и с `Secure`, если запрос пришёл по TLS или через прокси, который отправляет `X-Forwarded-Proto: https`), которая живёт `session_ttl_hours`; при `0` браузер удаляет её при закрытии, а сервер удаляет свою запись через 30 дней. В имени есть дайджест хоста, которому был адресован запрос, потому что cookie не разделяются по портам. Без него два сервера Coddy на одной машине, например релей и узел за ним, разлогинивали бы друг друга при каждом входе. |
| **`POST /coddy/auth/telegram`** | `{init_data}`, данные запуска веб-интерфейса, открытого как Mini App Telegram-бота. Подпись проверяется по токену бота (данные запуска не старше часа, каждый запуск принимается один раз), и войти может только пользователь из `gateways.telegram.admins`. Ему ставится cookie `coddy_tg_session_<host digest>` с HttpOnly и `SameSite=Strict`, которая открывает то же, что и cookie формы, в том числе за защитой только токеном, и перестаёт действовать, когда меняется токен, бот выключается или человек перестаёт быть админом. Всем остальным 403. `GET /coddy/auth/me` сообщает `telegram_login: true`, когда маршрут доступен. |
| **`POST /coddy/auth/logout`** | Удаляет сессию на сервере и делает cookie просроченной (cookie Mini App тоже). Идемпотентен. |

После входа cookie открывает каждый маршрут `/v1/*` и `/coddy/*`, включая потоки SSE - `EventSource`
с того же origin отправляет cookie, поэтому `?access_token=` не нужен. У cookie стоит
`SameSite=Strict`, и здесь это ничем не мешает (сама страница публична, и каждый вызов загруженной
страницы идёт на тот же origin), зато браузер никогда не прикрепит её к запросу, который вызвал другой сайт.
Сверх того, запросы с аутентификацией по cookie, которые **меняют состояние**, отклоняются с `403`, если
`Sec-Fetch-Site` не равен `same-origin` (или `none`) и `Origin` не совпадает с хостом запроса, поэтому скрипт,
который работает с этим API через cookie, должен отправлять заголовок `Origin`, а лучше предъявлять bearer-токен.
Bearer-запросы этой проверке никогда не подлежат, и поэтому `coddy --remote`, редактор и
релей работают без изменений.

Неверный пароль и неизвестный пользователь получают одинаковый `401` с одинаковым телом, а сравнение идёт за
постоянное время. На повторные неудачи с одного адреса сервер отвечает всё медленнее, задержка удваивается от
250 мс до предела в пять секунд и забывается после пятнадцати минут без попыток; попытка учитывается
до того, как её оценят, поэтому пачка запросов, пришедших одновременно, платит растущим ожиданием, а не
каждый её запрос видит чистый лист. Запросы с loopback никогда не замедляются, чтобы машина не могла запереть себя от собственного
агента, а поскольку иначе это исключение покрыло бы весь интернет за обратным прокси,
запрос, который пришёл *с* loopback, учитывается по адресу из `X-Forwarded-For` (или
`X-Real-IP`), если такой заголовок есть. Запрос, пришедший откуда-либо ещё, учитывается по тому, откуда он
на самом деле пришёл, а заголовки игнорируются. Сессии живут в памяти. Перезагрузка
конфигурации (например, сохранение настроек со страницы) их сохраняет, а перезапуск
процесса завершает. Смена пароля или переименование учётной записи завершает все открытые ею сессии на
следующем запросе, и ничего не нужно аннулировать вручную. Хранилище вмещает не больше 512 живых сессий,
первыми вытесняются самые старые.

`GET /coddy/config` никогда не возвращает `password_hash`; он сообщает `httpserver.login_configured` и
`httpserver.login_source` (`config` или `env`), а сохранение с экрана настроек оставляет
хеш на месте так же, как оставляет `auth_token`. Соседнее поле `auth_configured` означает ровно то, что говорит,
то есть что задан bearer-токен, поэтому сервер, закрытый паролем без токена, сообщает
`auth_configured: false` рядом с `login_configured: true`; спрашивайте `GET /coddy/auth/me`, когда
вопрос звучит как "нужны ли этому серверу учётные данные вообще". Документ по-прежнему описывает файл, поэтому учётная запись,
пришедшая из окружения, при сохранении никогда не записывается в `config.yaml`.

Форма входа работает для этого origin. Переключатель окружений по-прежнему подключается к **удалённому** серверу
с bearer-токеном, потому что cookie этого origin не уходит на другой origin.

Одно замечание о ссылках `${VAR}`. `login.user` и `login.password_hash` принимают их, как и любое другое
значение в `config.yaml`, и, как любое другое значение, они раскрываются при загрузке файла, поэтому сохранение
с экрана настроек записывает обратно **раскрытое** значение и превращает `user: "${CODDY_HTTP_USER}"`
в `user: pasha`. Этот файл всегда так обращался с `${VAR}`; если нужно, чтобы учётные
данные вообще не попадали в документ, используйте `CODDY_HTTP_USER` и `CODDY_HTTP_PASSWORD`, которые
в него никогда не попадают.

### Кросс-доменный доступ и удалённый веб-интерфейс

Встроенный веб-интерфейс может работать с **удалённым** сервером `coddy serve` (переключатель окружений меняет
базовый URL API и отправляет bearer-токен удалённого сервера). Это кросс-доменный вызов, поэтому
удалённый сервер должен явно включить CORS.

```yaml
httpserver:
  auth_token: "${CODDY_HTTP_TOKEN}"
  cors:
    enable: true
    allow_loopback: true          # the laptop's own coddy serve, on any loopback address and port
    allowed_origins: ["https://my-ui.example"]   # exact origins elsewhere; or ["*"]
  remotes:                       # optional: offered in the UI environment selector
    - name: "prod box"
      url: "https://box.example:12345"
      token: "${PROD_BOX_TOKEN}"   # optional: the bearer the UI and the console present
```

Когда `cors.enable` равен true, preflight-запросы `OPTIONS` для разрешённого origin возвращают `204` с
`Access-Control-Allow-Origin` (origin запроса или `*`, если так настроено), `Vary: Origin` и
`Access-Control-Allow-Headers: Authorization, Content-Type, X-Coddy-Session-ID`; неразрешённые origin
не получают заголовков CORS. Origin разрешён, когда `allowed_origins` называет его точно, когда
`allowed_origins` содержит `"*"` или когда включён `allow_loopback`, а origin имеет схему `http` или `https`
и loopback-хост (`localhost`, имя `*.localhost`, `127.0.0.0/8` или `[::1]`) на любом порту.
Список читается первым и по порядку, поэтому `"*"` в нём отвечает `*` каждому origin, которого не назвала ни одна запись
до него, включая loopback; origin, допущенный только через `allow_loopback`, возвращается как есть и никогда не
расширяется до `*`. Bearer-аутентификация всё равно действует для самого запроса, каким бы из трёх способов ни была допущена
страница, и `allow_loopback` и `"*"` безопасны ровно настолько, насколько надёжны эти учётные данные. Токен удалённого сервера
берётся либо из `token` его записи в `httpserver.remotes`, который **`GET /coddy/config`** отдаёт
каждой странице, которая его читает, либо из формы **Подключиться к…** веб-интерфейса, где его вводят и где интерфейс хранит его на стороне клиента для каждого удалённого сервера. Релей роя
отвечает кросс-доменной странице через `swarm.cors` (та же структура), а веб-интерфейс узнаёт его по
публичному **`GET /swarm/info`**, а не по **`/v1/models`**, который релей не обслуживает.

Поскольку `EventSource` не может отправить заголовок `Authorization` кросс-доменно, два маршрута подписки SSE,
**`GET /coddy/sessions/{id}/composer-stream`** и **`GET /coddy/events`**,
принимают токен ещё и как параметр запроса `?access_token=`. Больше ни один маршрут так не делает; где клиент может задать заголовок,
предпочитайте заголовок, потому что токен в строке запроса попадает в журналы доступа прокси.

## Встроенный веб-интерфейс (**`-tags=http,ui`**)

- **`GET /`** отдаёт **`index.html`**, **`styles.css`**, **`app.js`** и **`events-worker.js`** (SharedWorker, через который вкладки одного окружения совместно используют **`GET /coddy/events`**) из **`external/ui/`** (`go:embed`), когда при линковке вместе с **`http`** задан **`ui`**, а вместе с ними то, что делает веб-интерфейс устанавливаемым приложением: манифест веб-приложения **`/manifest.webmanifest`** (отдаётся как **`application/manifest+json`**), его иконки **`/icon-192.png`**, **`/icon-512.png`** и **`/icon-maskable-512.png`** и service worker **`/sw.js`**, который ничего не кеширует и показывает уведомления веб-интерфейса ([Установка веб-интерфейса как приложения](../surfaces/web-ui.md#установка-веб-интерфейса-как-приложения)). Как и остальная оболочка, они открыты и при **`httpserver.auth_token`**, и при форме входа, потому что браузер запрашивает их до входа. Ответы на **`/`**, **`/index.html`**, **`/app.js`**, **`/events-worker.js`**, **`/styles.css`** и эти файлы содержат **`Cache-Control: no-cache`**, чтобы обычная перезагрузка страницы подхватывала файлы после пересборки бинарника (URL фиксированные, без отпечатка). Рендереры, которые страница загружает по требованию (Mermaid, KaTeX и его шрифты), отдаются из **`/chunks/`** под именами с хешем содержимого и с **`Cache-Control: public, max-age=31536000, immutable`**;
- **Режим только API** - задайте **`ui.enable: false`** в конфигурации, чтобы запустить сервер без SPA, даже если тег **`ui`** вкомпилирован. Тогда **`GET /`** вместо интерфейса возвращает короткое текстовое уведомление (HTTP 404); каждый маршрут **`/v1/*`** и **`/coddy/*`** продолжает работать и по-прежнему требует **`httpserver.auth_token`**, если он задан. Пригодится для удалённой машины без собственного интерфейса, к которой подключаются другие интерфейсы;
- Рекомендуемый шаблон URL сессии - **`#/s/<sessionId>`** (история только на клиенте). Для **`POST /v1/responses`** и **`POST /v1/chat/completions`** отправляйте **`X-Coddy-Session-ID`** с идентификатором **`sess_<hex>`**, который проходит проверку на сервере (`internal/session/validate.go`);
- **`X-Coddy-Session-Origin: print`** в **`POST /v1/responses`** и **`POST /v1/chat/completions`** помечает сессию, которую создаёт запрос, как запуск одноразового режима печати (**`origin: print`** в **`session.json`**), и списки и окна выбора сессий не показывают её, пока об этом не попросят (**`include_print`**, **`origin=print`** в **`GET /coddy/sessions`**). Его отправляет **`coddy --remote <server> -p`** вместе с промптом, который создаёт его сессию. Сервер записывает пометку, только если запрос создаёт сессию, и никогда на уже существующую, а на любое другое значение отвечает **`400`**, ничего не создав ([Сессии](../features/sessions.md#теги-и-архив));
- **`GET /coddy/sessions`**, **`PATCH /coddy/sessions/{id}`** и другие маршруты **`/coddy/sessions/{id}/...`** определяют сессию **только** по сегменту пути **`{id}`** (дублирующего заголовка в OpenAPI нет; клиенты могут по-прежнему отправлять **`X-Coddy-Session-ID`**, но для этих URL он не участвует в выборе ресурса);
- Встроенный веб-интерфейс вызывает **`POST /v1/responses`** с **`stream: true`**. При открытии сессии и переподключении он читает **`GET /coddy/sessions/{id}/activity`** и **`GET /coddy/sessions/{id}/queue`**, не требуя строки сессии в отфильтрованном или постраничном списке **`GET /coddy/sessions`**. Активность на сервере управляет кнопкой остановки и элементами очереди отдельно от локального читателя потока; потерянный читатель не доказывает, что ход закончился. Существующий релей **`GET /coddy/sessions/{id}/composer-stream`** (SSE) даёт интерфейсу повторно получить байты, уже выданные для идущего хода, и дальше получать живые фрагменты до **`data: [DONE]`** или события ошибки. Новый **`POST /v1/responses`** отменяет эту подписку на релей на стороне клиента. Для ReAct (**`model`** **`agent`**, **`plan`** или **`ask`**) он отправляет необязательный **`metadata.model`** с **`id`** выбранной YAML-модели **`models[].model`** и необязательный **`metadata.runPlanSlug`**, чтобы реализовать сохранённый план проектирования (**`coddy.dev/runPlanSlug`** в ACP **`session/prompt`**; если **`model`** равен **`ask`**, ответ **`409`** приходит до начала хода) (из **`GET /v1/models`**, **`owned_by`** не **`coddy`**); по умолчанию берётся выбор, запомненный в **`coddy_llm_model`**, иначе первая по алфавиту строка. Каждый ход несёт ещё и **`metadata.surface: "webui"`**, и этот ход получает блок системного промпта, который сообщает модели, что веб-интерфейс рисует блоки **`mermaid`** и **`svg`** картинками и верстает LaTeX (**`external/httpserver/webui_prompt.go`**; на **`POST /v1/chat/completions`** тоже, и только для этого значения, поэтому API-клиент или удалённая консоль получают обычный промпт). Ещё ход несёт **`metadata.lang`** - язык интерфейса (**`en`**, **`ru`**): на нём документация, которую прикрепляют упоминания **`@coddy:`** этого хода и читают инструменты документации агента; удалённая консоль передаёт язык своего терминала. Когда выбранная модель объявляет **`reasoning_levels`**, он отправляет ещё и необязательный **`metadata.reasoning`** с выбранным уровнем; по умолчанию берётся **`reasoning_default`** модели, сохранённый выбор лежит в **`coddy_llm_reasoning`**. Упоминания **`@`** из **`input`** он отправляет в том виде, в каком их набрали. Сервер разрешает их в начале хода так же, как промпт любого интерфейса (см. **`docs/features/mentions.md`**), и упоминание может указывать на файл в любом месте диска, диапазон строк (**`@Dockerfile:21-31`** доходит до модели как **`<coddy_attachment ... lines="21-31">`** только с этими строками), листинг папки, другую сессию, правило, субагента, страницу встроенной документации или веб-страницу. **`GET /coddy/mentions`** обслуживает выбор по **`@`**, **`POST /coddy/mentions/check`** сообщает полю ввода, какие из набранных упоминаний разрешаются, чтобы подсвечивались только они, а **`GET /coddy/workspace/file`** обслуживает выбор диапазона строк, который открывается после **`:`**. Фрагменты SSE **по умолчанию** следуют дельтам **`chat.completion.chunk`** (**`delta.content`** для текста ассистента, **`delta.reasoning_content`** для потокового рассуждения модели, чтобы интерфейс держал раскрывающийся блок **размышляю** отдельно). Именованные строки **`event:`** (**`tool_call`**, **`tool_call_update`**, **`plan`**, **`token_usage`**, **`turn_progress`**, **`available_commands`**, **`message_queue`**, **`user_message`**) показывают ход работы инструментов и нарастающие итоги по токенам между раундами LLM; **`message_queue`** при каждом изменении несёт всю очередь сообщений сессии, а **`user_message`** несёт сообщение из очереди, которое агент только что прочитал, или сообщение после хода, чей собственный промпт начинается, в той точке, где оно вошло в диалог (см. **`docs/features/message-queue.md`**); поток хода резервирует **`provider_usage`** для снимка, выданного посреди хода (сейчас его никто не выдаёт; расход аккаунта за завершённый ход читается из **`GET /coddy/providers/{name}/usage`** или приходит по **`GET /coddy/events`**); когда **`memory.enable`** равен **true**, сервер выдаёт ещё и **`memory_run`** для субагента памяти этого хода (**`started`** с идентификаторами задачи и дочерней сессии, **`finished`** со статусом задачи, длительностью, признаком, был ли отчёт **`delivered`** модели в этом ходе, и, для упавшего запуска, ошибкой, на которой он закончился, в **`reason`**, либо **`skipped`** с причиной); текст по нему не передаётся, а запись о запуске - это строка задачи с **`agent.system`**, равным true, в **`GET /coddy/sessions/{id}/background-tasks`** плюс дочерний транскрипт, который она называет (см. **`docs/features/memory.md`**). Ход, который сервер начал сам, потому что завершились фоновые задачи, запущенные моделью с включённым пробуждением (**`notify_on_finish`**, включено по умолчанию), открывается событием **`background_wake`**. Его **`tasks`** называет каждую задачу с **`id`**, **`kind`**, **`label`**, **`agent`**, **`status`**, **`exitCode`**, **`durationMs`** и **`error`**, а первое сообщение хода сохраняется с теми же задачами, поэтому ни один клиент не показывает инструкцию как сообщение пользователя ни вживую, ни после перезагрузки; встроенный веб-интерфейс ничего не показывает на её месте, а в строке задачи стоит **`woke_agent`** (см. **`docs/features/background-tasks.md`**). JSON **`coddy_meta`** по обычному правилу идёт непосредственно перед **`data: [DONE]`**; для ходов agent/plan/ask он несёт ещё и **`stop_reason`** (`end_turn`, `cancelled`, `max_turns`, ...), чтобы удалённые клиенты восстановили причину остановки ACP. Если промпт начинается с команд настроек, они применяются до хода ([Настройки сессии](../features/session-settings.md)); промпт из одних команд не запускает ход, отдаёт потоком уведомление о каждом изменении в качестве ответа и заканчивается **`coddy_meta`** **`settings_only: "true"`**, чтобы клиент мог убрать строки, нарисованные для этого обмена. Из него ничего не сохраняется в транскрипте, а изменение видно в **`settings`** сессии. **`event: session_settings`** несёт снимок настроек каждый раз, когда настройки сессии меняются во время потока (команда, переключатель сессии в диалоге разрешения, **`switch_model`** модели), а **`notice`** только тогда, когда изменение сделал сам агент. **`event: session_goal`** несёт цель сессии (в форме **`GET /coddy/sessions/{id}/goal`**) каждый раз, когда она меняется во время потока (её задали через **`/goal`**, проверили, продолжили, приостановили, сбросили), а **`event: goal_turn`** открывает каждый ход, который начинает супервизор сессии (**`kind`** kickoff, continue, recover, resume или wrapup, **`index`** из **`limit`**, **`objective`**, **`reason`**, **`remaining`**); первое сообщение такого хода сохраняется с той же меткой, что и **`goal_turn`**, поэтому встроенный веб-интерфейс показывает строку цели в одну строчку вместо текста инструкции. Кнопка **Остановить генерацию** в поле ввода вызывает **`POST /coddy/sessions/{id}/cancel`** с **`X-Coddy-Session-ID`**, совпадающим с **`{id}`**. Сразу после отправки интерфейс вызывает **`AbortSignal`** на своём потоковом **`fetch`** этого хода (POST или релей), потому что браузер держит шесть соединений HTTP/1.1 на хост на все свои вкладки, и иначе отмена могла бы ждать соединения, которое занимает этот поток. Ход продолжается без потока; неудачная отмена показывает ошибку, оставляет элементы управления идущим ходом доступными для повтора и снова подключается к ходу через **`GET /coddy/sessions/{id}/composer-stream`**. Успешный ответ подтверждает кооперативную отмену, а завершение подтверждает **`turn_ended`** или свежий снимок активности, который сообщает о простое. Для агентного хода это соответствует ACP **`session/cancel`** (передача **`TurnCtx`** для прямых завершений **`models[].model`** использует тот же хук отмены). Отмена посреди потока всё равно **сохраняет** накопленный **`content`** ассистента за этот ход; **`GET /coddy/sessions/{id}/messages`** может ненадолго отставать от этой записи, поэтому SPA **сливает** полученные строки со своей теневой копией сессии или с транскриптом на экране (**`mergeTranscriptPreferLocalSuffix`** в **`external/ui/src/ui/chat/transcriptServerSnapshot.ts`**). Потоки нескольких сессий могут идти параллельно (**`pickStreamMutationBase`** в **`streamMutationBase.ts`** держит изменения от SSE в пределах своего **`X-Coddy-Session-ID`**);
- На первое сообщение пользователя в совсем новом чате (сессии в боковой панели ещё нет) интерфейс параллельно с **`/v1/responses`** отправляет **`POST`** на **`/coddy/describe`** с **`X-Coddy-Session-ID`** нового чата и его папкой в **`cwd`**, чтобы модели описали слэш-команды этой рабочей папки. Пока вызов не завершится (ответ, пустой **`short`**, ошибка или 30 секунд, после которых позднее название всё равно применяется), заголовок и строка чата в "Истории" показывают мерцающую заглушку вместо первого сообщения. Когда приходит **`short`**, заголовок и названия в списке сессий обновляются **сразу**; **`PATCH /coddy/sessions/{id}`** всё равно выполняется, как только заголовки ответа покажут канонический идентификатор сессии (и ненадолго **повторяет PATCH**, если сохранение отстаёт от describe), и несёт **`tags`**, которые предложил тот же ответ, поэтому название и теги нового чата вместе стоят одного вызова модели. Этот PATCH несёт **`titleIfUnpinned`**, и название становится лишь предложением. Сессия, которую уже назвали во время первого хода (в заголовке чата или инструментом агента **`session_describe`**), сохраняет своё имя, и применяются только теги;
- Встроенный веб-интерфейс открывает **Настройки** по адресу **`#/settings`**. Он загружает **`GET /coddy/config/schema`** (JSON Schema для редактора) и **`GET /coddy/config`** (текущие значения, включая **API-ключи**, необязательные URL **`proxy`** для каждого провайдера и токен бота **`gateways.telegram.token`**), а при сохранении вызывает **`POST /coddy/config/validate`** и **`PUT /coddy/config`**. Список **Модели** в форме провайдера и поле **Окно контекста** в форме логической модели вызывают **`POST /coddy/providers/models`** со строкой провайдера в том виде, в каком её держит форма (автоматический запрос не включает **`api_key_command`**, его отправляет только кнопка обновления), поэтому провайдер, который ещё не сохранён (например, сразу после входа через OAuth device flow), тоже показывает свои модели; форма логической модели вызывает ещё и **`GET /coddy/config/reasoning-levels`** по кнопке **Получить уровни ризонинга**, которая заполняет **`models[].reasoning_levels`** уровнями, найденными для редактируемого id модели (тип строки провайдера, на которую она указывает, отправляется как **`provider_type`**, поэтому несохранённый провайдер тоже учитывается). Блок **`gateways`** проходит через этот API туда и обратно, поэтому правка настроек в веб-интерфейсе больше не теряет конфигурацию Telegram. Отдельной аутентификации на этих маршрутах нет, поэтому открывайте **`coddy serve`** только в доверенных сетях;

- **Прогресс хода** передаётся именованным событием SSE **`turn_progress`** с полями **`startedAt`** (RFC3339, момент, когда ход был принят), **`elapsedMs`** (тот же факт в виде длительности, чтобы клиент, чьи часы расходятся с серверными, отсчитывал от своего текущего времени минус это значение), **`outputTokens`**, **`estimated`** и, только в первом событии, **`phase: "preparing"`**. Первое событие отправляется, как только ход принят, ещё до того, как он поднимает свои MCP-серверы и ждёт окно контекста своей модели (на холодном сервере это секунды), и встроенный интерфейс показывает его как "Готовлю сессию…"; собственные отчёты цикла фазы не несут. Затем событие отправляется в начале цикла (с нулём токенов, что клиент показывает как часы и "Жду ответ модели"), не чаще раза в секунду, пока идёт потоковый вызов модели, и после каждого вызова. **`outputTokens`** складывает то, что провайдер сообщил по завершённым вызовам хода, и оценку (символы / 4) того, что успел выдать идущий вызов, включая фрагменты аргументов вызовов инструментов по мере их поступления (или по завершении вызова у провайдеров без фрагментов); **`estimated`** равен true, пока в число входит оценка, и остаётся true для провайдера, который вообще не сообщает расход. Релей поля ввода не повторяет кадр, который уже покрыт снимком транскрипта клиента, поэтому клиент, подключившийся поздно, читает те же числа из **`GET /coddy/sessions/{id}/activity`**. Строгий по OpenAI поток **`POST /v1/chat/completions`** заменяет это событие комментарием SSE, как и любое именованное событие;
- **Прогресс ввода файла** - `tool_call_update` со `status: "pending"` может нести `_meta.coddy.toolInputProgress` для `write`, `edit` и `apply_patch`. В нём есть поля `path` (не длиннее 512 байт, пустой, пока не получен), `bytes` и `lines` (полученное декодированное содержимое), `argumentBytes` (полученные сырые байты JSON) и `preview` (последние шесть строк, не больше 1 КиБ, возможно, с неполной строкой). Это черновик, он никогда не служит исполняемыми аргументами или результатом инструмента. Обновления ограничены пятью в секунду на вызов плюс финальный сброс. Терминальный статус заменяет черновик. Клиенты обязаны вычищать управляющие последовательности терминала, прежде чем показывать сгенерированные моделью пути или превью. Строгий по OpenAI поток подавляет это именованное событие, как и другие обновления инструментов;
- **Картинки, которые вызов показал модели** - `tool_call_update` со статусом `completed` для вызова, который передал модели картинку (**`read`** файла PNG, JPEG, GIF или WebP), несёт `_meta.coddy.images` по одной записи на картинку с полями `name` (имя файла), `mime_type` (тип, отправленный модели), `asset` (копия, сохранённая в `assets/` сессии), `url` (**`GET /coddy/sessions/{id}/assets/{name}`**) и, если сделана миниатюра, `preview_url`. После перезагрузки строка инструмента в **`GET /coddy/sessions/{id}/messages`** несёт те же картинки в **`files`**. Встроенный веб-интерфейс показывает их превью под строкой вызова; байты картинки никогда не передаются в событии;

- **Текущее заполнение контекста** передаётся отдельным именованным событием SSE **`usage_update`** с **`used`** и **`size`**. Оно выдаётся повторно после ручного или автоматического сжатия контекста. **`token_usage`** остаётся счётчиком завершённых вызовов модели и не используется как числитель для окна контекста.

| Метод | Путь | Примечания |
|--------|------|-------|
| GET | `/` | Встроенный веб-интерфейс (**`-tags=http,ui`**) или **404** с подсказкой (**только `http`**). **`Cache-Control: no-cache`** на **`/`**, **`/index.html`**, **`/app.js`**, **`/events-worker.js`**, **`/styles.css`**, **`/manifest.webmanifest`**, **`/sw.js`** и иконках приложения, когда модуль UI слинкован; **`/chunks/*`** (с хешем содержимого в имени) отдаётся как **`immutable`** на год. |
| GET | `/openapi.yaml`, `/openapi.json` | Спецификация. |
| GET | `/docs`, `/docs/` | Swagger UI. |
| GET | `/v1/models` | Объединённый список - **`agent`**, **`plan`**, **`ask`** (у каждого **`owned_by`** равен **`coddy`**), затем каждая YAML-строка **`models[].model`** (**`id`** служит селектором, **`owned_by`** - префикс провайдера). Порядок такой - **`agent`**, **`plan`**, **`ask`**, затем **`models`** в порядке конфигурации (в том же порядке их выдаёт сервер). Используйте любой возвращённый **`id`** как **`model`** в POST. Строка, на которой работает сессия без выбранной модели, несёт **`default: true`**. Это настроенная **`agent.model`** или первая строка **`models[]`**, если **`agent.model`** называет модель, которой нет в конфигурации; пока **`agent.model`** пуст, этот флаг не несёт ни одна строка. Удалённая консоль показывает эту модель для сессии без собственной модели, а встроенный веб-интерфейс берёт модель по умолчанию из запомненного выбора (**`coddy_llm_model`**) или первую по алфавиту строку. Каждая строка несёт **`max_context_tokens`**, окно контекста, относительно которого сессия на этой модели меряет заполнение и порог автоматического сжатия контекста. Это **`max_context_tokens`** модели, иначе окно, которое сообщает список моделей её провайдера, иначе **`128000`** (строки профилей несут окно **`agent.model`**, и встроенный веб-интерфейс рисует по нему кольцо контекста). Каждая строка **`models[].model`** несёт ещё и **`multimodal`** (**`true`**, когда в YAML задано **`models[].multimodal: true`**; встроенный веб-интерфейс показывает в поле ввода кнопку прикрепления файла, когда у выбранной модели **`multimodal: true`**). Модели с рассуждением несут также **`reasoning_levels`** (массив, например **`["minimal","low","medium","high"]`**; у моделей без рассуждения его нет) и необязательный **`reasoning_default`** (уровень, заранее выбранный для новых чатов); **`off`** попадает в `reasoning_levels`, только если эта логическая модель задаёт **`allow_reasoning_off: true`**. Встроенный веб-интерфейс показывает в поле ввода выбор уровня рассуждения, когда **`reasoning_levels`** не пуст. Модели провайдера **`type: codex`** сообщают **`none`** там, где по одному id модели получился бы **`minimal`**, потому что бэкенд Codex этот уровень отклоняет. |

Новая локальная ветка начинается от свежей ветки по умолчанию в `origin`, ветка, которая есть только в `origin`, выгружается из `origin/<branch>` с отслеживанием, существующая локальная ветка переиспользуется со своей вершины, и worktree, в котором ветка уже выгружена, тоже переиспользуется. Переиспользование работает без сети, а для создания нужен доступный **`origin`**. Сама ветка по умолчанию, локальная ветка, которая её отслеживает, и ветка, выгруженная в основном чекауте (то есть **`worktree:true`** для текущей ветки), отклоняются с **`409`**. История больше собственного окна контекста суммаризатора сворачивается за несколько проходов и не отклоняется, каждый проход несёт уже готовую часть сводки, а прогресс доходит до всех клиентов сессии как строка вызова инструмента **`compact_context`**. **`200`** **`{"compacted":true,"summary","compacted_messages","kept_messages","model","steps"}`** (**`steps`** - число вызовов суммаризации, **1**, пока история помещается в один запрос); **`200`** **`{"compacted":false,"reason":"nothing_to_compact"}`** только когда нет предыдущего диалога, который можно свернуть; **`400`**, когда **`compaction.enable`** равен **false**, тело некорректно, **`model`** не называет ни одной настроенной модели или называет больше одной, или **`reasoning`** - уровень, которого суммаризатор не предлагает (это проверяется до допуска сессии, поэтому ничего не сжимается и ход не начинается); **`404`** для неизвестной сессии; **`409`**, пока другой ход агента держит блокировку поля ввода или сессия удаляется, и **`409`** для дочерней сессии, порождённой **`spawn_agent`** (транскрипт только для чтения). |

Изменённый **`mcp.project_trust`** применяется к активным сессиям без идущего хода ещё до того, как завершится ответ на сохранение, а также к будущим сессиям; сессия, в которой идёт ход, переподключается, когда этот ход заканчивается. Если переподключение не укладывается в срок сохранения, сессия остаётся на тех серверах, что у неё уже есть, и повторяет попытку на следующем ходу, так что один зависший сервер не может лишить её остальных.

### Снимки состояния для остановки и очереди

При открытии сессии и переподключении клиенты читают **`GET /coddy/sessions/{id}/activity`** и **`GET /coddy/sessions/{id}/queue`** для выбранного id. Эти чтения не зависят ни от подходящей строки в отфильтрованном или постраничном списке "Истории", ни от живого читателя хода, ни от другого изменения очереди. Веб-интерфейс и интерактивная удалённая консоль отслеживают активность сервера отдельно от жизненного цикла собственного промпта и потока. Браузер пропускает оба начальных чтения, пока его собственный POST проходит допуск, и, прежде чем считать сессию свободной, подтверждает свежим REST-запросом **`turn_ended`**, который пересёкся с ожидающим или уже принятым POST.

**`QueueSnapshot`** менеджера сессий читает список очереди и его **`version`** под одной блокировкой. HTTP-ответы очереди (**GET**, **POST**, **PATCH** и **DELETE**) и события **`message_queue`** используют эту пару, поэтому ответ не может пометить более старый список более новой версией. При обычных доставках для каждой сессии сохраняется наибольшая версия. Чтобы восстановиться после перезапуска браузера, свежий GET очереди фиксирует ревизию доставки и эпоху восстановления до запроса. Браузер отклоняет снимок, который пересёкся с любой доставкой очереди, а в остальных случаях может установить и меньшую версию, включая **`0`**. Такое восстановление переводит локальную эпоху вперёд и отклоняет ответы на изменения и кадры очереди из собственного потока или релея, полученные в более ранних эпохах. Повторённые уведомления **`turn_started`** не очищают список ожидания и не сбрасывают его версию.

Эти механизмы не меняют обработку неинтерактивных промптов и принадлежность запросов разрешений и вопросов и не подключают удалённую консоль к живому транскрипту другого клиента. Общие очереди работают только для клиентов одного процесса **`coddy serve`**; отдельные процессы локальной консоли или ACP, у которых общий только каталог сессий, сохраняют раздельные очереди и каналы ответов. Межпроцессная отмена по-прежнему использует маркер отмены в бандле.

### Два диалекта потока

Запрос **`POST /v1/chat/completions`** со **`stream: false`** возвращает JSON с **`usage.prompt_tokens`**, **`usage.completion_tokens`** и **`usage.total_tokens`**, если провайдер сообщает число токенов. Ход в режиме "Агент", "План" или "Чат" суммирует вызовы модели своего агентного цикла; вызовы порождённого им субагента (они учитываются в строке задачи этого субагента), сжатия контекста и запуска памяти в сумму не входят. Если провайдер сообщает кешированные входные токены, их несёт **`usage.prompt_tokens_details.cached_tokens`**; отдельные счётчики Anthropic для некешированных токенов, записи в кеш и чтения из кеша все входят в **`prompt_tokens`**. Если провайдер не присылает счётчиков, в JSON нет **`usage`**, чтобы клиенты могли отличить неизвестный расход от нулевого.

Два потоковых эндпоинта передают один и тот же ход в двух формах, и форму определяет тот, кто их читает. **`POST /v1/chat/completions`** со **`stream: true`** - интерфейс, на который направляют сторонние клиенты (VS Code Copilot через `chatLanguageModels.json`, SDK openai, всё, что разбирает `chat.completion.chunk` буквально), поэтому он строго следует контракту OpenAI и ничего к нему не добавляет: первый чанк с **`delta.role`** `assistant`; дельты **`delta.content`**, **`delta.reasoning_content`** и **`delta.tool_calls`**, у каждого варианта **`finish_reason: null`**; финальный чанк, у которого **`finish_reason`** равен **`stop`**, **`length`**, если ход закончился на **`max_turns`** / **`max_tokens`**, **`tool_calls`**, если прямая модель вызвала один из инструментов клиента, или **`content_filter`**, если фильтр содержимого провайдера оборвал прямой ответ; при **`stream_options.include_usage: true`** ещё один чанк с пустым массивом **`choices`** и **`usage`** хода (**`prompt_tokens`**, **`completion_tokens`**, **`total_tokens`**, просуммированные по вызовам модели в ходе из собственных счётчиков провайдера по тому же правилу, что и в JSON-ответе, нулевые, если провайдер ничего не сообщил, и **`prompt_tokens_details.cached_tokens`**, только если он сообщил о кешированном входе); затем **`data: [DONE]`**. Именованных кадров **`event:`** в нём нет, потому что такой клиент прочитал бы их как чанк без вариантов, но каждый такой кадр оставляет на своём месте SSE-комментарий, поэтому соединение остаётся активным, пока занят ход, в том числе в фазе инструментов; ход, который не выдал текста, всё равно открывает и завершает один вариант, потому что поток, который так и не завершил ни одного варианта, VS Code отображает как "Response contained no choices." **`POST /v1/responses`** - собственный канал coddy, его читают SPA, удалённая консоль (**`--remote`**, **`coddy acp --remote`**) и релей роя. Он несёт те же чанки плюс все именованные события ниже, последним **`coddy_meta`**.

  Прямой id **`models[].model`** в **`POST /v1/chat/completions`** означает, что coddy подменяет провайдера, и клиент приносит то, что принёс бы провайдеру. Его **`tools`** (функции-инструменты OpenAI) предлагаются модели как есть; **`tool_choice`** `none` их не передаёт, а любое другое значение оставляет выбор модели, потому что провайдеры не принимают параметра, который заставил бы её вызвать инструмент. Вызов, который делает модель, возвращается в потоке чанками **`delta.tool_calls`** (по чанку на вызов, с полными аргументами, **`index`** считает вызовы), а в JSON-ответе как **`message.tool_calls`**, с **`finish_reason`** **`tool_calls`**; клиент выполняет инструмент, повторяет сообщение ассистента с его **`tool_calls`** и отвечает сообщением **`tool`** под **`tool_call_id`**, и такой запрос может заканчиваться сообщением инструмента. **`content`** сообщения может быть строкой, `null` или массивом частей. Части **`text`** склеиваются, части **`image_url`** (data URL или адрес https) доходят как изображения до модели, у которой **`models[].multimodal`** равен true, и отбрасываются для любой другой модели, но никогда не превращаются в текст; они принимаются только в сообщениях пользователя, как у OpenAI, и для любой другой роли отклоняются с **`400`**, как и части других типов. То, что может передать клиент, ограничено: не больше 128 инструментов, **`parameters`** инструмента до 256 КиБ, 16 изображений на сообщение и 20 МиБ на строку URL изображения (data URL несёт саму картинку); сверх этого запрос отклоняется с **`400`**. Адрес изображения https передаётся провайдеру как есть, coddy его никогда не скачивает. У JSON-ответа, состоящего из вызовов инструментов, **`content`** равен `null`, как это делает OpenAI. Профили **agent** / **plan** / **ask** запускают собственные инструменты coddy, никогда не читают инструменты клиента и не принимают завершающего сообщения **`tool`**, хотя картинки последнего сообщения пользователя доходят до мультимодальной модели профиля. Ход **agent** / **plan** / **ask**, начатый через любой из эндпоинтов, публикуется в релей поля ввода в расширенной форме, что бы ни получил вызывающий, поэтому браузер, который смотрит сессию, в любом случае видит его вызовы инструментов.

## **`model`**, профили и прямой запрос к модели

- **`POST /v1/chat/completions`** и **`POST /v1/responses`** требуют, чтобы **`model`** был ровно одним **`id`** из **`GET /v1/models`** (рабочие профили сессии **agent** / **plan** / **ask** или элемент **`models[].model`**);
- **agent** / **plan** / **ask** выбирает агента Coddy (ReAct, инструменты). Необязательный JSON **`metadata.model`** (селектор **`models[].model`**) обновляет **`SelectedModelID`** сессии. Если опустить **`metadata`** или **`metadata.model`**, используется **`EffectiveModelID`** (сначала **`selectedModelId`** сессии, затем **`agent.model`**). **`metadata.model`**, равный **`null`**, **`""`** или неизвестному селектору, даёт **400**. Необязательный **`metadata.settingsVersion`** - версия последнего снимка настроек, который применил клиент. Если сервер с тех пор опубликовал более новый снимок, **`metadata.model`**, **`metadata.reasoning`** и режим из запроса игнорируются и действуют собственные настройки сессии, так что вкладка, которая не видела изменения, сделанного в другом месте, не может его отменить. Необязательный **`metadata.reasoning`** задаёт уровень рассуждения сессии (он разрешается после изменения **`metadata.model`**, если оно было) и должен быть одним из **`reasoning_levels`** действующей модели (**`null`** / **`""`** его сбрасывает; любое другое неподдерживаемое значение даёт **400**). Агент переводит уровень в **`reasoning_effort`** OpenAI или в **`budget_tokens`** расширенного мышления Anthropic; модели **`qwen3*`** у OpenAI-совместимых провайдеров (включая **`neuraldeep`**) также отправляют **`chat_template_kwargs`** **`{"enable_thinking": true}`**, чтобы переключатель мышления в шаблоне чата оставался включённым; провайдеры **`codex`** отправляют уровень как **`reasoning.effort`** Codex (**`minimal`** превращается в **`none`**) вместе с **`summary: auto`** и повтором зашифрованных рассуждений;
- **`model`** с YAML-селектором **`models[].model`** выполняет **один прямой запрос к LLM** на вызов (без ReAct); **`metadata`** с ключом **`model`** в этой ветке отклоняется с **400** (используйте **`model`** только как поле маршрутизации);
- В **`POST /v1/chat/completions`** прямая модель берёт параметры генерации из запроса на этот один запрос. **`max_tokens`** или его новое имя у OpenAI **`max_completion_tokens`** (запрос может нести оба, только если они совпадают) заменяет **`max_tokens`** модели, а **`temperature`** заменяет её **`temperature`**, включая **`0`**. Без них действуют настроенные значения, и ни один запрос не меняет конфигурацию и не влияет на другой запрос. Значение, которое провайдер не может отправить так, как просят, отклоняется с **400** до создания сессии и до обращения к провайдеру, то есть ограничение меньше 1, температура вне 0-2 (0-1 для провайдера **`anthropic`**) и любой из этих параметров у модели **`codex`**, потому что бэкенд Codex отклоняет оба. Запрошенная температура отправляется и вместе с уровнем рассуждения, хотя настроенная в таком случае не отправляется, а примет ли модель оба параметра, решает бэкенд (Qwen3 с мышлением на vLLM принимает, модели рассуждения OpenAI отказывают);
- **`reasoning_effort`** в том же запросе выбирает уровень рассуждения и должен быть одним из **`reasoning_levels`**, которые **`GET /v1/models`** перечисляет для этого id; любое другое значение или любое значение для модели, у которой уровней нет, даёт **400** и никогда не понижается молча. Если он опущен, равен **`null`** или **`""`**, действует **`reasoning_default`** модели, а модель без значения по умолчанию вообще не получает параметра рассуждения; это не то же самое, что запрос с уровнем **`none`**, который модель **`codex`** предлагает и получает именно так. Уровень передаётся как **`reasoning_effort`** OpenAI, как расширенное мышление Anthropic (где **`max_tokens`** запроса, который не оставляет места над бюджетом мышления, даёт **400** и молча не увеличивается) или как **`reasoning.effort`** Codex, и JSON-ответ сообщает его как **`metadata.reasoning_effort`**;
- Профили **agent** / **plan** / **ask** не читают ни одного из этих полей. Ход профиля состоит из серии вызовов LLM, каждый с настроенными значениями модели профиля, а уровень рассуждения берётся из **`metadata.reasoning`**;
- Прямой ответ считается законченным только по собственному конечному сигналу провайдера, то есть по **`finish_reason`** или **`[DONE]`** от OpenAI-совместимого сервера, по **`stop_reason`** от Anthropic, по **`response.completed`** или **`response.incomplete`** от Codex. **`response.incomplete`** у Codex сохраняет уже написанный текст и сообщает причину (**`max_output_tokens`** как **`finish_reason`** **`length`**, **`content_filter`** как **`content_filter`**; любая другая причина считается ошибкой), а **`response.failed`** - ошибка с кодом и сообщением бэкенда. Поток, который закрылся до какого-либо конечного сигнала или событие которого оборвалось внутри JSON, считается ошибкой, которая называет обрыв (**`500`** в JSON-ответе, кадр ошибки без завершённого варианта в потоке), и никогда не считается **`stop`**, а сбой после того, как текст дошёл до клиента, не повторяется, чтобы не выдать вторую копию текста;
- Сбой, на который провайдер модели ответил HTTP-статусом, сохраняет этот статус на пути к клиенту и в прямом запросе к модели, и в ходе **agent** / **plan** / **ask**, чтобы клиент мог отличить запрос, который провайдер никогда не примет, от недоступности. **4xx** провайдера возвращается клиенту с тем же статусом, например запрос сверх лимита входа по тарифу даёт **400**, отклонённый ключ - **401**. **429** несёт **`Retry-After`**, если провайдер назвал паузу или если Coddy решил не ждать сброса лимита использования. **5xx** провайдера становится **502 Bad Gateway** с **`Retry-After`** провайдера, если его назвал **503**, а **504** провайдера или тайм-аут запроса становится **504 Gateway Timeout**. Объект ошибки называет статус провайдера (**`{"error":{"message":"...","type":"upstream_error","upstream_status":400}}`**), и потоковый запрос несёт тот же объект в своём кадре ошибки. **500** оставлен для сбоев самого Coddy, в том числе для потока, оборванного до конечного сигнала.

Ответы без потоковой передачи содержат **`metadata`**, где **`model`** равен действующему YAML-селектору бэкенда (**`api_model`** может раскрывать id модели в REST).

## Сессии и заголовки

### Без **`X-Coddy-Session-ID`**

`POST /v1/chat/completions` и **`POST /v1/responses`** создают для такого обмена новый бандл сессии со случайным идентификатором (ACP **`session/new`**).

### С **`X-Coddy-Session-ID`**

1. Побеждает активный бандл в памяти;
2. иначе бандл загружается с диска, если существует **`session.json`**;
3. иначе вызывается **`session/new`** с переданным идентификатором (создаются новые пустые папки бандла).

На некорректный id сервер отвечает **HTTP 400**. Отдельные вспомогательные маршруты **`/coddy/*`** возвращают **503**, если хранилище недоступно (у `Manager` нет **`FileStore`**, в основном в тестах).

Создание бандла сессии (без заголовка или с id, для которого бандла ещё нет, шаг 3) и повторное открытие сохранённой сессии (шаг 2) пишут в папку сессий (**`<home>/sessions`** или **`sessions.dir`**). Когда том с этой папкой заполнен, **`POST /v1/responses`**, **`POST /v1/chat/completions`** и **`POST /coddy/sessions/{id}/workspace`** (первый вызов нового чата, в котором выбрана папка) отвечают **`507 Insufficient Storage`** с сообщением об ошибке **`no space left on device: the disk that stores Coddy sessions is full`**. Раньше они отвечали **`500`** **`session unavailable`**, а маршрут рабочей папки - **`400`** с текстом операционной системы. Ход не начинается, а сервер пишет причину в журнал на уровне error. Сессия, которую запрос начал создавать, не оставляет после себя папки, а сохранённая сессия остаётся с теми файлами, что у неё были. Веб-интерфейс показывает это сообщение рядом со статусом. Сессия, которая уже открыта, продолжает работать из памяти, когда сохранение не удаётся: сервер пишет каждое неудавшееся сохранение в журнал на уровне error, а то, что изменилось после последнего успешного сохранения, после перезапуска отсутствует в транскрипте. См. [Чат падает с `no space left on device`](../getting-started/troubleshooting.md#чат-падает-с-no-space-left-on-device).

### Модель для каждой сессии (встроенный UI)

- **`GET /coddy/sessions/{id}/messages`** возвращает **`model`** (действующий YAML-бэкенд сессии), **`selectedModelId`** (сохранённое в **`session.json`** переопределение, может быть пустым), **`selectedReasoning`** (действующий уровень рассуждения сессии, пустой, если у модели уровней нет) и **`mode`** (профиль сессии `agent`, `plan` или `ask`, удалённые клиенты восстанавливают его при загрузке);
- **`PATCH /coddy/sessions/{id}`** принимает **`selectedModelId`**, чтобы выбрать для сессии YAML-селектор **`models[].model`** (на неизвестный id ответ **400**), и **`selectedReasoning`**, чтобы задать уровень рассуждения (он должен быть одним из **`reasoning_levels`** модели, пустое значение сбрасывает его, на неподдерживаемое значение ответ **400**);
- при открытии чата SPA восстанавливает **Модель** и уровень рассуждения из снимка **`settings`**, то есть собственные значения сессии, тогда как **`model`** и **`selectedReasoning`** называют то, на чём работает идущий ход. Когда меняется **Модель**, SPA записывает cookie **`coddy_llm_model`** (значение по умолчанию для следующего чата, созданного кнопкой **Новый чат**) и отправляет **`PATCH`** для активной сессии.

## Корни памяти

Как и в `external/memory/README.md`, **`global`** использует настроенный **`memory.dir`** (запасной вариант **`$CODDY_HOME/memory`**). **`workspace`** указывает на **`$CWD/memory`** этого бандла сессии. Заполнители **`agentMemory`** остаются только для агента (`session.json`) и через этот REST не редактируются.

Интерактивные запросы разрешений на инструменты пропускаются, когда **`tools.permission_mode`** равен **`bypass`**. В остальных случаях встроенный UI показывает **`event: permission`** во время **`POST /v1/responses`** (**`stream: true`**) и завершает ход через **`POST /coddy/sessions/{id}/permission`** (так же, как для **`question`**).

## Флаги командной строки

Те же, что у **`coddy acp`** - **`--config`**, **`--home`**, **`--cwd`**, **`--sessions-dir`**, **`--session-id`**, **`--log-*`**, а также необязательные **`--scheduler`** и **`--mcp-project-trust ask|allow|deny`** (перекрывает **`mcp.project_trust`** для этого процесса, см. [mcp-integration.md](../features/mcp.md)).

Сетевые флаги - **`-H` / `--host`** и **`-P` / `--port`**. Без них используются **`httpserver.host` / `httpserver.port`** из YAML, а без тех - **`127.0.0.1:12345`**. По умолчанию сервер слушает loopback, потому что теперь один процесс запускает все включённые подсистемы, и оператор, которому нужен был Telegram-бот, не должен в качестве побочного эффекта получить API агента на всех интерфейсах. Чтобы принимать соединения с других машин, передайте **`-H 0.0.0.0`** (или задайте **`httpserver.host`**). Если сделать это без токена, появится предупреждение "reachable without authentication".

Аутентификация. **`--auth-token <token>`** (или **`CODDY_HTTP_TOKEN`**) включает проверку bearer-токена, не записывая секрет в **`config.yaml`**.

Переключатели подсистем. **`--http=false`** запускает всё остальное без API, **`--gateway`**, **`--swarm`** и **`--scheduler`** перекрывают свои ключи **`enable`** на один запуск, а собственные настройки релея задают **`--swarm-host`**, **`--swarm-port`**, **`--swarm-auth-token`**, **`--swarm-pairing-token`** и **`--swarm-allow-insecure`**.

## Сборка

```bash
# HTTP API only (no npm, no embedded SPA root)
make build TAGS=http

# HTTP API plus embedded SPA (**make ui-build** runs first)
make build TAGS="http ui"
```

`go test ./...` пропускает **`external/httpserver`**, если не запустить **`go test -tags=http`**. Тесты, относящиеся к SPA, компилируются при **`go test -tags=http,ui`** (**`make test`** из Makefile один раз запускает **`ui-build`**, а затем один **`go test`** со всеми тегами; матрица по сочетаниям тегов - **`make test-matrix`**, её запускает CI).

Для ручной проверки шлюза на одноразовом процессе **`coddy serve`** скрипт **`examples/test_httpserver.sh`** запускает демо на Python из **`examples/httpserver/`** (см. **`examples/README.md`**). Шагам, которые обращаются к chat или responses, нужен работающий бэкенд **`models`**.

## Просмотр рабочей папки сессии

Эти маршруты используют рабочую папку сессии **`{id}`** и при необходимости загружают её из хранилища.
Корень никогда не выбирается по параметру запроса или заголовку сессии. Пути задаются относительно
рабочей папки, и каждая операция с файловой системой ограничена `os.Root`. raw и text принимают
только обычные файлы. Символическая ссылка, ведущая за пределы папки, или специальный файл недоступны.

| Метод | Маршрут | Контракт |
|---|---|---|
| GET | `/coddy/sessions/{id}/workspace/tree` | Один уровень каталога, сначала папки, потом файлы, каждая группа отсортирована по имени. Для корня `path_rel` пуст. `limit` по умолчанию 200, максимум 1000. Передавайте `next_cursor` обратно как `cursor` без изменений (это непрозрачная позиция, на некорректную ответ `400`). Возвращает `entries` (`name`, `path_rel`, `kind`, `size_bytes`, `mod_time`), `next_cursor` и `has_more`. Виды записей - `file`, `directory`, `symlink` и `special`, размер каталога равен нулю. MIME-тип по содержимому для строк не определяется. `include_hidden=1` показывает скрытые имена, `node_modules` и `vendor`. Фильтрация влияет только на навигацию. |
| GET / HEAD | `/coddy/sessions/{id}/workspace/raw` | `path_rel` должен указывать на обычный файл. Фиксированный список разрешённых типов, который проверяет и расширение, и содержимое, допускает встроенный показ растровых изображений, аудио, видео, PDF и `.txt`. HTML, SVG и неизвестные типы всегда отдаются как вложение с `application/octet-stream`. `download=1` принудительно отдаёт вложение. Поддерживаются Range (206/416), слабый ETag по метаданным и условный ответ 304. Устанавливает `private, no-cache`, `nosniff`, `no-referrer` и CSP с песочницей. |
| GET | `/coddy/sessions/{id}/workspace/text` | Потоковое декодирование в кодировке, определённой по ограниченной выборке, в том числе для текста в устаревших кодировках. `offset` отсчитывается с нуля (по умолчанию 0, максимум 10000000), `max_lines` по умолчанию 300, максимум 1000. Возвращает `lines` без символов конца строки, `offset`, `next_offset`, `has_more`, `total_lines_known` (достигнут конец файла), `charset`, `etag`, `mod_time` и `size_bytes`. Размер файла не ограничен 512 КиБ, но каждая строка и страница ограничены 1 МиБ. `etag` привязывает следующую страницу к версии файла, при несовпадении или одновременной замене файла ответ 409. На содержимое, которое не удаётся декодировать, ответ 415, на слишком длинную строку 413. |
| POST | `/coddy/sessions/{id}/workspace/media-token` | Требуется обычная аутентификация API. Тело запроса - `{"path_rel":"clip.mp4","download":false}`. Возвращает `token` и `expires_at` с `Cache-Control: no-store`. Добавьте токен как `access_token` к запросу raw с тем же путём и тем же режимом скачивания. |

Медиатокен заменяет аутентификацию по bearer-токену или cookie **только** на маршруте raw,
включая HEAD и последующие запросы диапазонов. Его версионированный HMAC связывает сессию,
рабочую папку, путь, режим просмотра или скачивания и срок действия не больше одного часа.
Изменённый, просроченный или не подходящий к запросу медиатокен даёт 401, даже если вместе с ним
передан заголовок bearer. Маршруты tree и text и выпуск токена по-прежнему проходят обычную
проверку аутентификации.

Ключ подписи выводится с разделением доменов из настроенных учётных данных API
(`httpserver.auth_token`, токены из командной строки или окружения) либо из хеша пароля для входа,
если bearer-токен не настроен. Поэтому реплики с одинаковыми учётными данными и перезапуски
сохраняют URL, а смена этих учётных данных делает выданные URL недействительными. Сервер без
аутентификации использует случайный ключ на процесс. Учётные данные API в URL медиафайла не
попадают. CORS разрешает HEAD, Range и If-None-Match и открывает Content-Range, Accept-Ranges,
ETag и Content-Disposition.
