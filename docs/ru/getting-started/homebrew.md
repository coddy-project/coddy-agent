# Homebrew

Coddy уже сегодня устанавливается через Homebrew из собственного тапа, но пока не входит ни в один
из собственных репозиториев Homebrew. Эта страница разделяет две вещи - что пользователь запускает
сейчас и что нужно для отправки Coddy в Homebrew.

## В какой репозиторий должен попасть Coddy

У Homebrew два официальных тапа, и программы распределяются между ними по типу пакета.
Руководство [Adding Software to Homebrew](https://docs.brew.sh/Adding-Software-to-Homebrew#choose-a-package-type)
отправляет консольные программы с открытым исходным кодом, которые Homebrew может собрать из
исходников, в **homebrew/core** в виде формулы, а **homebrew/cask** оставляет для нативных
приложений macOS и для проприетарных программ или программ, которые распространяются только в
бинарном виде.

Coddy распространяется под лицензией MIT, работает только в командной строке и собирается из
исходников с помощью Go и Node, поэтому отправлять его нужно в
**[homebrew/core](https://github.com/Homebrew/homebrew-core) в виде формулы**, а не в homebrew/cask.
Страница [Acceptable Casks](https://docs.brew.sh/Acceptable-Casks#appropriate-package-type)
формулирует то же правило с другой стороны и добавляет, что отказ homebrew/core сам по себе не
делает программу подходящей для homebrew/cask.

Это исправляет исходный план из
[#160](https://github.com/coddy-project/coddy-agent/issues/160), где отправка планировалась в
homebrew/cask.

Наш собственный **cask** никуда не исчезает. Он устанавливает готовые архивы релиза для macOS, без
Go, без Node и без сборки, и именно его несёт наш тап и ставит лендинг. Для этой задачи cask
подходит, он не подходит только для собственного репозитория Homebrew.

## Установка сейчас

```bash
brew install coddy-project/coddy-agent/coddy
```

В тапе [coddy-project/homebrew-coddy-agent](https://github.com/coddy-project/homebrew-coddy-agent) лежит один
файл, **`Casks/coddy.rb`**. Каждый релиз собирает его с контрольными суммами своих двух архивов для
macOS, прикладывает к релизу как **`coddy.rb`** и коммитит в тап
(**`scripts/publish-homebrew-tap.sh`**), поэтому **`brew upgrade --cask coddy`** видит каждый новый
релиз. По полному имени Homebrew сам добавляет тап и доверяет этому одному cask. Ничего другого из
стороннего тапа Homebrew 7 не загружает, пока ему не доверяют. **`brew trust coddy-project/coddy-agent`**
доверяет всему тапу, и тогда короткое имя работает в любой команде.

Файл из релиза сам по себе больше не устанавливается. Вне режима **`HOMEBREW_DEVELOPER`** текущий
Homebrew загружает cask только из тапа. URL он читает как имя cask, поэтому
**`brew install --cask <URL>`** заканчивается на **`No Cask with this name exists`**
([#269](https://github.com/coddy-project/coddy-agent/issues/269)), а локальный файл отклоняет с
**`Homebrew requires casks to be in a tap`**. Файл в релизе остаётся для тех, кому он нужен, а путь
установки - тап.

После каждого релиза workflow **Homebrew tap** запускает эту команду на macOS-раннере с текущим
Homebrew и проверяет результат. Он же запускается раз в неделю и на пул-реквестах, которые меняют
cask ([build.md](../contributing/build.md#тап-homebrew)).

Cask написан под Homebrew 7. Автодополнения ставятся через **`bash_completion`** и
**`zsh_completion`**, единственный шаг установки - блок **`postflight_steps`**, а не Ruby-блок
**`postflight`**, а у **`url`** нет **`verified:`**. Этот шаг снимает **`com.apple.quarantine`**,
который Homebrew ставит на каждую загрузку cask. Бинарник подписан ad-hoc и не нотаризован, и с этим
атрибутом Gatekeeper останавливает его первый запуск. Для нотаризации нужен Apple Developer ID,
которого у проекта нет. Cask требует macOS 12 или новее, потому что бинарники Go 1.25 и новее на
более старых версиях не запускаются.

Cask устанавливает только Coddy и рекомендует **`tmux`** в своих caveats (**`brew install tmux`**).
У **`depends_on`** в cask нет необязательной формы, поэтому tmux, объявленный там, установился бы у
всех, а Coddy работает и без него. Пакеты deb и rpm предлагают tmux так же.

По документации Homebrew тап к тому же служит местом для всего, что отклоняют официальные
репозитории Homebrew
([Package Acceptance Policy](https://docs.brew.sh/Package-Acceptance-Policy#scope-and-third-party-taps)),
так что он пригодится при любом исходе отправки, описанной ниже.

## Формула

```bash
make brew-formula VERSION=1.0.13
```

**`scripts/build-homebrew-formula.sh`** подставляет в **`packaging/homebrew/coddy-formula.rb.tmpl`**
версию и SHA-256 архива исходников этого тега и записывает **`dist/formula/coddy.rb`**. Чтобы
посчитать хеш, скрипт скачивает архив, поэтому версия должна быть опубликованным тегом.

Формула собирает то же, что входит в бинарники релиза, - **`http ui scheduler memory cli gateway swarm metrics`**,
поэтому `brew install` и архив релиза дают одинаковый набор возможностей. Из-за этого **`node`**
стоит в зависимостях сборки рядом с **`go`**. Встроенное SPA генерируется, а не хранится в
репозитории, и **`go:embed`** нужно, чтобы эти файлы существовали до компоновки бинарника, который
их содержит. Формула запускает **`npm ci`**, а не **`npm install`**, потому что
[Acceptable Formulae](https://docs.brew.sh/Acceptable-Formulae#versioned-and-verifiable-sources)
запрещает разрешать плавающий набор зависимостей во время сборки.

**`tmux`** в формулу не входит. [Formula Cookbook](https://docs.brew.sh/Formula-Cookbook#specifying-other-formulae-as-dependencies)
не разрешает формулам в homebrew/core необязательные и рекомендуемые зависимости, а caveats
оставляет для того, что меняет сама упаковка Homebrew, поэтому рекомендация остаётся в cask и на
этих страницах.

Блок **`test do`** формулы запускает **`coddy -v`**, **`coddy sessions list`** и
**`coddy skills list`**. Этим трём командам не нужны ни сеть, ни конфигурация, и они завершаются
ошибкой, если бинарник не может добраться до **`~/.coddy`**.

**`coddy update`** уже отказывается перезаписывать файл, принадлежащий Homebrew, и вместо этого
выводит команду brew. Так Coddy выполняет [правило Acceptable Formulae о самообновляющихся
программах](https://docs.brew.sh/Acceptable-Formulae#self-updating-software). Установка из формулы
попадает в **`Cellar`** и обновляется через **`brew upgrade coddy`**, а cask попадает в
**`Caskroom`** и обновляется через **`brew upgrade --cask coddy`**. Coddy различает их по пути к
собственному исполняемому файлу, см. [update.md](update.md#установки-которыми-владеет-пакетный-менеджер).

## Предварительная проверка

```bash
make brew-check VERSION=1.0.13
```

**`scripts/check-homebrew-submission.sh`** проверяет ту часть критериев приёма Homebrew, которую
можно оценить снаружи. Скрипт выясняет, свободно ли имя **`coddy`** в обоих репозиториях, проходит
ли репозиторий порог известности, существует ли релиз, а также разбирается ли сгенерированная
формула, ссылается ли она на этот релиз, фиксирует ли контрольную сумму и нет ли в ней блока
**`bottle`** (такие блоки добавляет BrewTestBot, а не авторы формулы). Если что-то мешает отправке,
скрипт завершается с ненулевым кодом, а в конце выводит шаги, которые выполняются только на macOS.

### Известность - нерешённое препятствие

[Package Acceptance Policy](https://docs.brew.sh/Package-Acceptance-Policy#notability) задаёт два
порога, и какой из них применяется, зависит от того, кто открывает пул-реквест.

| Кто отправляет | Порог |
|---|---|
| Любой, кто не связан с проектом | 30 форков, 30 наблюдателей **или** 75 звёзд |
| Владелец репозитория, который отправляет собственный проект | 90 форков, 90 наблюдателей **или** 225 звёзд |

На версии 1.0.13 у репозитория 139 звёзд, 14 форков и 2 наблюдателя. Этого хватает для первой
строки, но не для второй, поэтому **отправка самим владельцем пока не допускается**, а отправка
кем-то другим допускается. Текущие числа покажет предварительная проверка. Она сама делает этот
подсчёт и сообщает, сколько репозиторию не хватает.

Ни один из порогов ничего не обещает. Политика Homebrew прямо говорит, что выполнение описанных
критериев не гарантирует приёма, и так же прямо, что невыполнение одного критерия не означает
обязательного отказа. Если метрики неверно отражают реальное использование, исключение нужно
обосновать в пул-реквесте, отметкой в чек-листе его не получить.

## Отправка

Всё, что дальше, требует машины с установленным Homebrew, и лучше всего подходит macOS. Ревьюеры
запускают **`brew audit`** и **`brew style`**, а формулу нужно проверить на платформе, для которой
она в первую очередь предназначена. Предварительная проверка выводит эти команды с уже
подставленными путями.

```bash
brew tap --force homebrew/core
cd "$(brew --repository homebrew/core)"
git checkout -b coddy origin/HEAD
cp /path/to/coddy-agent/dist/formula/coddy.rb Formula/c/coddy.rb
brew install --build-from-source --verbose --debug coddy
brew test coddy
brew audit --strict --online --new coddy
brew style coddy
```

Затем отправьте ветку в форк **Homebrew/homebrew-core** и откройте пул-реквест в этот репозиторий.
Форк делается от репозитория Homebrew, а не от нашего.
[How to Open a Homebrew Pull Request](https://docs.brew.sh/How-To-Open-a-Homebrew-Pull-Request)
описывает порядок, которого ждёт Homebrew, а **`brew bump-formula-pr`** нужен для последующих
обновлений версии, а не для новой формулы.

[CONTRIBUTING репозитория homebrew/core](https://github.com/Homebrew/homebrew-core/blob/master/CONTRIBUTING.md)
допускает пул-реквест, подготовленный с помощью ИИ или LLM, на условиях, от которых зависит, как
эта работа передаётся дальше (обоснование приведено в
[Responsible AI Usage](https://docs.brew.sh/Responsible-AI-Usage)):

- в пул-реквесте нужно указать, что использовался ИИ или LLM, и какой именно инструмент или модель;
- автор должен проверить всё сгенерированное, прежде чем просить Homebrew о ревью;
- ни один коммит не может приписывать работу ИИ или LLM как автору, соавтору, коммитеру или
  подписанту, в том числе через трейлер `Assisted-by` или `Co-developed-by`;
- автор сам отвечает на вопросы мейнтейнеров и замечания ревью, без ИИ или LLM;
- у того, кто не входит в число мейнтейнеров, одновременно может быть открыт только один
  пул-реквест, подготовленный с помощью ИИ.

Поэтому формула, эта страница и скрипты вокруг них готовятся здесь, а саму заявку открывает и
отстаивает человек. Делайте один пул-реквест на пакет и не объединяйте (squash) коммиты после того,
как отправили в него обновление.

## После приёма

Блок **`livecheck`** формулы отслеживает релизы на GitHub, поэтому обновления версии открывает
автоматика самого Homebrew, и отправка делается один раз, а не к каждому релизу. С нашей стороны
меняется немногое. **`brew install coddy`** начинает работать и на Mac, где тап не добавлен, документация
ставит эту команду первой вместо тапа, а установка из формулы получает от **`coddy update`**
подсказку **`brew upgrade coddy`**, что уже и происходит. Как пользователи cask из тапа перейдут на
формулу, решается вместе с этим изменением.
