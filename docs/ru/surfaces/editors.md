Coddy - ACP-сервер. `coddy acp` говорит по [Agent Client Protocol](https://agentclientprotocol.com/) через собственные stdin и stdout, поэтому редактор, плагин или скрипт, который реализует клиентскую сторону ACP, запускает бинарник и получает того же агента, что консоль и веб-интерфейс, - те же режимы и модели, ту же политику разрешений, те же скилы и те же бандлы сессий в `$CODDY_HOME`. В Coddy нет ничего специфичного для конкретного редактора - Zed, VS Code и харнес на Python подключаются одинаково.

## Что такое ACP

ACP стандартизирует то, как клиент общается с процессом агента. Клиент запускает агента, пишет в его stdin запросы JSON-RPC, разделённые переводами строк, и читает из его stdout ответы и уведомления `session/update`; в stderr идут логи, а протокол туда никогда не попадает. Coddy реализует сторону агента - `initialize`, `session/new`, `session/load`, `session/list`, `session/prompt`, `session/cancel`, `session/set_mode` и `session/set_config_option` - и обращается к клиенту за `session/request_permission`, `session/request_question`, `fs/read_text_file` и `fs/write_text_file`. `initialize` объявляет `loadSession`, когда настроено хранилище сессий (для `coddy acp` всегда), и пустой список `authMethods`, потому что шага входа нет.

Протокольный контракт - каждый метод, уведомление и полезная нагрузка - описан в [справочнике по протоколу ACP](../reference/acp-protocol.md). Эта страница о том, как подключить к нему клиента.

## Командная строка

```bash
coddy acp [flags]
```

| Флаг | Значение |
|---|---|
| `--home DIR` | каталог состояния агента (`CODDY_HOME`, по умолчанию `~/.coddy`) - конфигурация, сессии, скилы, расписки |
| `--config PATH` | `config.yaml` (`CODDY_CONFIG`, иначе `<home>/config.yaml`) |
| `--cwd DIR` | рабочий каталог сессии по умолчанию, когда клиент присылает пустой `cwd` (`CODDY_CWD`, по умолчанию cwd процесса); редакторы, которые передают путь в `session/new`, используют этот путь |
| `--sessions-dir DIR` | корень сессий (иначе `sessions.dir` из конфигурации, иначе `~/.coddy/sessions`) |
| `--session-id ID` | следующий `session/new` заново открывает этот бандл, если он есть, а иначе создаёт новый, папка которого называется `ID` |
| `--mcp-project-trust ask\|allow\|deny` | политика для `.coddy/mcp.json` рабочей папки в этом процессе; перекрывает `mcp.project_trust` |
| `--remote TARGET`, `--remote-token TOKEN` | проксирует весь протокол к удалённому `coddy serve` (см. [Управление удалённым сервером](#управление-удалённым-сервером)) |
| `--log-level`, `--log-output`, `--log-file`, `--log-format` | логирование; по умолчанию вывод идёт в stderr, а stdout должен оставаться свободным для протокола |
| `--scheduler` | запускает планировщик cron в этом процессе (нужен тег сборки `scheduler`) |
| `--skills-auto-discovery=false` | выключает для этого процесса инструмент `load_skill`, которым пользуется модель |
| `-t` / `--test-config`, `--dry-run` | проверяет конфигурацию (и то, на что она указывает) и завершается; см. [Конфигурация](../getting-started/configuration.md) |

Указывайте в настройках клиента **абсолютный путь** к бинарнику, а не полагайтесь на `PATH`. Некоторые харнесы запускают агента через `cmd /c` или `sh -c` без пользовательского `PATH`. Установщик одной командой кладёт бинарник в `~/.local/bin/coddy` в Linux и macOS и в `%LOCALAPPDATA%\Programs\coddy\coddy.exe` в Windows (см. [Установка](../getting-started/install.md#windows)). Каждый дополнительный флаг, например `--home` или `--remote`, идёт в список аргументов клиента после `acp`.

## Zed

Zed подключается к внешним агентам через настройку `agent_servers`. Откройте **Agent Settings**, перейдите в **External Agents**, нажмите **Add Agent** и выберите **Add Custom Agent**. Zed откроет `settings.json` с записью `agent_servers`, которую нужно заполнить. Добавьте одну запись для Coddy.

```json
{
  "agent_servers": {
    "Coddy": {
      "type": "custom",
      "command": "/home/you/.local/bin/coddy",
      "args": ["acp"]
    }
  }
}
```

Необязательный объект `env` в записи задаёт переменные для процесса - `CODDY_HOME`, если редактор должен использовать домашний каталог, отличный от `~/.coddy`, или ключ провайдера, которого нет в окружении вашего сеанса входа. Zed подхватывает изменение без перезапуска; выберите **Coddy** в разделе *External Agents* меню нового треда на панели агента.

Собственные режимы Coddy (`agent` / `plan` / `ask`), его настроенные модели и политика разрешений появляются в поле ввода Zed, а скилы видны как слэш-команды. Запрос разрешения показывается в собственном окне одобрения Zed. Запрос несёт варианты, которые предлагает Coddy, а ответ, который отправляет Zed, читается во вложенной форме, предписанной протоколом.

## VS Code

Подойдёт любое расширение ACP-клиента; в [демо-видео Coddy для VS Code](../../assets/video/vscode-acp.mp4) используется расширение **ACP Client** (`formulahendry.acp-client`). Укажите расширению бинарник так же, как в Zed. Команда - абсолютный путь к `coddy`, аргументы - `acp` и любые флаги. Панель расширения может показать то, что несёт протокол, - селекторы режима, модели и режима разрешений, которые возвращает `session/new`, вызовы инструментов и изменения файлов в ходе, слэш-команды и сессии, которые ей дают `session/list` и `session/load`. Где настраивается команда, решает расширение; Coddy видит только процесс, которым его запустили.

## Obsidian и другие клиенты

README Coddy называет Obsidian среди клиентов. В репозитории нет кода специально для Obsidian. Плагин или приложение, которое реализует клиентскую сторону ACP, подключается как любой другой клиент - запускает `coddy acp` и говорит по JSON-RPC через канал. Если клиент умеет запускать команду и читать её stdout построчно, всё остальное есть в справочнике по протоколу.

## Скрипты

`examples/acp/acp_e2e_todo.py` - эталонный клиент, харнес JSON-RPC с разделением по строкам, который проводит настоящий ход и проверяет список задач, вызовы инструментов и файлы, записанные агентом. Берите его за образец для своего клиента, а не составляйте цепочки строк `echo` в конвейер. Четыре свойства, которые должны быть у клиента, написанного вручную, по разделу [Stdio-клиенты](../reference/acp-protocol.md#клиенты-через-stdio-особенность-coddy) справочника:

- успешный ответ может не содержать `result`, когда обработчик ничего не возвращает (так делает `session/set_mode`), поэтому считайте завершением любую строку с `id` вашего запроса и без `method`;
- после `session/prompt` до итогового ответа приходит много уведомлений `session/update`; читайте построчно, пока не вернётся ваш `id`, а на `session/request_permission` и `session/request_question` в промежутке отвечайте ответом с тем же `id`;
- когда stdout не терминал, он может буферизоваться блоками, поэтому оберните бинарник в `stdbuf -oL -eL` или аналог, как это делает харнес;
- ожидающие запросы обрабатываются асинхронно; если ваш клиент рассчитывает на порядок, не отправляйте следующий RPC, пока не прочитали предыдущий ответ.

Весь набор ACP запускается командой `./examples/build_coddy.sh && ./examples/test_acp.sh` с `examples/config.demo.yaml`; `CODDY_BIN`, `CODDY_CONFIG`, `SESSION_ROOT` и `SESSION_ID` переопределяют то, что использует каждый скрипт (см. `examples/README.md`). Для быстрой проверки в одну строку скрипт вообще не нужен.

```bash
echo '{"jsonrpc":"2.0","id":0,"method":"initialize","params":{"protocolVersion":1,"clientCapabilities":{}}}' | coddy acp
```

## Что показывает редактор

Всё, что редактор показывает о Coddy, берётся из протокола, поэтому каждый клиент получает один и тот же набор.

| В клиенте | Откуда это берётся |
|---|---|
| Селектор режима (`agent`, `plan`, `ask`) | опция конфигурации `mode` в `session/new` и `session/load` (плюс устаревшее поле `modes`); меняется через `session/set_config_option` или `session/set_mode` |
| Селектор модели | опция конфигурации `model`, по строке на каждый `models[].model` в `config.yaml`, по умолчанию `agent.model`; отсутствует, если список пуст |
| Переключатель рассуждения или размышления | опция конфигурации `reasoning` в категории `thought_level` с уровнями, которые предлагает модель сессии (`off` последним и только если её логическая модель задаёт `allow_reasoning_off: true`); отсутствует у модели без уровней |
| Политика разрешений (`ask`, `accept_edits`, `bypass`) | опция конфигурации `permission_mode` в категории `_permission_mode`, которую клиент без особой обработки показывает как обычный селектор; режим принадлежит самой сессии и сохраняется в её `session.json`, поэтому переживает перезапуск агента; новая сессия начинает в режиме, выбранном последним в любом интерфейсе, включая эту опцию (`ask`, пока ничего не выбрано) |
| Слэш-команды | `available_commands_update` после `session/new` и `session/load` - команды настроек (`model`, `reasoning`, `think`, `nothink`, `agent`, `plan`, `ask`, `permissions` с подсказкой аргумента в `input.hint`), затем `compact`, `export` и `plugin`, затем все скилы из `skills.dirs`. Команды настроек выполняются из текста промпта, с `--once` или `--count=N` только на следующие ходы ([Настройки сессии](../features/session-settings.md)) |
| Запросы разрешений | `session/request_permission` с вариантами Allow, Allow always и Reject (плюс `allow_always_<program>` на всю программу для простой команды оболочки, а при `ask` переключатели сессии `allow_session_bypass` и, для записи файла, `allow_session_accept_edits`); отправляются только при `ask` (команды и запись) или `accept_edits` (команды); `bypass` никогда не спрашивает. Решает режим сессии, и запрос, который хук `PreToolUse` вызвал ответом `ask`, доходит до клиента даже при `bypass`. Когда включена [проверка безопасности команд](../features/decisions.md), команда оболочки, одобренная при `bypass`, перед запуском проходит эту проверку, и запрос до клиента не доходит |
| Вопросы | `session/request_question` от инструмента `question`; клиент отвечает одним массивом вариантов на каждый вопрос |
| Вызовы инструментов, чек-лист плана, расход токенов и аккаунта, часы хода и сгенерированные токены | обновления `tool_call` / `tool_call_update`, `plan`, `token_usage`, `provider_usage`, `turn_progress` |
| Ход, который никто не набирал, - фоновая задача, запущенная агентом, завершилась и разбудила его (`notify_on_finish`, включено по умолчанию) | обновление `background_wake`, затем то же пробуждение как цитата в тексте агента (`> Woken by a finished background task: bg_3 make test, failed, exit 2, 1m 30s`) в начале ответа, вне любого `session/prompt`; инструмент с проверкой разрешения внутри него спрашивает через `session/request_permission` ([Фоновые задачи](../features/background-tasks.md#пробуждение-агента-по-завершении-задачи)) |
| Список сессий и возобновление | `session/list` (необязательный фильтр `cwd`, который находит папку, как бы ни был записан её путь; `sessionId`, `cwd`, `title`, `updatedAt` в каждой строке) и `session/load`, который воспроизводит транскрипт и затем заново отправляет каталог команд |

Когда агент делегирует работу субагенту, собственные обновления дочернего агента в редактор не попадают, они идут в лог фоновой задачи. Единственное, что клиент получает от имени дочернего агента, - запрос разрешения, доставленный под `sessionId` родителя с заголовком, который начинается с `[subagent <name>]`. Спросить редактор можно только во время хода промпта, поэтому запрос фонового дочернего агента, который спрашивает уже после возврата хода, в редактор не отправляется. Под `coddy acp` дочернему агенту отказывают с причиной, о которой он сообщает, а с `--remote` запрос ждёт на сервере (в его веб-интерфейсе, в подключённой к нему консоли, в Telegram-чате сессии). MCP-серверы, которые клиент сам объявляет в `session/new`, подключаются так, как объявлены; серверы из `.coddy/mcp.json` рабочей папки сначала проходят проверку доверия (см. [Безопасность и доверие](../operate/security.md)).

## Сессии, общие с консолью и веб-интерфейсом

`coddy acp` хранит каждую сессию как бандл в `$CODDY_HOME/sessions/<sessionId>/` - `session.json`, `messages.json`, `assets/`, `todos/active.md`, `plans/` - в том же хранилище, которое открывают консоль и `coddy serve`. При общем домашнем каталоге тред, начатый в Zed, становится строкой в `coddy sessions list`, в истории веб-интерфейса и в выборе `/resume` консоли, и его можно продолжить из любого из них; через `session/list` редактор видит сессии остальных для открытой в нём папки. Файл конфигурации, скилы, правила, MCP-серверы, хуки и определения субагентов общие точно так же, потому что читаются из этого домашнего каталога и из рабочего каталога сессии.

Единственное требование - процессы должны сходиться в домашнем каталоге. Редактор, запущенный из лаунчера, может не унаследовать `CODDY_HOME`, которую экспортирует ваша оболочка, поэтому либо задайте её в блоке `env` клиента, либо передайте `--home` в аргументах. `--sessions-dir` и `sessions.dir` переносят хранилище для всех интерфейсов одинаково. `coddy acp --session-id <id>` заново открывает бандл из командной строки; `session/load` делает то же со стороны клиента.

## Управление удалённым сервером

```bash
coddy acp --remote nas02 --remote-token "$CODDY_REMOTE_TOKEN"
```

С `--remote` процесс не держит хранилища и не запускает ни планировщик, ни цикл агента. Каждый вызов сессии проксируется к удалённому `coddy serve`, его потоковый ответ переводится обратно в обновления ACP, а на запросы разрешений и вопросы отвечают через REST-маршруты сервера. Цель - настроенное имя удалённого сервера, `host:port` или URL `http(s)://`; токен берётся из `--remote-token`, из `token` подходящей записи `httpserver.remotes` или из `CODDY_REMOTE_TOKEN`, в этом порядке. Сессии хранятся только на сервере, `--session-id` по-прежнему называет бандл, который нужно заново открыть там, а селектор модели показывает каталог сервера. Запись редактора для удалённого сервера - та же запись с двумя флагами, добавленными в `args`. Подробности, токен и CORS описаны в разделе [Удалённый режим](../operate/remote.md).

## Решение проблем

- **Редактор не может запустить агента.** Укажите в конфигурации клиента абсолютный путь к бинарнику, потому что `PATH` часто не наследуется. В Windows установщик кладёт бинарник в `%LOCALAPPDATA%\Programs\coddy\coddy.exe`;
- **Агент запускается, но ничего не возвращается.** Выполните `coddy acp -t`, чтобы проверить конфигурацию, затем `coddy acp --dry-run`, чтобы проверить провайдеров, команды MCP, пути и, с `--remote`, сервер. Обе команды выводят каждую проблему с номером строки и завершаются, ничего не запуская;
- **Нужно увидеть, что делает процесс.** Добавьте в аргументы `--log-level debug`; по умолчанию логи идут в stderr, а `--log-output file --log-file <path>` пишет их в файл. Никогда не направляйте логи в stdout, который клиент читает как протокол;
- **MCP-сервер проекта не запускается.** Он ждёт одобрения. `coddy mcp list` его показывает, `coddy mcp trust <name>` одобряет, или запустите процесс с `--mcp-project-trust allow` для чекаута, которому доверяете;
- **Редактор не показывает сессий для папки, хотя в консоли они есть.** Редактор запрашивает `session/list` для открытой в нём папки (ACP Client в VS Code отправляет первую папку рабочей области), поэтому появляются только сессии, рабочий каталог которых совпадает с этой папкой. Консоли, запущенной в подпапке или в другом чекауте, среди них нет, а `coddy sessions list` без `--cwd` показывает всё. Папка находится, как бы ни был записан её путь, - чекаут через символическую ссылку, сохранённый под логическим путём, находится по физическому, а Windows и macOS не различают регистр; ранние релизы сравнивали две строки и пропускали сессию, которую консоль сохранила под другим написанием той же папки. Список запрашивается, когда раскрывается узел агента, и обновляется командой **ACP: Refresh Sessions**;
- **Редактор и оболочка видят разные сессии.** Два процесса используют разные домашние каталоги; задайте `CODDY_HOME` в блоке `env` клиента или передайте `--home`;
- **Ответ клиента на запрос разрешения игнорируется.** Coddy читает и вложенный результат, который отправляют редакторы, и плоскую форму; результат `cancelled` или вариант `reject` запрещают вызов, всё остальное его разрешает. Проверьте, какой `optionId` возвращает клиент.

Более общие сбои - бинарника нет в `PATH`, провайдер отвергает ключ, порт занят - описаны в разделе [Решение проблем](../getting-started/troubleshooting.md).
