# Правила и инструкции

Coddy читает постоянные инструкции из двух мест и добавляет их в системный промпт отдельно от скилов (**`{{.Skills}}`**).

- **Рабочая папка** - папки правил и `AGENTS.md` папки сессии; они приходят вместе с чекаутом и действуют для любого, кто его откроет;
- ваш **домашний каталог агента** (`~/.coddy`) - `AGENTS.md`, `DESIGN.md` и `rules/` рядом с `config.yaml`; они принадлежат тому, кто запускает Coddy, и действуют в любой рабочей папке.

Ни то, ни другое настраивать не нужно. Документы `AGENTS.md` и `DESIGN.md` приходят тремя слоями - ваш, слой рабочей папки и слой папок, в которых работает агент; эти слои читаются всегда, и ни одна настройка их не отключает ([AGENTS.md и DESIGN.md](#agentsmd-и-designmd)). Правила, которые действуют всегда, попадают к модели через **`{{.Rules}}`**, а правило, привязанное к путям, приходит с результатом инструмента или сообщением, которые первыми затрагивают подходящий путь. По умолчанию `instructions.files` пуст и только добавляет файлы ниже документов, в **`{{.Instructions}}`**.

## Порядок в промпте

Сверху вниз в собранном системном сообщении:

1. Инструменты;
2. Скилы;
3. Контекст плана (зависит от режима);
4. **Правила** - ваши `AGENTS.md` и `DESIGN.md`, затем документы рабочей папки, затем правила, которые действуют всегда;
5. **Инструкции проекта** - файлы из `instructions.files` в порядке перечисления;
6. Память сессии.

Шаблон из `prompts.dir` решает, куда встают его блоки, но не решает, придут ли документы. Coddy проверяет на их наличие то, что шаблон собрал, поэтому шаблон, который не выводит ни `{{.Rules}}`, ни `{{.Instructions}}` или выводит их только под ложным условием, всё равно получает документы и файлы из `instructions.files` (в своём слоте инструкций, если он есть, иначе в блоке "## Project instructions" сразу после него). Правила при этом не переносятся. Правила, которые действуют всегда, появляются только там, где шаблон выводит `{{.Rules}}`, а шаблон, в исходнике которого `{{.Rules}}` не упоминается, не получает и правил, привязанных к путям; правило, названное через `@rule:name`, приходит всё равно. Шаблон, который не удаётся прочитать или собрать, заменяется коротким запасным промптом, и документы, правила, которые действуют всегда, и файлы инструкций идут вслед за ним.

### Правила и кэш промпта

Провайдер кэширует запрос по префиксу, а системное сообщение открывает каждый запрос, и один
изменившийся в нём байт выбрасывает кэшированную копию всего диалога за ним. Поэтому в блоке правил
системного сообщения лежит только то, что не зависит от того, к чему обращается сессия, - пары
`AGENTS.md` и `DESIGN.md` и правила, которые действуют всегда. Этот блок собирается **один раз** при
старте сессии, и каждый ход переиспользует его байт в байт. `AGENTS.md`, изменённый во время сессии
агентом или вами, его тоже не сдвигает. Блок перечитывается после
[сжатия контекста](compaction.md), которое и так переписывает кэшированную историю, после перезагрузки
конфигурации или смены рабочей папки и когда сессию открывают в новом процессе. Чтобы сразу передать
модели изменённый файл, упомяните его. `@AGENTS.md` прикладывает его текущий текст к вашему сообщению,
то есть позже в диалоге, чем старый текст, который системное сообщение хранит до следующего поколения.

Правило, привязанное к путям, никогда не попадает в системное сообщение. Оно идёт в самом диалоге,
там, где диалог и так растёт, и его длина учитывается только один раз:

- **вызов инструмента**, который читает или записывает подходящий файл, приносит его в **результате
  этого вызова**, после вывода, под однострочной вводной, а вложенный `AGENTS.md` приходит так же, с
  вызовом, который заходит в его папку;
- **упоминание** приносит его в **сообщении пользователя** как вложение (`kind="rule"`). Так приходят
  правило только по упоминанию, которое назвал пользователь, а также правило, привязанное к путям, или
  вложенный `AGENTS.md`, которые активирует упомянутый файл или папка. См. [Упоминания](mentions.md#упоминания-и-кэш-промпта).

В обоих случаях правило приходит **один раз**. Пока модели ещё отправляется более ранний результат
или сообщение, где правило лежит с тем же текстом, следующее совпадение ничего не прикладывает. Когда
сжатие контекста сворачивает этот результат или сообщение в сводку либо когда файл правила с тех пор
изменился, следующий подходящий вызов инструмента или упоминание снова приносит правило с его текущим
текстом. Вызов, который читает или записывает сам документ правила (`read internal/api/AGENTS.md`,
правка `.cursor/rules/go.mdc`), не получает этот документ обратно как правило, потому что его текст уже
есть в выводе или модель сама его пишет. В веб-интерфейсе, консоли и редакторе показывается собственный
вывод инструмента, а правила передаются вместе с ним только модели.

## Обнаружение

Когда `rules.auto_discover` включён (по умолчанию), Coddy читает вашу собственную папку и **одну** папку проекта.

| Система | Путь | Примечания |
|--------|------|-------|
| `user` | `~/.coddy/rules/` | **Ваша**, не проектная. Читается в любой рабочей папке и никогда не входит в чекаут. Правило проекта с тем же именем файла перекрывает правило из этой папки |
| `coddy` | `.coddy/rules/` | Собственная папка Coddy, первая из просматриваемых папок проекта |
| `agents-dir` | `.agents/rules/` | Общее для всех инструментов дерево `.agents/` рядом с `.agents/skills` - правила для любого агента, который работает над проектом |
| `cursor` | `.cursor/rules/` | Папка Cursor, в диалекте `.mdc`, на котором написаны собственные правила Coddy |
| `claude` | `.claude/rules/` | Папка Claude Code |
| `codex` | `.codex/rules/` | Последняя. Codex хранит здесь свою политику команд `*.rules`, а это не правило для промпта, поэтому учитываются только файлы `.md` и `.mdc` |
| `agents` | вложенные `**/AGENTS.md` и `**/DESIGN.md` | Не папка правил. Читается при любых значениях `rules.auto_discover` и `rules.systems` ([AGENTS.md и DESIGN.md](#agentsmd-и-designmd)). Соглашение [agents.md](https://agents.md/) плюс заметка о дизайне рядом с ним; **читается по требованию**, только из папок, в которые заходит инструмент, дерево никогда не обходится (см. раздел "Активация"); в скрытые каталоги, `node_modules` и `vendor` Coddy не заходит |

Папки проекта образуют цепочку в порядке таблицы. Coddy читает **первую, в которой есть файл правила**, и ни одной после неё. Каждый агент хранит правила в своей папке, и проект, который работает с несколькими агентами, держит одни и те же правила в каждой из них (`.cursor/rules/workflow.mdc` и его зеркало для Claude Code `.claude/rules/workflow.md`), так что при чтении всех папок модель получила бы каждое правило дважды. Проект с `.coddy/rules/` читается только оттуда; проект, который пишет правила для всех агентов в `.agents/rules/`, читается оттуда; иначе Coddy берёт папку Cursor, а если нет и её, то папку Claude Code. Папка без файлов `.md` и `.mdc` (пустая или только с `*.rules` от Codex) не считается, и цепочка идёт дальше.

Каждая прочитанная папка рекурсивно просматривается на файлы `.md` и `.mdc`. Это небольшие папки правил, и больше ничего из рабочей папки при старте сессии не читается. Ваша собственная папка добавляется к той папке проекта, которую прочитал Coddy, а если имя файла встречается в обеих, побеждает файл проекта. Вложенные документы различаются по полному пути, поэтому никогда не сливаются друг с другом.

Вложенные файлы `AGENTS.md` **читаются по требованию**, так же как Codex читает цепочку `AGENTS.md` папки, в которой работает, а `DESIGN.md` рядом с таким файлом читается вместе с ним. Папка, которая описывает себя, читается, каким бы из двух файлов она это ни сделала, - это та же пара, которую Coddy читает для корня рабочей папки и для домашнего каталога агента. Дерево ради них никто не обходит. Когда вызов файлового инструмента или приложенный путь `file://` впервые указывает на путь, читаются все такие документы на цепочке папок от корня проекта (не включая его) до каталога этого пути, и они приходят с результатом этого вызова или в сообщении, к которому приложен путь. Чтение `a/b/c/f.go` подтягивает `a/AGENTS.md`, `a/b/AGENTS.md` и `a/b/c/AGENTS.md`, а также `DESIGN.md` тех из этих папок, где он есть. Соседняя папка, в которую никто не заходит, не открывается вовсе, а файл, записанный после старта сессии, подхватывается, как только инструмент заходит в его папку. Скрытые каталоги, `node_modules` и `vendor` обрывают цепочку. `run_command` ничего не активирует, потому что строку shell нельзя надёжно отнести к каталогу.

Благодаря этому остаётся пригодным к работе репозиторий с вендоренными соседними чекаутами (45 вложенных файлов, загруженных безусловно, стоили ~131 тыс. токенов системного промпта ещё до первого вопроса) и не зависает сессия, привязанная к домашнему каталогу. Обход `~` (в домашнем каталоге macOS сотни тысяч записей в одном только `~/Library`, они читаются с холодного диска и за запросами доступа к папкам) когда-то задерживал консоль до первого кадра. Содержимое больше 256 КиБ обрезается, как и в первых двух слоях.

**Корневая** пара в этот набор не входит. Это второй слой документов, он всегда находится в системном промпте ([AGENTS.md и DESIGN.md](#agentsmd-и-designmd)).

В CLI команда `coddy rules list [--cwd DIR]` печатает найденный каталог правил - исходную папку (`SOURCE`), диалект, которым прочитан каждый файл (`FORMAT`), режим активации (`APPLY`, `auto` или `mention`), входит ли правило в каждый промпт (`ALWAYS`, то есть auto-правило без масок и без привязки к каталогу) и что активирует остальные (`ACTIVATES ON`). Под таблицей `Project rules folder:` называет папку, из которой взяты правила проекта, `Not read:` - папки дальше по цепочке, где тоже есть правила (обычно копия тех же правил для другого агента), а `Only in a folder not read:` перечисляет файлы этих папок, для имени которых в прочитанной папке нет файла, то есть правила, без которых сессия обходится, а не зеркала уже имеющихся. `Could not read:` называет папку цепочки, которая существует, но не читается; цепочка её пропустила. Вложенных файлов `AGENTS.md` и `DESIGN.md` в таблице нет, потому что для их перечисления пришлось бы обходить рабочую папку; строка под таблицей сообщает, что они читаются по требованию из папок, в которые заходит инструмент.

```text
12 rule(s) under .
Project rules folder: .cursor/rules
Not read: .claude/rules (one project folder is read: the first of .coddy/rules, .agents/rules, .cursor/rules, .claude/rules, .codex/rules that holds a rule file)
```

## Форматы файлов правил

Расширение файла определяет диалект, которым читается правило. Оба диалекта принимаются в любой папке, поэтому в `.agents/rules/` правила Cursor и Claude Code лежат рядом, а файл, скопированный из `.cursor/rules/` или `.claude/rules/`, сохраняет свой смысл.

| Расширение | Формат | Ключи frontmatter | Заголовок без `alwaysApply` и без масок |
|-----------|--------|------------------|----------------------------------------------------|
| `.mdc` | Cursor ([документация](https://cursor.com/docs/rules)) | `description`, `globs` (строка через запятую или список), `alwaysApply` | Ручной режим. В Cursor `alwaysApply` по умолчанию равен false, поэтому тело попадает в промпт только по **`@name`** |
| `.md` | Claude Code ([документация](https://code.claude.com/docs/en/memory#organize-rules-with-clauderules)) | `paths` (список масок), необязательный `description` | Загружается безусловно, как в Claude Code |

Общее для обоих диалектов:

- Файл без frontmatter активен с первого хода;
- Маски (`globs` или `paths`, оба диалекта принимают любой из ключей) ограничивают правило. Его тело попадает к модели, когда подходящий файл впервые оказывается в работе, вместе с результатом инструмента или сообщением, которое этот файл принесло. Так работают auto-attach в Cursor и привязка к путям в Claude Code; Coddy применяет то же ограничение к правилам с `alwaysApply: true`, у которых есть маски, чтобы промпт оставался небольшим;
- Явный `alwaysApply` - главный переключатель для заголовка без масок. При `true` правило активно сразу, при `false` - только по упоминанию;
- Читаются концы строк CRLF, значения в кавычках и без, `[flow, lists]`, списки `- item` и комментарии `# comments` в конце строки.

Заголовки `.mdc` у Cursor часто невалидны как YAML, потому что `globs: **/*.go` начинается с символа алиаса YAML. Coddy сначала читает заголовок как YAML, а при неудаче переходит на построчный разбор, который знает эти ключи, поэтому такой файл сохраняет описание, маски и `alwaysApply` и не считается файлом без frontmatter.

```markdown
---
description: HTTP layer conventions
globs: external/httpserver/**/*.go, docs/reference/http-api.md
alwaysApply: false
---
```

```markdown
---
description: HTTP layer conventions
paths:
  - "external/httpserver/**/*.go"
  - "docs/reference/http-api.md"
---
```

Два заголовка выше означают одно и то же в `http-layer.mdc` и `http-layer.md`. Правило прикладывается автоматически, как только один из этих файлов приложен к сообщению или затронут.

### Glob-маски

Маски устроены как в Cursor и Claude Code. `*` совпадает в пределах одного сегмента пути, `**` - с любым числом каталогов, `{a,b}` задаёт альтернативы, `[abc]` - классы символов. Маски привязаны к корню проекта (cwd сессии), и файл сравнивается по пути относительно корня. Поэтому `internal/**/*.go` совпадает с `internal/agent/react.go`, но не с `external/x.go`, `*.md` означает markdown-файлы только в корне (для любой глубины пишите `**/*.md`), а файл вне рабочей папки, например соседний чекаут или кэш модулей, не совпадает ни с чем. В файлах `.mdc` несколько масок разделяются запятыми (`docs/**/*.md, README.md`); запятая внутри фигурных скобок (`*.{ts,tsx}`) маски не разделяет.

### Переход с более ранних релизов

Файлы правил, которые уже лежат на диске, после этого релиза могут сменить режим; результат показывает `coddy rules list`.

- Папки правил проекта больше не объединяются. Читается только первая из `.coddy/rules`, `.agents/rules`, `.cursor/rules`, `.claude/rules` и `.codex/rules`, в которой есть файл правила. Проект, который держал разные правила, скажем, в `.cursor/rules` и `.claude/rules`, теперь получает только правила Cursor; `coddy rules list` называет пропущенную папку под таблицей. Положите то, что должен читать Coddy, в `.coddy/rules` или `.agents/rules` либо сузьте цепочку через `rules.systems`;
- Правило с масками и вложенный `AGENTS.md` после совпадения больше не переносятся в системный промпт. Они приходят один раз с результатом инструмента или сообщением, которое принесло их путь, и ещё раз после сжатия контекста;
- `AGENTS.md`, `DESIGN.md` и файлы из `instructions.files` читаются при старте сессии и после сжатия контекста, перезагрузки конфигурации или смены рабочей папки, но не на каждом ходу. Чтобы сразу передать модели правку, упомяните `@AGENTS.md`;
- Слои `AGENTS.md` и `DESIGN.md` больше не зависят ни от каких настроек. Раньше `rules.auto_discover: false`, список `rules.systems` без `agents` и шаблон из `prompts.dir` без `{{.Rules}}` отбрасывали вложенные документы (а такой шаблон - ещё и пару из домашнего каталога агента); теперь они приходят в любом случае. По умолчанию `instructions.files` - пустой список вместо `["AGENTS.md", "DESIGN.md"]`, и ваш список добавляет файлы после документов, а не заменяет значение по умолчанию; записи с именами документов пропускаются, поэтому существующий список продолжает работать. Файл из `instructions.files` теперь обрезается на 256 КиБ, прежние релизы отправляли его целиком;
- Правило с `alwaysApply: false` вместе с `globs` прикладывается автоматически, как только подходящий файл приложен или прочитан. Прежние релизы оставляли такое правило только для упоминания. Чтобы правило осталось ручным, уберите `globs`;
- Правила `.md` без `alwaysApply` ведут себя как в Claude Code - без `paths` действуют безусловно, с ними привязаны к путям. Прежние релизы считали их правилами только по упоминанию. Чтобы правило `.md` осталось ручным, напишите `alwaysApply: false`;
- Маска без каталога, например `*.go`, совпадает только с файлами в корне проекта. Прежние релизы сравнивали её с именем файла на любой глубине; для такого поведения пишите `**/*.go`;
- Заголовки Cursor, невалидные как YAML (`globs: **/*.go`), теперь читаются. Прежние релизы отбрасывали весь заголовок, и такие правила действовали всегда и без масок; теперь они учитывают свой `alwaysApply` и ждут совпадения масок, как любое другое правило.

## Активация

| Правило | Поведение |
|------|----------|
| Маски (`globs` / `paths`), любой `alwaysApply` | Приходит **один раз**, когда подходящий файл впервые оказывается в работе. Вызов файлового инструмента (`read`, `edit`, `write`, ...), нацеленный на подходящий файл, приносит тело правила в своём результате, а упомянутый файл или папка (`@src/app.go`, вложение `file://` из редактора) - в этом сообщении пользователя. Папка, которую вызов перечисляет или по которой ищет (`grep`, `glob` по каталогу), glob-правила не приносит, его приносит вызов, который читает или записывает подходящий файл внутри неё. После того как сжатие контекста свернёт правило или его файл изменится и будет прочитан снова, следующее совпадение принесёт его опять |
| `alwaysApply: true` без масок | Сразу активно для всей сессии |
| `alwaysApply: false` без масок | **Никогда** не включается автоматически. Его тело приходит в сообщении пользователя, которое называет его через **`@ruleName`** или **`@rule:ruleName`** |
| Без `alwaysApply`, без масок, `.mdc` | Только по упоминанию (по умолчанию в Cursor) |
| Без `alwaysApply`, без масок, `.md` | Сразу активно (Claude Code загружает такое правило безусловно) |
| Без frontmatter | Сразу активно |
| Вложенные `AGENTS.md`, `DESIGN.md` | Читаются по требованию при любых значениях `rules.auto_discover` и `rules.systems` и при любом шаблоне. Первый вызов файлового инструмента внутри каталога документа читает его (вместе со всеми такими документами на цепочке папок выше) в результат этого вызова, а первое упоминание пути там - в это сообщение пользователя. Как и glob-правило, документ приходит один раз и ещё раз после сжатия контекста или изменения файла, поэтому правка, сделанная во время сессии, доходит до модели со следующим вызовом в этой папке. Файл, который уже есть в системном промпте (назван в `instructions.files` или достигнут по ссылке), второй раз не приходит. Для папок, в которые не заходит ни один инструмент и которые не называет ни одно упоминание, ничего не читается |

Правила только по упоминанию вызываются через **`@name`** (имя файла без расширения) или **`@rule:name`**; `@rule:name` также прикладывает по имени любое другое правило каталога. Это **не** слэш-команды, и в каталоге скилов они не появляются. `run_command` ничего не активирует, потому что строку shell нельзя надёжно отнести к пути.

## AGENTS.md и DESIGN.md

Папка описывает себя парой файлов, `AGENTS.md` и `DESIGN.md`, и Coddy читает их тремя слоями, всегда и в таком порядке:

1. **`~/.coddy/AGENTS.md`**, затем **`~/.coddy/DESIGN.md`** - ваш домашний каталог агента, читается в любой рабочей папке, чтобы ваши пожелания оказались перед моделью раньше, чем чекаут начнёт описывать себя;
2. **`AGENTS.md`**, затем **`DESIGN.md`** папки сессии;
3. пара каждой папки на цепочке от уровня под папкой сессии до файла, с которым работает агент; она читается в тот момент, когда до этого файла добирается файловый инструмент или упоминание, так же как Codex читает цепочку `AGENTS.md` папки, в которой работает, и прикладывается к этому результату инструмента или сообщению ([Активация](#активация)).

Читается тот файл, который существует. Если в домашнем каталоге есть только `DESIGN.md`, в промпт попадает он один, а отсутствующий файл ничего не стоит. Первые два слоя находятся в системном промпте, третий приходит позже в диалоге, потому что после старта сессии системное сообщение не меняется ([Правила и кэш промпта](#правила-и-кэш-промпта)). Каждый файл обрезается на 256 КиБ, а скрытая папка, `node_modules` или `vendor` обрывают цепочку.

Ничего из этого не настраивается и не отключается. Ни один ключ в `config.yaml` не называет эти файлы, `rules.auto_discover: false` и `rules.systems` касаются только папок правил, а шаблон из `prompts.dir` получает документы, что бы он ни выводил ([Порядок в промпте](#порядок-в-промпте)). Сессия, которая не должна видеть документов, запускается в папке, где их нет, с домашним каталогом агента, где их тоже нет. Цепочка начинается с папки сессии. Выше неё ничего не читается, даже корень git-репозитория, если сессию открыли в одной из его подпапок, а файл вне папки сессии не приносит никаких документов.

**Каждый файл один раз.** Файл доходит до модели не больше одного раза за поколение правил и опознаётся по реальному пути. Ссылки разрешаются, а регистр пути на Windows и macOS не учитывается. Побеждает первое вхождение в порядке слоёв, потому что его текст уже стоит в промпте выше всего, что могло бы его повторить:

- сессия, открытая в самом `~/.coddy`, читает пару один раз, как вашу;
- `AGENTS.md` проекта, который ссылается на ваш, считается вашим файлом и читается один раз;
- запись в `instructions.files`, которая называет документ из слоёв, ничего не добавляет, поэтому конфигурация, где всё ещё перечислены `AGENTS.md` и `DESIGN.md`, работает как раньше;
- вложенный документ, который уже есть в системном промпте через `instructions.files` или потому, что его папка и есть домашний каталог агента, не прикладывается повторно, когда инструмент заходит в эту папку.

Два слоя системного промпта читаются при старте сессии и хранятся, пока живут её правила. Правка попадает в промпт после следующего сжатия контекста, перезагрузки конфигурации или смены рабочей папки либо сразу через `@AGENTS.md`. Вложенный документ, который свернуло сжатие контекста, приходит снова со следующим вызовом инструмента или упоминанием, добравшимся до его папки, и повтором это не считается.

## Ваши собственные инструкции и правила

Чекаут описывает себя сам - как он собирается, какие в нём соглашения, какие команды опасны *именно в нём*. То, чего вы хотите от каждой сессии (язык ответов, стиль, который вы переносите из проекта в проект, команды, которые нельзя запускать никогда), к проекту не относится, и в его файлах этому не место. Такие файлы лежат в вашем домашнем каталоге агента, `~/.coddy`, и читаются в любой рабочей папке.

| Файл | Как попадает в промпт | Когда читается |
|------|-----------------------|-----------|
| `~/.coddy/AGENTS.md`, `~/.coddy/DESIGN.md` | первый слой документов, над собственной парой проекта ([AGENTS.md и DESIGN.md](#agentsmd-и-designmd)) | при старте сессии и снова после сжатия контекста, в любой рабочей папке |
| `~/.coddy/rules/*.md`, `*.mdc` | как любое правило проекта - в **`{{.Rules}}`**, если действуют всегда, иначе в результате инструмента или сообщении, которые приносят их путь, или в сообщении, которое их называет | по собственному frontmatter (всегда, по маске или через `@mention`) |

Ни то, ни другое не настраивается. Создать файл значит включить, удалить его значит выключить, и ни один ключ в `config.yaml` эти файлы не упоминает.

```bash
mkdir -p ~/.coddy/rules
$EDITOR ~/.coddy/AGENTS.md
```

Ваша пара читается первой, поэтому ваши пожелания оказываются перед моделью раньше, чем чекаут начнёт описывать себя, а собственные `AGENTS.md` и `DESIGN.md` проекта идут ниже. Они дополняют друг друга, ни один не заменяет другой. Напишите один из двух файлов или оба; отсутствующий файл ничего не стоит.

Ваши правила - обычные файлы правил с теми же диалектами, масками и режимами активации, что и у проекта. `go.mdc` с `globs: **/*.go` в `~/.coddy/rules/` ждёт Go-файла в том проекте, который открыла сессия, потому что маски привязаны к рабочей папке, а не к папке, откуда пришло правило. `coddy rules list` показывает их с источником `user` и называет эту папку под таблицей. Ваша папка читается рядом с той папкой проекта, которую выбрала цепочка, и никогда вместо неё. Последнее слово всё равно за проектом. Если у файла проекта и вашего файла одинаковое имя, побеждает файл проекта.

Доверие к этим файлам такое же, как к файлам проекта. И те и другие - текст, который направляет модель, и ни те ни другие сами ничего не запускают (см. [Безопасность](../operate/security.md)). Разница в том, кто их написал. Вашей папке расписка не нужна, потому что с `git clone` в неё ничего не приходит.

### Дополнительные файлы инструкций

`instructions.files` называет файлы, которые сессия читает после всех документов выше, в **`{{.Instructions}}`**, в те же моменты, когда читаются первые два слоя. По умолчанию список пуст и только добавляет файлы (документы читаются, назовёт он их или нет), поэтому команда или машина перечисляет в нём то, что свойственно именно ей.

```yaml
instructions:
  files:
    - "/srv/agents/house-style.md"  # an absolute path, shared by a fleet
    - "${CWD}/docs/conventions.md"  # this workspace
    - "${CODDY_HOME}/team.md"       # next to your config.yaml
```

Ведущая `~` раскрывается, как и два плейсхолдера, которые понимает конфигурация, - `${CODDY_HOME}` означает домашний каталог агента (`~/.coddy`), а `${CWD}` - рабочую папку сессии, которая читает файл. Абсолютная запись читается как есть, относительная разрешается от папки сессии. Файлы читаются в порядке перечисления в конце документов (в конце блока "## Project instructions", перед памятью сессии), каждый под заголовком `### <path>`, который называет его так же, как названы документы. Модель знает, из какого файла пришёл фрагмент, поэтому "следуй `infrastructure.md`" не отправляет её читать файл, который у неё уже есть. Относительная запись или запись с `${CWD}`, файла которой нет в рабочей папке, молча пропускается, и так один список обслуживает рабочие папки с разным набором файлов. Через запись, которая называет один и тот же файл в любой рабочей папке (абсолютный путь, `~`, `${CODDY_HOME}`), несколько агентов с собственными конфигурациями пользуются общим набором инструкций. Если такой файл прочитать не удаётся (его нет для этого процесса, как в случае папки, не смонтированной в контейнер, его нельзя прочитать под учётной записью, от которой работает Coddy, это папка или он пуст), сессия всё равно стартует без него, но сообщает об этом. В логе появляется предупреждение `instructions file not read` с записью, путём и причиной, в заголовке [консоли](../surfaces/console.md) под `[Context]` файл помечен `(not read: <reason>)`, а в `coddy --dry-run` для записи выводится строка с предупреждением ([Пробный запуск](../getting-started/configuration.md#пробный-запуск---проверка-того-на-что-указывает-файл)). О файле рабочей папки, который есть, но не читается, сообщается так же. Каждый файл обрезается на 256 КиБ, как и документы. Файл, который уже есть в промпте, второй раз не читается. `AGENTS.md` или `DESIGN.md` подпапки, перечисленный здесь, но отсутствующий при старте сессии, всё равно придёт вместе со своей папкой, когда появится, как вложенный документ; любой другой файл, которого не было при старте, читается со следующим поколением (после сжатия контекста, перезагрузки конфигурации или смены рабочей папки).

## Генерация правил

Используйте **`/rpa-gen-rules`**. Это один из скилов [стандартной поставки](skills.md#стандартная-поставка), поэтому он есть сразу после установки. Он сначала читает спецификации, документацию и код и выводит правила из найденного, вместо того чтобы просить вас описать проект. В правила входят слоистая архитектура от нижних зависимостей вверх, разработка по BDD/TDD и Rules Sync для намеренных зеркал.

Корневой `AGENTS.md` содержит общую базу. Правила Cursor `.mdc` и Claude Code `.md` - парные нативные представления с равнозначными телами и одинаковым замыслом активации. Если нужна поддержка Codex, скил устанавливает в `.codex/` проектный хук в режиме fail-open, который читает `.cursor/rules/*.mdc` напрямую; он не создаёт ни ручного индекса для Codex, ни третьей копии тел правил. Критичные ограничения остаются в корневой политике или в исполняемых проверках, а интеграции с другими хостами сохраняются, только если репозиторий уже документирует и тестирует их.

Coddy читает одну папку проекта, первую в цепочке, где есть правила ([Обнаружение](#обнаружение)). Проект, который скил настроил для Cursor и Claude Code, читается из `.cursor/rules/`, а его зеркало для Claude Code остаётся нетронутым и не загружается второй раз. Правила, написанные для самого Coddy, кладите в `.coddy/rules/`, а если их должны читать все агенты, то в `.agents/rules/`.

Подкоманды CLI `coddy rules generate` нет.

## Разбивка контекста (веб-интерфейс)

После каждого хода агента Coddy оценивает число токенов по категориям (`systemPrompt`, `toolDefinitions`, `rules`, `skills`, `mcp`, `conversation`) и отдаёт их в **`GET /coddy/sessions/{id}/stats`** как `contextBreakdown`. Кольцо контекста в поле ввода по щелчку открывает всплывающую панель с разбивкой. `rules` учитывает всё, что эта страница описывает как постоянную часть системного промпта, - документы `AGENTS.md` и `DESIGN.md`, правила, которые действуют всегда, и файлы из `instructions.files`.

## Конфигурация

```yaml
instructions:
  # Files added after the AGENTS.md and DESIGN.md documents, which are always
  # read and are not named here. Read in the order listed; ${CODDY_HOME}, ${CWD}
  # and ~ expand, an absolute entry is read as it stands, a relative one
  # resolves against the session working directory. Empty by default.
  files: []

rules:
  auto_discover: true
  # Optional filter: user, coddy, agents-dir, cursor, claude, codex. A project
  # folder left out is not part of the chain; of the ones admitted, the first
  # that holds a rule file is read. "agents" is still accepted and changes
  # nothing, the nested AGENTS.md files being always read; a list holding only
  # "agents" still reads no rule folder, an empty list reads them all.
  systems: []
```
