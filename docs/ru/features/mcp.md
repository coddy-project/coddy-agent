# Интеграция с MCP-серверами

## Обзор

Агент подключается к внешним серверам MCP (Model Context Protocol), которые дают ему дополнительные инструменты и ресурсы. MCP-серверы объявляются в двух файлах, а ACP-клиент может добавить свои:

1. **Глобальные** (область `global`) - пользовательский `~/.coddy/mcp.json` (аналог `~/.cursor/mcp.json` в Cursor; он лежит в домашней папке агента, поэтому окажется в другом месте, если её перенесли `CODDY_HOME` или `--home`), один запущенный сервер на все сессии процесса ([Общие серверы](#общие-серверы));
2. **Локальные** (область `local`) - `<workspace>/.coddy/mcp.json`, который накладывается поверх глобального списка для сессий в этой рабочей папке, один запущенный сервер на рабочую папку; локальная запись с тем же именем перекрывает глобальное определение;
3. **Сессионные** - их передаёт ACP-клиент в параметрах `session/new`.

`config.yaml` не объявляет ни одного MCP-сервера. В нём остаются только настройки `mcp`, не привязанные к отдельному серверу (`project_trust`, `idle_timeout_seconds`), а конфигурация, в которой ещё есть старый список `mcp_servers`, передаёт его при следующей загрузке ([Переезд из config.yaml](#переезд-из-configyaml)).

Инструменты всех подключённых MCP-серверов добавляются в список инструментов, который получает LLM в цикле ReAct (в режимах **`agent`** и **`plan`**).

## mcp.json (глобальный и локальный)

Оба файла mcp.json устроены так же, как у Cursor, - один объект `mcpServers` с ключами по именам серверов. `env` и `headers` - JSON-объекты (а не YAML-список пар name/value), а переключатели отдельных инструментов задаются в `disabledTools`.

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "${CWD}"],
      "env": { "SOME_TOKEN": "value" },
      "disabled": false,
      "disabledTools": ["write_file"]
    }
  }
}
```

Сломанный `mcp.json` записывается в лог и пропускается; сессия всё равно стартует с остальными уровнями.

### Значения

Значение (команда, аргумент, значение переменной окружения, URL, заголовок) разрешается при запуске сервера:

- `${CWD}` - рабочая папка сессии;
- `${NAME}` (или `${env:NAME}` в стиле Cursor) - эта переменная процесса Coddy, пустая, если она не задана, а `${NAME:-default}` подставляет `default`, если переменная не задана или пуста, поэтому токен не попадает в файл;
- `$${` означает буквальный `${`, любой другой `$` тоже буквальный (пароль со знаком доллара экранировать не нужно), а `~` в начале - домашняя папка пользователя.

Правила одинаковы в обоих файлах и для сервера, который передаёт ACP-клиент. Файл хранит ссылку на переменную, и одобрение объявления проекта хеширует ссылку, а не значение. Значение переменной окружения или заголовка никогда не показывается (список серверов выводит на его месте `<redacted>`, см. [API и интерфейс управления](#api-и-интерфейс-управления)), поэтому каждый интерфейс одобрения называет переменные, которые читает объявление (`reads: ${AWS_SECRET_ACCESS_KEY}`), и чекаут, сервер которого отправил бы одну из них, виден за этим ещё до одобрения. Одобрение тоже записывает эти имена. Одобрение, данное прежним релизом, когда `${NAME}` в файле проекта оставался буквальным, одобряло объявление, которое ничего не читало, поэтому о сервере проекта, значения которого называют переменную, Coddy спросит ещё раз, а одобрение сервера, который ничего не читает, остаётся в силе.

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
```

### Правки вне Coddy

`coddy serve`, консоль и `coddy acp` следят за `~/.coddy/mcp.json` и приводят живые сессии в соответствие примерно через две секунды после изменения файла, кто бы его ни изменил: редактор, агент своими файловыми инструментами, другой процесс. Согласуются только серверы, у которых изменилось объявление или переключатель, так же как при переключении в настройках. Добавленный сервер запускается, удалённый закрывается, переобъявленный запускается заново по новому объявлению, а остальные сохраняют свои процессы. Переключатель инструмента ничего не переподключает. Сессия посреди хода получает новый сервер, когда начинается её следующий ход. Файл, который не читается (пойманный на середине записи или сохранённый с опечаткой), ничего не останавливает. Запущенные серверы остаются, лог объясняет причину, а следующее читаемое сохранение сравнивается с тем, что было запущено. Изменение `.coddy/mcp.json` проекта доходит до сессии, когда она стартует, когда переключается на эту рабочую папку и когда сервер сохраняют, переключают или одобряют через `/mcp` или настройки.

## Переезд из config.yaml

Старые релизы читали серверы ещё и из списка `mcp_servers` в `config.yaml`. Первая загрузка такого файла переносит список в `~/.coddy/mcp.json` и убирает ключ из `config.yaml`:

- каждый сервер попадает в файл под своим именем, а `env` и `headers` превращаются в объекты; имя, которое файл уже объявляет, остаётся таким, как в файле;
- каждое значение сохраняет смысл, который имело в `config.yaml`. Ссылка на переменную окружения (`${GITHUB_TOKEN}` или просто `$GITHUB_TOKEN`) записывается как `${GITHUB_TOKEN}`, и файл разрешает эту ссылку при запуске сервера, поэтому секрет в файл не попадает; `${CODDY_HOME}` записывается как путь к домашней папке, на которую он указывал, `$$` как одиночный `$`, а `${CWD}` остаётся как есть;
- остальной `config.yaml` остаётся байт в байт, строки комментариев прямо над ключом уходят вместе с ним, старый файл сохраняется рядом как `config.yaml.bak-<time>`, а лог называет перенесённые серверы и те, что уже были в файле.

Если `~/.coddy/mcp.json` не читается, ничего не переносится. Лог объясняет причину, а старый список остаётся в `config.yaml` неиспользуемым, пока файл не исправят; сохранение из настроек оставляет его там как есть. Блок заканчивается там, где парсер находит следующий ключ, поэтому комментарий в нулевой колонке среди элементов, список без отступа или flow-список, закрытый в нулевой колонке, уходят целиком. Ключ внутри flow-отображения (`{mcp_servers: [...], ...}` в одну строку) блоком строк не считается - его серверы переносятся, ключ остаётся, и лог просит удалить его вручную. `config.yaml`, прочитанный из рабочей папки, потому что в домашней папке его нет, никогда не перезаписывается, и его серверы никогда не переносятся, ведь такой файл мог прийти вместе с чекаутом, а его серверы стали бы вашими в любой рабочей папке. `coddy -t` сообщает об оставшемся ключе предупреждением, в котором сказано, куда переезжают серверы, и ничего не записывает. Вкладка **MCP-серверы** в веб-настройках сохраняет свой адрес `#/settings/mcp_servers`.

## Доверие к рабочей папке для серверов проекта

Добавлено в ответ на [issue #80](https://github.com/coddy-project/coddy-agent/issues/80). До появления этой проверки создание или восстановление сессии для чекаута запускало всё, что просил `<workspace>/.coddy/mcp.json`, и нигде на пути к `cmd.Start()` не принималось решение о доверии.

Файл проекта лежит внутри репозитория, поэтому автор чекаута выбирает `command`, `args` и `env` процесса, который Coddy запустил бы при подготовке сессии, - ещё до того, как заработает модель и появится хоть один запрос разрешения на инструмент. Из-за этого Coddy по умолчанию не доверяет записям `<workspace>/.coddy/mcp.json` и запускает их только после того, как оператор одобрит именно это объявление для этой рабочей папки.

- `~/.coddy/mcp.json` пишет сам оператор, и этот файл **не** проходит проверку доверия;
- политику задаёт `mcp.project_trust` в `config.yaml`: `ask` (по умолчанию), `allow` (запускать серверы проекта автоматически; только для рабочих папок, которым вы уже доверяете), `deny` (никогда их не загружать, одобрить нельзя). `coddy acp` и `coddy serve` принимают ещё и `--mcp-project-trust ask|allow|deny`, который переопределяет конфигурацию только для этого процесса, - этим флагом пользуются джоба CI или точка входа контейнера вместо правки config.yaml. Неизвестное значение прерывает запуск, а не откатывается к значению по умолчанию. Изменённая политика доходит и до живых сессий. Переключённая на `deny`, она отбирает серверы проекта у сессий, которые их держат, и эти серверы останавливаются;
- одобрения хранятся в `~/.coddy/mcp-trust.json` с ключом из канонического пути рабочей папки и хеша SHA-256 той части объявления, которая задаёт команду (транспорт, команда, аргументы, env, url, заголовки). Каждая запись - расписка, которая называет одобренное: **имена** переменных окружения и заголовков и переменные, которые читают их значения, но никогда сами значения;
- изменение одобренной записи меняет хеш и отзывает одобрение, поэтому следующая сессия спросит снова. Включение, отключение и `disabledTools` хеш не меняют, потому что служат рабочими переключателями и границы доверия не задают;
- проверка доверия повторяется непосредственно перед запуском процесса или обращением к URL, и при запуске сессии, и при опросе из интерфейса управления, поэтому вывод списка серверов никогда не запускает неодобренную команду;
- каждый интерфейс одобрения **сначала печатает итоговое объявление**: транспорт, команду с аргументами (или URL), **имена** переменных окружения и заголовков, переменные процесса Coddy, которые читают их значения (`${NAME}`, [Значения](#значения)), рабочую папку, в которой запустился бы процесс, и файл, из которого прочитано объявление. Значения переменных окружения и заголовков никогда не печатаются и не сохраняются в расписке, ведь решение касается того, какие переменные получит дочерний процесс, а не того, что в них лежит. Это сознательно больше, чем запросы с одними именами у похожих агентов, потому что одобрение того, что нельзя прочитать, одобрением не считается.

Неодобренный сервер пропускается с предупреждением, где названы сервер, рабочая папка, хеш и команда для одобрения; сама сессия стартует как обычно с остальными серверами.

Одобрите его в том интерфейсе, которым пользуетесь.

```bash
coddy mcp list
```

```bash
coddy mcp trust <name>
```

`coddy mcp list` печатает каждый сервер объединённого списка с его областью, состоянием доверия и командой, которую он запустил бы; `coddy mcp trust <name>` ещё раз показывает те же подробности и затем записывает одобрение. `coddy mcp untrust <name>` отзывает его. Обе команды принимают `--cwd DIR`, чтобы работать с рабочей папкой, отличной от текущей. По HTTP те же решения принимают **`POST /coddy/mcp/{name}/trust`** и **`POST /coddy/mcp/{name}/untrust`**, а встроенный веб-интерфейс показывает кнопку со щитом и объявление в разделе **Настройки → MCP-серверы**. Саму политику правят на той же вкладке (**`POST /coddy/mcp/project-trust`**), рядом с серверами, которыми она управляет. Сервер, добавленный через API управления или редактор в интерфейсе, одобряется самим фактом записи, ведь команду оператор набрал сам.

При `allow` и `deny` решать по каждому серверу нечего, поэтому кнопка одобрения отдельного сервера полностью исчезает из интерфейса - `allow` и так запускает все серверы проекта, а `deny` не запускает ни одного. Щит предлагается только при `ask`.

Определения субагентов, найденные внутри рабочей папки (`.agents/agents`, `.coddy/agents`), следуют той же модели с **соседним хранилищем**: политика `subagents.project_trust` (`ask` / `allow` / `deny`), расписки в `~/.coddy/subagents-trust.json` с ключом из того же канонического пути рабочей папки, имени определения и хеша файла, одобрение через `coddy agents trust <name>` или `POST /coddy/subagents/{name}/trust`. Эти два файла намеренно разделены, чтобы одобрение MCP никогда не читалось как одобрение агента и наоборот. Дочерний агент, которому разрешены инструменты MCP, не заимствует подключения родителя. Настроенные серверы заново разрешаются для cwd дочернего агента **через эту проверку доверия**, в точности как для новой сессии, а серверы, которые передал ACP-клиент родителя, подключаются заново без проверки, как и при исходном подключении. Дочерний агент, в наборе инструментов которого не может быть имён MCP (встроенный `explore`), ни к чему не подключается. См. `docs/features/subagents.md`.

Файлы определений хуков внутри рабочей папки (`.coddy/hooks.json`, а также `.claude/settings.json` и `.claude/settings.local.json` от Claude Code) - третий вид локального содержимого проекта, которое исполняет код, и они следуют той же модели с третьим соседним хранилищем: политика `hooks.project_trust` (`ask` / `allow` / `deny`), расписки в `~/.coddy/hooks-trust.json` с ключом из канонического пути рабочей папки, пути файла относительно рабочей папки и хеша файла, одобрение через `coddy hooks trust <file>` или `POST /coddy/hooks/trust`. При `ask` задержанный файл разбирается и показывается в списке, но ни один его хук не запускается, а сессия записывает уведомление с командами одобрения. См. `docs/features/hooks.md`.

## Переключатели включения и отключения

В обоих файлах можно выключить целый сервер или отдельные инструменты, не удаляя их определения:

- `~/.coddy/mcp.json` и `./.coddy/mcp.json` - `"disabled": true` и `"disabledTools": ["tool_a"]` в каждой записи, если править объявления напрямую;
- для записей проекта переключатели, сделанные через `/mcp` или настройки, хранятся в `<home>/mcp-overrides.json` с ключом из рабочей папки и сервера. `.coddy/mcp.json` в чекауте не меняется, а эти переключатели перекрывают его значения по умолчанию. Удаление сервера проекта через API или интерфейс сбрасывает его переключатели, как только объявления не стало, поэтому следующий сервер с тем же именем стартует по собственному объявлению, а неудавшееся удаление оставляет переключатели сервера такими, какими они были. Пока этот файл не читается, все серверы проекта остаются выключенными, а глобальные серверы сохраняют свои переключатели; `/mcp` и настройки вместо списка серверов называют файл и ошибку разбора, пока его не исправят. Этот файл и `mcp-trust.json` пишутся под блокировкой, которую берёт каждый процесс домашней папки, поэтому консоль и `coddy serve`, которые одновременно что-то переключают или одобряют, не затирают друг друга.

Отключённые серверы не подключаются к новым сессиям. Отключённые инструменты (и все инструменты отключённого сервера) скрыты из списка инструментов LLM и отклоняются при вызове. Переключатели перечитываются на каждом ходе агента, поэтому их смена (правкой файлов или через HTTP API и веб-интерфейс, см. ниже) действует и на **уже работающие** сессии со следующего хода.

Переключение через `/mcp`, настройки или HTTP API к тому же сразу доходит до живых сессий, по одному серверу. Включённый сервер подключается в каждой живой сессии, для которой его пропускает проверка доверия, выключенный там закрывается, а остальные серверы сохраняют свои процессы, поэтому сервер автоматизации браузера не закрывает открытые страницы. Выключенный глобальный сервер останавливается для всего процесса, а включённый снова запускается ещё до того, как его попросит какая-либо сессия. Переключатель инструмента ничего не переподключает. Сессия посреди хода сохраняет свои инструменты до конца этого хода. Выключенный сервер или сервер, которому больше не доверяют, закрывается, когда ход заканчивается, а включённый запускается, когда начинается следующий ход сессии. Сохранение или удаление сервера через API или настройки доходит до живых сессий так же, а сервер с изменённым объявлением запускается заново по новому. Сервер, который не ответил на рукопожатие за 30 секунд, ничего не задерживает. Его пропускают, и следующий ход сессии пробует его снова.

## API и интерфейс управления

HTTP-шлюз (тег сборки `http`) отдаёт объединённый список серверов с опрошенными наборами инструментов и эндпоинты переключения под **`/coddy/mcp*`** (см. `docs/reference/http-api.md`), а встроенный веб-интерфейс показывает их в разделе **Настройки → MCP-серверы**: точку статуса у каждого сервера, значок области `global` / `local`, раскрывающийся список инструментов с переключателем у каждого и JSON-редактор записей mcp.json в стиле Cursor с выбором области (global пишет в `~/.coddy/mcp.json`, local пишет в `./.coddy/mcp.json`). Глобальные переключатели сохраняются в файле, где объявлен сервер, а переключатели проекта - в домашней папке оператора.

Список называет переменные окружения и заголовки каждого объявления, но никогда не возвращает их значения. Каждое значение выглядит как `<redacted>`, какой бы файл его ни объявил, а `reads` называет переменные процесса Coddy, из которых берутся значения. Команда, её аргументы и URL показываются как записаны, ведь именно их касается одобрение, поэтому секрету место в `env` или `headers`, а лучше в окружении в виде `${NAME}`. Ошибка опроса очищается так же, прежде чем попасть в список. URL показывается как записан, вместе со ссылками `${NAME}`, а значение, в которое разрешается объявление (значение переменной окружения или заголовка, переменная, которую оно читает, длиной от восьми символов), выглядит как `<redacted>`, даже если сервер вернул его обратно. `/mcp` в консоли и в Telegram показывает ту же очищенную ошибку.

Редактор открывается с записью из списка, включая заглушки. Значение, оставленное как `<redacted>`, сохраняет то, что хранится в файле, новое значение его заменяет, а ключ, удалённый из JSON, удаляется из записи; заглушка для ключа, значения которого в файле нет, отклоняется, потому что это значение нужно ввести. Сохранение называет открытое в редакторе объявление по его `fingerprint` (`PUT /coddy/mcp/{name}?fingerprint=`). Если к этому моменту в файле уже другое объявление, сохранение отклоняется (`409`) и ничего не записывается и не одобряется, поэтому откройте запись заново. Запись проекта сохраняет скрытое значение только с этим отпечатком, и поэтому значение, которое чекаут положил в файл после вывода списка, никогда не записывается обратно и не одобряется незамеченным.

Если загрузка или обновление списка не удались, настройки показывают ошибку и оставляют видимыми ранее загруженные серверы. Кнопка обновления остаётся доступной для новой попытки. Неудачное переключение, решение о доверии, удаление или сохранение сообщает об ошибке и освобождает свой элемент управления, чтобы оператор мог повторить попытку, не открывая настройки заново. Перекрывающиеся загрузки применяются по порядку - более медленный запрос, который ещё выполняется, никогда не перезаписывает строки, уже принесённые более новым, и не сообщает об ошибке поверх них.

*Некорректный ответ со списком теперь завершает загрузку и показывает причину.*

Наберите `/mcp` в поле ввода веб-интерфейса, чтобы открыть этот раздел настроек; слова после команды игнорируются, как и в консоли. В консоли `/mcp` открывает список глобальных серверов и серверов проекта с состоянием подключения и числом инструментов, а рядом с выключенным сервером, состояние которого - вердикт доверия, стоит `off`. Enter открывает управление сервером - включить или выключить сервер, раскрыть его инструменты и переключить один из них или выдать либо отозвать доверие для объявления проекта. Управление доверием подчиняется правилу веб-щита и предлагается только при `mcp.project_trust: ask`, потому что при `allow` и `deny` решать по каждому серверу нечего. Прежде чем записать доверие, консоль печатает над выбором всё объявление: транспорт, командную строку или URL, имена переменных и заголовков, рабочую папку и файл. Это управление работает и в удалённом режиме (`--remote`) через маршруты управления MCP на сервере. `/mcp` в Telegram перечисляет серверы и предлагает кнопки включения и выключения только для уже одобренных записей; в группе команде нужно упоминание бота (`/mcp@botname`), а о неудачном нажатии сообщается в сообщении меню. Одобряйте объявления проекта в консоли, CLI или веб-интерфейсе; чат не может выдать доверие к рабочей папке.

Одобрение из консоли, веб-щита или удалённой консоли называет показанное объявление по `fingerprint`, который сообщил список. Если чекаут переписал запись между выводом списка и одобрением, одобрение отклоняется (`409` по HTTP) и ничего не записывается. Выведите список серверов заново и просмотрите новое объявление.

## Вызовы MCP в транскрипте

Веб-интерфейс называет вызов MCP действием на его сервере (*запускаю get_issue на MCP-сервере github*) и открывает его карточкой, а не JSON. Полоса заголовка называет сервер и инструмент, аргументы показываются полями, а ответ читается по своей форме: JSON-объект - теми же полями, прочий JSON - с отступами, Markdown (заголовок, блок кода, список) - документом, всё остальное - моноширинным текстом. Числа и JSON показываются так, как их записал сервер, поэтому id больше 2^53 (snowflake из Discord или Twitter) не округляется, а повторённый ключ сохраняет оба значения. Неудачный вызов сохраняет свою ошибку сырым текстом. В транскрипт попадают только текстовые части ответа - Coddy передаёт модели содержимое `text` из результата `tools/call` и отбрасывает изображения и встроенные ресурсы. Карточка и скриншот есть на странице [Веб-интерфейс](../surfaces/web-ui.md).

## Поддерживаемые транспорты

### stdio (поддерживается)

MCP-сервер работает как дочерний процесс. Обмен идёт через stdin/stdout (JSON-RPC 2.0, по сообщению на строку). Дочерний процесс получает собственную группу процессов, поэтому остановка сервера останавливает и то, что он запустил ([Общие серверы](#общие-серверы)).

Coddy запускает `command` с `args` ровно так, как они записаны: программу по пути или по имени в `PATH`, запускатель пакетов вроде `npx -y <package>` или `uvx <package>`, контейнер через `docker run -i`. Всё, что нужно команде, обеспечивает оператор (Node.js для `npx`, сеть для пакета, которого ещё нет в кэше), а Coddy не переписывает аргументы и ничего не устанавливает. Программа, пакет `npx`, сервер streamable HTTP и сервер SSE проходят настоящий ход в `features/mcp_tool_calls.feature`, а в консоли - в `examples/cli/cli_e2e_mcp_servers.py`.

Конфигурация в `session/new`.
```json
{
  "name": "my-server",
  "command": "/path/to/mcp-server",
  "args": ["--stdio"],
  "env": [
    { "name": "API_KEY", "value": "secret" }
  ]
}
```

В `~/.coddy/mcp.json`.
```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/home/user/projects"]
    }
  }
}
```

### Streamable HTTP (поддерживается)

`type: http` подключается к `url` по транспорту MCP streamable HTTP (спецификация 2025-03-26). Сообщения JSON-RPC отправляются на эндпоинт методом POST, а ответы приходят телами `application/json` или фрагментами `text/event-stream`; `Mcp-Session-Id`, выданный при инициализации, повторяется в следующих запросах. `headers` отправляются с каждым запросом (например, `Authorization`). Записи только с URL (без `command` и без `type`) по умолчанию получают `http`. Если эндпоинт отвергает рукопожатие (старые серверы отвечают на POST кодом 4xx), клиент автоматически переходит на устаревший транспорт SSE по тому же URL, как это делают Cursor и Claude Code. Агент объявляет `mcpCapabilities.http: true` и `mcpCapabilities.sse: true`. Значение `type` - `stdio`, `http` или `sse`, а для `http` принимаются и псевдонимы `streamable-http` / `streamable_http`.

```json
{
  "mcpServers": {
    "remote-tools": {
      "type": "http",
      "url": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer ${MCP_TOKEN}" }
    }
  }
}
```

### SSE (поддерживается, устаревший)

`type: sse` принудительно включает транспорт HTTP+SSE версии 2024-11-05. GET-поток по `url` объявляет эндпоинт для POST в первом событии, а затем несёт все сообщения от сервера к клиенту. Используйте его для серверов, которые реализуют только старый протокол; `type: http` тоже доходит до них благодаря автоматическому откату.

В `.coddy/mcp.json` те же записи выглядят так же, как у Cursor.

```json
{
  "mcpServers": {
    "remote-tools": { "url": "https://mcp.example.com/mcp" },
    "legacy-tools": { "type": "sse", "url": "https://old.example.com/sse" }
  }
}
```

## Пространства имён инструментов

Чтобы избежать конфликтов, когда несколько MCP-серверов дают инструменты с одинаковым именем, к имени инструмента добавляется имя сервера:

- инструмент `read_file` MCP-сервера `filesystem` -> доступен как `filesystem__read_file`;
- встроенный инструмент `read_file` -> доступен как `read_file`.

Поскольку `__` отделяет имя сервера от имени инструмента, имена серверов не должны содержать `__` (API управления отклоняет такие имена).

## Как инструменты попадают к модели

Инструменты MCP **не** подставляются в текст системного промпта (в отличие от скилов, которые выводятся в раздел промпта). Они присоединяются к встроенным инструментам в нативном массиве `tools` для вызова функций в каждом запросе к LLM, по одному определению на включённый инструмент: имя `server__tool`, собственная `inputSchema` сервера и описание с префиксом `[server]`, чтобы модель различала серверы. Когда модель выдаёт вызов инструмента с `__` в имени, агент направляет его серверу-владельцу через его транспорт и возвращает результат MCP модели как обычное наблюдение инструмента - тот же цикл, что у встроенных инструментов, и тот же подход, что у Claude Code, Codex и Cursor. Сквозной успешный сценарий (два сервера по stdio и streamable HTTP, модель выбирает один по инструменту с пространством имён, результат попадает в итоговый ответ) описан в `features/mcp_tool_calls.feature` и для OpenAI-совместимого HTTP-интерфейса, и для сессии ACP.

## Модель разрешений

Может ли сервер **запуститься**, решает описанная выше проверка доверия к рабочей папке. О том, что работающий сервер может **делать**, Coddy не спрашивает. Вызовы инструментов MCP выполняются без встроенных запросов разрешения, которые охраняют запись в файловую систему и команды оболочки, а ограничивают их переключатели отключения. Запускайте MCP-серверы с учётными данными с минимальными привилегиями и отключайте ненужные инструменты.

## Общие серверы

Настроенный сервер запускается один раз для всех сессий, которые им пользуются, а не по разу на сессию. Каждая сессия и каждый субагент, которого она порождает, держат аренду подключения, общего для процесса:

- сервер из `~/.coddy/mcp.json` - один процесс на весь процесс Coddy. `coddy
  serve`, консоль и `coddy acp` запускают такие серверы при своём старте,
  раньше, чем их попросит какая-либо сессия, и держат их до своего выхода. Открывшаяся сессия находит их подключёнными, а закрывшаяся их не останавливает. Набор серверов следует за файлом. Добавленный или включённый сервер запускается сразу, удалённый или выключенный останавливается, как только его не держит ни одна сессия, а упавший запускается снова следующей сессией или ходом, которым он нужен. Разовый `coddy -p` запускает их для своей сессии и останавливает при выходе;
- сервер из `.coddy/mcp.json` проекта - один процесс на рабочую папку. Первая сессия рабочей папки, которой он нужен, запускает его, как только его пропустит проверка доверия, а остальные сессии этой рабочей папки пользуются им совместно. Когда его больше не держит ни одна сессия рабочей папки, он работает ещё `mcp.idle_timeout_seconds` (по умолчанию 300, то есть пять минут; `0` останавливает его сразу), поэтому сессия, которая за это время откроется в проекте (`/new` в консоли, новый диалог в чате, следующий запуск задания по расписанию, тот же проект, заново открытый в браузере), застаёт его работающим, а потом он останавливается. Две рабочие папки, которые объявляют одну и ту же команду, получают по своему процессу;
- глобальный сервер, у которого `command`, `args`, `env`, `url` или `headers` содержат `${CWD}`, в каждой рабочей папке разрешается по-своему, поэтому он тоже запускается по разу на рабочую папку, как сервер проекта, и не стартует раньше сессий.

Тайм-аут простоя действует для сервера, который конфигурация всё ещё хочет держать, но который сейчас не держит ни одна сессия. Выключенный сервер, сервер с отозванным одобрением, удалённый из своего файла и объявленный теперь иначе останавливаются, как только их не держит ни одна сессия, в том числе те, что уже выжидают тайм-аут. Тайм-аут задаётся в `config.yaml` (в веб-настройках для него нет поля, и при сохранении они его не трогают).

```yaml
mcp:
  project_trust: ask
  # seconds an MCP server no session holds keeps running; 0 stops it at once
  idle_timeout_seconds: 300
```

Сессии делят подключение, когда объявление разрешается для них одинаково: имя, транспорт, командная строка и окружение stdio-сервера (или URL и заголовки удалённого) и, для сервера, привязанного к рабочей папке, сама рабочая папка. Выключенный инструмент ничего не разделяет, потому что каждая сессия сама фильтрует свой список инструментов. Правка файла или переключатель согласуют живые сессии, как описано ниже, и сервер, объявление которого не изменилось, сохраняет свой процесс; сервер с изменённой командной строкой один раз запускается по новому объявлению, а старый процесс останавливается, когда его отпустит последняя сессия.

Остановить stdio-сервер значит закрыть его stdin (так MCP предписывает клиенту завершать работу), дать ему две секунды на выход, а затем завершить его группу процессов. Запускатель пакетов (`npx -y <package>`, `uvx <package>`) запускает настоящий сервер как свой дочерний процесс, и этот процесс тоже завершается. В Windows сервер работает в объекте задания (job object), который при закрытии завершает каждый процесс дерева, поэтому завершается и дочерний процесс, чей родитель уже вышел. Удалённый сервер отключается - его поток SSE закрывается, а сессия streamable HTTP завершается запросом `DELETE` с её `Mcp-Session-Id`. Вызов, который ещё ждёт ответа, сразу завершается ошибкой, когда его сервер останавливают.

Общий сервер, который завершился сам, удалённый сервер, разорвавший соединение, и сервер streamable HTTP, ответивший `404` на свою сессию (он перезапустился или сессия истекла), запускаются снова, когда начинается следующий ход сессии, которая ими пользовалась, - один раз для всех таких сессий. Вывод списка серверов (`/mcp`, Настройки → MCP-серверы, `/mcp` в чате) читает инструменты работающего сервера из его подключения и вторую копию не запускает. Серверы, которые ACP-клиент передаёт в `session/new`, делятся так же. Сессии, передающие одинаковое объявление, включая субагента, который наследует серверы родителя, держат один процесс, и он останавливается через `mcp.idle_timeout_seconds` после закрытия последней из них. Проверка доверия о них не решает, и ничто не держит их запущенными раньше сессии.

`coddy serve` пишет в лог `MCP server started` и `MCP server stopped` с причиной для каждого процесса сервера, который запускает и останавливает, поэтому по логу видно, сколько их работает и почему каждый остановился.

## Жизненный цикл MCP-сервера

### Выбранная веб-сессия

Вкладка MCP в настройках берёт локальные объявления проекта из рабочей папки выбранной сессии, а не из папки, где запустили `coddy
serve`. Запрос с выбранной сессией использует её рабочую папку, а запрос без сессии - рабочую папку сервера по умолчанию для нового чата. Локальные переключатели проекта, решения о доверии и правки обновляют только сессии этой рабочей папки, а глобальные объявления по-прежнему обновляют каждую затронутую сессию.

Открытие чата во встроенном веб-интерфейсе явно запускает в фоне его отложенные настроенные MCP-серверы. Это не задерживает отрисовку транскрипта, а следующий промпт дожидается ограниченной по времени попытки подключения, прежде чем получить список инструментов. Пассивные чтения, включая автодополнение слэш-команд, списки MCP в настройках и постраничное чтение транскрипта, никогда не запускают отложенный сервер.

1. При `session/new` сессия берёт каждый включённый сервер из объединённого списка `~/.coddy/mcp.json` + `./.coddy/mcp.json`, который пропускает проверка доверия рабочей папки, а затем подключает серверы, переданные ACP-клиентом. Настроенный сервер, который уже работает у другой сессии, используется совместно и заново не запускается ([Общие серверы](#общие-серверы)). Серверы подключаются **параллельно**, каждый со своим пределом в 20 секунд, включая серверы от ACP-клиента, которые второй попытки не получают, потому что заново объявить их может только этот клиент (это делает новая сессия). Вызов длится столько, сколько самый медленный сервер, а не сумму всех, а сервер, который запускается и так и не отвечает на `initialize` (stdio-команда точно так же, как удалённый URL, который принимает соединение и молчит), падает в одиночку с предупреждением, пока остальные подключаются рядом. Сессия, восстановленная с диска (заново открытая редактором через `session/load` или прочитанная веб-интерфейсом либо чатом), вместо этого подключает свои настроенные серверы перед первым ходом через ту же проверку доверия. Чтение сохранённого диалога не запускает ни одного процесса, тогда как раньше оно запускало набор серверов на каждую сессию, и они жили до конца работы сервера. Серверы от ACP-клиента по-прежнему подключаются при загрузке. Интерактивная консоль идёт на шаг дальше и подключает серверы открытой сессии, новой или продолженной, **после первого кадра** ([Консоль](../surfaces/console.md)). `coddy` рисует экран сразу, нижняя строка считает серверы, пока они поднимаются, а промпт, отправленный до их ответа, ждёт свой список инструментов в строке состояния (`Connecting MCP
   servers`);
2. Агент вызывает `tools/list` на каждом сервере и регистрирует инструменты;
3. Правка `~/.coddy/mcp.json`, пока работают сессии (в редакторе, в настройках, агентом через файловые инструменты), доходит до них так, как описано в разделе [Правки вне Coddy](#правки-вне-coddy). Каждый сервер, у которого изменилось объявление или переключатель, согласуется отдельно, простаивающая сессия - сразу, сессия посреди хода - когда начнётся её следующий ход. Серверы от ACP-клиента не затрагиваются;
4. Изменённый `mcp.project_trust` (сохранение настроек, `config_commit`, выбор политики на вкладке MCP) переподключает настроенные серверы каждой активной сессии; сессионные серверы от ACP-клиента остаются подключёнными. Переподключение **заново оценивает доверие** и не повторяет то, с чем стартовала сессия. Неодобренное объявление проекта остаётся незапущенным, а объявление, одобрение которого за это время отозвали, не возвращается. Сессию с **ходом в процессе** не подменяют посреди хода, ведь этот ход уже передал модели список инструментов, поэтому перезагрузка откладывается и применяется в момент, когда ход отпускает свою блокировку. У всех сессий один срок на сохранение, и подключение, которое этот срок прервал, отбрасывается, а не устанавливается, ведь сервер, зависший в первой переподключаемой сессии, не должен лишить инструментов остальные. Такие сессии сохраняют имеющиеся серверы и повторяют попытку на следующем ходе;
5. Смена рабочей папки сессии (`POST /coddy/sessions/{id}/workspace` - выбор папки, переход в worktree или переключение ветки на месте) заново подключает настроенные серверы для нового cwd тем же путём через отложенную перезагрузку и блокировку хода. `.coddy/mcp.json` новой рабочей папки объединяется со списком и заново проходит проверку доверия (объявление проекта там остаётся незапущенным при `mcp.project_trust: ask`, пока его не одобрят), настроенные клиенты прежней рабочей папки закрываются, а серверы от ACP-клиента остаются подключёнными. Эндпоинт отвечает `409`, пока в диалоге есть сообщения или идёт ход, а неудачное подключение выдаёт предупреждение и не прерывает смену. Смена, переподключение которой не уложилось во время, завершается, когда начинается следующий ход сессии, до того как этот ход получит свои инструменты, поэтому он никогда не работает на серверах проекта прежней папки;
6. Когда в цикле ReAct LLM вызывает инструмент MCP, агент передаёт вызов дальше (если инструмент или его сервер с тех пор не отключили);
7. Результаты возвращаются LLM как наблюдения инструментов;
8. Закрываясь, сессия отпускает свои серверы. Сервер проекта, как и сервер от ACP-клиента, останавливается через `mcp.idle_timeout_seconds` после того, как его отпустила последняя державшая его сессия, а глобальный сервер продолжает работать вместе с процессом.

Встроенный скил `/configure-coddy` объясняет агенту, как ставить сервер, когда пользователь об этом просит: проверить пакет и то, что ему нужно, объяснить, что он запустит, и только после согласия пользователя добавить запись в `~/.coddy/mcp.json` файловыми инструментами, сообщив пользователю, что инструменты появятся со следующим ходом.

## Обработка ошибок

- если MCP-сервер не запустился, сессия всё равно продолжает работу с предупреждением, а к серверу не подключаются заново на каждом ходе. Снова попробовать его запустить заставляют правка его объявления, его переключатель (`/mcp`, Настройки → MCP-серверы), изменённая политика доверия или новая сессия;
- от сервера, который запустился, но так и не ответил на `initialize`, отказываются через 20 секунд, и предупреждение называет этот предел. Когда начинается следующий ход сессии, его пробуют ещё раз, потому что первый запуск может не уложиться в предел по веской причине. `npx -y <package>` ставит пакет перед запуском (16 с для `@modelcontextprotocol/server-everything` на ноутбуке с пустым кэшем npm), и следующая попытка запускает его уже из кэша. Сервер, который не ответил и во второй раз, остаётся выключенным до одного из событий выше. Подключение, прерванное извне (сохранение, переподключающее много сессий под одним сроком, или завершившийся запрос), тоже повторяется на следующем ходе;
- за то, что делает собственная команда сервера до ответа, отвечает оператор. Запускатель пакетов вроде `npx -y <package>` при каждом запуске спрашивает у своего реестра последний релиз и ждёт сеть, а версия в `args` (`<package>@<version>`) избавляет его от обращения к сети;
- неудачные вызовы инструментов MCP возвращают LLM наблюдение с ошибкой;
- LLM может решить повторить вызов, воспользоваться другими инструментами или сообщить пользователю.
