# Скилы

Скилы - это наборы инструкций для повторного использования, которые дают агенту слэш-команды, знания предметной области и готовые сценарии работы. Из них строятся блок **`{{.Skills}}`** в системном промпте и каталог слэш-команд, который видят ACP-клиенты и веб-интерфейс.

> **Правила проекта** (`.coddy/rules`, `.cursor/rules` и другие) - отдельный механизм, который подставляется как **`{{.Rules}}`**. Не кладите правила в `skills.dirs`. См. [rules.md](rules.md).

## Стандартная поставка

Coddy носит набор скилов внутри бинарника и записывает их в **`${CODDY_HOME}/skills`**, как только видит, что их там нет. Ничего для этого не скачивается. Свежая установка получает их при первом запуске без сети, а скил, который читает файлы рядом со своим `SKILL.md`, находит их на диске, а не указывает на несуществующую папку.

| Скил | Что делает |
|-------|--------------|
| **`/configure-coddy`** | Меняет конфигурацию самого Coddy по вашей просьбе - настройки, провайдеры, модели, логирование, разрешения, MCP-серверы и скилы. Сверяется с первоисточником, готовит правки в стиле uci типизированными инструментами `config_get` / `config_set` и фиксирует их только после вашего подтверждения, так что `config_commit` применяет их и перезагружает на лету за один шаг; `config_rollback` возвращает снимок до фиксации. Никогда не выводит секреты. |
| **`/crossreview`** | Отправляет одно задание на ревью кворуму ревьюеров, которые не видят друг друга, - внешним консольным агентам для кода (Claude Code, Codex, Coddy, Cursor Agent, Devin, OpenCode, Gemini CLI, Qwen Code, Kimi, Koda) и внутренним дочерним агентам `explore` - через встроенный координатор `crossreview`, который собирает все ответы, проверяет каждую находку по коду и сам решает, что исправлять. Первый запуск (а позже `/crossreview:setup`) находит установленные CLI, спрашивает, каких агентов и какие их модели использовать, и сохраняет состав либо для проекта в `.coddy/crossreview.json`, либо для всех проектов в `${CODDY_HOME}/crossreview.json`, где его хранили и прежние версии. Тот же скил ставится в другие агенты из [EvilFreelancer/crossreview](https://github.com/EvilFreelancer/crossreview). |
| **`/rpa-init`** | Набирает контекст по репозиторию - читает код, документацию и тесты, настраивает окружение разработки так, как описано в проекте, запускает тесты и пишет короткий отчёт. Задание не нужно. |
| **`/rpa-feat`** | Добавляет функцию строго по BDD - план, падающие тесты, реализация, зелёные тесты, полный прогон, документация и примеры, в конце линтер. Нужно описание того, что строить. |
| **`/rpa-bugfix`** | Исправляет баг, начиная с теста-воспроизведения, затем само исправление, полный прогон и короткий отчёт. Нужно описание бага - ожидаемое поведение против фактического и как его воспроизвести. |
| **`/rpa-gen-rules`** | Пишет или обновляет правила проекта для агентов Cursor, Claude Code и Codex по тому, что на самом деле есть в репозитории. См. [rules.md](rules.md#генерация-правил). |

Записанные скилы становятся обычными скилами в вашей домашней папке Coddy. Их можно править, отключать через `coddy skills disable <name>`, удалять или обновлять из маркетплейса. Что поставка будет делать и чего не будет, записано в **`${CODDY_HOME}/skills/.bundled.json`** рядом с записанными ею скилами:

- скил, который поставка ещё ни разу не выдавала, записывается;
- удалённый вами скил остаётся удалённым - следующий запуск не записывает его снова;
- копия старше той, что в релизе, **заменяется**, поэтому `coddy update` приносит с собой и более новый скил. Копия, в которой версия не указана вовсе, считается старше (она появилась раньше, чем эти скилы стали нести версию) и тоже заменяется;
- более новая копия остаётся ровно такой, какая есть. Так же сохраняется и ваша правка - поднимите `metadata.version` копии в домашней папке выше версии из релиза, иначе её перезапишет следующий релиз, который поднимет свою;
- копия, которую Coddy не может прочитать (`SKILL.md` за правами доступа, которых у него нет), остаётся нетронутой. Она не отсутствует и не лишена версии, а поставка не судит о том, чего не может открыть.

Если `.bundled.json` есть, но не читается, поставка на этот запуск останавливается и сообщает об этом, а не гадает. Прочитанный как пустая запись, файл говорил бы, что ничего ещё не выдавалось, и поставка вернула бы все удалённые вами скилы. Замена скила переименовывает старую копию в сторону, а новую ставит на её место; если процесс убит между этими шагами, остаётся резервная копия без скила, и следующий запуск возвращает скил.

Домашняя папка, в которую Coddy не может писать (образ только для чтения, ограниченная учётная запись), ошибкой не считается. Вместо записанных копий отвечают копии внутри бинарника, только для чтения, и разницу замечает лишь скил, которому нужны файлы рядом с его `SKILL.md` (`references/` или `scripts/` у `crossreview`). Удалённого вами скила из поставки среди них нет. Запись о выдаче говорит, что он уже выдан, поэтому бинарник не предлагает его снова как скил, который нельзя удалить.

`crossreview` и скилы `rpa-*` живут в собственных репозиториях, чтобы один и тот же скил работал в Claude Code, Codex или Cursor, и копируются в `internal/skills/bundled/` (их `SKILL.md`, `references/` и `scripts/`) командой **`make skills-vendor`**; откуда берётся каждый, указано в `scripts/bundled-skills.json`.

### Маркетплейс в комплекте

**`EvilFreelancer/rpa-skills`**, каталог, из которого публикуются поставляемые скилы `rpa-*`, - это **системный источник**. Он действует так же, как поставляемые скилы, хотя не объявлен ни в одном `marketplaces.json` и ради него не записывается ни один файл, и ему доверяют в любой рабочей папке. Поэтому остальная часть этой коллекции доступна одной командой даже на машине, которую никто не настраивал.

```bash
coddy skills sync                 # install everything the catalogue publishes
coddy plugin marketplace list     # every source in effect, and whether it resolves
```

Это только адрес - Coddy обращается к нему лишь по вашей просьбе. Ни один файл его не объявляет, поэтому и убирать его неоткуда. `coddy plugin marketplace remove` отказывается его удалять (если только он не назван ещё и в одном из ваших файлов `marketplaces.json`, тогда команда убирает из файла эту лишнюю запись и сообщает, что сам маркетплейс остаётся), `DELETE /coddy/skills/sources` отвечает 400, а **Настройки → Навыки → Маркетплейсы** показывают его строку со щитом, на который нельзя нажать, и неактивной кнопкой удаления. Чтобы избавиться от скила, который он публикует, отключите или удалите этот скил (`coddy skills disable <name>`), а не каталог.

`GET /coddy/skills/sources` перечисляет его первым, с `origin: "system"`, и называет его в поле `system`, по которому клиент узнаёт, у каких строк нет кнопки удаления.

![Настройки, Навыки - список маркетплейсов со встроенным источником, вашим источником и источником проекта, который ждёт одобрения](../../assets/skills/skills-marketplaces-dark-1280.png)

*Настройки → Навыки → Маркетплейсы - встроенный `EvilFreelancer/rpa-skills` со щитом постоянного доверия, каталог из вашего собственного файла и источник, который объявляет проект, задержанный, пока щит не одобрит его для этой рабочей папки.*

## Где взять скилы

### skills.sh - реестр сообщества

Открытая экосистема скилов для агентов живёт на **[https://skills.sh](https://skills.sh)**. Скилы там - обычные репозитории GitHub с файлом `SKILL.md`, совместимые со всеми агентами, которые поддерживают этот формат (Cursor, Codex, Claude Code, Coddy и другие).

Ставятся они через **`npx skills`** (нужен Node.js).

```bash
# Search the registry
npx skills find [query]

# Install a skill globally into ~/.agents/skills/
npx skills add <owner/repo@skill>

# Update all installed skills
npx skills update

# Check for updates
npx skills check
```

Глобальные скилы попадают в **`~/.agents/skills/`**, и их видит любой агент, который читает эту папку.

### skillsbd - реестр, который ведут для Coddy

**[https://neuraldeep.ru/skills](https://neuraldeep.ru/skills)** - реестр **skillsbd**, который отбирают специально для Coddy. Установите его CLI.

```bash
npm install -g skillsbd
```

Основные команды.

```bash
# Search the registry
npx skillsbd search [query]

# Install a skill
npx skillsbd install <name>

# List installed skills
npx skillsbd list
```

Скилы из skillsbd по умолчанию тоже ставятся в **`~/.agents/skills/`**, поэтому Coddy подхватывает их автоматически через `skills.dirs` по умолчанию.

Просматривать и ставить скилы можно и в веб-интерфейсе Coddy - в поиске для установки блока **Установленные скилы** в разделе **Настройки → Навыки**.

## Маркетплейсы и источники

Coddy умеет сам, без внешних CLI, скачивать скилы из **репозитория GitHub**, по **git URL** или по **http(s) URL** файла `marketplace.json` [стандарта agents](https://agents.md). Для git-источников он запускает исполняемый файл Git, если тот есть, а иначе встроенный бэкенд go-git; промежуточные файлы загрузки лежат в `${CODDY_HOME}/tmp`, поэтому минимальному образу нужна домашняя папка Coddy с правом записи, но не системный `/tmp`. Что ему разрешено скачивать, объявляется в двух файлах одного формата и никогда в `config.yaml`.

| Файл | Кто пишет | Когда действует |
|------|------------|--------------|
| `${CODDY_HOME}/marketplaces.json` (`~/.coddy/marketplaces.json`) | вы - через `coddy skills add`, `coddy plugin marketplace add`, Настройки → Навыки | сразу, в любой рабочей папке |
| `.coddy/marketplaces.json` проекта | проект, который его коммитит; `coddy skills add --project`, **Этот проект** в настройках | как разрешает `skills.project_trust` ([ниже](#маркетплейсы-проекта-и-доверие)) |

```json
{
  "sources": [
    "artwist-polyakov/polyakov-claude-skills",
    "owner/repo@v1.2",
    "https://github.com/owner/single-skill.git"
  ],
  "marketplaces": [
    { "name": "neuraldeep", "source": "https://neuraldeep.ru/skapi/marketplace.json" }
  ]
}
```

- **Источник** устанавливается целиком. Синхронизация ставит все плагины, которые он публикует (все скилы репозитория без `marketplace.json`), и поддерживает их в актуальном состоянии. Источником служит `owner/repo` на GitHub (с `@ref`, чтобы закрепить ветку или тег), git URL или URL файла `marketplace.json`;
- **Маркетплейс** - это каталог, который запоминается под именем `name` из его `marketplace.json`. `plugin marketplace add` читает его список, плагины из него ставятся по одному через `plugin install <plugin>@<name>`, а обновление затрагивает только их.

Само объявление ничего не скачивает. Скачивают `coddy skills sync`, **Синхронизировать все** (или кнопка синхронизации у маркетплейса) в настройках или `POST /coddy/skills/sync`, а автоматически не скачивается ничего. Всё, что ставит запись, попадает в `${CODDY_HOME}/skills`, какой бы файл её ни объявил, поэтому маркетплейс проекта приносит свои скилы в вашу домашнюю папку Coddy, а не в чекаут. Встроенный [`EvilFreelancer/rpa-skills`](#маркетплейс-в-комплекте) действует наравне с обоими файлами. Запись, объявленная в обоих файлах, считается один раз, как ваша, а имя маркетплейса сохраняет источник, который дал ему ваш файл.

`coddy skills add <src>` объявляет источник в вашем файле, а с `--project` в файле проекта; `coddy plugin marketplace add <src>` добавляет маркетплейс в ваш файл. **Настройки → Навыки → Маркетплейсы** показывают каждую запись рабочей папки сессии с её видом (**все плагины** или **каталог**) и местом объявления (**встроенный**, **ваш**, **из проекта**). Поле добавления объявляет источник в вашем файле или, с **Этот проект** (когда у чата уже есть сессия), в файле проекта, а каждая строка синхронизируется и удаляется отдельно. Удаление строки правит только файл этой строки; `coddy plugin marketplace remove` убирает запись из обоих файлов.

### Маркетплейсы проекта и доверие

Файл проекта приходит вместе с `git clone`, как `.coddy/mcp.json` проекта и его определения субагентов, а запись в нём решает, какой код окажется в вашей домашней папке Coddy. Поэтому он действует только так, как разрешает **`skills.project_trust`**:

- **`ask`** (по умолчанию) - запись показывается с пометкой об ожидании одобрения и не синхронизируется и не предлагается к установке, пока вы не одобрите её для этой рабочей папки командой `coddy plugin marketplace trust <name | source>` в терминале в этой рабочей папке или щитом в её строке в разделе Настройки → Навыки. `coddy plugin marketplace list` и каждая синхронизация называют задержанные записи и команду, которая их одобряет. Одобрение привязано к рабочей папке и к записи (её виду, имени и источнику) и хранится в `${CODDY_HOME}/skills-trust.json`; запись, которую переписал чекаут, требует одобрения снова, а `coddy plugin marketplace untrust <key>` или щит отзывают его. Скилы, которые запись уже установила, остаются, пока вы их не удалите;
- **`allow`** - записи проекта действуют сразу;
- **`deny`** - записи проекта не действуют никогда и показываются как отключённые политикой.

Запись, которую вы сами вносите в проект (`coddy skills add <src> --project`, **Этот проект** в настройках), одобряется для этой рабочей папки в момент записи. `/plugin` в чате одобрить запись не может, ведь писать в чат умеет и модель, поэтому команда вместо этого указывает на терминал и щит.

### Переезд из config.yaml

Прежние версии хранили источники в `config.yaml` под ключом `skills.sources`, а добавленные маркетплейсы в `${CODDY_HOME}/skills/.marketplaces.json`. И то и другое переезжает в `${CODDY_HOME}/marketplaces.json` само:

- когда эта версия впервые загружает `config.yaml`, источники из `skills.sources` дописываются в файл в своём порядке (источник, который там уже есть в любом написании, и встроенный источник не повторяются), а `config.yaml` перезаписывается без ключа; старый файл остаётся рядом как `config.yaml.bak-<timestamp>`, а переезд записывается в лог вместе с тем, что перенесено;
- когда она впервые читает маркетплейсы, те, что помнит `.marketplaces.json`, добавляются в файл, если он ещё не объявляет такое имя или источник. `.marketplaces.json` остаётся и хранит только списки плагинов, которые Coddy прочитал из каждого маркетплейса.

Переезд подчиняется тем же правилам, что и переезд `mcp_servers` ([MCP](mcp.md#переезд-из-configyaml)). Если целевой файл не читается, ничего не переносится, а сохранение оставляет ключ на месте; у ключа внутри flow-отображения (`skills: {sources: [...], ...}`) источники переносятся, а сам ключ остаётся, и удалить его нужно вам; `config.yaml`, прочитанный из рабочей папки, потому что в домашней папке его нет, не перезаписывается и из него ничего не переносится, ведь его источники стали бы вашими. `coddy -t` сообщает об оставшемся в файле ключе `skills.sources` как о перенесённом и даёт ссылку сюда.

### Команда `plugin` (CLI и `/plugin` в чате)

Плагинами и маркетплейсами управляет один набор команд, одинаково доступный как CLI `coddy plugin ...` и как встроенная команда чата `/plugin` (детерминированная слэш-команда, которая выполняется без хода LLM, как `/compact`). Она понимает те же слова, что и Claude Code.

```bash
coddy plugin marketplace add <owner/repo | url>          # add a marketplace: read its plugin list, install nothing
coddy plugin install <plugin>@<marketplace>              # install one plugin of an added marketplace
coddy plugin marketplace update [<marketplace>]          # refresh the list and the plugins installed from it (alias: sync)
coddy plugin marketplace list [<marketplace>]            # marketplaces and sources, or the plugins of one marketplace
coddy plugin marketplace remove <marketplace | source>   # remove a marketplace or a source; installed skills stay
coddy plugin marketplace trust <marketplace | source>    # approve a project entry for this workspace (terminal only)
coddy plugin marketplace untrust <marketplace | source>  # withdraw that approval
coddy plugin install <owner/repo | url>                  # install every skill a source publishes, kept in sync
coddy plugin remove <name>                               # delete an installed skill (bundled = read-only)
coddy plugin enable <name>   |   plugin disable <name>   # toggle a skill
coddy plugin list                                        # installed skills with versions
```

В чате те же слова идут после `/plugin`. Например, установка одного скила из каталога [neuraldeep.ru](https://neuraldeep.ru) выглядит так.

```text
/plugin marketplace add https://neuraldeep.ru/skapi/marketplace.json
/plugin install yandex-wordstat@neuraldeep
```

А в терминале так.

```bash
coddy plugin marketplace add https://neuraldeep.ru/skapi/marketplace.json
coddy plugin install yandex-wordstat@neuraldeep
```

- **`marketplace add`** читает `marketplace.json` маркетплейса и запоминает его под именем `name`, которое тот даёт (выше это `neuraldeep`), вместе со списком публикуемых плагинов, но не ставит ни одного из них. Повторное добавление обновляет этот список и отвечает, что маркетплейс уже добавлен. Источник без `marketplace.json` или с `marketplace.json` без имени добавить нельзя; вместо этого установите его целиком через `plugin install <source>`. Маркетплейс объявляется в вашем `${CODDY_HOME}/marketplaces.json`, а прочитанный список плагинов хранится в `${CODDY_HOME}/skills/.marketplaces.json`;
- **`install <plugin>@<marketplace>`** ставит один плагин действующего маркетплейса, найденного по этому имени, - вашего или объявленного проектом и одобренного вами. Сначала команда заново читает маркетплейс, поэтому плагин, который маркетплейс опубликовал уже после добавления, ставится без обновления. Недобавленный маркетплейс, маркетплейс, который ещё ждёт одобрения, или плагин, которого нет в его списке, дают ошибку с указанием, что запустить;
- **`marketplace update <marketplace>`** заново читает маркетплейс и переустанавливает поставленные из него плагины, а те, что не ставились, так и остаются неустановленными. Команда работает по плагинам, поэтому скил, удалённый через `plugin remove`, возвращается, пока установлен другой скил того же плагина. Без имени она делает это для каждого действующего маркетплейса и синхронизирует каждый источник, то есть делает то же, что `coddy skills sync`;
- **`install <owner/repo | url>`** (без `@`) ставит все скилы, которые публикует источник. Команда объявляет источник в вашем `marketplaces.json`, и каждая синхронизация ставит и обновляет все его плагины. Этот контракт соблюдает каждый источник любого из двух файлов, включая встроенный `EvilFreelancer/rpa-skills`;
- **`marketplace list`** опрашивает каждый действующий маркетплейс и каждый источник и сообщает, где он объявлен и чем оказался - корректным маркетплейсом **valid marketplace** (стандарт agents, с именем, версией и числом плагинов), репозиторием без манифеста **no marketplace.json** (скилы находятся напрямую) или недоступным источником **unreachable**; запись проекта, ожидающая одобрения, показывается с командой одобрения и не опрашивается. С именем команда перечисляет плагины этого маркетплейса и отмечает установленные;
- **`marketplace trust <key>`** одобряет запись проекта для рабочей папки, в которой открыт терминал, и печатает, что именно одобрено: файл, который объявляет запись, адрес, который она читает, и хеш, к которому привязано одобрение. `untrust` отзывает одобрение. В чате обе команды вместо этого отвечают командой, которую нужно запустить.

`marketplace remove <marketplace>` убирает маркетплейс из объявившего его файла, вашего или проектного, а вместе с ним и источник с тем же адресом и его одобрение для проекта; установленные из него скилы остаются до `plugin remove <name>`. `install` и `marketplace add` затрагивают только то, что названо, и недоступность другого источника не приводит к их ошибке.

`plugin marketplace add` только добавляет маркетплейс. Ставьте его плагины по одному через `plugin install <plugin>@<marketplace>` или установите все плагины с постоянной синхронизацией через `plugin install <owner/repo | url>`.

Для самих файлов скилов остаются низкоуровневые команды `coddy skills`.

```bash
coddy skills list                                      # all skills (with a VERSION column)
coddy skills enable <name>  |  disable <name>
coddy skills add <src> [--project]  |  sync  |  remove <name>   # declare a source, fetch, delete
```

Три интерфейса умеют одно и то же, выбирайте удобный:

- **CLI** - `coddy plugin ...` (и `coddy skills ...`);
- **Чат** - команда `/plugin ...`;
- **Веб-интерфейс** - **Настройки → Навыки → Маркетплейсы** (добавить источник в ваш файл или в файл проекта, одобрить запись проекта её щитом, синхронизировать её или **Синхронизировать все**, удалить), проверка версий после каждой синхронизации и кнопка скачивания у скила (в подсказке *Скачать обновление*), если есть более новая версия. Поиск для установки там же предлагает и плагины действующих маркетплейсов.

### Версии и обновления

В `marketplace.json` маркетплейса у каждого плагина может быть указана `version` (семантическая версия), а frontmatter файла `SKILL.md` может нести собственную версию скила в отображении `metadata` формата Agent Skills.

```yaml
---
name: rpa-feat
metadata:
  version: 1.0.1
description: ...
---
```

Ключ `version:` верхнего уровня, который использовали старые скилы, по-прежнему читается; если в файле есть оба, побеждает `metadata.version`. Coddy записывает установленную версию в lock-файл `${CODDY_HOME}/skills/.remote.json` и показывает её в `coddy skills list`, `coddy plugin list`, строках скилов в HTTP API и в настройках веб-интерфейса. `coddy plugin marketplace sync` (или проверка версий, которую интерфейс запускает после каждой синхронизации, за ней стоит `GET /coddy/skills/updates`) заново читает манифест каждого источника и сообщает, у каких скилов в источнике есть более новая версия; кнопка скачивания у скила (в подсказке *Скачать обновление*, или `POST /coddy/skills/{name}/update`) заново синхронизирует источник только этого скила, чтобы её установить. Плагины без версии показываются без неё и никогда не помечаются как требующие обновления (ложных срабатываний нет).

Для плагина, опубликованного [zip-архивом](#плагины-опубликованные-zip-архивами), в записи которого нет `version`, записывается версия, построенная из самого архива, - `sha256:` и первые 12 шестнадцатеричных цифр его SHA-256, поэтому lock-файл меняется при каждом изменении архива. Если запись маркетплейса указывает `sha256` архива, проверка обновлений сравнивает их, и любое изменение считается обновлением (у хеша нет порядка). Запись без того и другого не помечается; `plugin marketplace sync` всё равно скачивает её заново и записывает новую версию.

### Как разрешается источник

1. Сокращения `owner/repo` и git URL клонируются без истории (shallow clone) и обновляются. Coddy использует Git CLI, если он есть, а иначе встроенный бэкенд go-git; URL API скачивается как JSON;
2. Если репозиторий (или ответ API) - **маркетплейс** стандарта agents (`.agents/plugins/marketplace.json` или `.claude-plugin/marketplace.json`), разрешается каждый плагин из его списка:
   - **внешний** источник (`{"source":"github","repo":"owner/repo"}` / `{"source":"url","url":"…","ref":"…"}`) клонируется;
   - источник-**архив** (`{"source":"archive","url":"https://…/plugin.zip","sha256":"…"}`) скачивается и распаковывается без git (см. [ниже](#плагины-опубликованные-zip-архивами));
   - **относительный** источник (`"./plugins/foo"`) читается изнутри репозитория маркетплейса;
3. Если **манифеста нет**, репозиторий напрямую просматривается в поисках `SKILL.md`;
4. Каждая найденная папка скила (корневой `SKILL.md`, `skills/<name>/`, `.claude/skills/<name>/` или `plugins/<p>/skills/<s>/`) копируется вместе с соседними `scripts/`, `references/`, `examples/` в `${CODDY_HOME}/skills/<name>/`, где её подхватывает обычный загрузчик.

Происхождение скилов отслеживается в `${CODDY_HOME}/skills/.remote.json`. Синхронизированные скилы лежат в обычной папке скилов, поэтому `enable`/`disable` работают с ними как с любыми другими; `remove` удаляет копию (повторный `sync` поставит её снова, если не убрать источник и из его `marketplaces.json`).

Для приватных репозиториев используются учётные данные, доступные выбранному бэкенду Git. Окружения без Git поддерживают источники HTTPS и `file://` через go-git; источникам SSH нужен механизм аутентификации, которым go-git может воспользоваться в этом процессе. Маркетплейс по HTTP(S) может называть только внешние URL плагинов по HTTP(S), и они проходят ту же защиту от SSRF, что URL API и архивы плагинов. Локальный или SSH-маркетплейс, который оператор выбрал явно, может разрешать плагины через свой транспорт того же вида, отличный от HTTP.

### Плагины, опубликованные zip-архивами

Маркетплейс может опубликовать плагин zip-архивом вместо git-репозитория, в том формате записи, который читает Claude Code.

```json
{
  "name": "demo",
  "description": "A skill packed by its marketplace",
  "source": {
    "source": "archive",
    "url": "https://example.com/plugins/demo.zip",
    "sha256": "<64 hex digits, optional>"
  }
}
```

Этот путь выбирает только `"source": "archive"`, а источник `url` с адресом на `.zip` по-прежнему клонируется через git. Установка такого плагина (`coddy plugin install https://example.com/marketplace/demo.json`, те же слова после `/plugin` в чате или поиск для установки в настройках) никогда не запускает git:

- **Только https.** Адрес архива и каждый редирект по пути должны быть `https`, и каждый сначала проходит защиту от SSRF, поэтому loopback-адреса, частные, общие (`100.64.0.0/10`) и link-local-адреса, а также эндпоинты метаданных облаков отвергаются до установки соединения;
- **sha256.** Если запись его указывает, он должен состоять из 64 шестнадцатеричных цифр и совпадать со скачанными байтами при каждом скачивании, иначе установка отменяется и ничего не записывается. Если объявленный маркетплейсом sha256 не совпадает с архивом, который он отдаёт, каждая установка этого плагина завершается ошибкой, пока маркетплейс не исправит запись;
- **Пределы.** Не больше 50 МиБ при скачивании, 200 МиБ после распаковки и 10 000 элементов в архиве;
- **Элементы архива.** Элемент с компонентом пути `..`, абсолютным путём или буквой диска, элемент, который служит символической ссылкой, устройством, каналом или сокетом, и файл, встречающийся дважды, отклоняют весь архив; все элементы проверяются до записи первого, и ничего не пишется за пределы временной папки. Папка `__MACOSX`, которую добавляет архиватор macOS, проверяется так же и затем пропускается;
- **Корень плагина и его скилы.** Корень плагина - это верх архива или единственная папка, в которую завёрнуто всё (так GitHub упаковывает репозиторий). Если в корне лежит манифест плагина `.claude-plugin/plugin.json` (или `.codex-plugin/plugin.json`), ставятся только скилы, которые он называет: папки из его поля `skills` (путь или список путей относительно корня, каждый указывает на папку скила или на папку с папками скилов; путь, выходящий за корень, игнорируется), или папки внутри `skills/`, если поле ничего не перечисляет, или, если и в `skills/` нет ни одной папки скила, сам корень плагина, когда в нём есть `SKILL.md`. Такой плагин состоит из одного скила, названного по `name` этого `SKILL.md`, а без него по имени плагина. `SKILL.md` в другом месте плагина, в тестовых данных или примерах, скилом не считается, и скил должен быть папкой, поэтому плоский `skills/<name>.md` скилом не считается. В архиве без манифеста ищется каждый `SKILL.md`, как и в клоне; git-плагин просматривается так же, поэтому находится и его корневой `SKILL.md`;
- **Исполняемые скрипты.** Файл, помеченный в архиве как исполняемый, записывается с правами `0755`, любой другой с `0644`.

Lock-файл записывает адрес архива рядом с маркетплейсом, а версию так, как описано в разделе [Версии и обновления](#версии-и-обновления).

## Расположение папок

![Вкладка "Навыки" в настройках - автообнаружение, дополнительные папки скилов, политика для маркетплейсов проекта, маркетплейсы и установленные скилы](../../assets/screenshot-fullhd-settings-skills.png)

*Вкладка "Навыки" в настройках - автообнаружение, дополнительные папки skills.dirs и политика для маркетплейсов проекта, маркетплейсы вместе со встроенным и установленные скилы, среди них поставляемые*

В каждой рабочей папке читаются четыре папки скилов, что бы ни говорил `config.yaml`, а затем дополнительные папки из `skills.dirs`. Они читаются в порядке таблицы, и **чем ниже папка в списке, тем она сильнее** - скил, имя которого встречается в нескольких папках, берётся из последней из них.

| Порядок | Папка | Что в ней |
|-------|--------|---------------|
| 1 (самая слабая) | `${HOME}/.agents/skills/` | Ваши скилы, общие для всех агентов; сюда ставят `npx skills` и `npx skillsbd` |
| 2 | `.agents/skills/` проекта | Скилы проекта, общие для всех агентов, которые с ним работают |
| 3 | `${CODDY_HOME}/skills/` (по умолчанию `~/.coddy/skills/`) | Собственные скилы Coddy - стандартная поставка, установки из маркетплейсов и плагинов, скилы, установленные из настроек |
| 4 | `.coddy/skills/` проекта | Скилы проекта для Coddy |
| 5 (самая сильная) | каждая запись `skills.dirs` по порядку | Папки, которые вы добавляете сами, например папка команды |

Значит, `.agents/skills` проекта перекрывает ваш `~/.agents/skills`, папки Coddy перекрывают обе папки агентов, `.coddy/skills` проекта перекрывает собственную папку Coddy, а папка из `skills.dirs` перекрывает все четыре. Четыре папки по умолчанию нельзя убрать настройкой - `skills.dirs` только добавляет к ним, а конфигурация без этого ключа читает только эти четыре.

```yaml
skills:
  dirs:
    - "~/my-team-skills"        # read after the four defaults, wins a name over them
    - "${CWD}/tools/skills"     # a folder of the workspace, like a relative "tools/skills"
```

- `${HOME}` и `~` раскрываются в вашу домашнюю папку, а `${CODDY_HOME}` - при загрузке файла конфигурации. `${CWD}` и запись с относительным путём (`.agents/skills`, `tools/skills`) указывают на папку в **рабочей папке сессии**, а не в той, из которой запущен сервер;
- папка, названная дважды (папка по умолчанию, ещё раз указанная в `skills.dirs`, как делали конфигурации, написанные до этой схемы, или проект, открытый в вашей домашней папке, так что `${HOME}/.agents/skills` и `.agents/skills` проекта совпадают), читается один раз, **на последнем своём месте**. Поэтому папка по умолчанию, названная в `skills.dirs`, переезжает ниже папок, перечисленных перед ней. Ссылка на папку, которая уже есть в списке, считается этой же папкой;
- несуществующая папка молча пропускается, поэтому папки по умолчанию ничего не стоят проекту, в котором нет ни `.agents/skills`, ни `.coddy/skills`;
- `coddy skills list` печатает прочитанные папки в этом порядке под заголовком **Search roots:**; Настройки → Навыки показывают каждый скил вместе с файлом, из которого он взят.

Скил может быть символической ссылкой, которая ведёт куда угодно на диске, в том числе за пределы проекта: папка скила, подключённая ссылкой в `.coddy/skills` или `.agents/skills` (`ln -s ~/shared-skills/review .coddy/skills/review`), отдельный файл скила `.md`, подключённый так же, `SKILL.md`, который сам служит ссылкой, или целая папка скилов (`.agents/skills`, `.coddy/skills`, `~/.agents/skills`) в виде ссылки на папку со скилами. Любая из этих форм попадает в список, вызывается через `/name` и предлагается `load_skill`; модель получает папку скила по пути через ссылку (`Skill directory: <project>/.coddy/skills/review`), поэтому файлы, которые называет скил (`scripts/`, `references/`), читаются и запускаются оттуда. Ссылка, которая никуда не ведёт, пропускается. Удаление такого скила в разделе Настройки → Навыки убирает ссылку и не трогает то, на что она указывает; если ссылкой служит вся папка скилов, удаляется папка скила внутри неё, как в любой папке.

`${CWD}` разрешает сессия, а не процесс. Сервер `coddy serve`, запущенный из любой папки (например, пользовательский сервис, запущенный из `$HOME`), отдаёт локальные скилы проекта каждой сессии, рабочая папка которой - этот проект. Папку выбирают при создании сессии (выбор рабочей папки в поле ввода, `POST /coddy/sessions/{id}/workspace` или `session/new` по ACP с `cwd`). Когда в диалоге появились сообщения, рабочая папка фиксируется, поэтому идущий чат сохраняет скилы той папки, в которой начался. `GET /coddy/slash-commands` и `GET /coddy/skills` получают сессию через **`X-Coddy-Session-ID`**; без него они описывают папку из параметра запроса **`cwd`**, а без обоих - рабочую папку сервера по умолчанию, которую `coddy skills list` и печатает для папки, где его запустили.

У нового чата в веб-интерфейсе нет сессии до первого сообщения, поэтому папка, выбранная на стартовом экране, передаётся в этих запросах параметром **`cwd`**. Если выбрать `data` и набрать `/`, рядом с глобальными скилами сразу появятся скилы проекта из `data/.agents/skills` и `data/.coddy/skills`; если выбрать папку без них, они уйдут из меню, а `/name` из другой рабочей папки перестанет выделяться как скил в поле ввода и в сообщениях транскрипта. Настройки → Навыки показывают скилы проекта той же папки, а после отправки первого сообщения сессия создаётся в ней, поэтому ход загружает те же скилы.

## Поддерживаемые форматы файлов

### `subdir/SKILL.md` (рекомендуется)

Один скил на папку. Этот формат совместим со стандартной раскладкой скилов агентов и с `npx skills`.

```
~/.agents/skills/
  code-review/
    SKILL.md
  docker-helper/
    SKILL.md
```

### Корневые `.md` / `.mdc` в папке скилов

Плоские файлы в корне папки из `skills.dirs` тоже регистрируются как скилы (имя файла без расширения становится именем слэш-команды).

### YAML frontmatter

В каждом файле скила должен быть блок frontmatter ровно с двумя полями, оба обязательны и не должны быть пустыми.

```markdown
---
name: code-review
description: One-line summary shown in the slash-command catalog and UI.
---

# Code Review

Full skill body here...
```

`name` задаёт каноничный идентификатор слэш-команды (например, `/code-review`) и, если задан, перекрывает имя, выведенное из файловой системы. `description` показывается в каталоге и на панели Настройки → Навыки.

Два необязательных поля выбирают, на чём работает скил. `model` называет id настроенной модели, а `reasoning` (псевдоним `effort`) - уровень рассуждения, который эта модель предлагает, `off` или `default`. Когда скил вызывают, через `/code-review` в промпте или через `load_skill` со стороны модели, они действуют до конца этого хода, а со следующим ходом возвращаются собственные настройки сессии ([Настройки сессии](session-settings.md#смена-модели-по-просьбе)).

```markdown
---
name: code-review
description: Review the pending change for correctness.
model: rpa/qwen3.8-27b
reasoning: high
---
```

## Включение и отключение без удаления

```bash
coddy skills list              # show all skills with enabled/disabled status
coddy skills disable <name>    # skip a skill without removing it
coddy skills enable <name>     # re-enable
```

Состояние отключения хранится в `~/.coddy/skills/.disabled` (обычный текст, одно имя на строку).

## Свой скил

Создайте папку в любом месте и добавьте в неё `SKILL.md`.

```markdown
---
name: my-skill
description: Short description shown in the catalog.
---

# My skill

Instructions the agent will follow when this skill is active.
```

Затем положите эту папку в одну из папок по умолчанию (`~/.agents/skills/`, `.agents/skills/` проекта, `~/.coddy/skills/`, `.coddy/skills/` проекта) или добавьте её родительскую папку в `skills.dirs` в `config.yaml`.

В работающей агентной сессии фиксация изменения `skills.dirs` или `skills.auto_discovery` через инструменты поэтапной правки конфигурации (`config_set` + `config_commit`) сразу перестраивает каталог скилов. Внешний установщик вроде `coddy plugin install` или `npx skills add` меняет файлы на диске, поэтому после него сделайте идемпотентную фиксацию `set skills.dirs=[...]`, чтобы обновить работающий загрузчик. Одно лишь объявление источника в `marketplaces.json` ничего не скачивает и не ставит.

Чтобы поделиться скилом, опубликуйте его на GitHub и добавьте на [skills.sh](https://skills.sh) или отправьте в [neuraldeep.ru/skills](https://neuraldeep.ru/skills).

## Когда читаются скилы

Сессия читает свои скилы с диска при старте (первая сессия консоли, `session/new` или `session/load` по ACP, новый чат в веб-интерфейсе), при смене рабочей папки и при перезагрузке конфигурации; по сети для этого ничего не читается.

- **Читается при старте, вместе с телами** - каждый `SKILL.md` (и корневой файл скила `.md` / `.mdc`) из папок, которые читаются для рабочей папки ([Расположение папок](#расположение-папок)), примерно 0,1 мс на скил, поэтому тысяча установленных скилов добавляет около 100 мс к первому кадру консоли; скилы, встроенные в бинарник, хранятся в памяти;
- **Никогда не читается при старте** - источники и маркетплейсы файлов `marketplaces.json`. Манифест или репозиторий источника скачивается только по запросу - `coddy skills sync`, `coddy plugin marketplace sync` и `/plugin`, Настройки → Навыки (**Синхронизировать все**, поиск для установки, кнопка скачивания у скила), `GET /coddy/skills/updates`, - поэтому большой маркетплейс или источник, который не отвечает, никогда не задерживает сессию.

Задержать старт могут настроенные MCP-серверы; консоль подключает их после первого кадра ([MCP-серверы](mcp.md#жизненный-цикл-mcp-сервера)).

## Как применяются скилы

На каждый `session/prompt` агент:

1. Использует скилы, которые сессия прочитала из папок своей рабочей папки ([Когда читаются скилы](#когда-читаются-скилы));
2. Все загруженные (и включённые) скилы всегда активны - их тела доступны как слэш-команды и подставляются по запросу;
3. Строит блок системного промпта **`{{.Skills}}`** - каталог слэш-команд со всеми скилами и полное тело каждого всегда активного или подходящего по glob скила, имени которого в каталоге **ещё нет**;
4. Ищет вызовы `/name` в тексте, который набрал пользователь, и **дописывает тело каждого найденного скила к сообщению пользователя** элементом `<coddy_attachment path="skill:name" kind="skill">` после набранного текста. Сообщение попадает в **историю сессии вместе с телом**, поэтому следующие ходы воспроизводят те же байты. Кэшированный префикс у провайдера сохраняется, а модель помнит полученные инструкции, пока сжатие контекста не свернёт сообщение в сводку ([Упоминания и кэш промпта](mentions.md#упоминания-и-кэш-промпта)). Транскрипт показывает сообщение в набранном виде, потому что веб-интерфейс отбрасывает элементы `kind="skill"`, и так же поступает воспроизведение истории, которое получают заново открытая консоль или ACP-редактор. Дополнительное сообщение, поставленное в очередь во время хода, получает тела своих скилов так же.

Тело, которое модель загружает сама инструментом `load_skill` (он предлагается, пока включён `skills.auto_discovery`), возвращается как результат этого вызова и остаётся в истории сессии, как любой другой результат инструмента.

В обоих случаях скил, который лежит на диске папкой, приходит с одной строкой в начале, `Skill directory: <path>`, где указана папка, из которой прочитан его `SKILL.md`. Скил называет свои файлы (`scripts/`, `references/`) относительными путями, и без этой строки модели пришлось бы искать их по диску. Скил стандартной поставки, прочитанный из бинарника (когда Coddy не может писать в домашнюю папку), указывает на копию, которую поставка записала в `${CODDY_HOME}/skills`, если такая есть; если такой копии на диске нет, строки тоже нет.

ACP-клиенты получают `available_commands_update` после `session/new` и `session/load`. Веб-интерфейс запрашивает `GET /coddy/slash-commands` для автодополнения.
