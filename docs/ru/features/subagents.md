# Субагенты

Долгое исследование или параллельная раздача работы (проверить три модуля, прогнать матрицу тестов по пакетам, изучить четыре библиотеки) забивает тот единственный диалог, за которым следит оператор. **Субагент** - дочерний агент со своим окном контекста, своим бандлом сессии и промптом роли, который оператор написал в markdown-файле. Родитель передаёт ему самодостаточную задачу, продолжает работать и получает обратно только итоговый отчёт дочернего агента.

Запуск субагента - это **задача в пуле фоновых задач** (`docs/features/background-tasks.md`). Ни планирование, ни тайм-ауты, ни панель задач, ни REST-интерфейс, ни сворачивание при остановке, ни хранение в `<session>/background/<task_id>/` не устроены для субагентов по-особому; новое здесь - второй вид задачи (`kind: agent`), дочерняя сессия за ней и инструмент, который её запускает.

## Когда модель делегирует

Сессия, которой разрешено запускать субагентов, получает в системном промпте раздел `## Subagents`. В нём сказано, что делает `spawn_agent`, когда делегирование окупается (работа, которая затопила бы контекст, или независимые части, которые можно выполнять параллельно с `background: true`), как собирать результаты отсоединённых запусков, и приведён каталог определений, которые сессия может использовать. Инструкция прямо говорит, что задачу в один шаг модель выполняет сама и что новый дочерний агент начинает с **пустым контекстом** - промпт должен нести всё, потому что дочерний агент не видит ничего из диалога родителя. Исключение - продолженный дочерний агент. Он сохраняет собственный транскрипт, поэтому его промпт говорит только, что делать дальше ([Продолжение запуска](#продолжение-запуска)). Обратно приходит только последнее сообщение дочернего агента, и пользователь его не видит, поэтому родителю велено пересказать важное в собственном ответе.

Раздел выводится в режимах `agent` и `plan` (агент в режиме "План" раздаёт исследование так же, как Explore в Claude Code; дочерний агент родителя в режиме "План" принудительно получает тот же режим) и никогда в режиме `ask`, который только читает и ничего не делегирует. Раздела нет, а инструмент скрыт у сессии, которая не может запускать субагентов, то есть когда функция выключена, у интерфейса нет менеджера сессий, ход идёт в режиме `ask` или сессия уже находится на глубине `subagents.max_depth`. Исключение - сессия, чьё собственное определение объявило список разрешённых `spawns`. Она сохраняет инструмент, а каталог сужается до перечисленных имён ([Глубина](#как-сужаются-возможности)).

## Хуки вокруг дочернего агента

Хуки оператора (`docs/features/hooks.md`) действуют и в дочерних агентах. `SubagentStart` срабатывает в родителе перед стартом дочернего агента (хук может отказать в запуске или передать дочернему агенту контекст, который добавляется перед его задачей), а `SubagentStop` срабатывает в родителе, когда ход дочернего агента закончился, и получает его исход и отчёт. Внутри дочернего агента все обычные события срабатывают для его собственного хода, а полезная нагрузка несёт блок `subagent` с именем дочернего агента, его родительской сессией и глубиной, так что хук может обрабатывать делегированную работу по-другому.

## Файлы определений

### Каталоги и приоритет

Определения ищутся в четырёх каталогах по умолчанию, которые читаются всегда, от низшего приоритета к высшему, а затем в дополнительных каталогах из `subagents.dirs`; более поздний каталог заменяет более ранний **по имени**:

1. `${HOME}/.agents/agents` - пользовательская область, папка в домашнем каталоге пользователя, общая для разных агентов;
2. `${CWD}/.agents/agents` - проектная область, общая папка внутри рабочей папки;
3. `${CODDY_HOME}/agents` - пользовательская область, собственные файлы Coddy оператора;
4. `${CWD}/.coddy/agents` - проектная область, файлы Coddy рабочей папки;
5. каждый элемент `subagents.dirs` по порядку, после каталогов по умолчанию, и при совпадении имени он побеждает их (по умолчанию список пуст).

Цепочка та же, что у скилов ([Скилы](skills.md#расположение-папок)), - `.claude/agents` от Claude Code не читается, пока его не назовёт `subagents.dirs` (`"${CWD}/.claude/agents"`; frontmatter таких файлов загружается без изменений). Каталог, названный дважды, читается один раз, на последнем своём месте. `${HOME}`, `${CODDY_HOME}`, `${CWD}` и начальная `~` раскрываются; относительный путь разрешается от cwd сессии. Три встроенных определения стоят ниже всех каталогов, поэтому пользовательский файл с тем же именем заменяет встроенное.

Область определяется по **каноническим путям**. Раскрытый каталог и cwd сессии проходят ту же нормализацию, что и в хранилище доверия MCP (абсолютный путь, разрешённые симлинки, очистка). Каталог, совпадающий с каноническим cwd или лежащий внутри него, относится к **проектной области** и подчиняется `subagents.project_trust` (ниже); всё остальное - **пользовательская область**. Поэтому рабочая папка, в которую попали через симлинк, всё равно владеет своим `.coddy/agents`.

Внутри одного каталога каждый файл `*.md`, включая вложенные, - одно определение; файлы и каталоги, имя которых начинается с точки, пропускаются. Принимается и `<dir>/<name>/AGENT.md`, причём имя по умолчанию он берёт у **каталога**, а не у основы имени `AGENT`. Файлы обходятся в лексическом порядке, и имя достаётся первому файлу, который его заявил; дубликат пропускается с предупреждением в логе, как и файл без frontmatter, без `description`, с недопустимым именем, режимом или режимом разрешений либо больше предельного размера.

### Frontmatter

Обязателен только `description`. `name` по умолчанию берётся из имени файла без расширения (или из имени каталога для `AGENT.md`) в нижнем регистре. Неизвестные ключи игнорируются, поэтому файлы, написанные для других агентов, загружаются.

| Поле | Псевдонимы | Значение |
|---|---|---|
| `name` | | Идентификатор вида `[a-z0-9][a-z0-9_-]*`; именно его модель передаёт в `spawn_agent`. |
| `description` | | Одна строка, которую видит родительская модель, чтобы выбрать агента; в каталоге обрезается до 200 символов. |
| `model` | | Идентификатор `models[].model` для дочернего агента. При неизвестном идентификаторе используется модель родителя, в логе агента появляется предупреждение, а в логе вывода задачи - заметка. |
| `reasoning` | `effort` | Уровень рассуждения, который предлагает модель дочернего агента, `off` или `default`. Если модель такого уровня не предлагает, используется её уровень по умолчанию, а в логе агента появляется предупреждение. |
| `mode` | | `agent` или `plan`. Пустое значение наследует режим родителя; родитель, который только читает (`plan`, а также `ask`, если запуск когда-нибудь будет сделан оттуда), всегда навязывает свой режим. Режим родителя - тот, в котором начался его ход, а не текущий режим сессии, поэтому смена режима посреди хода не может расширить права дочернего агента. |
| `tools` | | Список разрешённых, YAML-список или строка через запятую (`tools: read, grep`). Элементы - точные имена инструментов, одиночная `*` или шаблон `prefix*`, так что `context7__*` пропускает все инструменты одного MCP-сервера. Пустое значение означает всё, что есть у родителя. |
| `disallowed_tools` | `disallowedTools` | Список запрещённых с тем же синтаксисом; приоритетнее `tools`. |
| `permission_mode` | `permissionMode` | `ask`, `accept_edits` или `bypass`. Принимаются написания Claude Code (`default` и `prompt` для `ask`, `acceptEdits` / `accept-edits`, `bypassPermissions` / `bypass-permissions` / `dontask`). Поле может только **сузить** действующий режим родителя. |
| `max_turns` | `maxTurns` | Предел раундов ReAct дочернего агента. `0` означает `subagents.max_turns`, затем `agent.max_turns`. |
| `timeout_seconds` | | Собственный жёсткий предел определения на один запуск (порядок выбора тайм-аута см. ниже). |
| `background` | | `true` принудительно делает запуск отсоединённым, даже если модель просила запуск на переднем плане. |
| `hidden` | | Убирает определение из каталога для модели и из списков "unknown agent". Его всё равно можно запустить по имени, а список в CLI и каталог HTTP показывают его с флагом `hidden`. |
| `spawns` | | Список разрешённых запусков, YAML-список или строка через запятую из имён субагентов в синтаксисе шаблонов `tools` (`explore`, `peer-*`, `*`). Непустой список делает две вещи - дочерний агент может делегировать только совпадающим именам и может делать это на один уровень глубже `subagents.max_depth`, так что оркестратор на пределе всё равно запускает своих ревьюеров. Учитывается только для областей `builtin` и `user`. В проектном файле `spawns` разбирается и показывается в каталоге, но среда выполнения его игнорирует, так что определение из репозитория не может ослабить защиту глубины. |

### Тело задаёт роль

Всё после frontmatter - блок роли дочернего агента. Системный промпт дочернего агента начинается с фиксированной преамбулы (`## Your role as a subagent` - вы субагент *name*, родитель запустил вас для одной самодостаточной задачи, вы не видите ничего из диалога родителя, вы не можете задавать вопросы пользователю, до родителя доходит только ваше последнее сообщение, поэтому закончите кратким отчётом), за которой дословно идёт тело. Остальная часть промпта - обычный шаблон агента или плана, поэтому скилы, правила и блок окружения на месте, как в любой сессии.

Минимальное определение.

```markdown
---
name: reviewer
description: Reviews a diff or a module for defects and reports findings with file paths and lines.
tools: read, glob, grep, print_tree, run_command
permission_mode: ask
max_turns: 20
---
You review code. Read before you judge, cite `path:line` for every finding,
separate defects from style remarks, and end with a short verdict.
```

### Ограничения

Загрузчик и инструмент не дают дереву определений затопить промпт. Из каталога читается не больше **200** определений (остальные пропускаются с предупреждением), файл больше **256 КиБ** пропускается, тело роли больше **64 КиБ** обрезается с пометкой, `description` обрезается до **200** символов, а `prompt` для `spawn_agent` больше **32 КиБ** отклоняется. Метка задачи - `agent <name>: <description>`, где `description` - собственный аргумент вызова, а если его нет, первая строка промпта; вся метка ограничена **60** символами, как метки команд в пуле.

Каждое загруженное определение - **неизменяемое значение**, которое несёт свою область, свой путь и **дайджест** SHA-256 байтов файла. Файл читается один раз; доверие, набор инструментов и роль определяются по этому же значению, а не по повторному чтению.

## Встроенные определения

Три определения встроены в бинарник, чтобы делегирование работало ещё до того, как оператор напишет свой файл. Все они перечисляются с областью `builtin` и путём `(embedded)`.

- **`general`** - исполнитель общего назначения с **набором инструментов родителя** (без собственного ограничения `tools`) для многошаговых задач, исследований или независимых частей работы, которые можно выполнять параллельно. Роль велит ему читать, прежде чем что-либо менять, вносить минимальные правки, проверять результат, когда этого требует задача, никогда не повторять запрос разрешения, которое оператор не дал, и докладывать, что сделано и что родителю ещё предстоит решить;
- **`explore`** - исследователь с доступом только на чтение, который находит файлы, символы и места использования и собирает факты до того, как будут предложены изменения. Его список инструментов - ровно `read`, `keep_result`, `glob`, `grep`, `print_tree`, `websearch`, `webfetch`, `load_skill`, `coddy_docs_search`, `coddy_docs_read`, `background_list`, `background_output`, `background_wait`, то есть без `run_command`, без записи и без инструментов MCP. Один режим "План" не дал бы доступа только на чтение (в нём остаётся shell), поэтому список выписан явно. В этом наборе нет ни одного инструмента MCP, поэтому дочерний агент `explore` никогда не подключается к MCP-серверу;
- **`crossreview`** - скрытый (`hidden`) оркестратор, который отправляет один бриф на ревью внешним CLI агентов для кода (фоновые задачи `run_command`) и внутренним дочерним агентам `explore`, не даёт им видеть ответы друг друга, ждёт все ответы, сверяет каждую находку с кодом и сам решает, что исправить, что не стоит исправлять и что отклонить; его отчёт - последнее слово, которое передаёт родитель. Ради него и существует `spawns`. Его определение объявляет `spawns: [explore]`, поэтому он сохраняет `spawn_agent` на пределе глубины и делегирует ровно одному виду ревьюеров. Сессия доходит до него через встроенный скил `/crossreview`, который берёт на себя обнаружение CLI, вопросы об агентах и моделях, состав ревьюеров и бриф.

## Области и доверие к проекту

Определение, пришедшее с чекаутом, управляет инструментами дочернего агента, а проверка разрешений покрывает не всё, что дочерний агент может сделать. `websearch` и `webfetch` никого не спрашивают, вызовы MCP идут мимо запроса разрешения, а модель может делегировать по своей инициативе, потому что её к этому приглашает `description`. Поэтому определению **проектной области** доверяют так же, как проектному объявлению MCP, - по расписке, выданной вне диалога и привязанной к рабочей папке и содержимому файла, а не по запросу в чате (при `permission_mode: bypass` любой отправитель запросов в коде одобряет их автоматически, так что запрос мог бы оказаться одобрен без участия человека).

`subagents.project_trust` принимает те же значения, что и `mcp.project_trust`:

- **`deny`** - каталоги проектной области вообще не читаются. Поиск агентов, `coddy agents list` и каталог HTTP их пропускают; тест подтверждает, что файлы остаются непрочитанными;
- **`ask`** (по умолчанию) - определения проектной области загружаются и перечисляются как `needs_approval`, пока не появится расписка для `(canonical workspace, name, digest)`. Запуск такого определения без расписки **отклоняется** средой выполнения, и решение принимается по уже найденному определению. Результат инструмента сообщает, что определение взято из проектного файла, не одобренного для этой рабочей папки, и называет способы его одобрить, так что модель может сказать об этом оператору и повторить попытку позже. Блок каталога в промпте перечисляет такую запись **только по имени** с фиксированной пометкой, что она ждёт одобрения и как её одобрить; описание файла не показывается, пока нет расписки, поэтому недоверенный чекаут не может вставить в системный промпт родителя ни одной своей строки. Описания одобренных определений и определений пользовательской области перед выводом сводятся к одной строке;
- **`allow`** - определения проектной области ведут себя как пользовательские.

Встроенные определения и файлы пользовательской области всегда `trusted`. В любой области `permission_mode`, `tools` и `disallowed_tools` только сужают возможности родителя, `spawns` для проектной области игнорируется, а своих хуков, команд и объявлений MCP определение не несёт, поэтому ничто в нём не запускает процесс при загрузке.

Расписки хранятся в **`~/.coddy/subagents-trust.json`** (`<home>/subagents-trust.json`), рядом с `mcp-trust.json`, но в отдельном файле, поэтому одобрение MCP никогда не прочитается как одобрение агента, и наоборот.

```json
{
  "version": 1,
  "workspaces": {
    "/home/me/project": [
      { "name": "reviewer", "digest": "3f2a…", "path": "/home/me/project/.coddy/agents/reviewer.md", "approved_at": "2026-09-03T10:15:00Z" }
    ]
  }
}
```

Если переписать одобренный файл, его дайджест меняется и расписка перестаёт совпадать, поэтому следующий запуск снова отклоняется, пока файл не одобрят заново. Одобрение имени заменяет любую прежнюю расписку на это имя в этой рабочей папке. Хранилище перечитывает файл при каждом решении, поэтому одобрение, выданное из терминала, доходит до работающего агента при следующем запуске без перезапуска.

Где одобрять:

- **CLI** - `coddy agents list [--cwd DIR]` выводит рабочую папку, действующую политику и каталог с областью, состоянием доверия и флагами, а если проектные определения ждут одобрения, добавляет подсказку; `coddy agents trust <name> [--cwd DIR]` сначала выводит действующее объявление (файл, модель, режим, режим разрешений, списки инструментов, дайджест, путь к расписке), а затем записывает расписку на файл в том виде, в каком он лежит на диске сейчас; `coddy agents untrust <name> [--cwd DIR]` отзывает её. Встроенному имени или имени из пользовательской области одобрение не нужно, и команда об этом сообщает. `--cwd` по умолчанию - рабочий каталог процесса, разрешается так же, как в `coddy mcp`;
- **HTTP** (`coddy serve`) - `GET /coddy/subagents?cwd=<dir>` возвращает каталог; `POST /coddy/subagents/{name}/trust` и `POST /coddy/subagents/{name}/untrust` с телом `{"cwd": "<dir>"}` записывают и удаляют расписки. `cwd` должен быть абсолютным и по умолчанию равен рабочему каталогу самого сервера; тело запроса на одобрение может добавить `digest`, который показал каталог, и файл, переписанный с тех пор, отклоняется с кодом 409, а не одобряется вслепую. Строки каталога содержат `scope`, `trust` (`trusted` / `needs_approval`), булевы `trusted` и `needs_approval`, `digest`, `path`, `builtin`, `hidden` и ограничения, которые объявляет определение (`tools`, `disallowed_tools`, `permission_mode`, `timeout_seconds`, `max_turns`, `background`, `spawns` и `role_bytes`, размер тела роли), чтобы клиент мог показать, что объявляет определение. Ограничения, которого файл не объявляет, в строке нет, и это значит, что оно наследуется; само тело роли сервер никогда не отдаёт. Ошибки приходят как JSON `{"error":{"message"}}`. Подробности в `docs/reference/http-api.md`;
- вкладка **Настройки → Субагенты** в веб-интерфейсе перечисляет определения и одобряет их. Она начинается с переключателя `subagents.enable`, затем идут **Каталоги определений** и остальная форма конфигурации `subagents` в отдельном блоке **Настройки субагентов**, а под ними каталог рабочей папки сессии, открытой на экране (`spawn_agent` ищет определения от собственного cwd сессии, поэтому показана именно эта рабочая папка). У каждого определения видны имя, значок области, описание простым текстом и файл; шеврон перед именем раскрывает то, что объявляет определение, - модель, режим, режим разрешений, списки инструментов, тайм-аут, предел ходов, всегда ли оно запускается отсоединённым и размер его инструкций (ограничение, которое файл не задаёт, показано как унаследованное). При `ask` у проектного определения есть щит, как на вкладке MCP. Нажатие на него записывает расписку на файл, показанный в строке (дайджест уходит вместе с запросом, поэтому файл, переписанный в промежутке, отклоняется), а повторное нажатие отзывает расписку. Определение, которое ещё ждёт расписки, вдобавок несёт янтарный значок **нужно одобрение**, подсказка которого называет щит и `coddy agents trust <name>`;
- **Политика** - чекаут, которому вы уже доверяете, может запускать свои определения без расписок, если задать `subagents.project_trust: allow` в `config.yaml`, на вкладке **Настройки → Субагенты** веб-интерфейса (раздел конфигурации `subagents` с политикой и ограничениями пула) или через встроенный скил `configure-coddy`, который описывает этот ключ, чтобы агент мог подготовить `set subagents.project_trust=allow` и зафиксировать его обычным коммитом конфигурации, который проходит проверку разрешений. Политика применяется при сохранении формы.

## Инструмент `spawn_agent`

| Аргумент | Значение |
|---|---|
| `agent` | Имя определения (обязательный). |
| `prompt` | Задача, самодостаточная - цель, нужные пути, ограничения и что должно быть в отчёте (обязательный, не больше 32 КиБ). |
| `description` | Три-пять слов, которые называют задачу; становится меткой задачи и заголовком дочерней сессии. |
| `background` | Сразу вернуть идентификатор задачи, не дожидаясь отчёта. По умолчанию `false`. Определение с `background: true` включает его принудительно. |
| `expected_seconds` | Собственная оценка модели; управляет тикером статуса, а если тайм-аут не задан, то и жёстким тайм-аутом, с той же рекомендательной семантикой, что у фонового `run_command`. |
| `timeout_seconds` | Жёсткий предел для запуска. |
| `model` | Настроенный идентификатор модели для дочернего агента, приоритетнее `model` определения и модели родителя. Идентификатор, которого конфигурация не знает, отклоняется со списком настроенных. |
| `reasoning` | Уровень рассуждения дочернего агента - уровень, который предлагает его модель, `off` или `default`; приоритетнее `reasoning` определения. Уровень, которого модель не предлагает, отклоняется. |
| `notify_on_finish` | Для фонового запуска - разбудить родителя с исходом, когда дочерний агент закончит; по умолчанию включено там, где есть кому будить, а чтобы выключить, задайте явное `false` ([Фоновые задачи](background-tasks.md)). Принудительно **выключено** для запуска на переднем плане, чей отчёт и так возвращается в результате инструмента, и для любого запуска, сделанного дочерним агентом. |
| `resume` | Продолжить завершённый запуск этой сессии вместо нового дочернего агента - его идентификатор задачи (`bg_…`) или идентификатор дочерней сессии (`sess_…`) из более раннего результата. Дочерний агент сохраняет транскрипт и получает `prompt` как следующее сообщение; `agent` должен называть того же субагента ([Продолжение запуска](#продолжение-запуска)). |

Инструмент регистрируется, когда включён `subagents.enable`, и предлагается в режимах `agent` и `plan`, но никогда в режиме `ask`. **Собственного запроса разрешения** ему не нужно. Запуск дочернего агента сам по себе ничего не меняет, каждый вызов инструмента дочерним агентом проходит проверку отдельно, а доверие к проекту решается внутри хука среды выполнения до того, как что-либо стартует.

Запуск **на переднем плане** (по умолчанию) блокирует вызов инструмента, пока ход дочернего агента не закончится, и возвращает отчёт в конверте.

```
<subagent task="bg_3" session="sess_9f1c…" agent="explore" status="succeeded" turns="4">
<![CDATA[
…the child's last assistant message…
]]>
</subagent>
The user did not see this report: restate what matters in your own reply. The full transcript is session sess_9f1c… (Tasks panel → Show transcript).
```

`status` - вердикт пула по задаче (`succeeded`, `failed`, `timed_out`, `stopped`); если он отличается от `succeeded`, отдельная строка говорит об этом и велит модели относиться к отчёту соответственно, а у запуска, закончившегося ошибкой, она названа. Дочерний агент, который дошёл до `max_turns` или не выдал последнего сообщения, получает `failed` с этой причиной, даже если его ход вернулся без ошибки; текст, который он написал по пути к `max_turns`, возвращается как отчёт, а причина говорит, что это не вывод. `turns` - число раундов ассистента, которые этот запуск записал в транскрипт дочернего агента (продолженный запуск считает только свои). Отчёт обёрнут в CDATA, поэтому ничто написанное дочерним агентом не сломает конверт.

**Фоновый** запуск возвращается сразу.

```
Started subagent explore as background task bg_3 (child session sess_9f1c…).
Hard timeout 30m.
You will be woken with the outcome when it finishes, so you can end your turn now.
```

Последняя строка выводится по умолчанию там, где родителя есть кому разбудить. `coddy -p` не запускает механизм пробуждения, а транскрипт дочернего агента закрывается вместе с его ходом, поэтому там строка говорит, что модель никто не разбудит, и задача не записывает пробуждения ([Фоновые задачи](background-tasks.md#какой-процесс-будит-агента)). Явное `notify_on_finish: false` тоже оставляет задачу без пробуждения. Дальше запуск - обычная задача. `background_list` показывает её, `background_output` передаёт лог прогресса дочернего агента, `background_wait` ждёт её и возвращает лог, который заканчивается блоком отчёта, а `background_stop` останавливает дочернего агента. Если забрать готовый отчёт или остановить задачу, лишнего пробуждения не будет.

Отказы возвращаются как ошибки инструмента, которые называют сработавшую настройку. Это неизвестное имя (со списком видимых определений), имя вне списка `spawns` запускающего определения (с этим списком), проектный файл без расписки (с командами одобрения), достигнутый `subagents.max_depth`, промпт больше 32 КиБ, уже идущие `subagents.max_concurrent` запусков, собственный предел пула на сессию (`tools.background.max_concurrent`) и сворачивание пула перед остановкой. При `subagents.enable: false` инструмент вообще не регистрируется. Интерфейсу без менеджера сессий инструмент не предлагается, а если вызов всё же придёт, ответ скажет, что субагенты в этой сессии недоступны.

## Как сужаются возможности

Всё, что разрешено дочернему агенту, выводится из прав родителя в момент запуска и может только сужаться.

- **Режим.** Родитель, который только читает (`plan`, `ask`), всегда порождает дочернего агента в своём режиме. В остальных случаях действует `mode` определения, а если оно пустое, режим родителя. Режим родителя - тот, в котором был принят запускающий ход; `session/set_mode`, пришедший во время хода, не меняет ни режим дочернего агента, ни набор инструментов родителя, с которым пересекается набор дочернего;
- **Режим разрешений никогда не расширяется.** Дочерний агент работает с более строгим из двух режимов - действующего режима родителя и запрошенного определением - по шкале `ask` < `accept_edits` < `bypass`. Определение, которое просит `bypass` у родителя с `ask`, получает `ask`; пустой запрос наследует режим;
- **Пересечение наборов инструментов.** Действующий набор дочернего агента вычисляется один раз при запуске. Это собственный доступный набор родителя (набор его режима, а если родитель сам дочерний, его действующий набор), пересечённый с набором режима дочернего агента и со списком разрешённых определения, минус список запрещённых определения и минус обязательные исключения. Имена инструментов MCP входят в набор и сопоставляются по точному имени или по `prefix*`, поэтому дочерний агент видит MCP-сервер, только если он был у родителя и определение его пропускает;
- **Обязательные исключения.** `question` (дочерний агент не может спросить пользователя; `RequestQuestion` всегда отказывает), `config_set`, `config_changes`, `config_commit`, `config_revert`, `config_rollback` (дочерний агент не может переписать конфигурацию самого агента), `plan_exit` (дочерний агент не может выйти из режима "План" за оператора) и `spawn_agent` для дочернего агента на пределе глубины;
- **Двойная проверка.** Описания инструментов, которые видит модель дочернего агента, отфильтрованы по набору, а каждый вызов проверяется ещё раз до проверки разрешений, вызовы MCP тоже. Выдуманный или повторённый `run_command` получает ответ `tool run_command is not available to this subagent` и не выполняется;
- **Глубина.** `subagents.max_depth` ограничивает вложенность. При значении по умолчанию `1` сессия запускает дочерних агентов, которые сами запускать уже не могут; у дочернего агента на пределе инструмента нет, а запуск глубже предела отклоняется. Явный `0` запрещает запуск везде. Есть одно ограниченное исключение. Определение, которое объявляет `spawns`, сохраняет `spawn_agent` на пределе и может делегировать ровно на один уровень глубже, ровно именам из списка. Список `spawns` ограничивает имена на любой глубине, а дочерний агент глубже предела никогда не получает инструмент, так что исключение даёт ровно одно дополнительное поколение (ради встроенного оркестратора `crossreview` оно и существует);
- **Модель.** Дочерний агент наследует модель, на которой работает сессия родителя, если только `model` определения не называет настроенный идентификатор `models[].model`; при неизвестном идентификаторе остаётся модель родителя, а замена отмечается и в логе агента, и в логе вывода задачи;
- **Ходы.** `max_turns` определения, иначе `subagents.max_turns`, иначе `agent.max_turns`;
- **MCP.** Серверы подключаются для дочернего агента, только если его действующий набор может содержать имена MCP. Настроенные серверы заново разрешаются для cwd дочернего агента через проверку доверия рабочей папки так же, как для новой сессии, а серверы, переданные ACP-клиентом родителя, подключаются заново по объявлениям, которые сохранил родитель. Дочерний агент владеет своими клиентами и сам их закрывает; у родителя ничего не заимствуется, поэтому перезагрузка родителя или его выгрузка не оборвёт дочернего агента посреди работы.

## Запросы разрешений дочерних агентов

Дочерний агент в режиме `ask` или `accept_edits` всё равно проходит проверку разрешений, а собственного клиента у него нет. Поэтому каждый запуск создаёт **релей**, которому принадлежат отправитель родителя и ход родителя, сделавший запуск (контекст вызова инструмента), а также собственная отмена дочернего агента:

- пока запускающий ход жив, запрос пересылается клиенту родителя с **идентификатором сессии родителя** и заголовком `[subagent <name>] Run: <tool>`, поэтому ACP-редактор, модальное окно консоли, веб-интерфейс или чат Telegram показывают его в диалоге родителя. Ожидание следит и за дочерним агентом, так что остановленный дочерний агент разблокируется с отказом; если ход родителя заканчивается, пока запрос ещё на экране, эта копия снимается, а запрос передаётся брокеру (ниже), поэтому на него отвечают один раз, там, где диалог ещё читают;
- когда запускающий ход уже вернулся (обычное состояние **отсоединённого** запуска), запрос никогда не трогает транспорт завершённого хода. Он идёт к **брокеру отсоединённых разрешений** интерфейса (ниже), а там, где брокера нет, сразу отклоняется с причиной, которую дочерний агент сообщает вместо утверждения, будто пользователь ответил отказом (`permission not granted: this subagent is running detached ...`);
- одновременно идёт **не больше одного запроса на сессию родителя**. Арбитр выстраивает в очередь запросы всех дочерних агентов этого родителя, и ровно это может представить запись HTTP об ожидающем разрешении (одна на сессию). Двух дочерних агентов, спросивших одновременно, спрашивают по очереди;
- дочерний агент, запущенный более поздним ходом, несёт контекст этого хода, поэтому завершённый ход более раннего отсоединённого дочернего агента не приводит к отказу ему.

Как с этим сочетаются собственные настройки оператора. Сессия родителя в режиме `bypass` отключает запросы у родителя и у каждого дочернего агента, который **наследует** этот режим. Определение, которое сужает режим до `ask` или `accept_edits`, - другой случай. Релей ставит на каждый пересылаемый запрос отметку с действующим режимом самого дочернего агента, и каждый отправитель, который умеет одобрять автоматически (ACP-сервер, HTTP-мост, консоль, режим печати, Telegram-шлюз), решает по этой отметке, а не по сессии родителя. Такого дочернего агента спрашивают там, где может ответить человек (SPA, консоль, консоль или ACP-клиент с `--remote`, локальный ACP-редактор, чат Telegram, где вопрос задаётся кнопками), и ему отказывают там, где ответить некому (режим печати, непотоковый HTTP-ход). По пути наверх отметка только ужесточается. Запрос агента-внука проходит через два релея, и промежуточный дочерний агент не может снова его расширить, а запрос, который хук `PreToolUse` вызвал ответом `ask`, сохраняет `ask` даже у дочернего агента в режиме `bypass`. Пересланный запрос предлагает только **разрешить** и **отклонить**; ответов "всегда" в нём нет, потому что запуск дочернего агента - один ход и постоянное разрешение не могло бы его пережить. На пересланные запросы отвечают вживую или никак. HTTP-мост не записывает их в запись ожидающего разрешения родителя, поэтому перезагрузка страницы или переподключение не может вернуть такой запрос (его снимает собственный тайм-аут дочернего агента или конец хода родителя), а эту запись проверка разрешений родителя оставляет за собой.

### Отсоединённые запуски - запрос переживает ход

`background: true` просит запуск, который переживёт запустивший его ход, поэтому и проверка разрешений должна его пережить. Когда запускающего хода уже нет, релей передаёт запрос **брокеру** (`agent.DetachedPermissionBroker`, точка расширения того же вида, что и `SubagentRuntime`) и ждёт на нём. Как с фоновым субагентом в Claude Code, запрос появляется в диалоге, который читает человек, и называет субагента, который спрашивает; **Отклонить** отказывает в одном этом вызове, а субагент продолжает работу.

| Интерфейс | Где появляется запрос отсоединённого дочернего агента |
|---|---|
| Веб-интерфейс (`coddy serve` с HTTP-интерфейсом) | в конце чата родительской сессии, в такой же карточке, как встроенный запрос, с именем субагента в заголовке |
| Консоль | модальное окно разрешения с заголовком `[subagent <name>] ...`, в том числе между ходами; запрос, пришедший, пока открыто другое модальное окно, ждёт его закрытия |
| Консоль с `--remote` | то же модальное окно для сессий, которые открыла эта консоль, а о запросе сообщает поток событий сервера |
| Telegram (`coddy serve` со шлюзом) | сообщение с кнопками **Allow** и **Reject** в чате, которому принадлежит сессия родителя |
| `coddy acp`, режим печати, запуск по расписанию | нигде - дочернему агенту сразу отказывают с причиной, указанной выше, и он её сообщает |

- **`coddy serve` предлагает запрос всем интерфейсам сразу.** Исполнитель ходов общего менеджера сессий передаёт каждому ходу среду выполнения в роли брокера, и каждый интерфейс при запуске предлагает себя (`serve.Runtime.AddDetachedPermissionApprover`), - это HTTP-сервер и Telegram-бот для сессий своих чатов. Первый ответ закрывает запрос, а все остальные копии снимаются - карточка уходит из веб-чата, модальное окно удалённой консоли закрывается, сообщение в Telegram меняется на *No longer waiting*. Интерфейс, который не может показать запрос, в этом не участвует; если не может ни один, дочернему агенту отказывают с причиной;
- **Запрос, который ещё на экране родителя, когда ход заканчивается, переходит так же.** Фоновый дочерний агент обычно начинает спрашивать, пока родитель ещё пишет ответ, и решение человека может не успеть до конца этого ответа; поток, по которому пришёл запрос, исчезает вместе с ходом, поэтому релей снимает копию, которую показал клиент родителя (консоль убирает модальное окно, HTTP-мост перестаёт ждать, сообщение в Telegram меняется на *No longer waiting*), и поднимает запрос через брокер, где на него отвечают один раз, как на отсоединённый. Только там, где брокера нет, дочернему агенту отказывают с указанной выше причиной. В веб-интерфейсе встроенная карточка завершённого хода уходит вместе с его потоком, а отвечает карточка в конце чата;
- **Веб-интерфейс** читает запрос из строки фоновой задачи заблокированного запуска (`pending_permission` в `GET /coddy/sessions/{id}/background-tasks`) и перечитывает строки по `event: subagent_permission` из `GET /coddy/events` (фазы `asked` и `settled`), а опрос задач служит запасным путём. Ответ уходит в `POST /coddy/sessions/{child}/permission`. Новых маршрутов нет. Хаб разрешений индексируется по `(session id, tool call id)`, а не по живому ходу, и обработчик обращается к нему до проверки, которая держит транскрипт дочернего агента только для чтения. Консоль, подключённая через `--remote`, читает те же события (снимок при подключении повторяет запросы, которые ещё ждут) и отправляет ответ в тот же маршрут;
- **Telegram** без вопросов одобряет то, что просит собственный агент чата, но о запросе субагента спрашивает inline-кнопками, во время хода и после него. Ответить может только человек, чья сессия спросила, - в группе с индивидуальными сессиями нажатие другого участника игнорируется;
- Запрос **не** занимает слот арбитра родителя. Этот слот существует, потому что у родителя одна запись ожидающего разрешения, а отсоединённый запрос привязан к своей дочерней сессии и может ждать минутами; живой запрос соседнего дочернего агента не должен стоять за ним в очереди. Ответов "всегда" здесь тоже нет;
- Ничего не сохраняется. Ожидание держит горутина, поэтому запрос не может пережить процесс, который его поднял; после перезапуска запуска уже нет, и панель задач показывает его задачу со статусом "Осиротела";
- Ожидание заканчивается вместе с собственным контекстом запуска, который отменяют тайм-аут пула, явная остановка и завершение работы. Ожидающий запуск по-прежнему учитывается в `subagents.max_concurrent` и в `tools.background.max_concurrent` родителя, и это честно отражает, чем он занят, а запрос, на который никто не отвечает, держит запуск до его жёсткого тайм-аута.

## Параллельность и тайм-ауты

К запуску применяются два предела, и каждый отказ называет свой ключ:

- **`subagents.max_concurrent`** (по умолчанию 4) действует **на весь процесс** и задаёт число дочерних циклов LLM, которые могут идти одновременно, какая бы сессия их ни запустила. Семафор с изменяемым размером отказывает, а не ставит в очередь, как того требует правило пула "отказ, а не очередь"; сообщение велит модели подождать через `background_wait` или `background_list` и попробовать снова. Снижение предела под нагрузкой никогда не останавливает работающего дочернего агента; новые запуски отклоняются, пока их число не опустится ниже нового предела. Значение перечитывается при каждом запуске, поэтому коммит конфигурации применяется без перезапуска;
- **`tools.background.max_concurrent`** - предел задач пула **на сессию**, а задача дочернего агента регистрируется под сессией **родителя**, поэтому запуски субагентов учитываются вместе с задачами родителя, как его фоновые команды. Запуск, отклонённый из-за этого предела, называет `tools.background.max_concurrent`, чтобы модель различала два предела.

Жёсткий предел одного запуска выбирается в таком порядке - `timeout_seconds` вызова, затем `timeout_seconds` определения, затем `expected_seconds × 3`, но не меньше 60 с, затем `subagents.default_timeout_seconds` (1800). Результат ограничен сверху `tools.background.max_timeout_seconds`, в точности как для фоновой команды. Когда предел достигнут, дочерний агент отменяется, а задача записывается как `timed_out`, то есть как сбой, а не успех.

## Когда обрывается связь с провайдером

Субагент работает без присмотра - пока он идёт, его транскрипт никто не читает и никто не может напечатать ему "продолжай". Сбой канала его провайдера модели (соединение, закрытое удалённым хостом, сброс, 5xx от прокси, замолчавший поток) не означает сбоя задачи, поэтому дочерний агент пережидает его так же, как интерактивный ход ([Провайдер отказывает посреди хода](../getting-started/troubleshooting.md#провайдер-падает-посреди-хода)), только дольше. Написанный текст остаётся в транскрипте, а после паузы шаг выполняется снова, и модель просят продолжить с того места, где она остановилась. Интерактивный ход переживает два неудачных вызова подряд и заканчивается на третьем, потому что дальнейшее решает человек, который его читает. Субагент и запуск по расписанию переживают пять подряд и заканчиваются на шестом, с паузами 5 с, 20 с, 80 с, 2 мин и 2 мин при значении `agent.llm_retry_base_ms` по умолчанию, то есть около шести минут, если у запуска на них хватает времени. Каждое восстановление занимает один из ходов запуска (`max_turns`), а жёсткий тайм-аут запуска обрывает паузу и завершает запуск как `timed_out`, поэтому запуск с коротким тайм-аутом или низким пределом ходов сдаётся раньше. Успешный вызов начинает отсчёт заново. Субагент памяти сохраняет интерактивный бюджет, поскольку его отчёт важен только ходу, который его ждёт, а `agent.llm_retry_max: 0` выключает восстановление везде.

Windows сообщает о мёртвом соединении собственными кодами Winsock - `WSAECONNRESET` (`wsarecv: An existing connection was forcibly closed by the remote host.`) и `WSAECONNABORTED` (`An established connection was aborted by the software in your host machine.`). Оба считаются оборванным соединением, как `connection reset by peer` в Linux ([issue #389](https://github.com/coddy-project/coddy-agent/issues/389)).

Каждое переподключение - строка в логе прогресса задачи после текста, который написал дочерний агент, поэтому запуск, пережидающий сбой, не выглядит зависшим.

```
subagent general (task bg_5, session sess_e20a…) starting
[assistant] Reading the files
↻ provider failed (provider "cockpit" (http://localhost:62557/v1): openai stream: read tcp 127.0.0.1:53107->127.0.0.1:62557: wsarecv: An existing connection was forcibly closed by the remote host.); reconnecting in 5s (attempt 1 of 5)
[assistant] …the rest of the answer…
```

### Продолжение запуска

Если провайдер лежит дольше, запуск заканчивается без отчёта, как и по тайм-ауту или пределу ходов, а транскрипт хранит всё, что запуск сделал. Родитель не запускает второго субагента на ту же задачу с пустым контекстом. `spawn_agent` с `resume`, равным идентификатору задачи запуска (или идентификатору его дочерней сессии), продолжает того же дочернего агента. Дочерняя сессия открывается заново из своего бандла, `prompt` становится её следующим сообщением после прежнего транскрипта, а запуск становится новой задачей родителя (новый идентификатор `bg_…`) на той же дочерней сессии.

```json
{"agent": "general", "resume": "bg_5", "prompt": "The provider is back. Go on from where you stopped."}
```

- Запуск проверяется как новый, по определению в его нынешнем виде - расписка доверия, режим, режим разрешений, набор инструментов, уровень рассуждения и тайм-аут. `agent` должен называть субагента, которому принадлежал запуск. Дочерний агент сохраняет заголовок, а также модель, на которой работал прежний запуск, если вызов не называет другую; модель, удалённая с тех пор из конфигурации, заменяется так же, как неизвестная, и лог задачи называет обе. Ничего из того, что было разрешено прежнему запуску, не переносится. Разрешения, выданные на его запросы, остаются в прошлом, и продолженный запуск спрашивает снова;
- Транскрипт продолжается в том виде, в каком его оставили, с одной поправкой. Вызов, для которого в нём нет результата (запуск остановили или он вышел по тайм-ауту посреди пачки вызовов, либо процесс умер во время вызова), получает ответ, что результат не записан и вызов мог выполниться, а мог и нет, поэтому модель проверяет текущее состояние, прежде чем повторить вызов. Провайдер отклоняет запрос, в котором есть вызов без результата, так что без этого ответа продолженный запуск упал бы на первом же шаге;
- Запуск, транскрипта которого нет на диске, отклоняется ещё до старта - его дочерняя сессия так и не была создана (запуск упал по дороге) или дочернего агента с тех пор удалили;
- Дочерний агент продолжается только в той рабочей папке, где он работал. Если сессия переехала в другую папку, продолжение отклоняется, потому что пути и результаты в транскрипте относятся к старой; запустите там нового субагента для этой задачи;
- Продолжить можно только завершённый запуск этой сессии. Запуск, который ещё идёт, отклоняется (сначала дождитесь его через `background_wait` или остановите через `background_stop`), как и субагент памяти и всё, что не дочернее для этой сессии. Запуск по расписанию - всегда дочерний для сессии своего задания и никогда для чата;
- Отчёт, число ходов и конверт принадлежат продолженному запуску. Ответ, который дал прежний запуск, не выдаётся за отчёт запуска, который ничего не написал. Лог задачи начинается с `subagent <name> (task bg_…, session sess_…) resuming`, а фоновое продолжение отвечает `Resumed subagent <name> as background task bg_…`;
- Неуспешный запуск говорит, как продолжить, там, где его читает родитель. Конверт запуска на переднем плане и блок отчёта в логе задачи содержат `call spawn_agent with resume="bg_5" and agent "general" …`, а перед этим `The run was cut by a failure of the model provider, not by its task.`, если причина была в этом, и ход, который будит неудачный фоновый запуск, называет тот же вызов. Каталог в системном промпте родителя тоже об этом говорит.

Интерфейс по-прежнему не может написать дочернему агенту - транскрипт остаётся только для чтения для всех, кроме родителя, который его запустил ([Дочерние сессии](#дочерние-сессии)).

## Дочерние сессии

Запуск создаёт дочернюю сессию с обычным идентификатором сессии. Идентификатор генерируется до того, как подключается пул, поэтому его несёт уже самый первый снимок задачи; продолженный запуск заново открывает дочернюю сессию того запуска, который продолжает ([Продолжение запуска](#продолжение-запуска)). По идентификатору не видно, что сессия делегирована (это тот же **`sess_<24 hex>`**, что получает чат), её отличают место бандла и метаданные. Дочерняя сессия - настоящий бандл сессии **внутри бандла родителя**, в **`<sessions root>/<parent>/subagents/<child>/`**, собранный так же, как его собирает `session/new` (скилы, каталог правил, сохранение), с заголовком, закреплённым за меткой задачи, и с `session.json`, в котором есть `subagentRun: true`, `parentSessionId`, `subagentName`, `subagentTaskId` и `subagentDepth`. Дочерний агент, который запускает собственного дочернего агента, вкладывает его на уровень глубже. Пока дочерний агент работает, он зарегистрирован как живая сессия, поэтому транскрипт читается из единственного живого состояния; после завершения транскрипт отдаёт бандл, как у любой закрытой сессии.

- **Скрыты из истории.** Дочерние сессии не попадают ни в один список по умолчанию - ни в раздел **История** веб-интерфейса, ни в `GET /coddy/sessions`, ни в `coddy sessions list`, ни в `coddy -c`, ни в ACP `session/list`. `GET /coddy/sessions?include_subagents=true` их включает;
- **Транскрипты только для чтения.** Интерфейс не может написать дочернему агенту; продолжает его только родитель, который его запустил, через `resume` в `spawn_agent` ([Продолжение запуска](#продолжение-запуска)). Любой промпт к дочерней сессии, кроме собственного хода задачи дочернего агента (`POST /v1/responses` из поля ввода, ACP `session/prompt`, промпт консоли, запрос на выполнение плана, фоновое пробуждение), отклоняется с `subagent sessions are read-only transcripts: <child> belongs to <parent>`; по HTTP это **409** с именем родителя. SPA показывает транскрипт дочернего агента, а вместо поля ввода выводит уведомление со ссылкой на родительский чат;
- **Из панели задач.** На карточке задачи агента тегом служит имя агента, заголовком - описание запуска, а строка метаданных называет модель, на которой работает дочерний агент, и токены, которые его вызовы уже потратили (входные и выходные вместе, текущий вызов оценивается, пока провайдер не сообщит точное число), так что запуск, который сжигает большой контекст, виден уже во время работы. Строка `GET /coddy/sessions/{id}/background-tasks` несёт те же числа в `agent.model`, `agent.input_tokens` и `agent.output_tokens`, а запись задачи хранит итоговые. Раскрытая карточка показывает **Показать транскрипт** (переход на `#/s/<child id>`) там, где у задачи shell стоит её команда. Пока запуск идёт, отчётом служит живой лог прогресса в поле вывода карточки; транскрипт показывает вызовы инструментов дочернего агента и его итоговый ответ;
- **Удаление каскадное.** `DELETE /coddy/sessions/{id}` удаляет всё дерево по одному пути - запрошенную сессию и всех её потомков, найденных обходом папок `subagents/` её бандла от корня к листьям. Сначала останавливается задача, представляющая каждый узел, и Coddy дожидается её завершения (задача дочернего агента живёт под родителем, поэтому так останавливаются и работающий дочерний агент, и работающий потомок), затем все оставшиеся задачи каждого узла, и только после этого бандлы удаляются начиная с самых глубоких, запрошенная сессия последней. Ещё до всего этого активный ход любого узла отменяется и Coddy дожидается его конца, а ход, пришедший во время удаления, отклоняется; ход, который игнорирует отмену дольше тайм-аута ожидания (15 с), прерывает удаление, и ничего не удаляется (HTTP `409`). После пометки дерево сканируется заново, пока не перестанут появляться новые потомки, поэтому дочерний агент, созданный в момент начала удаления, удаляется вместе с деревом, а не остаётся сиротой. В удалённый бандл потом ничего не пишется.

## Запуски по расписанию

Запуск, который стартует планировщик ([Планировщик](../operate/scheduler.md)), - дочерний агент того же рода. Это задача вида `agent` под сессией задания, дочерняя сессия с транскриптом, тот же лог прогресса, то же закрытие и то же правило только для чтения. Отличаются родитель (сессия задания, которая никогда не выполняет ходов, а не чат) и то, что сообщают дочернему агенту. Его блок роли говорит, что это задание по расписанию, запущенное без присмотра, его `session.json` содержит `schedulerJobId` и `schedulerTrigger`, а уведомление в транскрипте ведёт к запускам задания, а не к родительскому чату. Задание может назвать определение (`agent:` в своём frontmatter), чтобы работать с его ролью, инструментами, моделью, уровнем рассуждения и сужением разрешений, по тому же правилу доверия, что и обычный запуск субагента, и с тем же правилом для уровня (он применяется, если модель запуска его предлагает); без определения у запуска полный набор инструментов его режима. Такой запуск находится на глубине 0, поэтому в пределах `subagents.max_depth` может запускать собственных дочерних агентов, которые учитываются в `subagents.max_concurrent`, как любой запуск.

## Правила жизненного цикла

- **Один ход на запуск.** Запуск - ровно один ход промпта дочернего агента по обычному пути менеджера сессий, поэтому он берёт блокировку хода, сообщает о начале и конце активности, учитывает отмену из другого процесса и сохраняется, как любая сессия. Продолженный запуск - ещё один ход той же дочерней сессии, открытой заново из бандла и снова закрытой по его окончании ([Продолжение запуска](#продолжение-запуска));
- **Перед закрытием дочерний агент доводит до конца собственную работу.** Дочерний агент `general` наследует фоновый `run_command`, а ниже предела глубины и `spawn_agent`, поэтому, когда его ход возвращается, у него может остаться работающая команда или отсоединённый агент-внук. Закрытый дочерний агент - транскрипт только для чтения, у которого не осталось хода, чтобы их собрать, поэтому до того, как убрать живую запись, каждую задачу дочернего агента останавливают и дожидаются её конца (дескриптор внука отменяет этого внука, и его собственное закрытие рекурсивно идёт тем же путём). Записи завершённых задач остаются в бандле дочернего агента. Время на это, ограниченное трёхсекундной отсрочкой остановки пула на каждую задачу, засчитывается в собственный жёсткий тайм-аут дочернего агента. Затем клиенты MCP дочернего агента закрываются, а его живая запись удаляется; бандл остаётся на диске;
- **Никого не будят от имени дочернего агента.** Запуск, сделанный дочерним агентом, никогда не несёт `notify_on_finish`, а разбуженный ход, адресованный дочерней сессии, отклоняется проверкой только для чтения, поэтому задача, завершившаяся около закрытия, хода не запускает;
- **Ход родителя отменён (остановка).** Дочерний агент на переднем плане работает на контексте, производном от вызова инструмента родителя, поэтому отменяется вместе с родителем, а результат инструмента сообщает итоговый статус. Отсоединённый дочерний агент работает на контексте, отвязанном от вызова инструмента, потому что этот контекст заканчивается, как только инструмент возвращается; он намеренно продолжает работать, и остановить его можно из панели задач или через `background_stop`;
- **Остановка и сворачивание.** При сворачивании сервер останавливает задачи агентов так же, как команды - каждый дескриптор отменяет своего дочернего агента, дочерний агент закрывается, а его слот ограничителя освобождается. Когда пул сворачивается, ничего нового не стартует;
- **Каждый путь выхода освобождает слот.** Отказ пула, неудача при создании дочерней сессии (записывается как задача `failed`), тайм-аут, остановка, отмена родителя, паника в запуске (перехватывается и сообщается как `failed` с текстом паники) и нормальное завершение проходят через одно идемпотентное завершение, поэтому слот никогда не теряется и не освобождается дважды;
- **Родитель выгружен или перезагружен.** У дочернего агента своё состояние и свои клиенты MCP, поэтому ничего, от чего он зависит, не закрывается у него из-под ног.

## Строки задач и лог вывода

Строка задачи агента (`background_list`, `GET .../background-tasks`, сохранённый `meta.json`) содержит `kind: "agent"`, метку `agent <name>: <description>`, `session_id` родителя, `tool_call_id` запускающего вызова (чтобы строка транскрипта сохраняла живой чип) и `agent: {"name": "<name>", "session_id": "sess_…"}`. pid в ней нет - за ней стоит дескриптор, а не процесс ОС, поэтому проверка уцелевших процессов никогда не примет его за процесс.

Дочерний агент никогда не пишет в поток родителя. Его прогресс уходит в приёмник вывода задачи короткими строками лога, и именно их показывают `background_output` и панель, пока запуск идёт.

```
subagent explore (task bg_3, session sess_9f1c…) starting
→ grep
✓ grep
[assistant] The runtime is wired in four places…
=== subagent report ===
agent: explore | task: bg_3 | session: sess_9f1c… | outcome: end_turn | turns: 4 | duration: 41s
--- report ---
…the child's last assistant message…
```

`✗ <tool> (failed)` отмечает вызов инструмента, который упал или был отклонён, в том числе вызов вне набора инструментов дочернего агента, а `↻` - переподключение после сбоя провайдера ([Когда обрывается связь с провайдером](#когда-обрывается-связь-с-провайдером)). `outcome` - причина остановки дочернего агента (`end_turn`, `cancelled`, `failed` или другая причина остановки ACP), `turns` - число раундов ассистента, которые записал этот запуск (то же число, что в конверте запуска на переднем плане), а если запуск закончился ошибкой, перед отчётом стоит строка `error:`.

## Системные дочерние агенты - субагент памяти

Одного дочернего агента среда выполнения запускает сама. При включённом `memory.enable` каждый ход пользователя запускает **субагента памяти**, который вспоминает и сохраняет долговременные заметки ([Долговременная память](memory.md)). Он построен на том же механизме, что и дочерний агент `spawn_agent` (задача вида `agent` в пуле, дочерняя сессия внутри бандла родителя, тот же транскрипт и лог), но запускается собственным кодом запуска, поэтому не все правила запуска к нему относятся:

- его строка задачи содержит `agent.system: true` и имя `memory`; панель задач помечает его карточку тегом `memory` там, где у делегирования стоит имя его агента, а инструменты пула для модели его не показывают и отклоняют его идентификатор;
- его пропускают сверх `tools.background.max_concurrent` и никогда не учитывают в этом пределе, `subagents.max_concurrent` его тоже не считает; его собственные пределы - два запуска на сессию и шестнадцать на процесс;
- у него шесть инструментов, которых нет у родителя, и это единственное исключение из правила, что набор дочернего агента только сужается. Набор зафиксирован в коде, выдаётся только этому дочернему агенту и никогда через файл определения и не достаёт ни до чего, кроме двух корней заметок. Его режим всегда `agent`; ход в режиме "Чат" сужает его до трёх инструментов вспоминания;
- `SubagentStart` и `SubagentStop` для него не срабатывают (они описывают делегирования, выбранные моделью); внутри дочернего агента обычные события срабатывают с `"kind": "memory"` в блоке `subagent` полезной нагрузки;
- ему не нужны ни релей разрешений (ничто в его наборе не проходит проверку разрешений), ни определение, поэтому файл определения с именем `memory` остаётся допустимым и описывает другого дочернего агента, которого в панели задач отличает тег.

## Удалённый режим

Субагенты живут там же, где менеджер сессий. Когда консоль или `coddy acp` работают в режиме `--remote` (`docs/surfaces/console.md`, раздел "Удалённый режим"), менеджер, дочерние сессии, задачи пула и расписки доверия находятся на хосте `coddy serve`:

- определения читаются из папок **сервера** (`~/.agents/agents` пользователя сервера, `${CODDY_HOME}/agents` домашнего каталога сервера, `.agents/agents` и `.coddy/agents` из cwd сессии на сервере, затем его `subagents.dirs`);
- проектное определение одобряется **на сервере** - `coddy agents trust <name> --cwd <workspace>` на этом хосте или `POST /coddy/subagents/{name}/trust` с bearer-токеном. Локальные подкоманды `coddy agents` читают и пишут только локальный домашний каталог и ничего не знают о `--remote`;
- запросы разрешений дочернего агента идут тем же путём, что и запросы родителя. Релей пересылает их под сессией родителя, HTTP-мост выдаёт SSE-событие `permission` (даже когда сессия родителя на сервере работает в `bypass`, потому что решает собственный режим дочернего агента), удалённая консоль или ACP-клиент показывает запрос с префиксом `[subagent <name>]` и отвечает на него через `POST /coddy/sessions/{parent}/permission`;
- **отсоединённый** дочерний агент, который спрашивает после окончания запустившего его хода, тоже доходит до удалённой консоли. Сервер объявляет запрос в `GET /coddy/events`, а консоль открывает модальное окно для сессий, которые она открыла, и отвечает через `POST /coddy/sessions/{child}/permission`. Тот же запрос ждёт в родительском чате SPA, которое отдаёт этот хост, и в чате Telegram, если сессия принадлежит такому чату; побеждает первый ответ. Удалённый ACP-клиент его не показывает, и пока никто не ответит, запуск ждёт до своего жёсткого тайм-аута;
- вызов `spawn_agent` и его отчёт возвращаются потоком, как любой вызов инструмента, поэтому строка статуса консоли и в удалённом режиме показывает `Running a subagent` (блок инструмента над ней называет, какой именно); транскрипт дочернего агента остаётся на сервере, и его читают из SPA, которое отдаёт тот же хост (панель задач, "Показать транскрипт"), или через `GET /coddy/sessions/{child id}/messages`;
- настройки `subagents.*` принадлежат серверу. Меняйте их в настройках SPA этого хоста или скилом `configure-coddy` из удалённой сессии (инструменты конфигурации работают на сервере); `max_concurrent` применяется к следующему запуску в каждой сессии, какой бы ход его ни сохранил;
- расписка привязана к рабочей папке сессии **на стороне сервера**, а для сессии, созданной удалённой консолью или ACP-клиентом, это cwd сервера по умолчанию (поле `cwd` в строках `GET /coddy/sessions` или `GET /coddy/workspace/context` с заголовком сессии); подвал удалённой консоли показывает локальную папку, а не этот путь. Одобрение, которое можно скопировать и вставить.

  ```bash
  curl -sS -X POST "$CODDY_URL/coddy/subagents/marker-reporter/trust" \
    -H "Authorization: Bearer $CODDY_REMOTE_TOKEN" -H 'Content-Type: application/json' \
    -d '{"cwd": "/srv/checkouts/project"}'
  ```

- при обрыве соединения ход на сервере, его дочерний агент на переднем плане и любой открытый запрос продолжают работать на стороне сервера (ходы отвязаны от запроса); удалённая консоль сообщает об ошибке потока, `/resume` показывает исход, когда ход закончится, а запрос, на который ответили после того, как сервер его снял, игнорируется и не роняет ход;
- разбуженный ход (`notify_on_finish` у отсоединённого запуска или фоновой команды) выполняется на сервере - в чате Telegram, привязанном к сессии, или на релее поля ввода сессии, где на его запросы разрешений могут ответить веб-интерфейс и консоль, которая следит за ходом через `--remote`; если ни того, ни другого нет, вызов инструмента внутри него, требующий разрешения, отклоняется, если только собственный режим разрешений сервера не bypass ([Фоновые задачи](background-tasks.md#под-coddy-serve)).

Исполняемые проверки - сценарий "A subagent's permission prompt reaches the remote client even when the server bypasses its own" в `features/remote_client.feature`, живой `examples/acp/acp_e2e_remote_subagents.py` и шаг с субагентом в `examples/cli/cli_e2e_remote.py`.

## Конфигурация

Все настройки - обычные ключи `config.yaml` в `subagents:`; таблица полей лежит в `docs/reference/config.md` (раздел `subagents`), веб-интерфейс правит их на вкладке **Настройки → Субагенты**, а встроенный скил `configure-coddy` меняет их через инструменты поэтапной правки конфигурации.

```yaml
subagents:
  enable: true
  dirs: []                    # extra folders after the four defaults, e.g. "${CWD}/.claude/agents"
  project_trust: ask          # ask | allow | deny
  max_concurrent: 4           # child runs in flight across the whole process
  max_depth: 1                # 1: children cannot spawn; 0: nobody spawns
  default_timeout_seconds: 1800
  max_turns: 0                # 0 follows agent.max_turns
```

`tools.background` по-прежнему ограничивает пул, в котором живёт запуск, - его `max_concurrent` на сессию, предел `max_timeout_seconds` и `output_buffer_bytes` для лога прогресса.

## Что не вошло

Последующая работа, намеренно не вошедшая в это изменение, - сообщения работающему дочернему агенту, изоляция дочернего агента в worktree, хуки и MCP-серверы на уровне определения, правка определений из веб-интерфейса (определение по-прежнему файл, который пишете вы; **Настройки → Субагенты**, `coddy agents trust` и HTTP-маршрут его только одобряют), очередь вместо отказа при заполненном пуле и живой SSE-релей для дочернего агента (вместо него транскрипт читается из живого состояния или из бандла).
