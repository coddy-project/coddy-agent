# Хуки ZCode для правил проекта

Эта страница для **контрибьюторов, которые работают с этим репозиторием через клиент ZCode**. Она парная к странице [Хуки Codex для правил проекта](codex-hooks.md); обе доставляют модели одни и те же файлы `.cursor/rules/*.mdc`, каждая через механизм хуков своего клиента.

## Зачем нужен хук

ZCode загружает свой файл инструкций (`AGENTS.md`) один раз за сессию, начиная поиск с рабочего каталога и поднимаясь до корня проекта. Отсюда те же два следствия, что и у Codex:

- сессия, запущенная в корне репозитория, никогда не загружает вложенный `AGENTS.md`;
- подключения правил по glob-шаблонам нет. У ZCode нет аналога поля `globs` из `.cursor/rules/*.mdc`, поэтому область действия правила задаётся только местом файла в дереве.

Этот репозиторий хранит правила в родном формате Cursor в `.cursor/rules/*.mdc`, и адаптер ZCode читает эти файлы напрямую. Дерево Cursor служит лишь входными данными адаптера и не задумано как универсальный формат политик. Если направить модель к другому файлу и попросить его прочитать, это останется рекомендацией, которую модель может пропустить.

`.zcode/hooks/attach_rules.py` закрывает этот пробел для правил с областью действия. Он вставляет тела правил прямо в сессию и не требует отдельной копии для ZCode.

## Что и когда срабатывает

| Событие | Матчер | Что вставляется |
|---|---|---|
| `SessionStart` | `startup\|resume\|clear\|compact` | каждое правило, у которого во frontmatter стоит `alwaysApply: true` |
| `PreToolUse` | `^(Edit\|Write\|MultiEdit\|ApplyPatch)$` | правила, чьи `globs` покрывают файл из ожидающего вызова инструмента |

Конфигурация лежит в `.zcode/config.json`, в разделе `hooks.events`. Хуки из файлов конфигурации по умолчанию выключены, поэтому конфигурация задаёт `hooks.enabled: true`. Оба обработчика запускают один и тот же скрипт, а он выбирает ветку по полю `hook_event_name` из полезной нагрузки хука. Псевдоним `ApplyPatch` включён в матчер `PreToolUse`, потому что у ZCode есть псевдонимы `Write`/`Edit` ← `ApplyPatch`.

В этом репозитории при старте сессии приходит `russian-wording`. Тематические правила по Go, HTTP, шлюзу и UI привязаны к путям и подключаются по требованию. Правка, затрагивающая `external/httpserver/server.go`, подтягивает `api-layer`, `architecture`, `code-style`, `implementation-order`, `testing` и `workflow`; правка в `external/ui/src/` добавляет к ним `ui-spa` и `ui-verification`.

## Как это работает

Адаптер проекта сам разбирает frontmatter файлов `.mdc` (`description`, `globs` в виде скаляра или списка и `alwaysApply`). Запятые в кавычках, удвоенные одинарные кавычки, экранированные символы в двойных кавычках и комментарии YAML в допустимых формах (скаляр, однострочный или многострочный flow-список, блочный список) декодируются или отбрасываются, как положено. Входные данные он берёт из `.cursor/rules/` и отдельной копии тела правила для ZCode не хранит. Новый файл правила Cursor не требует никакой настройки адаптера. Что полезно знать:

- **Сопоставление с glob-шаблонами написано вручную.** `fnmatch` не подходит, потому что его `*` захватывает и `/`, из-за чего `external/httpserver/**/*.go` не находит `external/httpserver/server.go`. Скрипт переводит glob-шаблоны в регулярное выражение, где `**/` означает "ноль или больше каталогов", `*` остаётся внутри одного сегмента, а одиночный `**` покрывает что угодно;
- **Пути берутся из структурированных полей инструмента.** ZCode передаёт хуку JSON-объект, поэтому скрипт обходит `tool_input` и оставляет строковые значения под известными ключами, в которых бывают пути (`file_path`, `path`, `notebook_path`, `source`, `destination`, `new_path`, `old_path`, ...). Аналог для Codex тоже принимает эти поля и вдобавок разбирает заголовки `apply_patch`. Вложенные и абсолютные пути нормализуются перед сопоставлением;
- **Каждое правило с областью действия вставляется не больше одного раза за активный контекст сессии.** Состояние хранится в JSON-файле `<tempdir>/zcode-attach-rules-<repository-hash>/<session_id>.json` с ключом из репозитория и id сессии, поэтому разные клоны не подавляют друг друга. `resume` сохраняет дедупликацию правил с областью действия, а `startup`, `compact` и `clear` сбрасывают состояние до набора постоянных правил. Параллельные процессы доставляют правила по очереди под блокировкой на сессию, а состояние обновляется атомарной заменой файла. Id правил записываются только после успешного вывода контекста, так что при сбое вывода правила остаются доступны для следующей попытки. Если блокировка или запись состояния недоступны, контекст подходящих правил всё равно выводится, а дедупликация может на время деградировать до повторной доставки;
- **При ошибке хук ничего не блокирует.** Некорректный JSON в stdin, файл правила, который не удалось разобрать, или каталог состояния без права на запись - во всех этих случаях скрипт завершается с кодом 0 и ничего не выводит. Сломанное правило никогда не заблокирует правку.

## Включение

Хуки из файлов конфигурации ZCode выключены, пока не задано `hooks.enabled: true`, поэтому закоммиченный `.zcode/config.json` уже включает их запуск. В отличие от Codex, отдельной проверки доверия для каждого хука нет - конфигурация рабочей папки с `enabled: true` выполняется безусловно, и для настройки, общей для всего репозитория, так и задумано. Откройте репозиторий в ZCode, и оба обработчика заработают; больше ничего делать не нужно.

## Интерпретатор в Windows

Команда хука вызывает `python`, а не `python3`. В Windows имя `python3` часто принадлежит заглушке Microsoft Store, которая ничего не печатает и завершается с ненулевым кодом, а настоящий интерпретатор называется `python` (или запускается через лаунчер `py`). В Unix-подобных системах `python` обычно тоже есть; если в системе есть только `python3`, укажите его в команде в `.zcode/config.json`. Шаблонная переменная `${ZCODE_PROJECT_DIR}` внутри сессии ZCode раскрывается в корень репозитория.

## Проверка и отладка

Сначала запустите контрактные тесты адаптеров репозитория.

```bash
make test-agent-rules
```

Они проверяют `globs` в виде скаляра и списка YAML, структурированные пути правок, активацию правил провайдеров, доставку в OpenCode и отсутствие ручного индекса для Codex.

Запустите скрипт вручную с синтетической полезной нагрузкой. Он читает JSON из stdin и пишет JSON в stdout, поэтому сессия ZCode не нужна.

```bash
echo '{"hook_event_name":"PreToolUse","tool_name":"Edit","session_id":"probe","tool_input":{"file_path":"external/httpserver/server.go"}}' | python .zcode/hooks/attach_rules.py
```

Поведение при старте сессии.

```bash
echo '{"hook_event_name":"SessionStart","session_id":"probe","source":"startup"}' | python .zcode/hooks/attach_rules.py
```

Пустой вывод - допустимый ответ, и означает он одно из трёх - ни один glob не совпал, правило уже отправлено в этой сессии или вход не удалось понять. Чтобы повторить проверку, очистите состояние дедупликации.

```bash
rm -rf "${TMPDIR:-/tmp}"/zcode-attach-rules-*
```

Чтобы проверить скрипт на временном каталоге правил и отдельном состоянии, не трогая общие для сессий значения по умолчанию, задайте `ZCODE_RULES_DIR` и `ZCODE_RULES_STATE_DIR`.

## Добавление или изменение правила

Правьте `.cursor/rules/*.mdc`, как и раньше. Хук не нужно менять при добавлении или переименовании темы, потому что он читает каталог при каждом событии.

- правило доступно из ZCode, только если в его frontmatter есть `globs` или `alwaysApply: true`;
- в том же изменении обновите намеренно поддерживаемую пару для Claude Code и держите тексты правил эквивалентными;
- после изменения frontmatter правил или любого из двух адаптеров на Python запустите `make test-agent-rules`.

## Связь с хуком Codex

Этот скрипт и `.codex/hooks/attach_rules.py` решают одну задачу и делят большую часть логики (`parse_rule`, `glob_to_regex`, состояние на сессию, разделение `SessionStart`/`PreToolUse`, пропуск без блокировки при ошибке). Оба принимают известные структурированные поля с путями; вариант для Codex вдобавок разбирает заголовки `apply_patch`. Держите общую логику синхронной и проверяйте оба адаптера через `make test-agent-rules`.

По документации ZCode, хуки и конфигурация лежат в `~/.zcode/cli/config.json` (пользовательская область) и `<repo>/.zcode/config.json` (область рабочей папки); поддерживаются события `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure` и `Stop`.
