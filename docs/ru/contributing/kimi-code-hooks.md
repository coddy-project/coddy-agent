# Хуки Kimi Code для правил проекта

Эта страница для контрибьюторов, которые работают с репозиторием через Kimi Code. Для Kimi Code она аналог страниц [Хуки Codex](codex-hooks.md) и [Хуки ZCode](zcode-hooks.md). Все три адаптера читают одни и те же файлы `.cursor/rules/*.mdc` через хуки жизненного цикла своего клиента.

## Зачем нужен хук

Kimi Code читает `AGENTS.md` репозитория, но не обрабатывает поля `globs` и `alwaysApply` в `.cursor/rules/*.mdc`. Просьба открыть подходящее правило перед каждой правкой остаётся рекомендацией, которую модель может пропустить.

`.kimi-code/hooks/attach_rules.py` сам читает frontmatter и передаёт тела правил модели. Дерево Cursor служит входными данными адаптера, а не универсальным форматом политик. Отдельной копии правил для Kimi Code адаптер не хранит.

## Что и когда срабатывает

Kimi Code (проверено на версии 2.3.2) даёт хуку два пути к модели. Поле `message`, которое печатает хук `UserPromptSubmit`, Kimi Code добавляет к промпту пользователя. Причину, по которой хук `PreToolUse` отказал в вызове, Kimi Code возвращает модели как результат этого вызова. Вывод хука `SessionStart` и вывод хука `PreToolUse`, который пропускает вызов, Kimi Code отбрасывает, поэтому адаптер на них не опирается.

| Событие | Матчер | Что делает хук |
|---|---|---|
| `UserPromptSubmit` | нет | добавляет к первому промпту сессии каждое правило, у которого во frontmatter стоит `alwaysApply: true` |
| `PreToolUse` | `^(Edit\|Write)$` | отказывает первому вызову, который затрагивает файлы под ещё не отправленными правилами с областью действия, и передаёт эти правила как причину отказа; модель повторяет вызов, и повтор выполняется |
| `PostCompact` | нет | забывает, какие правила уже отправлены, чтобы после сжатия контекста они пришли снова |

Все три записи запускают один скрипт, который выбирает ветку по полю `hook_event_name` из JSON. Путь вызова `Edit` или `Write` Kimi Code передаёт в `tool_input.path`. Скрипт распознаёт и другие известные поля с путями, в том числе во вложенных структурах, а относительный путь отсчитывает от папки, в которой работает сессия.

Отказ несёт не больше 45 000 символов, потому что более длинный результат инструмента Kimi Code сохраняет в файл и показывает модели только его начало. Если правила для вызова длиннее, каждая попытка приносит следующую часть, и вызов выполняется, когда придут все части. Для Go-файла этого репозитория обычно нужно два отказа.

## Включение

Kimi Code читает декларации хуков только из **пользовательского** `~/.kimi-code/config.toml` или `$KIMI_CODE_HOME/config.toml` и запускает их в каждом проекте из папки, в которой работает сессия. Поэтому репозиторий хранит `.kimi-code/hooks.toml` как фрагмент, который нужно перенести в пользовательский файл конфигурации. Сам Kimi Code этот фрагмент не загружает.

1. Добавьте три записи `[[hooks]]` из `.kimi-code/hooks.toml` в пользовательский `config.toml` и сохраните хуки, которые там уже есть. Не заменяйте этим фрагментом весь файл конфигурации;
2. В каждой команде замените `/path/to/coddy-agent` абсолютным путём к вашему клону. Если в пути есть пробелы, возьмите его в кавычки;
3. Запустите `kimi doctor`, чтобы проверить файл, затем откройте новую сессию Kimi Code.

Каждая команда называет скрипт по абсолютному пути, поэтому проект, открытый в Kimi Code, не может запустить через эти записи собственный скрипт. Скрипт отвечает только сессиям, которые работают внутри его клона. В других проектах он молчит, как и в другом клоне, вложенном в этот, например в связанном worktree. Чтобы подключить ещё один клон репозитория, добавьте для него отдельный набор записей с его путём.

Каждая команда заканчивается на `|| exit 0`. Если путь устарел, например после переноса клона, Python завершается с кодом 2, а код 2 Kimi Code считает отказом в промпте или в правке. `|| exit 0` гасит этот код, и хук просто ничего не делает. После переноса клона обновите путь.

Фрагмент вызывает `python3`. В Windows пишите `python`, потому что там имя `python3` может принадлежать заглушке Microsoft Store вместо установленного интерпретатора.

## Как это работает

- **Frontmatter разбирается так же, как в остальных адаптерах на Python.** Поддерживаются `globs` в виде скаляра и списка YAML, запятые в кавычках, экранированные символы, комментарии и многострочные flow-списки без сторонней YAML-библиотеки;
- **Сопоставление с glob-шаблонами написано вручную.** `**/` означает ноль или больше каталогов, `*` остаётся внутри одного сегмента пути, а одиночный `**` покрывает что угодно. Абсолютные пути внутри клона становятся относительными к его корню, относительные отсчитываются от папки сессии, а пути, которые оказываются за пределами клона, игнорируются;
- **Каждое правило приходит в сессию не больше одного раза до следующего сжатия контекста.** Состояние лежит в `<tempdir>/kimi-code-attach-rules-<repository-hash>/<session_id>.json`, поэтому клоны не влияют друг на друга. Возобновлённая сессия сохраняет состояние, а `/new` и `/clear` начинают сессию с новым id. Параллельные процессы синхронизируют доставку с помощью отдельной блокировки для каждой сессии, а состояние обновляется атомарной заменой файла;
- **Отказ выдаётся только после того, как он записан.** Если состояние нельзя заблокировать, записать или прочитать обратно, правка выполняется без правил с областью действия, так что повторный вызов никогда не получает отказ из-за тех же правил. Правила с `alwaysApply: true` в этом случае всё равно добавляются к промпту и могут повторяться;
- **При ошибке хук ничего не блокирует.** Некорректный JSON, нечитаемое правило или каталог состояния без права на запись не приводят к отказу. Хук доставляет инструкции и ничего не запрещает.

## Проверка и отладка

Запустите контрактные тесты адаптеров репозитория. Они проверяют Kimi Code вместе с остальными клиентами и читают вывод хука так же, как Kimi Code 2.3.2.

```bash
make test-agent-rules
```

Запустите настоящий скрипт с синтетической полезной нагрузкой Kimi Code из корня клона. Если в полезной нагрузке нет `cwd`, скрипт считает папкой сессии свою рабочую папку.

```bash
echo '{"hook_event_name":"UserPromptSubmit","session_id":"kimi-probe","prompt":"hello"}' | python3 .kimi-code/hooks/attach_rules.py
echo '{"hook_event_name":"PreToolUse","session_id":"kimi-edit-probe","tool_name":"Edit","tool_input":{"path":"cmd/coddy/providers.go"}}' | python3 .kimi-code/hooks/attach_rules.py
```

Первая команда печатает JSON-объект, в поле `message` которого лежат правила с `alwaysApply: true`. Вторая печатает отказ, в нём `hookSpecificOutput.permissionDecision` равно `deny`, а `permissionDecisionReason` содержит правила. Повторяйте её, чтобы получить следующую часть, пока вывод не станет пустым. Пустой вывод при коде выхода 0 означает, что ни один glob не совпал, правило уже отправлено в этой сессии, папка лежит за пределами клона или входные данные не удалось разобрать. Для повторной проверки используйте новый id сессии, укажите в `KIMI_CODE_RULES_STATE_DIR` путь к временному каталогу или удалите `<tempdir>/kimi-code-attach-rules-*`, чтобы очистить состояние. Для изолированных тестов укажите в `KIMI_CODE_RULES_DIR` каталог с фикстурными правилами внутри клона.

После изменения пользовательского файла конфигурации проверяйте хуки в **новой** сессии Kimi Code. Текущая сессия могла не перезагрузить их. Первый промпт покажет блок `UserPromptSubmit hook` с правилами `alwaysApply: true`, а первая правка Go-файла ещё до выполнения получит отказ, в котором придут правила с областью действия.

## Связь с другими адаптерами

Скрипт использует тот же разбор frontmatter, сопоставление путей, блокировки и файлы состояния, что и `.zcode/hooks/attach_rules.py`. Оба получают пути правок в полях JSON и не требуют заголовков Codex `apply_patch`. Доставка отличается, потому что Kimi Code не читает ни `additionalContext`, ни вывод `SessionStart`. Как и [плагин OpenCode](opencode-hooks.md), этот адаптер один раз отказывает в записи, чтобы передать правила с областью действия. При изменении адаптеров синхронизируйте общие части, а каждый изменённый адаптер проверяйте через `make test-agent-rules`.
