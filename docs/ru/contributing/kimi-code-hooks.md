# Хуки Kimi Code для правил проекта

Эта страница для контрибьюторов, которые работают с репозиторием через Kimi Code. Для Kimi Code она аналог страниц [Хуки Codex](codex-hooks.md) и [Хуки ZCode](zcode-hooks.md). Все три адаптера читают одни и те же файлы `.cursor/rules/*.mdc` через хуки жизненного цикла своего клиента.

## Зачем нужен хук

Kimi Code читает `AGENTS.md` репозитория, но не обрабатывает поля `globs` и `alwaysApply` в `.cursor/rules/*.mdc`. Просьба открыть подходящее правило перед каждой правкой остаётся рекомендацией, которую модель может пропустить.

`.kimi-code/hooks/attach_rules.py` сам читает frontmatter и передаёт тела правил модели. Дерево Cursor служит входными данными адаптера, а не универсальным форматом политик. Отдельной копии правил для Kimi Code адаптер не хранит.

## Что и когда срабатывает

Kimi Code (проверено на версии 2.3.2) даёт хуку два пути к модели. Поле `message`, которое печатает хук `UserPromptSubmit`, Kimi Code добавляет к промпту пользователя. Причину, по которой хук `PreToolUse` отказал в вызове, Kimi Code возвращает модели как результат этого вызова. Вывод хука `SessionStart` и вывод хука `PreToolUse`, который пропускает вызов, Kimi Code отбрасывает, поэтому адаптер на них не опирается.

| Событие | Матчер | Что делает хук |
|---|---|---|
| `UserPromptSubmit` | нет | добавляет к первому промпту сессии каждое правило, у которого во frontmatter стоит `alwaysApply: true` |
| `PreToolUse` | `^(Edit\|Write)$` | отклоняет первый вызов, затрагивающий файлы, на которые распространяются ещё не отправленные правила с областью действия, и передаёт эти правила как причину отказа; модель повторяет вызов, и повтор выполняется |
| `PostCompact` | нет | забывает, какие правила уже отправлены, чтобы после сжатия контекста они пришли снова |

Все три записи запускают один скрипт, который по полю `hook_event_name` из полезной нагрузки JSON определяет, какое событие обрабатывает. Путь вызова `Edit` или `Write` Kimi Code передаёт в `tool_input.path`. Скрипт распознаёт и другие распространённые поля с путями, в том числе во вложенных структурах, а относительный путь отсчитывает от папки, в которой работает сессия.

В причину отказа помещается не больше 45 000 символов, потому что Kimi Code выносит более длинный результат инструмента в файл и показывает модели только начало результата. Если правила для вызова длиннее этого предела, хук передаёт их частями, по одной части на попытку, и вызов выполняется, когда придут все части. Для Go-файла этого репозитория обычно нужно два отказа.

## Включение

Kimi Code читает декларации хуков только из **пользовательского** `~/.kimi-code/config.toml` или `$KIMI_CODE_HOME/config.toml` и запускает их в каждом проекте из папки, в которой работает сессия. Поэтому репозиторий хранит `.kimi-code/hooks.toml` как фрагмент, записи которого нужно добавить в пользовательский файл конфигурации. Сам Kimi Code этот фрагмент не загружает.

1. Добавьте три записи `[[hooks]]` из `.kimi-code/hooks.toml` в пользовательский `config.toml` и оставьте хуки, которые там уже есть. Не заменяйте этим фрагментом весь файл конфигурации;
2. В каждой команде замените `/path/to/coddy-agent` абсолютным путём к вашему клону. Если в пути есть пробелы, возьмите его в кавычки;
3. Запустите `kimi doctor`, чтобы проверить файл, затем откройте новую сессию Kimi Code.

В каждой команде указан абсолютный путь к скрипту, поэтому проект, открытый в Kimi Code, не может запустить через эти записи собственный скрипт. Скрипт реагирует только на сессии, которые работают внутри его клона. В других проектах он молчит, как и в любом другом клоне внутри этого, например в связанном worktree. Чтобы подключить другой клон репозитория, добавьте ещё один набор записей с путём к нему.

Каждая команда заканчивается на `|| exit 0`. Если путь устарел, например после переноса клона, Python завершается с кодом 2, а Kimi Code считает код 2 отказом принять промпт или выполнить правку. `|| exit 0` заменяет этот код нулём, и хук ничего не делает. После переноса клона обновите путь.

Фрагмент вызывает `python3`. В Windows пишите `python`, потому что `python3` может указывать на заглушку Microsoft Store, а не на установленный интерпретатор.

## Как это работает

- **Frontmatter разбирается так же, как в остальных адаптерах на Python.** Поддерживаются `globs` в виде скаляра и списка YAML, запятые в кавычках, экранированные символы, комментарии и многострочные flow-списки без сторонней YAML-библиотеки;
- **Сопоставление с glob-шаблонами написано вручную.** `**/` означает ноль или больше каталогов, `*` остаётся внутри одного сегмента пути, а одиночный `**` покрывает что угодно. Абсолютный путь внутри клона пересчитывается от корня клона, относительный отсчитывается от папки сессии, а пути, которые оказываются за пределами клона, игнорируются;
- **Каждое правило приходит в сессию не больше одного раза до следующего сжатия контекста.** Состояние лежит в `<tempdir>/kimi-code-attach-rules-<repository-hash>/<session_id>.json`, поэтому один клон не может подавить доставку правил в другом. Возобновлённая сессия сохраняет состояние, а `/new` и `/clear` начинают сессию с новым id. Параллельные процессы выполняют доставку по очереди под блокировкой, отдельной для каждой сессии, а состояние обновляется атомарной заменой файла;
- **Отказ выдаётся только после того, как он записан.** Если состояние не удаётся заблокировать, записать или прочитать после записи, правка выполняется без правил с областью действия, поэтому повторный вызов уже не получит отказ из-за тех же правил. Правила с `alwaysApply: true` в этом случае всё равно добавляются к промпту и могут повторяться;
- **При сбое хук ничего не отклоняет.** Некорректный JSON, нечитаемое правило или каталог состояния, недоступный для записи, не приводят к отказу. Хук доставляет инструкции, но не заставляет модель их выполнять.

## Проверка и отладка

Запустите контрактные тесты адаптеров репозитория. Они проверяют Kimi Code вместе с остальными клиентами и читают вывод хука так же, как Kimi Code 2.3.2.

```bash
make test-agent-rules
```

Запустите сам скрипт с синтетическими полезными нагрузками Kimi Code из корня клона. Если в полезной нагрузке нет `cwd`, папкой сессии скрипт считает текущую папку своего процесса.

```bash
echo '{"hook_event_name":"UserPromptSubmit","session_id":"kimi-probe","prompt":"hello"}' | python3 .kimi-code/hooks/attach_rules.py
echo '{"hook_event_name":"PreToolUse","session_id":"kimi-edit-probe","tool_name":"Edit","tool_input":{"path":"cmd/coddy/providers.go"}}' | python3 .kimi-code/hooks/attach_rules.py
```

Первая команда печатает JSON-объект, в поле `message` которого содержатся правила с `alwaysApply: true`. Вторая печатает отказ, в котором `hookSpecificOutput.permissionDecision` равно `deny`, а `permissionDecisionReason` содержит правила. Повторяйте её, чтобы получить следующую часть, пока вывод не станет пустым. Пустой вывод при коде выхода 0 означает, что ни один glob-шаблон не совпал, правило уже отправлено в этой сессии, папка лежит за пределами клона или входные данные не удалось разобрать. Для повторной проверки используйте новый id сессии, укажите в `KIMI_CODE_RULES_STATE_DIR` путь к временному каталогу или удалите `<tempdir>/kimi-code-attach-rules-*`, чтобы очистить состояние. Для изолированных тестов в `KIMI_CODE_RULES_DIR` можно указать каталог с тестовым деревом правил внутри клона.

После изменения пользовательского файла конфигурации проверяйте хуки в **новой** сессии Kimi Code и не считайте, что уже открытая сессия перезагрузила их. Первый промпт покажет блок `UserPromptSubmit hook` с правилами `alwaysApply: true`. Первая правка Go-файла будет отклонена ещё до выполнения, а причина отказа будет содержать правила с областью действия.

## Связь с другими адаптерами

Разбор frontmatter, сопоставление с glob-шаблонами, блокировки и файлы состояния у этого скрипта общие с `.zcode/hooks/attach_rules.py`. Оба получают пути изменяемых файлов в полях JSON и не требуют заголовков Codex `apply_patch`. Доставка отличается, потому что Kimi Code не читает ни `additionalContext`, ни вывод `SessionStart`. Как и [плагин OpenCode](opencode-hooks.md), этот адаптер один раз отказывает в записи, чтобы передать правила с областью действия. При изменении адаптеров синхронизируйте общие части, а каждый изменённый адаптер проверяйте через `make test-agent-rules`.
