# Хуки Kimi Code для правил проекта

Эта страница для контрибьюторов, которые работают с репозиторием через Kimi Code. Для Kimi Code она аналог страниц [Хуки Codex](codex-hooks.md) и [Хуки ZCode](zcode-hooks.md). Все три адаптера читают одни и те же файлы `.cursor/rules/*.mdc` через хуки жизненного цикла своего клиента.

## Зачем нужен хук

Kimi Code читает `AGENTS.md` репозитория, но не обрабатывает поля `globs` и `alwaysApply` в `.cursor/rules/*.mdc`. Просьба открыть подходящее правило перед каждой правкой остаётся рекомендацией, которую модель может пропустить.

`.kimi-code/hooks/attach_rules.py` сам читает frontmatter и вставляет тела правил в контекст хука. Дерево Cursor служит входными данными адаптера, а не универсальным форматом политик. Отдельной копии правил для Kimi Code адаптер не хранит.

## Что и когда срабатывает

| Событие | Матчер | Что вставляется |
|---|---|---|
| `SessionStart` | `startup\|resume` | каждое правило, у которого во frontmatter стоит `alwaysApply: true` |
| `PreToolUse` | `^(Edit\|Write)$` | правила, чьи `globs` покрывают файл из ожидающего вызова инструмента |

Оба обработчика запускают один скрипт, который выбирает ветку по полю `hook_event_name` из JSON. Kimi Code передаёт пути `Edit` и `Write` в `tool_input.path`; скрипт также распознаёт другие известные поля с путями во вложенных структурах.

## Включение

Сейчас Kimi Code читает декларации хуков из **пользовательского** `~/.kimi-code/config.toml` или `$KIMI_CODE_HOME/config.toml`. Конфигурация хуков из рабочей папки автоматически не загружается. Поэтому `.kimi-code/hooks.toml` в репозитории - фрагмент для объединения с пользовательским файлом конфигурации, а не автоматически подключаемый файл конфигурации.

Добавьте две записи `[[hooks]]` из `.kimi-code/hooks.toml` в пользовательский `config.toml`, сохраните уже настроенные хуки и откройте новую сессию Kimi Code. Не заменяйте этим фрагментом весь файл конфигурации. Декларации действуют глобально, а команда использует путь относительно текущей рабочей папки. В клоне без `.kimi-code/hooks/attach_rules.py` команда не подключит правила, а fail-open в Kimi Code не прервёт работу сессии.

Команда вызывает `python`, а не `python3`, потому что в Windows имя `python3` может принадлежать заглушке Microsoft Store вместо установленного интерпретатора. Python 3 должен быть в `PATH`; если в Unix-подобной системе есть только `python3`, измените команду в пользовательском файле конфигурации.

## Как это работает

- **Frontmatter разбирается так же, как в остальных адаптерах на Python.** Поддерживаются `globs` в виде скаляра и списка YAML, запятые в кавычках, экранированные символы, комментарии и многострочные flow-списки без сторонней YAML-библиотеки;
- **Сопоставление с glob-шаблонами написано вручную.** `**/` означает ноль или больше каталогов, `*` остаётся внутри одного сегмента пути, а одиночный `**` покрывает что угодно. Абсолютные пути внутри клона становятся относительными к его корню; пути за его пределами, включая относительные с выходом за корень, игнорируются;
- **Каждое правило с областью действия вставляется не больше одного раза за активный контекст сессии.** Состояние лежит в `<tempdir>/kimi-code-attach-rules-<repository-hash>/<session_id>.json`, поэтому клоны не влияют друг на друга. `resume` сохраняет дедупликацию правил с областью действия, а `startup` сбрасывает её. Параллельные процессы синхронизируют доставку с помощью отдельной блокировки для каждой сессии, а состояние обновляется атомарной заменой файла. Если блокировка или запись состояния недоступны, контекст всё равно выводится, но правила могут временно повторяться;
- **При ошибке хук ничего не блокирует.** Некорректный JSON, нечитаемое правило или каталог состояния без права на запись не приводят к блокирующему ответу. Хук доставляет инструкции и не служит границей безопасности.

## Проверка и отладка

Запустите контрактные тесты адаптеров репозитория, которые проверяют Kimi Code вместе с остальными клиентами.

```bash
make test-agent-rules
```

Запустите скрипт с синтетической полезной нагрузкой Kimi Code.

```bash
echo '{"hook_event_name":"SessionStart","session_id":"kimi-probe","source":"startup"}' | python .kimi-code/hooks/attach_rules.py
echo '{"hook_event_name":"PreToolUse","session_id":"kimi-edit-probe","tool_name":"Edit","tool_input":{"path":"external/httpserver/server.go"}}' | python .kimi-code/hooks/attach_rules.py
```

При совпадении скрипт выводит JSON-объект с `hookSpecificOutput.additionalContext`. Пустой вывод при коде выхода 0 означает, что ни один glob не совпал, правило уже отправлено в этой сессии или входные данные не удалось разобрать. Для повторной проверки используйте новый id сессии, укажите в `KIMI_CODE_RULES_STATE_DIR` путь к временному каталогу или удалите `<tempdir>/kimi-code-attach-rules-*`, чтобы очистить состояние дедупликации. Для изолированных тестов укажите в `KIMI_CODE_RULES_DIR` каталог с фикстурными правилами.

После изменения пользовательского файла конфигурации проверяйте хуки в **новой** сессии Kimi Code. Текущая сессия могла не перезагрузить их.

## Связь с другими адаптерами

Скрипт повторяет `.zcode/hooks/attach_rules.py`. Оба получают пути правок в полях JSON и не требуют заголовков Codex `apply_patch`. При изменении адаптеров синхронизируйте разбор frontmatter, сопоставление путей, блокировки и работу с состоянием, а каждый изменённый адаптер проверяйте через `make test-agent-rules`. OpenCode использует плагин; см. [Хуки OpenCode](opencode-hooks.md).
