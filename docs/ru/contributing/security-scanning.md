# Сканирование AppSec

*Как открытые сканеры (trivy, semgrep, govulncheck) запускаются локально и в CI, куда попадают отчёты, как их читать и как ужесточается гейт. Модель безопасности самого агента - что он может выполнять, режимы разрешений, доверие к проекту - описана на странице [Безопасность и доверие](../operate/security.md).*

В issue [#374](https://github.com/coddy-project/coddy-agent/issues/374) попросили подключить к репозиторию открытые сканеры AppSec. Вызываются они только из одного скрипта, поэтому находка, которая роняет пайплайн, воспроизводится на машине разработчика одной командой.

```bash
make security          # every scanner, the CI gate behaviour
make sec-trivy         # trivy only
make sec-semgrep       # semgrep only
make sec-govulncheck   # govulncheck only
make sec-report        # every scanner, gate off — findings never fail, errors still do
```

Каждая цель - тонкая обёртка `SEC_*` вокруг `scripts/security-scan.sh`; если нужна комбинация, для которой цели нет, вызывайте скрипт напрямую.

## Что запускается

- **trivy** - сканирование файловой системы чекаута: уязвимости зависимостей (`go.mod`, `package-lock.json`, …), секреты и ошибки конфигурации IaC (Dockerfile). Находки по конфигурации собираются, но остаются **вне гейта**, потому что это вопросы политики, а не уязвимости;
- **semgrep** - SAST с наборами правил из реестра, перечисленными в `SEMGREP_CONFIGS` (по умолчанию `p/golang p/typescript`). Пока только отчёт, потому что накопившихся находок столько, что гейт с первого дня заблокировал бы каждый пул-реквест;
- **govulncheck** - сверка кода с базой уязвимостей Go со всеми поставляемыми тегами сборки, кроме `ui` (`GOVULNCHECK_TAGS`, из `make print-lint-tags-no-ui`; ресурсов SPA, которые встраивает `ui`, в свежем чекауте нет, а Go-кода, где могла бы спрятаться уязвимость, этот тег не добавляет). Он читает граф вызовов, поэтому отличает уязвимую функцию, которую код вызывает, от функции, которая просто лежит в требуемом модуле, чего trivy не умеет; и он оценивает стандартную библиотеку инструментария, которым идёт сборка, а её trivy не видит вовсе. Именно так нашлись отказ в обслуживании в `x/crypto/ssh`, достижимый из инструмента `ssh`, и релиз, собранный версией Go, в которой не хватало года исправлений стандартной библиотеки (см. [Инструментарий Go](#инструментарий-go)).

## Запуск и версии

Если бинарник сканера есть в `PATH`, используется он; иначе запускается закреплённый docker-образ (`aquasec/trivy`, `semgrep/semgrep`, константы `tag@sha256:` в начале `scripts/security-scan.sh`). Собственного образа у govulncheck нет. Закреплённый образ Go (`GO_IMAGE`) запускает релиз из `GOVULNCHECK_VERSION` через `go run` и держит кэши модулей и сборки в `dist/security/.cache/`. `SEC_DOCKER=0` запрещает этот запасной путь, для машин, где docker под запретом.

Чтобы обновить сканер, скачайте новый образ, возьмите его дайджест (`docker images --digests`), обновите константу, запустите `make security` и сравните сводку с предыдущей - обновление правил или базы может изменить находки без единого коммита, поэтому каждое обновление идёт отдельным небольшим пул-реквестом.

## Отчёты

Всё складывается в `dist/security/` (каталог игнорируется git):

- `trivy.json`, `semgrep.json` - полные находки всех уровней серьёзности;
- `govulncheck.json` - JSON-поток govulncheck, то есть каждая запись об уязвимости с трассой, которая к ней ведёт (`govulncheck -tags <tags> ./...` выводит то же текстом);
- `trivy.sarif`, `semgrep.sarif` - для GitHub code scanning; SARIF trivy не включает секреты, потому что code scanning сохраняет найденный текст;
- `summary.md` - число находок по уровням серьёзности, его и показывает сводка задания CI;
- `.cache/` - кэши сканеров, чтобы повторные запуски были быстрыми.

## Гейт

Отчёт и гейт разделены. Сканирование всегда пишет полный отчёт, затем скрипт считает уровни серьёзности по JSON и решает, каким будет код выхода.

| Параметр | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `SEC_FAIL_TRIVY` | `UNKNOWN\|LOW\|MEDIUM\|HIGH\|CRITICAL\|off` | `CRITICAL` | Падать на находках уязвимостей и секретов этого уровня и выше |
| `SEC_FAIL_SEMGREP` | `ERROR\|WARNING\|INFO\|off` | `off` | То же в собственных уровнях серьёзности semgrep |
| `SEC_FAIL_GOVULNCHECK` | `symbol\|package\|module\|off` | `symbol` | Падать на уязвимой функции, которую вызывает код (`symbol`), ещё и на уязвимом пакете, который он только импортирует (`package`), или на любом уязвимом модуле, который он требует (`module`) |
| `GOVULNCHECK_TAGS` | теги сборки через запятую | все поставляемые теги, кроме `ui` | С какими тегами govulncheck компилирует дерево |
| `SEC_SCANNERS` | любой список через запятую из `trivy`, `semgrep`, `govulncheck` | все три | Какие сканеры запускаются |
| `SEMGREP_CONFIGS` | значения `--config` через пробел | `p/golang p/typescript` | Наборы правил из реестра (плавающие псевдонимы, находки могут меняться при обновлении правил) |
| `SEMGREP_APP_TOKEN` | токен | не задан | Необязателен; снимает ограничения частоты запросов к реестру и включает правила Pro. Пул-реквесты из форков его никогда не видят, и задание там намеренно работает только на отчёт |
| `SEC_DOCKER` | `0\|1` | `1` | Разрешить запасной путь через docker |

Неизвестное значение параметра, отсутствующий инструмент, неработающий docker или упавшее сканирование считаются эксплуатационной ошибкой и роняют прогон, в том числе под `sec-report`, где прощаются только *находки*.

Сама база уязвимостей не закреплена. Локальный прогон и CI совпадают в точности, только если видят одно и то же состояние базы, поэтому перезапустите проверку локально, прежде чем списывать падение в CI на окружение.

У govulncheck нет уровней серьёзности, поэтому его гейт вместо них учитывает глубину. По умолчанию прогон падает только на уязвимой функции, которую вызывает код; запись об уязвимости в модуле, который никто не импортирует (например, неподдерживаемый `golang.org/x/crypto/openpgp`, для которого нет исправления), выводится на уровне `module` и остаётся информационной.

## Инструментарий Go

В `go.mod` две строки: `go 1.26.0`, самый старый Go, который компилирует модуль, и `toolchain go1.26.8`, самый старый релиз, с которым линкуется любая сборка. CI устанавливает Go по строке `go` (`actions/setup-go` с `go-version-file`), после чего команда `go` переключается на релиз из `toolchain` (`GOTOOLCHAIN=auto`, значение по умолчанию у официального Go), поэтому задания тестов, релизные архивы и пакеты линкуются ровно со стандартной библиотекой этого релиза. Переключение идёт только вверх. Docker-образ (на этапе сборки которого задан `GOTOOLCHAIN=auto`, потому что официальный образ закрепляет `local`) и локальная сборка используют Go из образа `golang:1.26` или установленный Go, если тот новее, а это только добавляет исправления.

Без строки `toolchain` каждая сборка использовала ровно релиз из строки `go`. Архивы времён 1.25 собирались с `go1.25.0`, без всех исправлений безопасности стандартной библиотеки, вышедших после него, и govulncheck с этим инструментарием перечисляет 32 таких уязвимости в функциях, которые вызывает код (`crypto/tls`, `crypto/x509`, `net/http`, `net/url`, `os.Root`, `archive/tar`, …).

govulncheck оценивает стандартную библиотеку того инструментария, который выбирает `go`, поэтому еженедельное сканирование падает, когда патч-релиз Go исправляет уязвимость, до которой доходит код. Исправление - пул-реквест в одну строку.

```bash
go mod edit -toolchain=go1.26.N   # the patch release that carries the fix
make sec-govulncheck              # green again
```

В том же изменении поднимите `GO_IMAGE` в `scripts/security-scan.sh` до того же релиза, чтобы запасной путь через docker не скачивал инструментарий при каждом запуске. Строку `go` поднимайте, только когда коду нужны более новые язык или библиотека.

## Разбор находок и подавление

- **`.trivyignore.yaml`** - принятые находки CVE и ошибок конфигурации, каждая запись со `statement` и датой `expired_at`, чтобы список устаревал, а не прощал новые проблемы вечно;
- **`trivy.yaml`** - `scan.skip-dirs` для путей, которых нет в свежем чекауте (`node_modules`, `dist`, …). Trivy не учитывает `.gitignore`, и без этого локальное сканирование обходит деревья, которых CI никогда не видит. Подавления правил для секретов поддерживаются, но требуют того же срока действия и письменного обоснования, что и принятая CVE; по возможности лучше правило `skip-dirs`/`skip-files` или исправление;
- **`.semgrepignore`** - минимальный (`.venv`); semgrep сам учитывает `.gitignore`. Подавление в строке пишется как `// nosemgrep` (Go/TS) или `# nosemgrep` (YAML/shell), всегда с комментарием-обоснованием, лучше с id правила (`// nosemgrep: <rule-id>`). semgrep сохраняет подавленную находку в своём SARIF с записью `suppressions`, а code scanning всё равно поднял бы по ней оповещение, поэтому `scripts/security-scan.sh` исключает такие находки из `semgrep.sarif`, как уже делают `semgrep.json` и гейт;
- тестовые фикстуры содержат намеренно поддельные учётные данные (`sk-test`, PEM-блоки в `pictures_test.go`, ключи-заглушки в `examples/`). Это ожидаемые находки; принимайте их через файлы игнорирования выше, а не "исправляйте" фикстуру.

## CI - `.github/workflows/security.yaml`

Workflow запускается на пул-реквестах, пушах в `main`, по еженедельному cron в понедельник и вручную. Задание вызывает `make security`, загружает оба файла SARIF в code scanning (с разными значениями `category`), прикладывает `dist/security/` как артефакт и выводит сводку по уровням серьёзности в сводку задания, даже когда гейт не пройден.

Пул-реквесты из форков сканируются и проходят гейт как обычно, но загрузка их SARIF пропускается - токен форка не может писать в `security-events`, а недоверенный код никогда не должен заносить находки в историю code scanning этого репозитория. Артефакт всё равно содержит находки для мейнтейнеров. Чтобы гейт блокировал слияния, задание workflow (`AppSec scanners`) нужно отметить как обязательное в защите ветки.

## Поэтапное ужесточение

Гейт задуман так, чтобы ужесточаться по мере разбора накопившихся находок, и каждый шаг - отдельный пул-реквест со своим разбором:

1. `SEC_FAIL_TRIVY=CRITICAL` ← сейчас;
2. `SEC_FAIL_TRIVY=HIGH`;
3. `SEC_FAIL_SEMGREP=ERROR`, затем `WARNING`;
4. включить в гейт `misconfig` и более широкие наборы semgrep (`p/bash`, `p/yaml`, `p/dockerfile`, `p/react`), когда их находки будут разобраны.
