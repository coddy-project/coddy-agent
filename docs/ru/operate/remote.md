# Удалённый режим

`coddy serve` на одной машине можно вести с другой. Консоль и `coddy acp` принимают `--remote`, у веб-интерфейса внизу боковой панели есть меню окружения, и все три обращаются к HTTP API сервера - агент, его инструменты, его сессии и политика разрешений живут на сервере, а клиент отображает транскрипт и отвечает на вопросы и запросы разрешений. Эта страница - руководство пользователя; проектный документ с обоснованием и отложенными частями - [Дизайн удалённого управления](../../plans/remote-control.md).

## Что такое удалённый режим

| Клиент | Как подключается | Что нужно от сервера |
|---|---|---|
| консоль (`coddy`, `coddy cli`, `coddy -p "..."`) | `--remote <target>` | HTTP API (тег сборки `http`, `httpserver.enable`, включён по умолчанию) |
| редактор по ACP (`coddy acp`) | `--remote <target>` | то же |
| веб-интерфейс | меню окружения внизу боковой панели | то же, а также CORS на сервере |

С `--remote` локальный процесс не держит хранилища сессий, не запускает ни планировщик, ни цикл агента; каждый вызов сессии проксируется на сервер через `/v1/*` и `/coddy/*`, а потоковый ответ возвращается по SSE и переводится в обновления, которые консоль и ACP-клиент уже понимают. Спецификации - `features/remote_client.feature` и `features/cli_remote.feature`; живые проверки - `examples/cli/cli_e2e_remote.py`, `examples/acp/acp_remote.py` и `examples/httpserver/http_e2e_remote.py`.

## Как указать удалённый сервер

`--remote` принимает три варианта записи:

- **имя из конфигурации** из `httpserver.remotes` в собственном `config.yaml` клиента (без учёта регистра);
- голый **`host:port`**, к которому спереди добавляется `http://`;
- полный **URL `http://` или `https://`**, при необходимости с префиксом пути.

Адрес должен быть голым origin - строка запроса, фрагмент или учётные данные пользователя в URL отвергаются. Именованный удалённый сервер хранит имя, URL и, если вы решите держать его там, токен, который нужно предъявить.

```yaml
httpserver:
  remotes:
    - name: nas02
      url: "https://nas02.example:12345"
    - name: office-relay
      url: "http://relay.lan:12346"
      token: "${CODDY_RELAY_TOKEN}"   # optional, see The token below
```

```bash
coddy --remote nas02                 # by name
coddy --remote 192.168.1.20:12345    # bare host:port, plain http
coddy acp --remote https://nas02.example:12345
```

Тот же список `remotes` сервер предлагает в меню окружения своего веб-интерфейса, так что запись работает в двух ролях - заведите её в конфигурации машины, за которой вы работаете. Релей роя указывается так же; меню узнаёт его и перечисляет агентов за ним ([Меню окружения](#меню-окружения)).

## Токен

На сервере аутентификация выключена, пока не задан токен. Её включают `httpserver.auth_token` в `config.yaml` (с подстановкой `${ENV}`), `--auth-token` у `coddy serve` или переменная `CODDY_HTTP_TOKEN`; после этого каждый маршрут `/v1/*` и `/coddy/*` требует `Authorization: Bearer <token>`, а иначе отвечает `401`. Оболочка SPA и её статические файлы остаются публичными, чтобы браузер мог загрузить страницу и спросить токен; `/docs` и `/openapi.*` защищены, если не задано `httpserver.public_docs: true`. `GET /coddy/config` никогда не возвращает токен (он сообщает только `auth_configured`), а токен, переданный флагом или через окружение, переживает горячую перезагрузку `PUT /coddy/config` и не записывается в файл. Сервер, привязанный не к loopback и без токена, при старте пишет в лог предупреждение, если не задано `httpserver.allow_insecure: true`.

Токен предъявляет API-клиент. В браузере нет поля, куда его ввести, поэтому с одним только токеном веб-интерфейс показывает `Unauthorized (401)`; форма входа, описанная ниже, - браузерная половина той же проверки.

На клиенте токен берётся из первого найденного источника:

- `--remote-token`;
- `token` той записи `httpserver.remotes`, к которой относится цель, - записи с этим именем, записи с этим адресом или записи релея, если цель - точка монтирования его узла (`<relay>/swarm/nodes/<name>`, она берёт клиентский токен релея);
- `CODDY_REMOTE_TOKEN`.

Токен записи побеждает переменную, потому что он привязан к одному адресату, а переменная - ни к какому. Он необязателен, и у хранения его в файле есть цена - его получает каждый браузер, который читает конфигурацию этого сервера (`GET /coddy/config`), так же как получает `api_key` провайдера, и любой, кто может прочитать файл. Запишите его как ссылку `${ENV}`, чтобы сам секрет лежал в `.env`. Без него веб-интерфейс принимает токен в своей форме **Подключиться к…** и хранит его только в браузере (`localStorage`, для каждого удалённого сервера отдельно), а консоль читает флаг или переменную.

У `coddy serve` нет собственного TLS, поэтому токен, отправленный на адрес `http://` не на loopback, идёт открытым текстом; консоль и `coddy acp` выводят предупреждение, когда это вот-вот произойдёт. Поставьте перед сервером обратный прокси, который терминирует TLS, или подключайтесь к нему через SSH-туннель, при котором адрес остаётся на loopback.

```bash
ssh -N -L 12345:127.0.0.1:12345 nas02   # in one terminal
coddy --remote 127.0.0.1:12345          # in another
```

## Форма входа

`coddy serve` в сети доступен для чтения каждому, кто найдёт порт, - транскрипты, вывод инструментов, обозреватель рабочей папки, редактор конфигурации. `httpserver.login` закрывает его одной учётной записью оператора, и через форму браузер входит под ней. По умолчанию она выключена; конфигурация, в которой она не упомянута, работает точно так же, как раньше.

```bash
coddy serve set-password --user pasha
```

Команда дважды спрашивает пароль, записывает хеш argon2id прямо в `config.yaml` (комментарии и порядок ключей сохраняются) и включает форму. С этого момента анонимный браузер получает вместо приложения экран входа, и ничего под `/v1/*` или `/coddy/*` не читается, пока он его не пройдёт. Сама страница и её статические файлы остаются публичными, чтобы экран мог загрузиться; `/docs`, как и раньше, следует `public_docs`.

Для контейнера или юнита systemd учётную запись можно задать в окружении - `CODDY_HTTP_USER` и `CODDY_HTTP_PASSWORD` (обычно в `$CODDY_HOME/.env`). Они сами включают форму, побеждают учётную запись из файла и никогда в него не записываются. Явное `login.enable: false` выключает форму, даже если переменные заданы.

```yaml
httpserver:
  host: 0.0.0.0
  auth_token: "${CODDY_HTTP_TOKEN}"   # for coddy --remote, coddy acp --remote, a relay, scripts
  login:
    enable: true
    user: "pasha"
    password_hash: "$$argon2id$$v=19$$..."
    session_ttl_hours: 720            # 0 = until the browser closes
```

**Эти два вида учётных данных не взаимозаменяемы.** Форма нужна браузерам; всё, что не браузер, - `coddy --remote`, `coddy acp --remote`, релей роя, который монтирует этот узел, Python-харнесы, **Authorize** в Swagger - по-прежнему предъявляет bearer-токен. Если закрыть сервер только паролем без `auth_token`, всё это ломается, и `coddy serve` пишет об этом в лог при старте. Если с сервером работает что-то кроме браузера, задайте оба.

Вход ставит cookie с `HttpOnly` и `SameSite=Strict`, который открывает те же маршруты, что и токен, включая потоки. Выход (пункт внизу боковой панели) удаляет сессию на сервере, поэтому копия cookie, снятая в другом месте, тоже перестаёт работать. Сессии живут в памяти - они переживают сохранение настроек со страницы, перезапуск процесса их завершает, а смена пароля завершает все сессии, открытые с ним. Полное поведение, включая правило CSRF для записей с аутентификацией по cookie и ограничение частоты попыток при неверном пароле, описано в [HTTP API](../reference/http-api.md#вход-в-веб-интерфейс-необязательно).

У `coddy serve` по-прежнему нет собственного TLS, поэтому пароль, введённый на странице с адресом `http://` не на loopback, идёт открытым текстом точно так же, как токен. Поставьте перед сервером обратный прокси, который терминирует TLS, или подключайтесь через SSH-туннель, описанный выше.

## CORS для веб-интерфейса

Если браузер загрузил интерфейс с одного origin и вызывает API другого, удалённый сервер должен явно включить CORS.

```yaml
httpserver:
  auth_token: "${CODDY_HTTP_TOKEN}"
  cors:
    enable: true
    allow_loopback: true          # the laptop's own coddy serve, on any loopback address and port
    allowed_origins: ["https://my-ui.example"]   # exact origins elsewhere; or ["*"]
  remotes:                       # optional: offered in this server's own UI
    - name: "prod box"
      url: "https://box.example:12345"
```

Когда `cors.enable` включён, preflight-запрос с разрешённого origin получает `204` с `Access-Control-Allow-Origin` (origin возвращается эхом или `*`, если так настроено) и `Access-Control-Allow-Headers: Authorization, Content-Type, X-Coddy-Session-ID`; origin, которого нет в списке, не получает заголовков CORS, и браузер сообщает о заблокированном запросе. Какие origin разрешены, задают три настройки. `allowed_origins` перечисляет их точно, причём `http://localhost:12345`, `http://127.0.0.1:12345` и `http://localhost:5173` - три разных origin. `allow_loopback` пропускает любую страницу, отданную с машины самого браузера (origin `http` или `https` с хостом `localhost`, именем `*.localhost`, адресом из `127.0.0.0/8` или `[::1]`, на любом порту), - это случай ноутбука, где веб-интерфейс приходит с собственного `coddy serve`, а его порт меняется от установки к установке; origin возвращается эхом и никогда не расширяется до `*`. `"*"` пропускает любую страницу откуда угодно, а поскольку список читается первым, `"*"` в нём отвечает `*` и loopback-origin, включён `allow_loopback` или нет. Bearer-токен по-прежнему проверяется на самом запросе, какая бы из трёх настроек ни пропустила страницу. CORS решает, покажет ли браузер странице ответ, а не даст ли его сервер, поэтому `allow_loopback` и `"*"` безопасны ровно настолько, насколько безопасен токен или форма входа перед API; `coddy serve` предупреждает об этом при старте, а `--dry-run` сообщает, если любая из них включена, а сервер не требует учётных данных ([Безопасность и доверие](security.md#http-интерфейс)). У релея роя свой CORS, `swarm.cors`, с теми же тремя ключами - странице, отданной в другом месте и работающей с релеем, нужен её origin там, а за узел за релеем отвечает CORS релея и никогда не CORS узла.

![Предупреждение о состоянии удалённого сервера, которого CORS не пускает к странице на loopback-адресе](../../assets/remote/env-banner-cors-loopback-dark-1280.png)

*Страница, отданная собственным coddy serve ноутбука, - предупреждение называет список точных origin и переключатель `allow_loopback`, который пропускает страницу на любом порту*

`EventSource` не умеет отправлять заголовки, поэтому два маршрута подписки SSE, `GET /coddy/sessions/{id}/composer-stream` и `GET /coddy/events`, принимают ещё и `?access_token=`; встроенный интерфейс вместо этого получает эти потоки через fetch, поэтому его заголовок применяется и токен не попадает в URL. Справка - [HTTP API](../reference/http-api.md#аутентификация-необязательно).

## Меню окружения

Окружение - пункт внизу боковой панели веб-интерфейса, ниже пункта "Настройки" и выше пункта "Выйти". Пока страница управляет собственным сервером, на нём значок ноутбука, а пока она управляет удалённым - два шеврона, направленных друг к другу; точка показывает, отвечает ли этот хост, а подсказка называет **Локальное** или активный удалённый сервер. На планшете или телефоне это один из значков верхней панели, и он никогда не прячется в **Ещё**. Его меню открывается рядом с боковой панелью (на узком экране - листом снизу), в нём есть раздел **Окружение** с пунктом "Локальное" и раздел **Удалённые** с настроенными на сервере `remotes` и пунктом **Подключиться к…** (имя, URL, токен). Список читается с собственного сервера страницы, когда меню открывается, и ещё раз всякий раз, когда конфигурация этого сервера заменяется, поэтому удалённый сервер, добавленный сохранением настроек или `config_commit` агента, появляется без перезагрузки страницы. Запись без `name` показывается под именем, которое сообщает сам удалённый сервер (это имя релея, то есть имя его хоста, если `swarm.name` не задаёт другое, или имя хоста агента), с адресом рядом, а если он ничего не сообщает - только по адресу. При выборе записи интерфейс сразу подключается к ней и запускает приложение заново, поэтому список сессий, модели и значения по умолчанию перечитываются с выбранного бэкенда - между двумя удалёнными серверами на месте, без перезагрузки страницы, а на "Локальное" и обратно с перезагрузкой. Если выбрать запись, на которой страница уже стоит, всё перечитывается заново - так можно вернуться к удалённому серверу после того, как он лежал; оболочка SPA всегда приходит с локального origin, поэтому **Локальное** остаётся доступным в меню, даже когда удалённый сервер не работает.

![Меню окружения рядом с боковой панелью - релей, его агенты и удалённые серверы, которыми пока нельзя пользоваться](../../assets/env-menu-states-dark-1280.png)

*Релей со списком своих агентов под ним, релей, которому нужен его токен, ещё один, которого CORS не пускает к странице, и один, который не отвечает*

При открытии меню у каждого удалённого сервера спрашивается, можно ли им пользоваться, и ответ показывает точка - зелёная, когда сервер отвечает и принимает токен, красная, когда нет, жёлтая, пока идёт опрос. Под красной точкой на отдельной строке написано, почему:

- **Не отвечает** - по этому адресу ничего не слушает или адрес неверен;
- **Не принимает токен** - агенту нужен его `httpserver.auth_token`, релею его клиентский токен (`swarm.auth_token`); для удалённого сервера без токена в конфигурации **Ввести токен** открывает форму подключения, заполненную для него;
- **Ответ заблокирован CORS** - что-то отвечает, но браузер не отдаёт ответ этой странице; так из браузера выглядит выключенный CORS (или отсутствие в нём этого origin). Строка называет origin этой страницы и ключ, в который его нужно добавить, - `swarm.cors.allowed_origins` на релее, `httpserver.cors.allowed_origins` на coddy serve, а если сама страница открыта с loopback-адреса (собственный `coddy serve` ноутбука), то и переключатель `allow_loopback`, который пропускает её на любом порту.

Релей распознаётся по его публичному `GET /swarm/info` - собственного `/v1` у него нет, поэтому каталог моделей у него не спрашивают. Его токен проверяется на `GET /swarm/nodes`, и когда токен принят, меню перечисляет агентов за релеем на любую глубину переходов, так что до узла один клик и не нужно идти через карту релея ([Рой, интерфейс](swarm.md#интерфейс)).

Активное окружение опрашивается так же при загрузке, каждые 30 секунд и при фокусе окна. Если им нельзя пользоваться, баннер говорит, какой из трёх случаев произошёл, называет настройку, которая это исправит, и предлагает **Переключиться на локальное** вместо пустого экрана. Выбор окружения и токены удалённых серверов, введённые в форму, хранятся в браузере (`coddy_env`, `coddy_env_tokens`); токен из конфигурации туда не копируется. Недавние папки хранятся для каждого окружения отдельно, как и экран, на котором окружение оставили, - при возврате на "Локальное" вы попадаете в тот диалог, где ушли из него, а удалённый сервер открывается там, где вы его оставили, или на своей главной странице.

## Что где работает

| На сервере | На клиенте |
|---|---|
| цикл ReAct и вызовы модели, с провайдерами и ключами сервера | отображение транскрипта, рассуждений, блоков инструментов, обновлений плана, статистики токенов и контекста |
| файловые и shell-инструменты, в рабочей папке сервера | выбор модели, который заполняется из `GET /v1/models` сервера |
| MCP-серверы, хуки, субагенты и их расписки | запросы разрешений и вопросы, ответы на которые идут через `POST /coddy/sessions/{id}/permission` и `.../question` |
| бандлы сессий, файл конфигурации и коммиты самонастройки агента | отмена (`POST /coddy/sessions/{id}/cancel`), получение полного вывода инструмента по `ctrl+o` |

Сессия, которую создаёт удалённая консоль или ACP-клиент, живёт в рабочей папке сервера по умолчанию (`coddy serve --cwd`, `CODDY_CWD`, иначе там, где был запущен сервер); нижняя строка удалённой консоли всё равно показывает локальную папку. Веб-интерфейс переносит сессию в другую папку на сервере через свой чип папки. `/export` пишет в рабочую папку сервера. `/resume`, `-c` и `--session-id` работают со списком сессий сервера, и локальный фильтр по папке не применяется. Команды настроек (`/model`, `/reasoning`, `/agent`, `/plan`, `/ask`, `/permissions`, с `--once` или `--count=N`) меняют сессию сервера, включая режим разрешений, через тот же `PATCH /coddy/sessions/{id}`, что использует веб-интерфейс, и изменение видят все клиенты этой сессии ([Настройки сессии](../features/session-settings.md)). `/reasoning [level]` и `shift+tab` в консоли сохраняют выбранный уровень рассуждения в сессии на сервере. Стартовый баннер показывает `remote: <url>`, а подсказка при выходе печатает команду переподключения с `--remote`.

Решения о доверии тоже принимает сервер. MCP-сервер проекта, файл хуков или определение субагента одобряется на том хосте - либо через CLI там же (`coddy mcp trust`, `coddy hooks trust`, `coddy agents trust`), либо через API с bearer-токеном (`POST /coddy/mcp/{name}/trust`, `POST /coddy/hooks/trust`, `POST /coddy/subagents/{name}/trust`, в каждом рабочая папка на сервере передаётся как `cwd`); локальные подкоманды `--remote` не принимают. Запрос разрешения субагента доходит до удалённого клиента в родительской сессии с префиксом `[subagent <name>]`, даже когда сам сервер работает с `tools.permission_mode: bypass`. См. [Субагенты](../features/subagents.md#удалённый-режим).

## Ограничения

- один bearer-токен на сервер, без пользователей и ролей - тот, у кого он есть, получает весь API, включая редактор конфигурации и файлы рабочей папки;
- внутри `coddy serve` нет TLS, шифрование даёт прокси или туннель;
- режим разрешений, который переключает удалённый клиент (`/permissions`, `--permission-mode`, переключатель для сессии в диалоге), действует на сессию сервера для всех её клиентов и живёт в памяти сервера - перезапуск `coddy serve` возвращает сессию к `tools.permission_mode`;
- при обрыве соединения ход на сервере, его дочерние сессии и любой открытый запрос продолжают работать; `/resume` показывает результат, когда ход закончится, а ответ на запрос, который сервер уже отозвал, игнорируется. Если выйти из консоли посреди хода, она недолго ждёт, пока отмена дойдёт до сервера;
- сессия выполняет один ход за раз - второй клиент, отправивший промпт в ту же сессию, получает `409`, пока первый ход держит блокировку;
- веб-интерфейс достаёт до удалённого сервера, только если тот пропускает origin интерфейса через свой `cors` (`swarm.cors` на релее) - точный origin в `allowed_origins` или `allow_loopback` для страницы, отданной собственным `coddy serve` ноутбука; если мешает именно это, меню пишет об этом в строке удалённого сервера.

## Проверка удалённого сервера из командной строки

```bash
coddy --dry-run --remote nas02
curl -sS -H "Authorization: Bearer $CODDY_REMOTE_TOKEN" https://nas02.example:12345/v1/models
```

`--dry-run` (в консоли и в `coddy acp`) выполняет проверку конфигурации, затем проверяет всё, на что указывает файл, включая цель `--remote`, и завершается со статусом 1, если какая-то проверка не прошла. Каждый настроенный удалённый сервер проверяется с токеном своей записи; релей распознаётся как релей, а `--remote`, указывающий на корень релея, отвергается со списком точек монтирования его агентов, которые нужно указать вместо него (`<relay>/swarm/nodes/<name>`), потому что сам релей ничем не управляет. Строка `curl` - первый запрос, который точка статуса в интерфейсе делает к агенту. На стороне сервера `coddy serve --dry-run` сообщает адрес, к которому привязался бы, и не занят ли уже порт. См. [coddy serve и демон](serve.md).

Проектный документ [Дизайн удалённого управления](../../plans/remote-control.md) описывает направление, которое вошло в релиз (API с аутентификацией, CORS, выбор окружения и Go-клиент за `--remote`), и части, которые не вошли, - TLS внутри сервера и обратный туннель с реестром агентов, который позже взял на себя [релей роя](swarm.md) со своим обратным туннелем HTTP/2.
