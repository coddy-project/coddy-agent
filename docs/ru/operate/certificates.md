# Сертификаты и TLS: практическое руководство

HTTP-слушатель агента Coddy принимает подключения по HTTP. Отдельный прокси или транспортный сервис отвечает за входящий HTTPS, проверку клиентских сертификатов, хранение и продление сертификатов. Релей может сам обслуживать HTTPS с существующими сертификатом и приватным ключом из `swarm.tls` ([Swarm](swarm.md), [Шифрование и прокси](swarm.md#шифрование-и-прокси)). Он принимает TLS 1.2 и новее. После замены сертификата перезапустите релей. Исходящий HTTPS проверяет сертификат сервера и имя хоста через системное хранилище доверия. Coddy проверяет bearer-токены, выполняет авторизацию и ограничивает вызовы shared models.

## Граница развёртывания

HTTP backend должен слушать loopback или работать в изолированной сети, доступной только транспортному сервису. Публичный HTTPS-эндпоинт не требует открывать его HTTP backend в публичную сеть.

- **Веб-интерфейс, HTTP API и shared models:** завершайте HTTPS на reverse proxy и передавайте HTTP в Coddy. Отключите буферизацию ответов SSE и задайте подходящий таймаут чтения потоков;
- **Прямые подключения Swarm, регистрация и upstream-релеи:** публикуйте HTTPS через внешний сервис или настройте сертификат и ключ релея в `swarm.tls`. В объявленных URL указывайте эндпоинт, доступный вызывающей стороне;
- **Обратный туннель Swarm:** после рукопожатия HTTP/1.1 `POST /swarm/tunnel` идёт двунаправленный поток HTTP/2 с обратными ролями клиента и сервера. Используйте TCP-прокси с завершением TLS, который согласует `http/1.1` через ALPN и сохраняет байты после рукопожатия. Обычный HTTP reverse proxy не заменяет его, если явно не поддерживает такой переход протокола;
- **Доверие к частному CA для исходящих запросов:** установите центр сертификации в хранилище доверия процесса Coddy. В системах с поддержкой `SSL_CERT_FILE` и `SSL_CERT_DIR` эти переменные задают источники корневых сертификатов;
- **Клиентские сертификаты исходящих соединений:** их предъявляет отдельный транспортный компонент. В Coddy настроек клиентских сертификатов нет.

Сертификат удостоверяет соединение на внешнем сервисе. Coddy всё равно требует подходящий основной токен, токен shared models, клиента релея или регистрации. Заголовок, добавленный прокси после проверки сертификата, не служит credential для Coddy.

## Порядок развёртывания

Настройте и проверьте транспорт до открытия публичного эндпоинта.

1. Разверните внешний HTTPS и проверьте имена серверов, доверие и продление сертификатов;
2. Ограничьте прямой доступ ко всем HTTP backend;
3. Укажите внешние HTTPS-эндпоинты в объявленных URL и адресах клиентов;
4. Запустите `coddy -t --dry-run --config <file>` и изучите каждое замечание;
5. Через публичный эндпоинт проверьте HTTPS, авторизацию токенами, SSE, вызовы shared models и все используемые пути Swarm.

### Управление сертификатами

Внешний сервис хранит сертификаты и приватные ключи, продлевает сертификаты и применяет правила доступа. Настройте права на его хранилище и мониторинг продления отдельно от Coddy.

Релей может обслуживать HTTPS с существующей цепочкой PEM-сертификатов и приватным ключом из `swarm.tls.cert_file` и `swarm.tls.key_file`. Укажите оба пути или оставьте оба пустыми для HTTP. Релей принимает TLS 1.2 и новее. После замены любого из файлов перезапустите релей. Этот TLS-слушатель относится только к релею. Он не добавляет HTTPS слушателю агента, не выпускает сертификаты, не предоставляет PKI и не включает клиентский mTLS.

Не копируйте приватные ключи в репозиторий, issue, лог или чат.

## Внешний HTTPS для HTTP API

Привяжите HTTP-слушатель Coddy к loopback. Сохраните существующие настройки авторизации; в этом минимальном примере слушателя они намеренно не показаны.

```yaml
httpserver:
  enable: true
  host: 127.0.0.1
  port: 12345
```

Например, Caddy завершает HTTPS с публично доверенным сертификатом и передаёт ответы без буферизации.

```caddyfile
coddy.example.com {
    reverse_proxy 127.0.0.1:12345 {
        flush_interval -1
    }
}
```

Если развёртывание требует клиентские сертификаты, настройте их проверку и правила для их субъектов во внешнем сервисе. Сохраните проверку токена в Coddy за этим сервисом. Внешний сервис также отвечает за ACME, отзыв сертификатов, списки разрешённых IP, WAF и аудит соединений.

Этот пример HTTP-прокси не обслуживает обратный туннель Swarm. Его транспорт должен сохранять рукопожатие `POST /swarm/tunnel` и следующий за ним двунаправленный поток байтов. Выделите отдельный эндпоинт или используйте развёртывание с поддержкой этого протокола и проверьте его до допуска туннельных подключений.

## Проверка и устранение ошибок

Проверяйте подключение снаружи границы TLS, а не только HTTP backend.

```bash
coddy -t --dry-run --config <file>
curl -H "Authorization: Bearer $SHARED_TOKEN" https://coddy.example.com/coddy/llm/models
```

- Неизвестный центр сертификации означает, что процесс Coddy не доверяет CA эндпоинта. Установите правильный CA в его среду доверия; не отключайте проверку сертификата;
- Несовпадение имени хоста означает, что URL и SAN сертификата расходятся. Исправьте эндпоинт или сертификат;
- Успешное рукопожатие, за которым следует `401`, означает, что credentials приложения отсутствуют или неверны. Сертификат не заменяет токен;
- Туннель, который регистрируется, но не передаёт запросы, может находиться за HTTP-прокси, не сохраняющим поток байтов после рукопожатия `POST /swarm/tunnel`. Проверьте переход протокола, heartbeat при простое, разрыв и переподключение;
- Если поток зависает за прокси, проверьте буферизацию и таймауты. Проверьте отмену вызова и обнаружение исчезнувшего клиента через реальный эндпоинт развёртывания.

Для shared models убедитесь, что исчезнувший клиент освобождает слот. TCP-таймаут живучести видит непосредственного соседа, которым служит прокси, а не клиента за ним. Прикладная проба обнаруживает отсутствие участвующего клиента, но внешний сервис также должен прекращать передачу потока, если его клиент исчез. Успешное TLS-рукопожатие не подтверждает живучесть всей цепочки.
