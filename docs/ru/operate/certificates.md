# Сертификаты и TLS: практическое руководство

Coddy принимает подключения по HTTP. Отдельный прокси или транспортный сервис отвечает за входящий HTTPS, mTLS, сертификаты и их продление. Исходящий HTTPS по-прежнему проверяет сертификат сервера и имя хоста через системное хранилище доверия. Bearer-токены, авторизация и ограничения shared models остаются в Coddy.

Из Coddy удалены встроенный центр сертификации, `coddy tls`, TLS-слушатели и настройки сертификатов для отдельных соединений. Старая конфигурация отклоняется, в том числе пустые блоки и ключи со значением `false`; незаметного перехода на HTTP нет.

## Граница развёртывания

HTTP backend должен слушать loopback или работать в изолированной сети, доступной только транспортному сервису. Публичный HTTPS-эндпоинт не требует открывать его HTTP backend в публичную сеть.

- **Веб-интерфейс, HTTP API и shared models:** завершайте HTTPS на reverse proxy и передавайте HTTP в Coddy. Отключите буферизацию ответов SSE и задайте подходящий таймаут чтения потоков;
- **Прямые подключения Swarm, регистрация и upstream-релеи:** публикуйте HTTPS через внешний сервис. В объявленных URL указывайте эндпоинт, доступный вызывающей стороне;
- **Обратный туннель Swarm:** после рукопожатия HTTP/1.1 `POST /swarm/tunnel` идёт двунаправленный поток HTTP/2 с обратными ролями клиента и сервера. Используйте TCP-прокси с завершением TLS, который согласует `http/1.1` через ALPN и сохраняет байты после рукопожатия. Обычный HTTP reverse proxy не заменяет его, если явно не поддерживает такой переход протокола;
- **Доверие к частному CA для исходящих запросов:** установите центр сертификации в хранилище доверия процесса Coddy. В системах с поддержкой `SSL_CERT_FILE` и `SSL_CERT_DIR` эти переменные задают источники корневых сертификатов;
- **Клиентские сертификаты исходящих соединений:** их предъявляет отдельный транспортный компонент. В Coddy настроек клиентских сертификатов нет.

Сертификат удостоверяет соединение на внешнем сервисе. Coddy всё равно требует подходящий основной токен, токен shared models, клиента релея или регистрации. Заголовок, добавленный прокси после проверки сертификата, не служит credential для Coddy.

## Миграция существующей установки

Проводите миграцию как одно изменение развёртывания. Сохраните совместимую пару старого бинарника и старой конфигурации для осознанного отката.

1. Разверните внешний TLS или mTLS и проверьте имена серверов, доверие и продление сертификатов;
2. Ограничьте прямой доступ ко всем HTTP backend;
3. Подготовьте конфигурацию без ключей из таблицы ниже. Сохраните HTTPS URL внешних эндпоинтов; не заменяйте их HTTP ради успешной проверки;
4. Запустите новым бинарником `coddy -t --dry-run --config <file>` и изучите каждое замечание;
5. Переключите бинарник и конфигурацию вместе, затем проверьте HTTPS, авторизацию токенами, SSE, вызовы shared models и все используемые пути Swarm.

| Удалённая настройка | Замена |
| --- | --- |
| `tls` | Управление сертификатами во внешнем сервисе |
| `httpserver.tls`, `swarm.tls` | Внешнее завершение TLS и защищённый HTTP-слушатель |
| `swarm.node_tls` | Системное доверие и внешний транспорт, если требуются клиентские сертификаты |
| `swarm.join[].dial` и `swarm.upstreams[].dial`: `ca_file`, `cert_file`, `key_file`, `auto`, `insecure_skip_verify` | Системное доверие и внешний транспорт; `dial.proxy` по-прежнему поддерживается |
| `providers[]`: `ca_file`, `client_cert_file`, `client_key_file`, `tls_auto` | Системное доверие и внешний транспорт; URL, прокси и credentials по-прежнему поддерживаются |

Запуск, проверка конфигурации, dry-run, перезагрузка, сохранение Settings, config commit и rollback отклоняют эти ключи до того, как они потеряются при декодировании. Несовместимая конфигурация не запускает автоматическое восстановление из резервной копии. Отклонённая перезагрузка сохраняет действующую конфигурацию; отклонённый rollback не перезаписывает файл.

### Существующие файлы сертификатов

Coddy больше не читает и не меняет `$CODDY_HOME/tls`. Установка, обновление и запуск службы не создают и не продлевают сертификаты. Существующие файлы остаются на диске.

Перед ручным удалением проверьте, не использует ли их другой сервис или старая установка Coddy. Сохраните файлы, нужные для отката. Не копируйте приватные ключи в репозиторий, issue, лог или чат.

## Внешний HTTPS для HTTP API

Привяжите HTTP-слушатель Coddy к loopback. Сохраните существующие настройки авторизации; в этом минимальном примере слушателя они намеренно не показаны.

```yaml
httpserver:
  enable: true
  host: 127.0.0.1
  port: 12345
```

Например, Caddy завершает HTTPS с публично доверенным сертификатом и передаёт ответы без буферизации.

```caddyfile
coddy.example.com {
    reverse_proxy 127.0.0.1:12345 {
        flush_interval -1
    }
}
```

Для mTLS настройте проверку клиентских сертификатов и правила для их субъектов во внешнем сервисе. Проверка токена в Coddy за ним остаётся включённой. Внешний сервис также отвечает за ACME, отзыв сертификатов, списки разрешённых IP, WAF и аудит соединений.

Этот пример HTTP-прокси не обслуживает обратный туннель Swarm. Его транспорт должен сохранять рукопожатие `POST /swarm/tunnel` и следующий за ним двунаправленный поток байтов. Выделите отдельный эндпоинт или используйте развёртывание с поддержкой этого протокола и проверьте его до переключения существующей установки.

## Проверка и устранение ошибок

Проверяйте подключение снаружи границы TLS, а не только HTTP backend.

```bash
coddy -t --dry-run --config <file>
curl -H "Authorization: Bearer $SHARED_TOKEN" https://coddy.example.com/coddy/llm/models
```

- Неизвестный центр сертификации означает, что процесс Coddy не доверяет CA эндпоинта. Установите правильный CA в его среду доверия; не отключайте проверку сертификата;
- Несовпадение имени хоста означает, что URL и SAN сертификата расходятся. Исправьте эндпоинт или сертификат;
- Успешное рукопожатие, за которым следует `401`, означает, что credentials приложения отсутствуют или неверны. Сертификат не заменяет токен;
- Отказ на старом TLS-ключе означает, что конфигурацию ещё нужно мигрировать. Удалять ключ до защиты backend небезопасно;
- Туннель, который регистрируется, но не передаёт запросы, может находиться за HTTP-прокси, не сохраняющим поток байтов после рукопожатия `POST /swarm/tunnel`. Проверьте переход протокола, heartbeat при простое, разрыв и переподключение;
- Если поток зависает за прокси, проверьте буферизацию и таймауты. Проверьте отмену вызова и обнаружение исчезнувшего клиента через реальный эндпоинт развёртывания.

Для shared models убедитесь, что исчезнувший клиент освобождает слот. TCP-таймаут живучести видит непосредственного соседа, которым теперь служит прокси, а не клиента за ним. Прикладная проба обнаруживает отсутствие участвующего клиента, но внешний сервис также должен прекращать передачу потока, если его клиент исчез. Успешное TLS-рукопожатие не подтверждает живучесть всей цепочки.
