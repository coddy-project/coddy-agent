# Сертификаты и TLS: полевое руководство

Coddy использует TLS в нескольких местах. **TLS отвечает только за транспорт**: слушатель предъявляет сертификат, клиент проверяет его и при необходимости предъявляет свой, а слушатель, которому задан центр сертификации клиентов, при рукопожатии отклоняет узел, сертификат которого не строит к нему цепочку. **Coddy не читает из сертификата идентичность**: ни имя, ни subject, ни класс, ни бюджет. Сертификат - не учётные данные; учётные данные - токен. Всё после рукопожатия (кто может вызвать что, лимиты для клиента, правила адресов, отзыв, аудит) регулируется там, где это делать лучше всего: на L7 reverse proxy перед Coddy и в окружающей инфраструктуре ([куда уходят остальные риски](#куда-уходят-остальные-риски)).

**Coddy сам выпускает нужные ему сертификаты** стандартной библиотекой Go, без внешних инструментов: при установке, обновлении и по запросу, через [`coddy tls`](#встроенные-сертификаты-coddy-tls). Собственные сертификаты (корпоративный центр, купленный сертификат, ACME) настраиваются так же, только файлы указываются вручную: Coddy читает их и не интересуется происхождением ([собственные сертификаты](#собственные-сертификаты)).

Всё здесь **включается по желанию**. Релей или узел без настроек сертификатов использует обычный HTTP. Это правильно для loopback-адреса, reverse proxy, завершающего TLS, или туннеля.

## Схема

TLS используют шесть соединений. Для каждого одна сторона **обслуживает** (у неё есть сертификат и ключ), а другая **подключается** (она проверяет предъявленный сертификат и может предъявить свой).

| Соединение | Сторона сервера | Подключающаяся сторона | Ключи (со встроенными сертификатами) |
|---|---|---|---|
| Заимствующий Coddy к узлу или точке монтирования релея | `httpserver.tls` (узел), `swarm.tls` (релей) | строка провайдера типа `coddy` | `providers[].tls_auto` (или `ca_file`, `client_cert_file`, `client_key_file`) |
| Узел присоединяется к релею | `swarm.tls` | запись присоединения | `swarm.join[].dial.auto` (или `dial.ca_file`, `cert_file`, `key_file`) |
| Релей к узлу, который зарегистрировался по адресу | `httpserver.tls` на узле | релей | `swarm.node_tls.auto` (или `ca_file`, `cert_file`, `key_file`) |
| Релей к узлу или дочернему релею, указанному вручную | `httpserver.tls`, `swarm.tls` | релей | `swarm.upstreams[].dial.auto` (или `dial.*`) |
| Браузер к веб-интерфейсу узла или релея | `httpserver.tls`, `swarm.tls` | браузер | собственные хранилища браузера |
| Консоль и ACP с `--remote` | `httpserver.tls`, `swarm.tls` | `coddy --remote` | нет: только системные корни, без клиентского сертификата |

Что **сервер** требует от вызывающих, задаётся в том же блоке, что и его сертификат: `client_ca_file` - центр, по которому проверяются клиентские сертификаты, а с ним рукопожатие **требует** сертификат, строящий к нему цепочку (`require_client_cert: true` делает то же со встроенным набором). Это всё, что делает сертификат. Вызывающего пропускает его **токен**.

## Что читает Coddy: правила, которые решают всё

Это факты о коде, а не предпочтения. Большинство проблем возникает из-за одного из них.

- **Только PEM-файлы.** Файл сертификата - PEM: сначала **leaf**, затем промежуточные сертификаты ("полная цепочка"). Файл ключа - один приватный ключ PEM: `PRIVATE KEY` (PKCS#8), `RSA PRIVATE KEY` или `EC PRIVATE KEY`. DER, PKCS#12 (`.pfx`, `.p12`), Java keystore и ключи в аппаратном токене или системном хранилище **не читаются**. Встроенные сертификаты уже в PEM;
- **Без парольных фраз.** Приватный ключ с парольной фразой использовать нельзя: Coddy негде её запросить, и он сообщает `tls: failed to parse private key`. У встроенных ключей её нет, файлы записываются с режимом `0600`;
- **Назначения ключей проверяет стек TLS.** Сервер проверяет у клиентского сертификата расширенное назначение ключа `clientAuth` (либо отсутствие назначений); клиент проверяет у серверного `serverAuth` (либо отсутствие назначений). Сертификат публичного центра выдан для серверов и всё чаще имеет только `serverAuth`: клиентским он быть не может;
- **Имя хоста сверяется с SAN серверного сертификата**, а не с CN. Серверу по адресу (`https://10.0.0.5:12346`) нужна запись **IP** в SAN; серверу по имени нужно это имя (wildcard покрывает ровно одну метку). Встроенный серверный сертификат содержит имя хоста, `localhost`, loopback-адреса, адреса интерфейсов, а также хосты bind и `advertise_url` из `config.yaml`; `tls.names` или `coddy tls ensure --name` добавляют другие;
- **`ca_file` заменяет системные корни для этого соединения.** С ним для подключения доверены только центры из файла, без него - системные. Файл может содержать несколько сертификатов, а **самоподписанный сертификат сам себе центр**: так клиент доверяет самоподписанному серверу, указав файл его сертификата в `ca_file`. Встроенный `bundle.pem` - такой файл: CA этой машины и CA, которым ей велено доверять;
- **Системные корни принадлежат ОС.** В Linux это набор дистрибутива (`SSL_CERT_FILE` и `SSL_CERT_DIR` учитываются); в macOS - настройки доверия Keychain; в Windows - хранилище сертификатов. Приватному центру, установленному там, доверяет каждая программа, читающая системное хранилище, поэтому `ca_file` (или встроенный `tls_auto`) - более узкий выбор;
- **Проверки отзыва нет.** Ни CRL, ни OCSP не используются: отзыв - задача proxy или инфраструктуры, а сертификат с этой стороны действует до своей даты. Встроенные leaf действуют год и продлеваются за 30 дней до окончания;
- **Минимальная версия - TLS 1.2.** Собственный слушатель узла обслуживает только HTTP/1.1, чтобы общий вызов сохранял отдельное соединение ([граница живости](../features/shared-models.md#пропавший-узел)).

**Когда читается каждый файл.** Пара слушателя и его центр клиентов - **состояние запуска**: изменение любого из них, включая продлённый серверный сертификат, требует перезапуска `coddy serve`. Пара подключающейся стороны (`client_cert_file`, `dial.cert_file`, `node_tls.cert_file`, встроенная клиентская пара) читается **при каждом рукопожатии** (два файла читаются каждый раз и разбираются заново, только если изменились их байты), поэтому продлённый сертификат применяется следующим соединением без перезапуска; изменённый `ca_file` подхватывается при следующей сборке транспорта соединения (следующий вызов строки `coddy`; следующее начало присоединения).

## Встроенные сертификаты: `coddy tls`

Coddy сам выпускает нужные ему сертификаты стандартной библиотекой Go без внешнего инструмента (без `openssl`, без `mkcert`) в `$CODDY_HOME/tls` (режим 0700, ключи 0600):

| Файл | Что это |
|---|---|
| `ca.crt`, `ca.key` | CA этой машины: ECDSA P-256, десять лет, длина пути 0. **Ключ CA никогда не покидает машину.** |
| `server.crt`, `server.key` | сертификат слушателей этой машины: год, `serverAuth`, содержит имя хоста, `localhost`, loopback-адреса, адрес каждого не-link-local интерфейса, хосты bind и `advertise_url` конфигурации и каждое `--name` |
| `client.crt`, `client.key` | сертификат, который эта машина предъявляет при подключении: год, `clientAuth` |
| `trusted/*.crt` | CA других машин, которым эта машина получила указание доверять |
| `bundle.pem` | этот CA плюс каждый доверенный CA: на него указывают `ca_file` клиента и `client_ca_file` слушателя |

```bash
coddy tls ensure            # make what is missing or ending; nothing to do when all is right
coddy tls status [--json]   # what is there, the names, the days left, what ensure would do
coddy tls renew             # issue both certificates again now (the CA stays)
coddy tls export > a-ca.crt # this machine's CA certificate, the one thing to give a peer
coddy tls trust a-ca.crt    # trust another machine's CA (a file, or - for stdin)
coddy tls issue client ci -o ./ci   # a client certificate for something that has no Coddy
```

`ensure` идемпотентен, его безопасно запускать одновременно откуда угодно: он строит план по файлам на диске, применяет его под файловой блокировкой атомарными записями (сначала ключ, потом сертификат), никогда не заменяет действующий CA (это делают только `--force-ca` или истёкший CA, и команда сообщает, что после этого каждый узел должен доверять новому CA), а leaf перевыпускает только по названной причине: он отсутствует, его ключ не подходит, он подписан другим CA, истёк, до окончания осталось 30 дней или меньше, либо отсутствует нужное имя.

**Две машины доверяют друг другу без передачи приватного ключа**: на A выполните `coddy tls export > a-ca.crt`, на B - `coddy tls trust a-ca.crt`, затем повторите в обратную сторону; после этого обе стороны проверяют серверные и клиентские сертификаты друг друга по своим `bundle.pem`. Что значит доверие: CA, которому вы дали `trust`, доверяют **собственные подключения Coddy, использующие bundle** (`auto: true`, `tls_auto`), и больше никто, поскольку bundle никогда не добавляется в системное хранилище или браузер. Но в этих подключениях владелец его ключа может подтверждать любое имя, поскольку встроенные CA не ограничены именами. Доверяйте машинам, которым доверили бы трафик, и предпочитайте один CA для одного домена доверия.

**Используйте это из конфигурации**: добавьте `auto: true` в блок с файлами сертификатов, и его значения заполнятся этими файлами (явно названный файл имеет приоритет для каждого ключа; в `config.yaml` ничего не записывается).

| Блок | Что заполняет `auto: true` |
|---|---|
| `httpserver.tls`, `swarm.tls` (слушатель) | `cert_file`, `key_file` серверной парой; с `require_client_cert: true` - `client_ca_file` bundle, поэтому рукопожатие требует клиентский сертификат, строящий цепочку к CA этой машины или доверенному CA |
| `swarm.node_tls`, `swarm.join[].dial`, `swarm.upstreams[].dial` | `ca_file` bundle, `cert_file` и `key_file` клиентской парой |
| `providers[].tls_auto: true` (тип `coddy`) | `ca_file` bundle, `client_cert_file` и `client_key_file` клиентской парой |

`tls.names` добавляет в серверный сертификат имена, которые Coddy не видит (имя proxy, DNS-алиас, публичный адрес). `coddy serve` выпускает то, что запрашивает блок, до начала прослушивания или подключения, `coddy -t --dry-run` сообщает об отсутствующем или истекающем, `coddy tls ensure` делает это вручную, а слушатель читает пару при запуске, поэтому продлённый серверный сертификат требует перезапуска.

TLS здесь отвечает только за транспорт: сертификат допускает узел на рукопожатии, не является учётными данными, и Coddy не читает из него имя. Публичные сертификаты (ACME, корпоративный CA) настраиваются так же с вручную указанными файлами. Всё остальное (кто может вызвать что, rate limits, allowlist, отзыв, аудит) относится к reverse proxy и инфраструктуре: [куда уходят остальные риски](#куда-уходят-остальные-риски).

## Сценарии со встроенными сертификатами

### Одна машина, браузер или скрипт

```yaml
httpserver:
  tls:
    auto: true      # the server pair of ~/.coddy/tls, made at start
```

Браузер или скрипт, открывающий её, должен один раз доверить CA этой машины: `coddy tls export > coddy-ca.crt`, затем импортируйте этот файл как доверенный центр в браузер (Firefox: Settings, Certificates, Authorities; Chrome и система: менеджер сертификатов ОС) или передайте его в `curl --cacert coddy-ca.crt https://host:12345/...`. Не задавайте `require_client_cert` на узле, веб-интерфейс которого открывают люди: браузер не имеет клиентского сертификата, если вы его не импортировали, а у `coddy --remote` нет параметра для предъявления клиентского сертификата.

### Узел и заимствующий Coddy

На узле (`httpserver.tls.auto: true`, `require_client_cert: true`, `shared_models.tokens`) и у заимствующего (`providers[].tls_auto: true`) один раз обменяйте центры в обе стороны и перезапустите узел (он читает свой bundle при запуске):

```bash
node$      coddy tls export > node-ca.crt          # copy node-ca.crt to the borrower
borrower$  coddy tls export > borrower-ca.crt      # copy borrower-ca.crt to the node
borrower$  coddy tls trust node-ca.crt
node$      coddy tls trust borrower-ca.crt
```

После этого заимствующий проверяет серверный сертификат узла по своему bundle и предъявляет свою клиентскую пару, которую рукопожатие узла принимает, потому что узел доверяет CA заимствующего. Токен заимствующего (токен общей модели, `httpserver.shared_models.tokens` на узле) по-прежнему разрешает ему перечислять и вызывать общие модели: один сертификат даёт `401`. Приватные ключи не покидают свои машины. `coddy -t --dry-run` у заимствующего достигает узла встроенными файлами и сообщает об отсутствующем.

### Релей, узлы и заимствующие

```yaml
# the relay
swarm:
  tls: {auto: true, require_client_cert: true}   # nodes that join and borrowers present a client certificate
  node_tls: {auto: true}                         # towards nodes that registered themselves over an address
  clients:
    - {name: acme, scope: shared_models, nodes: ["nas02"], token: "${ACME_RELAY_TOKEN}"}
# a node
httpserver:
  tls: {auto: true, require_client_cert: true}
swarm:
  join:
    - {url: "https://relay.example:12346", name: nas02, pairing_token: "${PAIRING}", advertise_url: "https://nas02.example:12345", dial: {auto: true}}
```

Каждая машина этой схемы доверяет CA машин, с которыми общается (`export` и `trust` между релеем, каждым узлом и каждым заимствующим), и каждая выпускает собственные сертификаты. Сквозной тест этой страницы запускает ровно такую схему ([тесты, подтверждающие эту страницу](#тесты-подтверждающие-эту-страницу)).

### Что-то без Coddy: скрипт, proxy

`coddy tls issue client NAME -o DIR` выпускает для него клиентский сертификат, подписанный CA этой машины, и записывает в `DIR` `NAME.crt`, `NAME.key` (режим `0600`) и `ca.crt` (CA, которому нужно доверять). Передайте `NAME.key` один раз по каналу, которому доверяете; ключ CA никогда не покидает машину.

### Продление и замена CA

`coddy tls ensure` (запускается за вас из `coddy serve`, `coddy update`, `coddy serve install`) перевыпускает leaf за 30 дней до окончания или при отсутствии имени и никогда не заменяет действующий CA. CA заканчивается через десять лет или заменяется `coddy tls ensure --force-ca`: после этого каждый узел, доверявший старому CA, должен доверять новому (`export`, `trust`), а каждый leaf выпускается от него заново. `coddy tls status` и `coddy -t --dry-run` сообщают, когда что-то заканчивается.

## Собственные сертификаты

Сертификат корпоративного центра, купленный, ACME (Let's Encrypt), центра Microsoft или Vault, `mkcert`: укажите файлы в тех же ключах, и они имеют приоритет над `auto: true`.

```yaml
httpserver:
  tls:
    cert_file: /etc/coddy/server.crt     # the leaf first, then its intermediates
    key_file: /etc/coddy/server.key      # one PEM key, no passphrase
    client_ca_file: /etc/coddy/clients-ca.pem   # optional: the handshake then requires a certificate that chains to it
```

- **Серверный сертификат** должен содержать в SAN хост или IP, к которому подключаются вызывающие, а клиенту, не доверяющему его центру, нужен `ca_file` (либо `tls_auto`, когда центр добавлен через `coddy tls trust`);
- **Клиентскому сертификату** нужно назначение `clientAuth`: купленный для веб-сервера сертификат - серверный, и его отклонят. Его указывают в `client_cert_file` и `client_key_file` (`dial.cert_file`, `node_tls.cert_file`);
- **Ключ с парольной фразой, `.pfx` или `.p12`** преобразуйте на машине, которая его использует: `openssl pkey -in enc.key -out plain.key` и `openssl pkcs12 -in x.pfx -nodes`. Защитите открытый файл как любой секрет (режим `0600`, учётная запись, запускающая Coddy, никогда не репозиторий и не образ). Под менеджером сервисов предпочтите его хранилище учётных данных;
- **ACME и публичные сертификаты** лучше завершать в reverse proxy, который сам их продлевает (Caddy, Traefik, nginx с модулем ACME): Coddy тогда слушает loopback обычным HTTP за ним, а [proxy делает остальное](#куда-уходят-остальные-риски). Прямой слушатель читает пару при запуске, поэтому продление требует перезапуска;
- **Аппаратные токены, smart card, TPM и системное хранилище** не поддерживаются: ключ должен быть файлом.

## Проверка и смысл ошибок

```bash
coddy tls status                       # the files, the names, the days left, what ensure would do (--json for a script)
coddy -t --dry-run                     # every pair loads and has not expired; each provider, join and upstream is dialled with its own pair
# from outside, with openssl as an inspector only
openssl s_client -connect node.example:12345 -servername node.example -CAfile ~/.coddy/tls/bundle.pem \
  -cert ~/.coddy/tls/client.crt -key ~/.coddy/tls/client.key </dev/null 2>&1 | sed -n '/Verification/p'
curl --cacert ~/.coddy/tls/bundle.pem --cert ~/.coddy/tls/client.crt --key ~/.coddy/tls/client.key \
  -H "Authorization: Bearer $SHARED_TOKEN" https://node.example:12345/coddy/llm/models
```

| Что видно | Причина и исправление |
|---|---|
| `x509: certificate signed by unknown authority` (подключающаяся сторона) | Серверный сертификат не подписан ничем из `ca_file` или bundle. Доверьте его центру: `coddy tls trust node-ca.crt`. |
| `x509: certificate is valid for A, not B` / `cannot validate certificate for 10.0.0.5 because it doesn't contain any IP SANs` | Имени или адреса, к которому вы подключаетесь, нет в SAN серверного сертификата. Добавьте его: `tls.names` или `coddy tls ensure --name 10.0.0.5` (команда перевыпустит серверный сертификат). |
| `remote error: tls: bad certificate` / `certificate required` (подключающаяся сторона) | Сервер требует клиентский сертификат, а предъявленный отсутствует или отклонён: его не подписал центр, которому доверяет сервер (`coddy tls trust` на сервере, затем перезапуск), он истёк или **не имеет назначения `clientAuth`**. |
| Сертификат проходит рукопожатие, но каждый вызов получает `401` | Цепочка верна, но **токен не отправлен**: сертификат не учётные данные. Отправьте токен общей модели, клиентский токен релея или основной токен. |
| Узел отвечает, но веб-интерфейс не загружается в браузере | Задан `require_client_cert` (или `client_ca_file`), но у браузера нет сертификата. Не требуйте его на узле, который люди открывают в браузере. |
| `coddy --remote` завершается ошибкой сертификата | У него нет `ca_file`: центр должен быть в системном хранилище либо на него должна указывать `SSL_CERT_FILE` (Linux, BSD). При клиентском CA на сервере он вообще не подключится. |
| `tls: failed to parse private key` | У ключа есть парольная фраза или он не PEM. Преобразуйте его, как описано выше. |
| `tls: private key does not match public key` | Эти два файла не образуют пару. Сравните `openssl x509 -in c.crt -noout -pubkey` и `openssl pkey -in k.key -pubout`. |
| Всё работало до продления | Слушатель читает пару при запуске: после продления перезапустите `coddy serve`. Пара подключающейся стороны перезапуска не требует. |
| `coddy tls trust` сообщает, что файл - приватный ключ или не CA | `trust` принимает **сертификат CA** (то, что печатает `coddy tls export`), никогда не ключ и не leaf. |

## Для агентов: Codex, Claude Code, Coddy и другие

Этот раздел адресован AI-агенту, который настраивает сертификаты для человека. Человек может вставить блок ниже в инструкции агенту.

> **Инструкции для агента, настраивающего TLS для Coddy.**
> 1. **Сначала спросите о сценарии**: кто обслуживает, кто подключается, есть ли уже собственный сертификат человека и открывают ли узел браузеры. Не выбирайте центр сами.
> 2. **Предпочитайте встроенные сертификаты**: `coddy tls ensure` выпускает CA и оба сертификата без внешнего инструмента, `auto: true` (и `tls_auto: true` у провайдера) их использует, `coddy tls export` и `coddy tls trust` обменивают центры двух машин. Используйте собственные файлы человека только когда они у него есть.
> 3. **Никогда не читайте, не печатайте, не вставляйте и не записывайте в лог приватный ключ.** Указывайте только путь к файлу ключа. Не используйте `cat`, не помещайте ключ в коммит, issue или этот диалог. Ключи создаются и остаются на машине, которая их использует; передавайте **сертификаты и центры, никогда не ключи**.
> 4. **Coddy не читает из сертификата идентичность**: не проектируйте ничего, что зависит от имени или subject в сертификате. Что разрешено владельцу сертификата, решает reverse proxy; учётные данные - токен.
> 5. **Запишите конфигурацию, затем запустите `coddy -t --dry-run --config <file>` и `coddy tls status`** и прочитайте каждое замечание. **Никогда не "исправляйте" ошибку сертификата через `insecure_skip_verify`**, не доверяйте центру на уровне всей системы, когда подходят `ca_file` или `tls_auto`.
> 6. **Не трогайте хранилище доверия ОС, хранилище браузера, юнит сервиса или что-либо требующее `sudo` без вопроса.** Сообщите, что измените и зачем.
> 7. **Пара слушателя и центр его клиентов читаются при запуске**: сообщите человеку, что нужен перезапуск, и не перезапускайте сервис, которым пользуются другие люди, без вопроса.
> 8. **Сообщите результат с доказательствами**: выполненная команда, напечатанная ею строка и то, что остаётся сделать человеку (скопировать сертификат CA на другую машину, импортировать его в браузер, продлить до даты).

Для сессии Coddy встроенный скил `configure-coddy` содержит те же правила и ту же таблицу ключей; агент, настраивающий Coddy через него, следует им без дополнительных указаний.

## Тесты, подтверждающие эту страницу

Сказанное на этой странице о TLS-стеке и функциях сертификатов Coddy подтверждается тестами, поэтому изменение, делающее это неверным, ломает сборку:

- **Центр**, [`internal/pki`](../../../internal/pki/pki_test.go): планировщик как таблица (состояние на диске и желаемое состояние задают шаги; действующий CA заменяется только принудительно или после окончания, leaf - только по названной причине, второй запуск ничего не делает), сбой на каждой записи, который восстанавливает следующий запуск, восемь одновременных запусков с одним итоговым CA и две машины, доверяющие друг другу в настоящем mutual-TLS рукопожатии. [`features/tls_builtin.feature`](../../../features/tls_builtin.feature) запускает команды (`ensure`, `export`, `trust`, `issue client`) и запуск с `auto: true`;
- **Модели**: `p7-pki-plan` (Promela: установщик, обновление, запуск сервиса и оператор одновременно, смерть на каждой записи, изменение мира под ними и читатель, загружающий пару), `p7-gate` (Promela: учётные данные, сохраняющиеся для каждого маршрута, и защёлка, которую никакой ввод не заставляет менять решение авторизации сертификатом) и сеть Петри блокировки в [`docs/plans/remote-model-provider-models`](../../plans/remote-model-provider-models);
- **В процессе**, [`internal/netx/certscenarios_test.go`](../../../internal/netx/certscenarios_test.go) запускает каждый сценарий настоящим loopback-рукопожатием с функциями Coddy: самоподписанный клиентский сертификат как собственный anchor; самоподписанный серверный сертификат, которому доверяют через `ca_file`; приватный центр, выпускающий оба конца; промежуточный сертификат; сертификат только с `serverAuth`, отклонённый как клиентский; истёкшие и ещё недействительные сертификаты; ключ с парольной фразой, отклонённый; клиентская пара, заменённая на диске и использованная следующим рукопожатием без перезапуска;
- **Сквозной тест**, [`examples/tls/tls_e2e_builtin.py`](../../../examples/tls/tls_e2e_builtin.py) (`make test-tls-e2e`, `examples/tls/test_tls.sh`; нужен только `python3`) запускает настоящие процессы `coddy` на состояниях четырёх машин: везде `coddy tls ensure`, `export` и `trust` между ними, релей и узел на встроенных сертификатах, оба требующие клиентский сертификат, заимствующий, достигающий узла напрямую и через релей с токеном (один сертификат даёт `401`; без сертификата или с сертификатом CA, которому никто не доверяет, соединения нет), собственного клиента заимствующего (`coddy -t --dry-run` с `tls_auto`) и продление, которое принимает работающий узел.

Одно TLS-взаимодействие эта страница не подтверждает: ACME, центр Microsoft и хранилище сертификатов браузера требуют настоящей системы и описаны по документации этих систем и кода выше, а не исполняются здесь.

## Куда уходят остальные риски

С TLS Coddy делает одно: транспорт. Слушатель предъявляет сертификат, клиент доверяет центру и может предъявить собственный сертификат, а с `client_ca_file` рукопожатие отклоняет узел, сертификат которого не строит цепочку к этому центру. **Coddy не читает из сертификата идентичность**: ни имя, ни subject, ни класс, ни бюджет. Сертификат не учётные данные; учётные данные - токен. Каждый иной риск безопасности регулируется там, где это лучше делать: на **L7 reverse proxy** перед Coddy и в окружающей **инфраструктуре**.

| Риск | Где он регулируется |
|---|---|
| Кто по subject сертификата может вызвать какой маршрут | proxy (nginx `ssl_verify_client` с `map` по `$ssl_client_s_dn`, Envoy RBAC по аутентифицированному principal, Traefik, Caddy) |
| Rate limits на клиента, ограничение соединений, защита от медленных клиентов | proxy (`limit_req`, например, с ключом subject клиента) |
| IP allowlist, правила WAF, контроль ботов и злоупотреблений | proxy и сеть (firewall, security group, mesh policy) |
| Публичные сертификаты, ACME, корпоративный PKI, списки отзыва, OCSP | proxy или вручную указанные файлы в настройках Coddy (он читает их и не интересуется происхождением) |
| Аудит подключившихся | access log proxy |
| Изоляция узла или релея | сеть: приватный сегмент, firewall, mesh |
| Что хранит Coddy | токены (`auth_token`, токены общих моделей, токен клиента релея) и слоты и окна, которые не читают сертификат |

Минимальная схема: proxy завершает TLS публичным или корпоративным сертификатом, требует и проверяет клиентский сертификат, принимает решение по его subject, ограничивает каждого клиента и передаёт обычный HTTP в Coddy на loopback или приватный адрес. Coddy за ним сохраняет собственную проверку токена и игнорирует любой заголовок, добавленный proxy. Это отправные точки, а не часть тестового набора Coddy:

```nginx
# nginx: mutual TLS, a decision by subject, a limit per client, an SSE-friendly forward to Coddy on loopback
limit_req_zone $ssl_client_s_dn zone=coddy_clients:10m rate=30r/m;
map $ssl_client_s_dn $coddy_client_allowed {
    default 0;
    "CN=ops-laptop,O=Example" 1;
}
server {
    listen 443 ssl;
    server_name coddy.example.com;
    ssl_certificate        /etc/nginx/tls/coddy.crt;
    ssl_certificate_key    /etc/nginx/tls/coddy.key;
    ssl_client_certificate /etc/nginx/tls/clients-ca.pem;
    ssl_verify_client on;
    location /coddy/llm/ {
        if ($coddy_client_allowed = 0) { return 403; }
        limit_req zone=coddy_clients burst=5 nodelay;
        proxy_pass http://127.0.0.1:12345;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;        # the completions stream is Server-Sent Events
        proxy_read_timeout 1h;
    }
}
```

```
# Caddy: mutual TLS in front of Coddy, streaming not buffered
coddy.example.com {
    tls {
        client_auth {
            mode require_and_verify
            trusted_ca_cert_file /etc/caddy/clients-ca.pem
        }
    }
    reverse_proxy 127.0.0.1:12345 {
        flush_interval -1
    }
}
```

Через proxy узел видит proxy, а не конечного клиента: лимиты общих моделей, которые хранит Coddy (слот и окно на токен), считаются по токену, а лимиты на клиента относятся к proxy. Релей и его узлы следуют тому же правилу: поставьте proxy перед релеем, а узлы оставьте в приватной сети.
