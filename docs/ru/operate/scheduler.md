# Планировщик

## Обзор

Планировщик - необязательный исполнитель заданий в духе cron. Он читает плоские файлы заданий `*.md` (YAML frontmatter и тело в markdown) из двух фиксированных мест - ваши собственные задания из **`${CODDY_HOME}/scheduler`** и задания проекта, которые репозиторий носит с собой, из **`<workspace>/.coddy/scheduler`**, - и запускает каждое доверенное задание, когда подходит его время. Каждый запуск - **фоновая задача агента**, то же самое, что запускает вызов `spawn_agent` ([Субагенты](../features/subagents.md)), то есть задача вида `agent` в пуле фоновых задач ([Фоновые задачи](../features/background-tasks.md)) с дочерней сессией за ней, причём все они висят под одной сессией на задание. Эта сессия задания и есть история его запусков, и панель запусков веб-интерфейса показывает её так же, как панель "Задачи" чата показывает задачи чата. Планировщик компилируется только с тегом сборки **`scheduler`**.

Составные части:

- **`external/scheduler`** - точка входа **`Serve`**, которую **`coddy serve`** запускает при **`scheduler.enable`**; консоль и **`coddy acp`** запускают тот же демон с **`--scheduler`**;
- **`external/scheduler/daemon`** - тик раз в минуту по UTC и **рантайм**, который начинает запуск, останавливает его, знает, выполняется ли задание, применяет политику хранения и ведёт сессию задания;
- **`external/scheduler/storage`** - поиск плоских заданий в обоих корнях, правила изоляции заданий проекта, YAML frontmatter, cron по UTC, файл-спутник **`.state`**, одобрения заданий проекта (**`scheduler-trust.json`**) и рабочие папки, которые сканирует демон (**`scheduler-workspaces.json`**);
- **`external/scheduler/service`** (**`schedservice`**) - общий CRUD, строки запусков, структуры данных для HTTP и инструментов (без циклических зависимостей с **`internal/tools`**);
- **`external/scheduler/tools`** - **`schedtools`** регистрирует инструменты **`coddy_scheduler_*`** (по одному файлу `*.go` на инструмент в **`tools/`**), когда **`scheduler.enable`** равен true;
- **`internal/agent/scheduled_run.go`** - **`RunScheduledJob`**, сам запуск, на том же исполнителе дочерних запусков, которым пользуется **`spawn_agent`**.

Парсер cron использует **пять полей** (**минута час день месяц день недели**) в **UTC**. Срабатывания вычисляются **на границах минут UTC** (секунда **0**, наносекунды **0**), как в **crond**. Демон просыпается раз в минуту UTC, читает файлы заданий и запускает задание, только если эта минута подходит под выражение, а контрольная точка в **`.state`** строго раньше этой минуты. Поэтому **`* * * * *`** выполняется **не чаще раза в минуту UTC**. Поля с шагом, например **`*/2 * * * *`**, используют ту же сетку минут, что vixie cron (минуты **0,2,4,…** UTC); **`*/3 * * * *`** использует **0,3,6,…** UTC.

Изменения поля **`schedule`** в файле задания читаются при следующем сканировании (без перезапуска).

## Сборка

- Только планировщик - `go build -tags=scheduler ./cmd/coddy`;
- HTTP и планировщик - `go build -tags=http,scheduler ./cmd/coddy` (для встроенного SPA добавьте `,ui` вместе с `http`).

## Включение

Демон планировщика и инструменты активны, если в конфигурации задано **`scheduler.enable: true`** или если вы передали **`coddy serve --scheduler`**, **`coddy acp --scheduler`** или **`coddy --scheduler`** (консоль). Демону нужен менеджер сессий, из которых состоят запуски, поэтому он стартует, когда этот менеджер уже создан; голый релей роя его никогда не запускает.

REST-маршрутам в **`/coddy/scheduler`** нужен **`-tags=http,scheduler`**; см. **`docs/reference/http-api.md`**.

Задания - это файлы **`*.md`**, лежащие **непосредственно** в одной из двух папок; вложенные подкаталоги при поиске не просматриваются. Ни одну из этих папок нельзя перенастроить.

- **Пользовательские задания** лежат в **`${CODDY_HOME}/scheduler`**. Они ваши, и им всегда доверяют;
- **Задания проекта** лежат в **`<workspace>/.coddy/scheduler`** и переезжают вместе с репозиторием, так что команда может держать свою работу по расписанию рядом с кодом. Они запускаются только после того, как им начали доверять (следующий раздел).

Старый ключ **`scheduler.dir`** больше не читается. `coddy -t` сообщает о нём как о перенесённом ключе, а следующий запуск копирует задания из этой папки (вместе с их файлами-спутниками **`.state`**) в **`${CODDY_HOME}/scheduler`** и удаляет ключ из `config.yaml`, сохраняя старый файл как `config.yaml.bak-<time>`. Задание, которое в домашней папке уже есть с теми же байтами, пропускается (его контрольная точка переносится, если в домашней папке её нет); задание, которое там есть с другими байтами, копируется как **`<id>-migrated.md`** (или **`<id>-migrated-2.md`** и далее, если это имя занято), так что ни одно задание молча не перестаёт работать. Старая папка остаётся как была.

Идентификатор задания уникален в обеих областях. Задание проекта не может взять id пользовательского задания, а пользовательское задание не может взять id задания проекта из рабочей папки, известной планировщику (в обоих случаях ответ **409**, и при создании, и при переименовании). Файл проекта, который всё же приходит с конфликтующим id, помечается как **conflict** и не запускается, пока его не переименуют.

У каждого задания есть один файл-спутник: **`basename.state`** рядом с **`basename.md`** для пользовательского задания и **`${CODDY_HOME}/scheduler/.projects/<key>/<job_id>.state`** для задания проекта (ключ выводится из рабочей папки), поэтому ничего из того, что пишет планировщик, не попадает в чекаут. Это небольшая JSON-запись с контрольной точкой cron (**`last_scheduled_utc`**) и, после первого запуска задания, id его **сессии задания** (**`session_id`**). Каждый из двух записывающих компонентов сохраняет оба поля, поэтому запись контрольной точки не теряет указатель на сессию, а первый запуск не теряет контрольную точку. Переименование задания через API или редактор переносит файл-спутник вместе с файлом, так что история запусков следует за переименованием. Файл-спутник без указателя (удалённого вручную или записанного старой версией Coddy) не оставляет историю без хозяина: демон находит сессию задания в корне сессий по указанному в ней id задания и снова записывает указатель.

Демон записывает контрольную точку **до начала запуска**, используя **начало минуты UTC**, на которой сработало задание, поэтому следующий минутный тик не запускает ту же минуту повторно, пока запуск ещё идёт. Контрольные точки записываются **атомарно** (временный файл и переименование в том же каталоге). Если контрольной точки ещё нет (или в ней устаревшая метка времени до 1980 года, оставленная старыми сборками), первый запуск следует расписанию **в стиле vixie** по настенным часам и выражению из пяти полей, а не догоняет пропущенное с начала эпохи Unix. Включать планировщик для одного домашнего каталога Coddy должен только **один** долгоживущий процесс, ведь два демона, читающие одни и те же задания, могут сработать дважды.

Необязательное поле frontmatter **`paused: true`** пропускает и тики cron, и **`POST …/run`**, пока задание не возобновят.

## Задания проекта и доверие

Задание проекта - это содержимое репозитория, которое по таймеру запускает агента с вашими разрешениями, поэтому к нему применяется та же проверка доверия, что к MCP-серверам, определениям субагентов и хукам проекта. Политику задаёт **`scheduler.project_trust`**:

- **`ask`** (по умолчанию) - задание проекта показывается в списке, но запускается (по cron или вручную) только после того, как вы одобрили его для этой рабочей папки. Одобрение - это расписка в **`${CODDY_HOME}/scheduler-trust.json`**, привязанная к рабочей папке, id задания и sha256 файла, поэтому задание, которое потом изменилось (`git pull`, ручная правка), снова ждёт одобрения;
- **`allow`** - задания проекта запускаются как ваши собственные;
- **`deny`** - задания проекта показываются в списке и никогда не запускаются.

Задание проекта, **которое вы создали через Coddy** (веб-интерфейс, REST API из сессии или `coddy_scheduler_job_create` с `scope: "project"`), сразу одобряется для записанных байтов, ведь его создали вы. Тот же файл, дошедший до другого человека через git, для него не одобрен. Правка через Coddy сохраняет доверие к заданию, только если ему доверяли до правки; пауза или правка задания, пришедшего с чекаутом, его не одобряет. Ни один инструмент не одобряет задание проекта, одобрение - решение человека, которое принимают в веб-интерфейсе или через REST.

Панель показывает пользовательские задания в группе **Общие**, затем задания проекта из рабочей папки чата в группе **Этот проект**, затем задания всех остальных рабочих папок, которые обслуживает планировщик. Строка, которая не запускается, объясняет почему (**ждёт одобрения**, **запрещено**, **конфликт id**, **ошибка**); у задания, ждущего одобрения, вместо кнопки запуска стоит щит, который открывает задание вместе с его исходным файлом. Щит там одобряет ровно показанные байты (сервер отвергает дайджест, который больше не совпадает с файлом), а у одобренного задания отзывает одобрение. Новое задание создаётся как **Общее**, если вы не выберете **Этот проект**, а для этого нужен чат в этом проекте.

Каждое доверенное задание, пользовательское или проекта, выполняется в единственном демоне процесса и его единственном пуле задач, под общими **`scheduler.max_queue`** и **`scheduler.timeout`**. Демон сканирует:

1. пользовательские задания;
2. задания проекта своего рабочего каталога;
3. задания проекта каждой рабочей папки, у которой есть одобрение;
4. задания проекта каждой рабочей папки, о которой сессия спрашивала планировщик (они перечислены в **`${CODDY_HOME}/scheduler-workspaces.json`**), и именно так задание запускается при **`allow`**, где ничего никогда не одобряется.

Доверие решается по одному чтению файла до записи контрольной точки cron, и запуск строится из того же прочитанного содержимого, поэтому файл, подменённый в промежутке, никогда не запустится под одобрением, которого не получал. Демон один раз на каждое содержимое пишет в лог, что пропустил задание и почему.

Правила изоляции для заданий проекта: **`.coddy`**, **`.coddy/scheduler`** и файлы заданий должны быть настоящими папками и файлами, а не ссылками (ссылка показывается как **ошибка**, и через неё ничего не записывается); у рабочей папки, чья папка проекта оказалась бы внутри **`${CODDY_HOME}`** (Coddy запущен в `$HOME` с домашним каталогом по умолчанию), заданий проекта нет; а **`cwd`** задания проекта должен быть пустым (его рабочая папка), относительным путём, который остаётся внутри рабочей папки, или абсолютным путём, который после разрешения ссылок указывает на рабочую папку или папку внутри неё (такой путь часто встречается в заданиях, написанных до появления заданий проекта).

## Формат файла задания

Поля frontmatter:

- **`description`** (строка) - краткое описание для человека;
- **`schedule`** (строка) - crontab из пяти полей, UTC;
- **`cwd`** (строка, необязательно) - для пользовательского задания пустое значение означает cwd процесса Coddy, а относительные пути разрешаются от него во время запуска; для задания проекта пустое значение означает его рабочую папку, и принимается только путь внутри рабочей папки, относительный или абсолютный;
- **`model`** (строка, необязательно) - переопределение модели сессии для запуска;
- **`mode`** (строка, необязательно) - **`agent`**, **`plan`** или **`ask`** (по умолчанию **`agent`**);
- **`agent`** (строка, необязательно) - имя определения субагента (**`subagents.dirs`**, см. [Субагенты](../features/subagents.md)), и запуск выполняется с его ролью, списком разрешённых инструментов, моделью, уровнем рассуждения и сужением разрешений. `reasoning` определения применяется, если модель запуска (`model` задания, иначе модель определения, иначе настроенная) предлагает этот уровень, как при обычном порождении субагента; уровень, которого она не предлагает, отбрасывается с предупреждением в логе агента, а `reasoning: default` оставляет собственный уровень модели. Определению из области проекта, как и при любом порождении, нужна расписка доверия; задание, которое называет неодобренное определение, не стартует, а ручной запуск об этом сообщает. При пустом значении запускается обычный агент с полным набором инструментов режима;
- **`permission_mode`** (строка, необязательно) - **`ask`**, **`accept_edits`** или **`bypass`**, то есть что запуск может делать без вопросов. Пустое значение означает **`bypass`**, режим по умолчанию для работы без присмотра, в котором планировщик всегда и работал; определение, названное в **`agent`**, может его только сузить. В запуске по расписанию на запросы никто не отвечает, поэтому при **`ask`** или **`accept_edits`** вызов, требующий разрешения, **отклоняется**, а не ждёт ответа; отказ сообщает запуску, что спросить было некого, и тот докладывает, чего не смог сделать, а не утверждает, что отказал оператор ([Субагенты](../features/subagents.md), раздел "Отсоединённые запуски");
- **`paused`** (булево, необязательно) - если true, задание не выполняется.

Тело - markdown, который служит разовой инструкцией пользователя для этого запуска планировщика.

Системный промпт запуска говорит, что это задание по расписанию, запущенное без присмотра (с id задания и слотом cron или пометкой "by hand"), что на вопросы никто не ответит и что последнее сообщение сохраняется как запись о запуске; если задание называет определение, за этим следует роль определения. Скилы, правила и блок окружения присутствуют, как в любой сессии, а настроенные MCP-серверы подключаются для cwd задания через проверку доверия к рабочей папке, если только определение задания не исключает все их инструменты.

## Запуски

У каждого задания есть одна обычная сессия, **сессия задания**, которая создаётся при первом запуске и записывается в файл-спутник. Собственных ходов она никогда не выполняет. Промпт к ней отклоняется (**409** по HTTP с указанием задания), она не попадает в "Историю" и ни в один список по умолчанию (её показывает **`GET /coddy/sessions?include_scheduler=true`**), и существует она для того, чтобы у запусков задания был родитель. Запуск - потомок этой сессии, и хранится он там же, где хранится дочерняя сессия `spawn_agent`.

```
<sessions root>/<job session>/
  session.json                 schedulerRun: true, schedulerJobId: <job_id>
  background/<task_id>/        the run's task record and progress log
  subagents/<run session>/     the run's transcript (subagentRun, schedulerJobId, schedulerTrigger)
```

Строка задачи запуска содержит **`kind: "agent"`**, метку **`<job_id> · cron 2026-09-18 10:00 UTC`** (или **`· manual …`**) и **`agent: {"name": <job_id or its definition>, "session_id": <run session>}`**. Лог прогресса запуска - то же, что панель "Задачи" показывает для любого запуска субагента (строки `→ tool`, `✓ tool`, `[assistant]` и завершающий блок `=== subagent report ===`); транскрипт запуска - это сессия запуска, только для чтения, с уведомлением, которое называет задание и ведёт обратно к запускам задания. Статусы те же, что у пула: **`running`**, **`succeeded`**, **`failed`** (ход закончился ошибкой), **`timed_out`** (сработал **`scheduler.timeout`**), **`stopped`** (отменён), **`orphaned`** (процесс умер, пока запуск шёл).

- **Для одного задания - один запуск за раз.** Демон резервирует задание до того, как что-либо стартует, поэтому тик cron и ручной запуск не могут запустить его оба; слот по расписанию, который наступает, пока идёт запуск, пропускается и записывается в лог;
- **`scheduler.max_queue`** ограничивает число одновременно идущих запусков по всем заданиям. Тик сверх предела пропускает задание в этом слоте с предупреждением; ручной запуск сверх предела получает ответ **409**;
- **`scheduler.timeout`** - жёсткий лимит запуска; пул, как и для любой задачи, ограничивает его значением **`tools.background.max_timeout_seconds`**, а демон при старте предупреждает, если лимит планировщика выше этого предела;
- **Обрыв соединения с провайдером не завершает запуск.** За запуском по расписанию никто не следит, поэтому он, как и субагент, выдерживает до пяти неудачных вызовов провайдера подряд, тогда как ход в чате сдаётся после двух. При **`agent.llm_retry_base_ms`** по умолчанию это около шести минут, если **`scheduler.timeout`** оставляет запас. Каждое переподключение запуск пишет в свой лог прогресса (**`↻ provider failed (...); reconnecting in 20s (attempt 2 of 5)`**, [Субагенты](../features/subagents.md#когда-обрывается-связь-с-провайдером));
- **Отмена** останавливает задачу запуска; запуск записывается как **`stopped`**;
- **Хранение.** **`scheduler.retain_sessions`** (по умолчанию **5**) хранит столько **завершённых** запусков на задание, самых новых по времени старта; когда запуск завершается, более старые теряют запись задачи и транскрипт. **Очистить** в панели запусков (**`DELETE /coddy/scheduler/jobs/{job_id}/runs`**) удаляет все завершённые запуски. Удаление задания удаляет его сессию задания вместе со всеми запусками под ней;
- **Между запусками в памяти ничего не остаётся.** Сессия завершённого запуска выводится из работы, а её записи в пуле освобождаются; записи возвращаются из бандлов, когда панель их запрашивает. Работа, которую запуск оставил после себя (переведённый в фон `run_command`, порождённый им субагент), останавливается, когда ход запуска возвращается, как и у любого дочернего агента;
- **Перезапуск.** Запуск, во время которого умер процесс, показывается как **`orphaned`**; контрольная точка не даёт его слоту сработать снова.

Запуск по расписанию находится на глубине порождения **0**, поэтому в пределах **`subagents.max_depth`** он может порождать собственных субагентов, и они, как любые порождённые, учитываются в **`subagents.max_concurrent`**. Завершённая задача его никогда не будит (`notify_on_finish` выключен для всего, что он запускает).

Запуски планировщика из версий до этой схемы (бандлы **`sched_`** верхнего уровня) по-прежнему скрыты из "Истории" и не показываются как запуски; если они не нужны, удалите их вручную.

Логи процесса демона остаются краткими (**`slog`** - **`scheduler_run_spawn`** и **`scheduler_run_finish`** с заданием, сессией запуска, задачей и статусом); полные трассы хранятся в сессии запуска.

## Запуски в веб-интерфейсе

Задания сгруппированы по области (см. раздел "Задания проекта и доверие"). Каждая строка задания показывает его последний запуск (точку статуса и часы, как в панели "Задачи") и кнопку **Запуски**, которая открывает запуски задания, то есть панель фоновых задач сессии задания, пристыкованную там же, где пристыковывается редактор задания (внизу редактора есть такая же кнопка). Маршрут - **`#/scheduler/jobs/<job_id>/runs`**; ссылка, которая называет один запуск (**`.../runs/<task_id>`**), открывает панель с раскрытой карточкой этого запуска, а затем убирает id из адреса. Каждый запуск показан карточкой. У выполняющегося запуска есть кнопка остановки, завершённые стоят под счётчиком **Завершённых**; щелчок раскрывает карточку на месте с логом прогресса запуска, его длительностью и кнопкой **Показать транскрипт**, которая открывает сессию запуска. Раскрытыми могут быть сразу несколько карточек. Панель опрашивает **`GET /coddy/sessions/{job session}/background-tasks`** каждые 2,5 с, пока идёт запуск, и каждые 15 с в остальное время, точно так же, как панель чата.

## HTTP API

С **`-tags=http,scheduler`** маршруты **`GET /coddy/scheduler/jobs`** (строки содержат **`scope`**, **`workspace`**, **`trust`**, **`running`**, **`session_id`** и **`last_run`**; без заголовка сессии или **`cwd`** выводятся только пользовательские задания), CRUD заданий (**`scope=project`** обращается к заданию проекта, которое создаётся в рабочей папке сессии из **`X-Coddy-Session-ID`**), **`trust`** / **`untrust`** для заданий проекта, **`pause`** / **`resume`**, **`run`** (**202** с **`task_id`**, **`session_id`** и **`run_session_id`**), **`cancel`**, **`GET …/runs`** и **`DELETE …/runs`** повторяют слой **`schedservice`**; сама панель запусков опрашивает маршруты фоновых задач сессии. Если **`scheduler.enable`** равен false, ответ **`503`**. OpenAPI добавляет эти пути, только если **scheduler** скомпонован в бинарник (см. **`external/httpserver/scheduler_http.go`** и **`scheduler_http_stub.go`**).

## Инструменты (когда планировщик включён)

- каждый инструмент, работающий с одним заданием, принимает **`scope`** - **`user`** (по умолчанию) или **`project`**, то есть задание проекта из рабочей папки сессии;
- **`coddy_scheduler_jobs_list`** - список заданий (**`include_body`** необязателен): пользовательские задания и задания проекта из рабочей папки сессии и из рабочих папок, которые обслуживает планировщик, каждое со своим **`trust`**;
- **`coddy_scheduler_job_get`** - одно задание в JSON, включая **`body`**;
- **`coddy_scheduler_job_create`** / **`coddy_scheduler_job_replace`** / **`coddy_scheduler_job_patch`** (необязательный **`new_job_id`** переименовывает файл задания; **`agent`** и **`permission_mode`** - такие же поля, как остальные);
- **`coddy_scheduler_job_delete`**;
- **`coddy_scheduler_job_pause`** / **`coddy_scheduler_job_resume`**;
- **`coddy_scheduler_job_run`** - ручной запуск (не сдвигает **`.state`** cron); отвечает задачей и сессией запуска;
- **`coddy_scheduler_job_cancel`**;
- **`coddy_scheduler_job_runs`** - строки запусков задания.

Старые имена **`coddy_scheduler_list`**, **`read`**, **`write`**, **`delete`**, **`validate`** удалены.

## Пример задания (минутный тик)

```md
---
description: "Minute tick"
schedule: "* * * * *"
cwd: ""
mode: agent
---

In the session working directory run

bash -lc 'date -u +%FT%TZ > tick.txt'
```

Задание под определением только для чтения и с суженным режимом разрешений.

```md
---
description: "Nightly audit"
schedule: "0 3 * * *"
mode: agent
agent: reviewer
permission_mode: accept_edits
---

Review yesterday's commits and write the findings to docs/audit/<date>.md.
```
